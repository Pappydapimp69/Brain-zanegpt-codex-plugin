## E19 — priority guard needs total order tiebreak
- Date: 2026-09-29
- Project: pappydapimp69/the-game-the-waiting-city
- Tags: [ui][state][architecture][testing]
- What: Re-verified the first-writer-guard and priority-consulting-guard lessons with a third role and tied priorities, showing a priority-consulting guard is only order-invariant if its comparison is a total order.
- Why built: Both prior entries were tested with distinct priorities only; ties were never swept, and real content will give two roles equal priority.
- Design: Deterministic model with three roles, priority levels 0..2 over all 27 assignments, all 6 handler registration orders (162 cases per guard). Guards: none, first-writer, strict-greater priority, and priority then role-id. Truth is the max by (priority, role id).
- Got right: Swept every registration order and separated ties at the top from the rest, so the tie effect could be isolated instead of averaged away.
- Where/why it failed: none and first-writer were each wrong 108/162 and order-dependent in 27/27 assignments. Strict-greater looked fixed but was still wrong 39/162, all of them in the 72 cases where the top priority was tied, and order-dependent in 12/27 assignments.
- Fix: Compare the tuple (priority, role id) instead of priority alone: wrong 0/162, wrong-on-ties 0/72, order-dependent 0/27.
- Why this fix: A strict comparison on a partial order leaves ties to fall back to whoever registered first, which reintroduces the very handler-order dependence the guard was meant to remove.
- Rule of thumb: When a guard consults priority, make the comparison a total order with an explicit tie-break, and include tied priorities in the sweep, or registration order sneaks back in.

## E18 — multirole entity last writer emission order
- Date: 2026-09-29
- Project: pappydapimp69/the-game-the-waiting-city
- Tags: [ui][state][architecture][testing]
- What: Re-verified, from an emission-order angle, the waiting-city#E3 hazard of one entity holding two roles whose handlers both write the same view state, and the guard-cannot-be-retroactive result that resolving the role before dispatch is the fix.
- Why built: The prior guard lesson had a single source; this sandbox sweeps a different variable (event emission order versus handler registration order) to see which one actually decides the final view.
- Design: Deterministic model, no RNG or timing. One NPC with shop and quest roles; command talk emits talked then quests_offered. Swept handler registration order x quest available x shop open (8 states) and the two event emission orders, across naive, resolve-before-dispatch and separate-entities strategies.
- Got right: Counted wrong final view, wrong intermediate flash, and wrong side effect separately, so partial fixes could not hide behind a correct final view.
- Where/why it failed: Naive dispatch got the final view right 8/8 only because quests_offered happened to be emitted last; swapping emission order gave a wrong final view in 2/8 states, and handler registration order changed the final view in 0/4 states. Naive also flashed the wrong modal and ran the wrong side effect in 2/8 states even with the lucky order.
- Fix: Resolve the intended role from state before dispatch and emit only that role's event: 0/8 wrong final, 0/8 wrong flash, 0/8 wrong side effect under both emission orders. Separate entities gave the same 0/8 result.
- Why this fix: The final view under overlapping handlers is decided by last-writer-wins on emission order, not by handler order, so it is correct by accident; only removing the losing event stops flashes and side effects.
- Rule of thumb: A multi-role entity that is correct today may be correct only because of event emission order; reordering emits breaks it silently, so pick the role before dispatch instead of letting handlers race.

## E17 — the game the waiting city pity collapse boundary also needs constant roll
- Date: 2026-07-13
- Project: pappydapimp69/the-game-the-waiting-city
- Tags: [determinism][gamedesign][testing]
- What: Composing `sandbox-loot-pity#E1` (decay/hard-cap dup-protection pools inevitably collapse over long runs; the correct fix is hard exclusion — `effectiveWeight = 0` and removal from the eligible pool once a cap is hit — rather than asymptotic decay) with `the-game-the-waiting-city#E9` (AI decisions must consume a CONSTANT number of RNG rolls regardless of branch/outcome, since multiple entities share one RNG stream per tick) surfaced a THIRD distinct trigger for violating E9's invariant, beyond the already-filed affordability-branch (E14) and error/catch-branch (E15) triggers: the COLLAPSE BOUNDARY of a pity/dup-protection pool — the tick where its eligible candidate set first narrows to exactly one. At that boundary, "the result is forced, don't bother rolling" is the natural next optimization on top of E1's own recommended hard-exclusion fix, and it silently skips a roll.
- Why built: `brain train group` surfaced `sandbox-loot-pity + the-game-the-waiting-city` as an untested seam requiring sandbox verification, not just reasoning, per current policy (tension T22). Deliberately tested a state-accumulation-triggered mechanism, distinct from E14's per-tick boolean and E15's exception-path trigger.
- Design: Deterministic Node.js sandbox (seeded mulberry32, no wall-clock/Math.random). Entity A is a waiting-city-style AI decision using an E1-style hard-cap move-variant pool (with a pity reset once every move is capped); entity B is an unrelated fixed-2-rolls-per-tick patroller sharing the same RNG stream. `buggy` variant skips the roll when the eligible pool collapses to exactly one candidate ("no need to roll, it's forced"); `fixed` variant always rolls regardless. Ran 300 ticks across 4 seeds (12345, 1, 999, 42424242), plus a fixed-vs-fixed control (sanity check for zero false-positive divergence) and a follow-up sweep varying pool width/cap size across a 5000-tick horizon to measure how far the FIRST collapse event can be delayed relative to a plausible short (50-tick) regression-fixture length.
- Got right: Ran a fixed-vs-fixed control first (0/300 differences) to rule out any inherent nondeterminism in the harness itself before trusting the buggy-vs-fixed comparison. Directly counted collapse-to-one events (50-58 per 300-tick run) to confirm the triggering branch is genuinely reached at a realistic rate, not a rare corner case requiring cherry-picked parameters.
- Where/why it failed: Under `buggy`, entity A's own roll count dropped from 300 (fixed baseline) to 246-253 across seeds — one skipped roll per collapse event. Entity B's decision sequence diverged on 290-292 of 300 ticks (97%+) across every seed, first diverging as early as tick 8. Under `fixed` (always roll, use only when a real choice exists), B's sequence was unaffected. The follow-up sweep showed onset delay is directly tunable by content: with a narrow pool (MAX_USES=3, 3 move variants) the first collapse hit by tick 8 (a short fixture would catch it), but with a wider, still-realistic pool (MAX_USES=30, 6 move variants) the first collapse was delayed to ticks 171-178 — comfortably past a plausible 50-tick short golden-fingerprint fixture, while still firing well within a normal-length playthrough.
- Fix: Same fix shape as E14 and E15 — at the collapse boundary, always draw the roll a sub-decision would need even when the outcome is forced (exactly one legal candidate), and use the drawn value only to select among however many candidates remain (trivially, the one).
- Why this fix: E1's own hard-exclusion fix is roll-count-safe everywhere except this specific boundary; "don't roll when there's nothing to choose" reads as a harmless, even virtuous optimization (why waste a call) but is precisely the shape E9 requires NOT be taken, because the roll's existence — not its outcome — is what other entities' downstream draws depend on.
- Rule of thumb: When a decay/cap-based pity or dup-protection mechanism (loot-pity#E1's territory — verify over many iterations, since these pools look fine right up until they collapse) is embedded inside a roll-count-disciplined decision system (E9's territory), audit specifically at the mechanism's COLLAPSE BOUNDARY — where its eligible set narrows to one or zero candidates — for a skipped "no need to roll" shortcut. This trigger is the hardest of the three now-documented E9-violation shapes (affordability/E14, exception-path/E15, collapse-boundary/E17) to catch via testing, because its onset is a function of accumulated play and content tuning (pool width, cap size) rather than a static, immediately-reachable branch — a short regression fixture can systematically miss it while it remains fully live in normal-length real play.
- Provenance (verified/assumed): VERIFIED first-hand — deterministic Node.js sandbox, seeded mulberry32, 4 seeds x 300 ticks, measured entity B's decision-sequence divergence (290-292/300 ticks differing under `buggy`, 0/300 under `fixed` and under the fixed-vs-fixed control), entity A's roll-count drop (300->246-253 under buggy), and a parameter sweep confirming onset delay scales with pool width (8 ticks at MAX_USES=3 up to 171-178 ticks at MAX_USES=30). This is a general architectural-composition risk, not a claim about literal current `the-game-the-waiting-city` shipping code — its real `src/sim/ai.js` implements simple fixed-roll patrol/chase/attack/return/flee FSM movement, not a weighted move-variant picker with pity/dup-protection state, so this specific collapse-to-one shape does not currently exist in that repo; no live-unfixed bug is being flagged.

## E16 — the game the waiting city commit veto hides from fsm
- Date: 2026-07-13
- Project: pappydapimp69/the-game-the-waiting-city
- Tags: [architecture][gamedesign][ai][testing]
- What: Composing `sandbox-combined-movement-stack#E1` (an A*-style replanner's deliberate "trust my own/destination cell unconditionally" exception needs an independent commit-time occupancy veto to stay safe when another body has moved onto that cell) with `the-game-the-waiting-city#E9`'s territory (AI decisions live inside the authoritative reducer's fixed per-kind FSM, driven by an integer BFS in `src/sim/pathfind.js`) found that waiting-city's shipped code already implements movement-stack E1's recommended fix — `bfsNextStep` returns the player's own tile as a valid step target for an adjacent enemy exactly as E1 predicted, but `commitMove`'s independent `claimed.has(key)` occupancy check correctly vetoes the actual overlap (0/48 overlaps across an 8-neighbor x 6-seed sweep of live code). The composition surfaces a higher-order rule neither entry states on its own: a safe commit-time veto is not the same guarantee as "the FSM correctly anticipated that veto before transitioning" — the veto can silently convert into a wasted decision/dead tick exactly at the boundary condition the trust exception exists to handle.
- Why built: `brain train group` surfaced `sandbox-combined-movement-stack + the-game-the-waiting-city` as an untested seam requiring sandbox verification, not just reasoning, per current policy (tension T22).
- Design: Cloned the real `pappydapimp69/the-game-the-waiting-city` repo (not a reimplementation) and wrote a deterministic Node.js sandbox that directly imports the actual `src/sim/ai.js`, `src/sim/pathfind.js`, `src/sim/rng.js`, `src/sim/content.js`, driving `decideEnemyAction`/`bfsNextStep`/`commitMove` with a seeded `makeRng` (no wall-clock, no `Math.random`). Swept an 8-neighbor x 6-seed grid to test an enemy whose FIRST-EVER `decideEnemyAction` evaluation happens while already adjacent to the player, using Warden-class content (`aggro: 99`, effectively always aggros on first tick), plus a control using normal `sentry` content (`aggro: 5`) approaching gradually one tile/tick.
- Got right: Confirmed the safety property FIRST (0/48 overlaps — the veto genuinely works, matching E1's recommended fix) before investigating whether it had a hidden cost, avoiding the mistake of assuming a working safety mechanism is a complete fix. Traced the control case (gradual approach) across 8 ticks to confirm the wasted-tick effect is specific to the already-adjacent boundary condition and does NOT occur under normal gradual engagement, ruling out "this always happens" as an overbroad claim.
- Where/why it failed: An enemy whose first AI-evaluated tick finds it already adjacent to the player transitions `patrol -> chase` (not straight to `attack`) and wastes that tick doing nothing, because `bfsNextStep` returns the player's own tile as the "next step," `commitMove`'s occupancy veto correctly blocks landing on it, but the FSM had already committed to a `chase`-branch decision assuming the move would succeed — reaching `attack` only one tick later than it should have. Reproduced 48/48 times for always-aggro content. The control (`sentry`, aggro margin 5, safely exceeding the max 2-tile/tick convergence) never hits this path, because by the time distance reaches 1 the entity is already in `chase` and the FSM's explicit `distToPlayer<=1` check in the `stillEngaged` branch correctly routes to `attack` first.
- Fix: Not applied to shipping code (flagging only, per instructions) — the FSM's decision function should check the SAME adjacency/occupancy condition `commitMove` will veto on, before choosing which branch to transition to, rather than discovering the veto's outcome only after the fact via a wasted tick. Concretely: when the BFS-selected next step is the player's own occupied tile, `decideEnemyAction` should route directly to the `attack` branch instead of `chase`, mirroring the `stillEngaged` branch's existing `distToPlayer<=1` check.
- Why this fix: The existing `stillEngaged` branch already has the correct check (`distToPlayer<=1` -> attack) — this bug only exists because a FIRST-TIME transition (patrol->chase) doesn't yet have that check, since it wasn't written with the "already adjacent on the very first tick" boundary case in mind.
- Rule of thumb: When a planner has a deliberate "trust the destination/own cell unconditionally" exception (movement-stack#E1) paired with an independent commit-time occupancy veto, verifying the veto prevents overlap only confirms a SAFETY property — it says nothing about whether the decision/FSM layer that chose the plan can detect the veto's outcome before committing to a state transition that assumed success. Check both properties at the same boundary condition (here: target exactly adjacent) — a working veto can still produce a silent, low-severity behavioral defect (a wasted AI tick) invisible to any test that only checks positions/overlap.
- Provenance (verified/assumed): VERIFIED first-hand against the REAL, currently-shipping `pappydapimp69/the-game-the-waiting-city` source (`src/sim/ai.js`, `src/sim/pathfind.js`), not a reimplementation — deterministic sandbox, seeded RNG, 8-neighbor x 6-seed sweep (48/48 reproductions), plus an 8-tick control trace ruling out the gradual-approach case. Live, currently-shipped, low-severity behavior (no overlap, no crash, no determinism violation — this path never rolls the RNG) whose real-world reachability depends on content spawning/aggroing an enemy exactly Chebyshev-distance-1 from the player on its first AI-evaluated tick (e.g. an ambush spawn, or a boss already-adjacent on encounter).

## E15 — the game the waiting city error branch also needs constant roll
- Date: 2026-07-13
- Project: pappydapimp69/the-game-the-waiting-city
- Tags: [determinism][gamedesign][testing][architecture]
- What: Composing `sandbox-combined-skilltree-formula#E1` (a formula referencing an undeclared dependency works by topological-round coincidence, and can flip from silent-success to a thrown `undefined variable` error after a totally unrelated edit elsewhere in the dependency graph) with `the-game-the-waiting-city#E9` (AI decisions inside the authoritative reducer must consume a CONSTANT number of RNG rolls regardless of branch/outcome) surfaced a distinct trigger for violating E9's invariant: not an affordability/boolean branch (already covered by E14), but an EXCEPTION/error-recovery branch. A naive `catch (err) { return earlyDecision }` around a formula-eval step inside an RNG-drawing decision — a pattern that looks like a reasonable safety net in isolation — skips whatever roll(s) the decision would otherwise have drawn once the formula throws, silently perturbing every other entity sharing the RNG stream.
- Why built: `brain train group` surfaced `sandbox-combined-skilltree-formula + the-game-the-waiting-city` as an untested seam requiring sandbox verification, not just reasoning, per current policy (tension T22). Deliberately tested a different mechanism than the already-filed E14 (affordability branch) and the already-filed recursion pinned-gate-value finding, to avoid restating prior work.
- Design: Deterministic Node.js sandbox (seeded mulberry32, no wall-clock/Math.random). A real toposort (Kahn's algorithm, FIFO tie-break, uncanonicalized — matching E1's own documented design) orders formula nodes; a minimal fail-loud expr evaluator raises `undefined variable` when a referenced var hasn't been resolved yet in evaluation order. Entity A's decision function evaluates an `aggroThreshold` formula that has an undeclared dependency on `haste`; whether `haste` resolves before `aggroThreshold` in a given topo ordering determines success or throw. Two variants of A's decision: `buggy` (catch-and-return-early on formula error, skipping the second roll) and `fixed` (always draw both rolls, use a safe default value only if the formula errored). Entity B (unrelated, waiting-city-style) always draws exactly 2 rolls per tick, unchanged. Ran both variants across 4 seeds (12345, 1, 999, 42424242), 50 ticks each, before and after an edit that lengthens ONLY haste's own dependency chain (aggroThreshold's own formula/deps stay byte-identical) — enough to flip topo order and flip aggroThreshold from silent-success to throw.
- Got right: Confirmed the edit genuinely flips A's own formula outcome (before-edit: eval OK, value=12; after-edit: throws `undefined variable 'haste'`) before checking B, ruling out "the edit was a no-op" as an alternative explanation. Also confirmed the FIXED variant still surfaces the underlying formula error correctly (`errored: true` visible in the decision output) rather than silently swallowing it — the fix changes only the roll-count discipline, not error visibility.
- Where/why it failed: Under the `buggy` variant, A's rolls-per-tick dropped from 2 (before-edit) to 1 (after-edit) purely because the catch block returned early before drawing the second roll. Across all 4 seeds, entity B's decision sequence diverged on all 50/50 ticks, with the first difference at tick 0. Under the `fixed` variant (always draw both rolls; use a safe default only when the formula errored), A's total roll count was invariant (100 rolls over 50 ticks, both before and after the edit, every seed), and entity B's decision sequence was byte-for-byte identical across the edit in every seed (0/50 ticks differing).
- Fix: Inside any RNG-drawing decision function, every control-flow exit — not just conditional/affordability branches (E14) but also `catch`/error-recovery paths — must draw the same rolls the decision would draw on its normal path. On error, draw the roll(s) as usual and fall back to a safe default VALUE, rather than returning early and skipping the draw.
- Why this fix: expr's fail-loud undefined-variable check (E1) is doing exactly its job, and a `try/catch` that prevents an uncaught exception from crashing a game tick is independently a reasonable safety pattern — E9's roll-count invariant is broken by the specific COMPOSITION of the two, not by either alone. The natural-looking shape "on error, log and return early" is exactly the shape that violates E9 the same way an affordability check does, just via a different trigger.
- Rule of thumb: When a formula/expression system with a documented "throws on bad/undeclared input after unrelated graph edits" fragility (E1's territory) is embedded inside a decision function that must preserve a constant-RNG-roll-count invariant (E9's territory), audit EVERY control-flow exit inside that decision for skipped rolls — not just boolean/affordability branches (E14), but also catch blocks and other error-recovery paths. A formula system's own correct, well-tested error handling (throwing precisely and loudly) does not by itself guarantee roll-count safety in a caller that reacts to that error by returning early instead of still drawing and using-a-default.
- Provenance (verified/assumed): VERIFIED first-hand — deterministic Node.js sandbox, seeded mulberry32, 4 seeds x 50 ticks, measured entity B's decision-sequence divergence (50/50 ticks differing under `buggy`, 0/50 under `fixed`) and A's own roll-count invariance (100/100 both variants of `fixed`, 100->50 under `buggy`). This is a general architectural-composition risk, not a claim about literal current `the-game-the-waiting-city` shipping code (its real AI/stats code was not re-audited for this specific exception-path shape, since it doesn't currently have a skilltree-formula-style undeclared-dependency graph) — no live-unfixed bug is being flagged here.

## E14 — the game the waiting city affordability branch needs constant roll too
- Date: 2026-07-13
- Project: pappydapimp69/the-game-the-waiting-city
- Tags: [determinism][gamedesign][testing]
- What: Composing `sandbox-dbz-combat#E4` (a ki-cost economy has a real affordability boundary that content tweaks routinely shift) with `the-game-the-waiting-city#E9` (AI decisions inside the authoritative reducer must consume a CONSTANT number of RNG rolls regardless of branch, or a content tweak silently re-perturbs unrelated entities sharing a tick) surfaced a specific, previously-undocumented risk: E9's constant-roll rule is easy to satisfy at the TOP-LEVEL "which action" branch while still violating it at an AFFORDABILITY sub-branch — "only roll the special-move sub-choice when the resource pool can afford it" reads as reasonable and E9-compliant in isolation, but is exactly the kind of decision that makes E9 easy to violate by accident, because the affordability check itself is a branch whose outcome (and thus whether the sub-roll happens) shifts every time a cost constant is tuned.
- Why built: `brain train group` surfaced `sandbox-dbz-combat + the-game-the-waiting-city` as an untested seam requiring sandbox verification, not just reasoning, per current policy (tension T22).
- Design: Two entities decided per tick in fixed sorted order (mirroring waiting-city's `Object.keys(state.enemies).sort()`), sharing one seeded RNG stream (mulberry32, no wall-clock). Entity A is a dbz-combat-style ki-costed decision-maker with two variants: `buggy` (rolls a target-bias, then ONLY rolls a sub-choice if `ki >= specialCost`) and `fixed` (always rolls the sub-choice per E9's literal rule, using the result only when affordable). Entity B is an unrelated waiting-city-style patroller always drawing exactly 2 rolls, unchanged between runs. Both variants were re-run with only `specialCost` changed (10 -> 11, a routine balance tweak), and B's decision sequence was diffed across the two runs, across multiple seeds.
- Got right: Confirmed A's own branch mix genuinely changed under the cost tweak (60->54 special picks out of 200 ticks in one seed) before checking B — ruling out "the tweak was a no-op" as an alternative explanation for any observed divergence, and isolating the actual causal mechanism (shared-stream roll-count drift) from a confound.
- Where/why it failed: Under the `buggy` variant, entity A's own rebalance (touching only A's economy) caused entity B's decision sequence to diverge in 157-167 of 200 ticks (78-84%) across every seed tested (12345, 1, 999, 42424242), starting as early as tick 6 — purely because A's variable roll consumption (0 or 1 extra roll depending on affordability) shifted every subsequent draw from the shared RNG stream. Under the `fixed` variant (always draw the sub-choice roll, gate only its USE on affordability), B's decision sequence was byte-for-byte identical across both cost tunings in every seed (0/200 differing), and total rolls consumed became invariant (`ticks x 4` exactly, vs. `660`/`654` under `buggy`).
- Fix: Apply E9's constant-roll-count discipline at the AFFORDABILITY branch specifically, not just at the top-level action-choice branch: always draw the roll a sub-decision would need, and use the drawn value only when the resource check passes — never skip the draw itself based on affordability.
- Why this fix: E9's own stated rule ("every decision must consume a constant number of RNG rolls regardless of outcome") is written broadly enough to already cover this case in principle, but its own worked examples (patrol always rolls 2, a car always rolls once) don't include a resource-gated branch, making it easy to satisfy the rule's letter at the top level while violating its spirit one level down, inside a specific decision's own internal branching.
- Rule of thumb: When porting a resource-costed decision (dbz-combat-style: "can I afford this option") into an architecture with a constant-roll-count discipline (waiting-city-style: "every AI decision draws the same number of rolls no matter what"), apply the discipline at EVERY branch point inside that decision, not just at the top-level action choice — an affordability check is exactly the kind of branch a content tweak (rebalancing a cost) will routinely flip, and skipping a roll based on its outcome reintroduces the shared-RNG-stream entanglement the top-level discipline was built to prevent, even though the top-level rule reads as satisfied.
- Provenance (verified/assumed): VERIFIED first-hand — built and ran a deterministic Node.js sandbox (seeded mulberry32, no wall-clock) implementing both variants across 4 seeds (12345, 1, 999, 42424242) and a cost-tuning change (10->11), directly measuring entity B's decision-sequence divergence (157-167/200 ticks differing under `buggy`, 0/200 under `fixed`, consistent across all seeds) and total roll-count invariance (`fixed` always `ticks x 4`, `buggy` varying with the cost tuning).

## E13 — ship the tech leap without making it the story
- Date: 2026-07-09
- Project: pappydapimp69/the-game-the-waiting-city
- Tags: [gamedev][gamedesign]
- What: When a project ships its biggest-ever technical leap, the tempting move is to make that leap the STORY (lampshade it, build the narrative around it). This game did the opposite on purpose: it ships the saga's first real enemy AI while deliberately refusing to make the game about AI — the in-fiction reason "the enemies are suddenly competent" is the mundane "a tyrant's trained soldiers, not the feral things in the Reach," and the richer "an intelligence gains agency" theme is explicitly RESERVED for the next installment. The cost: you forgo the dramatic "the enemies woke up" reveal now, and constrain all of this game's writing to avoid the very vocabulary (consciousness, artificial) the tech would invite.
- Why built: Phase 3 is the first time anything in the saga moves and decides on its own — a genuine engineering milestone the prior game even set up in-fiction ("I haven't learned to move yet. The next one will."). The obvious, plausible alternative is to cash that in immediately: make Phase 3 the "the machines awakened / Skynet turn" story, matching the mechanical leap with the matching narrative beat.
- Design: The saga's own 5-part arc structure already reserves the "artificial threat" beat for Phase 4, not Phase 3 (Phase 3 is the "tyrant" arc). So the design gives Phase 3 a mundane, load-bearing in-fiction explanation for competent enemies — trained human soldiers under a tyrant — and keeps ALL "learning" language in this game's fiction in the vocabulary of training/drilling/discipline, never consciousness or artificiality. The technical leap ships fully; the thematic payoff is deliberately deferred.
- Got right: The choice actually made — decouple the technical milestone from the narrative milestone. Ship real AI now, but frame it as ordinary competence so nothing has to be lampshaded, and bank the "an intelligence gains agency" theme for when the story structure actually calls for it (Phase 4). ## E12 — saga independence by duplication versioned code
- Date: 2026-07-09
- Project: pappydapimp69/the-game-the-waiting-city
- Tags: [gamedev][tooling][process]
- What: A multi-game saga can carry state forward two ways: a SHARED runtime engine every game imports, or INDEPENDENCE-BY-DUPLICATION where each game re-implements its own spine and the ONLY thing that crosses between games is an opaque, versioned, checksummed save code. This saga deliberately chose the second: "this repo may reuse the earlier games' architecture but never edits them and shares no runtime code — continuity travels only through the saga.v2 import / saga.v3 export code." The cost is real and it is the exact opposite of DRY.
- Why built: Five games shipped over time, each static-hosted with zero dependencies, each needing to (a) accept the prior game's run and (b) hand off to the next — while never breaking an already-shipped, already-played sibling. The obvious alternative is a shared `saga-engine` package all five import and upgrade together.
- Design: `src/sim/saga.js` defines the carryover contract: `SAGA<N>.<base64 canonical JSON>.<fnv1a32 checksum>`, versioned FOREVER. Game 3 hardcodes `IMPORT_PREFIX='SAGA2'`/`IMPORT_VERSION='saga.v2'` (what it reads from Wrong Sky) and `EXPORT_PREFIX='SAGA3'`/`SAGA_VERSION='saga.v3'` (what it writes for game 4). Imported choices (ravagerFate from the Prologue, riftChoice from Wrong Sky) are remembered and re-exported alongside this game's own wardenFate, so the chain accumulates. `importSaga` NEVER throws on bad input — a mistyped/altered code returns `{ok:false,error}` (checksum-verified), and every sequel accepts the prior code OR a fresh start: "the code is a courtesy, never a wall."
- Got right: The choice actually made — each game rebuilds its own determinism spine (rng/canonical/fingerprint/reduce) and shares NO imported runtime module; the cross-game surface is reduced to a single frozen string format with an embedded version tag and integrity checksum. A shipped game can never be broken by a later game's change because there is nothing live to change underneath it; a version (`saga.v2`) can be supported forever without any shared-library upgrade treadmill; and the whole thing stays a static, dependency-free page.
- Where/why it failed: The trade-off accepted — total loss of single-source-of-truth. A bug or gap fixed in one game does NOT propagate; it must be hand-carried into every sibling that copied the same spine before the fix existed. This project realized that cost repeatedly IN THE SAME SESSION: the mobile world-scale bug (#E7), the `ontouchstart` touch-detection bug (#E6), and the nested-import cache-bust gap (#E8) were each found here and then re-fixed by hand in the sibling the-game-wrong-sky (commits 9cef0ee / 980b011 / 695dce0) — and #E8 is precisely a "known gap sat unfixed in every sibling that copied the boilerplate before it was catalogued." A shared engine would have fixed all five at once; duplication means N fixes and the standing risk of a forgotten sibling.
- Fix: Chose independence + a versioned/checksummed handoff code over a shared engine, and mitigated the duplication cost with discipline rather than abandoning the choice: canonical JSON + FNV-1a checksum so a handoff can't silently corrupt, a permanent version tag so an old code is rejected cleanly (not misparsed) by a newer game, "accept the code OR start fresh" so a broken/absent code never blocks a player, and (per #E8) a memory catalog that turns "re-discover the gap in each sibling" into "propagate the known fix to all siblings in one pass." The naive shared-engine alternative was rejected because it would couple five independently-shipped static games into one upgrade unit, where a change for game 5 could regress game 1.
- Why this fix: When artifacts must ship independently and stay playable forever, coupling them through shared live code trades duplication for a worse failure mode — a change anywhere can break a frozen, already-released elsewhere. A narrow, versioned, self-validating data contract as the ONLY cross-artifact dependency buys permanent backward compatibility and blast-radius isolation, at the known, manageable price of propagating fixes by hand (and a catalog that makes propagation a checklist, not a rediscovery).
- Rule of thumb: For a series of independently-shipped, must-stay-working-forever artifacts (saga games, versioned public APIs, embeddable widgets), prefer independence-by-duplication with a single narrow versioned+checksummed data handoff over a shared runtime library — you gain permanent backward compat and isolation, but you MUST budget for the inverse-of-DRY cost: every fix propagates by hand to each sibling that copied the spine. Make the handoff self-describing (version tag) and self-validating (checksum), make consuming it always optional ("a courtesy, never a wall"), and keep a written catalog of known gaps so a fix found in one copy is propagated to all, not rediscovered per copy.

## E10 — building fade globalalpha not offscreen filter compositing
- Date: 2026-07-09
- Project: pappydapimp69/the-game-the-waiting-city
- Tags: [gamedev][rendering]
- What: A "walk behind a tall object and it turns translucent" reveal can be done richly (composite through an offscreen buffer, or apply `ctx.filter` per element) or cheaply (`globalAlpha` on a plain `fillRect`, drawn straight onto the visible canvas). This game deliberately chose the cheap path — specifically to avoid repeating a prior game's per-tile `ctx.filter` performance bug — and accepted that the effect is limited to a flat alpha fade and can't be the fuller grayscale-style reveal the previous game used.
- Why built: The Waiting City's visual signature is multi-tile buildings that fade to translucent when the player stands north of (behind) them. The prior game (Wrong Sky) had a comparable visual reveal implemented via offscreen compositing / filters, which produced a real, diagnosed performance problem: applying `ctx.filter` inside a per-tile / per-entity hot loop (hundreds of draws per frame) was expensive.
- Design: `src/app/renderer.js` draws each building footprint as a facade last among world-space content (so it occludes the ground layer). When `view.py < b.y && view.px >= b.x-1 && view.px <= b.x + b.w` (player behind and within the building's width), it sets `ctx.globalAlpha = BUILDING_FADE_ALPHA` for that building's `fillRect`s and resets to 1 after — no offscreen buffer, no `ctx.filter` anywhere in the per-tile/per-entity hot loop. The only `ctx.filter` in the file is a single one-line NPC recolor, deliberately kept out of the tile loop.
- Got right: The choice actually made — express the whole reveal as `globalAlpha` on the primitives already being drawn, on the live canvas, with no compositing stage. `globalAlpha` on a plain `fillRect` is essentially free per call, so the effect scales to hundreds of building tiles per frame with no measurable cost, and there is no offscreen-buffer allocation/blit and no filter re-parse per draw. Verified at ~50ms/frame worst case in headless Chromium with no stalls — the exact class of bug the prior game hit is structurally impossible here.
- Where/why it failed: The trade-off accepted — a flat alpha fade is strictly less expressive than what offscreen compositing / filters buy. Wrong Sky's approach could do a grayscale-style reveal (desaturate, not merely dim); alpha alone can only make a thing more transparent, uniformly. Any effect that needs per-pixel color transformation, a blur, or blending a separately-rendered layer is off the table with this choice. The design gave up that expressive ceiling in exchange for guaranteed cheapness.
- Fix: Chose `globalAlpha`-on-visible-canvas over an offscreen-buffer/`ctx.filter` reveal, because the richer path had already been proven to cause a per-draw-call performance bug in the sibling game, and this game's reveal (dim the facade so the player shows through) genuinely only needs transparency — not recoloring. The naive "reuse the prior game's fancier reveal machinery" was rejected on the concrete evidence of that prior perf bug, not on speculation: the same visual GOAL was satisfied by the cheapest primitive that meets it.
- Why this fix: Reach for the cheapest rendering primitive that actually satisfies the visual goal, especially inside a per-tile/per-entity hot loop — `globalAlpha` costs nothing, `ctx.filter` and offscreen compositing cost per call and per frame. When a prior project already paid for the expensive path with a diagnosed perf bug, that evidence should directly gate the next project's choice: don't re-import fancier machinery than the new effect requires just because it's available.
- Rule of thumb: For "walk-behind" / occlusion-reveal effects, if the effect is only a fade (make it show-through), use `globalAlpha` on the existing fill primitives on the live canvas — do NOT reach for `ctx.filter` or an offscreen-buffer composite inside a per-tile/per-entity hot loop; those cost per draw call and are a known frame-time trap. Only pay for compositing/filters when the effect genuinely needs per-pixel color work (grayscale, blur, layer blends) that alpha can't express — and accept that flat-alpha's expressive ceiling is the price of that cheapness.

## E9 — ai decisions inside authoritative reducer
- Date: 2026-07-09
- Project: pappydapimp69/the-game-the-waiting-city
- Tags: [gamedev][state][process]
- What: Where you put autonomous-agent "thinking" (enemy/NPC AI) is a real architectural fork, not a detail. The team chose to call `decideEnemyAction`/`decideCarStep` from inside reduce.js's `TICK` case (`src/sim/ai.js`), iterating `Object.keys(state.enemies).sort()`, so movement is authored state-transition logic, not a presentation output. Enemy ATTACK stays a separate presentation-issued `ENEMY_STRIKE` command (a discrete proximity+cooldown event the sim shouldn't own), but MOVEMENT is sim-internal.
- Got right: The choice actually made — put AI decision-making inside the authoritative reducer, so the existing golden-fingerprint replay exercises the AI for free and any future AI tuning is caught as a fingerprint drift instead of silently invalidating fixtures. The AI only ever sees `state` (+ `state.rng`), so there is no wall-clock parameter available to leak — the ambient-time/randomness ban this file lives under covers the AI automatically. Cars reuse the exact same movement machinery (minus aggro) as a non-hostile proof the mechanism generalizes.
- Where/why it failed: The trade-off accepted — AI logic loses everything the presentation layer would have given it for free. No wall-clock or frame delta, no `Math.random` (must draw from `state.rng` via `nextInt`), no floating point, and a discipline the render-layer version would never need: each decision must burn a FIXED roll count even when the roll changes nothing (patrol always consumes 2 rolls; a car always rolls once even with a single legal direction) so future content can't retroactively shift other movers' rolls. - Why this fix: A replay/determinism guarantee is only worth what it actually covers. Any logic that decides authoritative state but lives outside the replayed function is invisible to the golden test — you get a green fingerprint that proves nothing about your hardest code. Putting the agent logic where the guard can see it converts "hope the AI is deterministic" into "the AI is a covered regression surface," at the cost of writing it under the sim's integer/no-ambient-time rules.

Accept the tax that comes with it: seed all randomness from the sim's own RNG, ban wall-clock/float, and make every decision consume a constant number of RNG draws regardless of branch taken, so a later content change can't retroactively perturb unrelated entities sharing that tick. Keep genuinely discrete, presentation-triggered events (an attack on proximity+cooldown) as their own commands; it's continuous per-tick decision-making that must live in the reducer.

## E7 — waitingcity world scale must fit shorter screen axis
- Date: 2026-07-09
- Project: pappydapimp69/the-game-the-waiting-city
- Tags: [gamedev][rendering][mobile]
- What: A top-down camera's world-to-screen scale formula that fits N tiles along canvas HEIGHT unconditionally is a landscape-only assumption (H is the constraining/shorter screen dimension) — it silently breaks on any portrait screen, where H is the LARGER raw-pixel dimension, blowing the zoom level way up and leaving only a sliver of width on screen.
- Why built: A player reported "the screen scale is wrong" on mobile. `renderer.js` computed `const scale = H / (16 * TILE)` — fit exactly 16 tiles of world vertically, always, regardless of device.
- Design: The backing canvas store tracks `window.innerWidth/innerHeight × devicePixelRatio` (main.js's resize()), so on a real phone in portrait the canvas is often TALLER in raw pixels than any desktop browser window (e.g. 780×1688 at DPR 2, vs. a typical desktop window's 1280×720). The scale formula only ever looked at H, with the unstated assumption baked in at authoring time (on a desktop landscape window, H is always the smaller dimension, so "fit 16 tiles to H" reads as "fit 16 tiles to whichever dimension is shorter" — that equivalence quietly stops holding on portrait).
- Got right: Traced the actual math instead of guessing — computed what `scale` and the resulting visible-tile-count would be for a real portrait viewport (390×844 CSS, DPR 3 → 780×1688 canvas backing store) versus the assumed-landscape case, and confirmed the discrepancy (portrait: ~7.4 tiles of width visible vs. the intended 16) before touching code.

- Why this fix: Preserves the exact existing desktop/landscape experience (verified via a before/after screenshot — pixel-identical framing) while fixing portrait by construction by generalizing "fit the constraining dimension" from its silently-landscape-only special case to any aspect ratio.
- Rule of thumb: A camera/viewport scale formula authored and only ever tested on a landscape desktop window that references ONE fixed screen dimension ("fit N units to H" or "to W") is implicitly encoding an aspect-ratio assumption, not a general rule — replace the single dimension with `Math.min(W, H)` (or the dimension the design actually wants to bound) before shipping to any device where portrait is possible, and verify with an actual portrait-viewport screenshot, not just a resized desktop window (a resized desktop window is still landscape-biased and won't surface this).

- Why built: Considering whether the new confidence-gated perception system (regular guards read hp/power/AI-state once the player has enough real encounters with that kind, win or loss — see the companion entry on validating the exception) should also apply to the one-shot Warden boss fight, via some attempt-counting scheme (e.g. "the Warden gets more readable each time you fight it").
- Design: Read `game.js`'s actual respawn implementation rather than assuming "die → retry the fight" is what happens.
- Got right: Didn't assume; went and read the code path that death actually triggers before designing around it.
- Where/why it failed: `const respawn = JSON.stringify(world)` is captured once at session start (see the related, already-filed lesson on why that snapshot exists — projects/pappydapimp69__the-game-wrong-sky.md, wrongsky-snapshot-run-start-for-respawn). On player death, `world = JSON.parse(respawn)` restores that ONE snapshot — reverting the entire session's progress (every quest, every kill, every item), not just the current fight. An attempt-based boss mechanic assumes "try, lose, try again" is cheap; here, losing to the boss costs the whole playthrough. The two designs are incompatible unless the respawn model itself changes.
- Fix: Kept the Warden on its original flat perception-stat gate instead — a deliberate, named exception to the new confidence system, not an oversight. No code needed changing for the boss at all; the fix was catching the mismatched assumption before writing code that would have been quietly unusable (an attempt-based reveal nobody could actually exercise more than once per session).
- Why this fix: Cheaper to discover "this mechanic has no reachable design space" by reading the retry path than to build the mechanic and find out via playtest that it never gets used because losing the boss fight means abandoning the run.
- Rule of thumb: A mechanic that scales with "number of attempts at X" is only viable if attempting X again is actually cheap for the player. Read the literal retry/respawn/reload code path for X before designing around repeated attempts — "you can always just try again" is a UX assumption, not a given, and a full-session-revert respawn (common in small deterministic-sim games that snapshot session start for simplicity) silently invalidates it for any one-shot encounter.
