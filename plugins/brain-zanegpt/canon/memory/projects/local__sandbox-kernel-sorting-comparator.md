## E1 — sorting invalid comparator order dependent outputs
- Date: 2026-10-09
- Project: local/sandbox-kernel-sorting-comparator
- Tags: [sorting][correctness][algorithm][determinism][testing]
- What: An invalid sort comparator (cyclic, boolean-returning, NaN-bearing, or tolerance-based "equal if close") was run through the stdlib sort over every input order of small data sets. Each family gave a different output for different input orders, raised no error, and the exact outputs changed between interpreter versions. The same comparators gave one output whenever the violating tuple was not present in the data.
- Why built: The sorting kernel claims an invalid comparator gives order-dependent undefined results, but its only evidence was one cyclic example from two start orders. This build counts distinct outputs over all permutations for several invalid families, and also tests the "quantise instead" repair from the floating-point dedupe lesson on the sort path.
- Design: Python stdlib sorted() with cmp_to_key. Control comparator is a consistent total order (6 values, 720 permutations). Invalid families: rock-paper-scissors cycle on RRPPSS (90 distinct input orders), a JS-style comparator returning 0/1 and never -1 on 6 distinct values, NaN among 5 values (120 perms) under plain < and under sign(a-b), a tolerance comparator on the chain 0, .6, 1.2, 1.8, 2.4 with eps 1. Break cases: cycle with only two of its three symbols, and tolerance on values spaced wider than eps. Scale: 96 items, 200 fixed-seed shuffles. A pure-Python run-detect plus binary-insertion model of the small-list path is compared with the real sort. The same file was run on 3.11, 3.12 and 3.13.
- Got right: The control gave 1 distinct output of 720. The boolean comparator gave 720 distinct outputs of 720 (the output just echoes the input, and only the one already-sorted input is sorted). NaN gave 22 distinct outputs of 120 under both plain < and sign(a-b), 17 of 22 with the non-NaN part mis-sorted. The tolerance chain gave 16 distinct of 120. Both break cases gave exactly 1 output, so the defect needs the violating tuple present in the data. No call raised an exception (0 across all runs).
- Where/why it failed: Four of my written predictions came out wrong. (1) The cycle gave 24 distinct outputs on 3.13, above my 2-20 bound; on 3.11 and 3.12 it gave 12, so the same comparator and inputs differ by interpreter version. (2) Quantising with round(v/eps) does NOT give an identical output for every input order: 4 distinct outputs for the chain, because the grouping is identical (1 distinct partition) but each bucket keeps its input order under a stable sort. (3) At 96 items, 200 shuffles gave 134 distinct outputs on 3.11/3.12 and 185 on 3.13, short of my 190 guess. (4) The small-list model matched the real sort on 200 of 200 lists of length 40 on 3.11 and 3.12 (3 of 200 at length 130), but only 114 of 200 on 3.13, so the small-list path changed.
- Fix: For a quantised tolerance, sort on the pair (round(v/eps), v): that gave 1 distinct output where the bucket-only key gave 4. For a cycle, sort on an explicit rank map (1 distinct output). For NaN, filter or partition NaN out before sorting (1 distinct). For a boolean comparator use a plain key (1 distinct).
- Why this fix: Each repair replaces a pairwise relation that can be inconsistent with a key computed once per item, which is a total order by construction. The bucket key alone only makes the partition deterministic; the value in the pair makes the order within a bucket deterministic too, so the quantise advice from the dedupe lesson holds for grouping but needs a tiebreak for sorting.
- Rule of thumb: Treat an invalid comparator's output as unspecified, not merely unsorted: it varies with input order and with interpreter version, and no error is raised. Tests must permute the input, include the violating tuple together (a cycle or near-equal chain or NaN), and compare outputs across orders. For tolerance or cycles, sort on a key tuple (bucket, value) or an explicit rank; do not rely on a model of one version's sort internals.
- Provenance (verified/assumed): Verified first-hand: every number above came from the sandbox runs on interpreters 3.11, 3.12 and 3.13 in this session. The 3.13 small-list change was observed only as a model mismatch (114 of 200), and its cause was inferred from the mismatch, not read from the source.
