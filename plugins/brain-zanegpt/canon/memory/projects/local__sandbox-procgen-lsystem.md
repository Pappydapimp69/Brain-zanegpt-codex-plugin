## E1 — sandbox procgen lsystem bbox outpaces segment count
- Date: 2026-07-11
- Project: local/sandbox-procgen-lsystem
- Tags: [algorithm][gamedev][gamedesign]
- What: An L-system turtle-graphics generator (classic fractal-plant production rule `F -> F[+F]F[-F]F`) was measured across iterations to check the intuitive assumption that "more iterations = more visual detail/density." It does not hold: segment count grows exactly 5.00x per iteration once the ratio stabilizes (by iteration ~4-5), but the bounding-box AREA grows roughly 9x per iteration over the same range — meaning the structure's spatial footprint outpaces its detail count, so higher-iteration output is measurably SPARSER (more spread out relative to its segment density), not denser.
- Why built: A procgen-algorithm sandbox to characterize L-system growth behavior for potential use in generating organic structures (trees, vines, roots) for this saga's own procedural-content pipeline, since "just increase iteration count for more detail" is a common naive assumption worth checking empirically before relying on it.
- Design: Expand the axiom string via the production rule for N iterations, interpret the result with a turtle (F=move forward and draw, +/-=rotate by a fixed angle, []=push/pop position+heading for branching), and measure segment count and bounding-box dimensions per iteration. Also swept the turn angle (20-45 degrees) to check whether small angle changes cause large/chaotic shape changes, and compared against a structurally different "bushier" rule with more branches per rewrite.
- Got right: Choosing to measure BOTH segment count and bounding-box area separately (not just one proxy for "detail") was the right call — it's exactly what surfaced the actual finding, since either metric alone would have looked unremarkable (segment count growth looks like clean exponential growth on its own; bbox growth alone looks like normal expansion).
- Where/why it failed: The naive assumption ("more iterations = a more detailed-looking structure at a similar scale") is wrong for this rule: area grew from 2.6 to 177,989 square units over 6 iterations (a ~68,000x increase) while segment count only grew ~3,125x over the same range — the shape is expanding in space nearly 22x faster than it's adding detail, relative to iteration 1's baseline ratio. A second, independent surprise from comparing rules: a "bushier" production rule (8 F's per rewrite vs. the plant rule's 3 F's, so more segments added per iteration) produced a SMALLER bounding box than the sparser plant rule by iteration 4-5 (1,970 vs. 2,197 area units at iteration 4; 8,476 vs. 19,777 at iteration 5) despite having more total segments at every iteration measured — more branches per rewrite does not imply a spatially larger result, because a rule with more turns per unit of forward movement can curl a structure in on itself rather than reaching outward. Angle sensitivity, by contrast, was NOT chaotic for this rule: sweeping the turn angle from 20 to 45 degrees produced smooth, monotonic bounding-box growth (22.0 to 40.8 width units) with no sudden jumps, contradicting a common assumption that L-systems are unpredictably sensitive to small parameter changes — at least for this specific self-similar branching rule class.
- Fix: Not applicable — no bug was found, this is a characterization result informing future generator design, not a fix to existing project code. The verified, portable takeaway for actually using L-systems in a game: fix iteration count LOW (3-4) for anything that needs to fit a bounded viewport/tile budget, and get size/shape variation from OTHER parameters (turn angle, step length, choice of production rule) instead of iteration count, since iteration count is the parameter most likely to blow a rendering/collision budget unpredictably.
- Why this fix: Segment count and spatial reach are two genuinely independent axes of an L-system's behavior, not two views of the same "amount of detail" — a generator that exposes only "iteration count" as its tunable parameter conflates them, and a caller who wants "more detail, similar size" or "bigger, similar detail" needs to reach for the RIGHT parameter (production rule complexity for the former, iteration count or step length for the latter), which this project's characterization now makes an informed choice rather than a guess.
- Rule of thumb: When tuning an L-system (or any recursive/self-similar procedural generator) for game use, measure segment/node count and spatial bounding box as SEPARATE metrics before assuming either one is a proxy for "visual richness" — they can and do diverge, sometimes in the opposite direction from intuition (a rule that adds more segments per rewrite is not guaranteed to produce a spatially larger result). Cap iteration count deliberately for any generator whose bounding box you haven't verified grows sub-exponentially, since exponential segment growth commonly comes paired with faster-than-exponential spatial growth, not slower.
- Provenance (verified/assumed): VERIFIED first-hand — ran the actual generator (Node.js sandbox), exact figures (5.00x segment growth ratio stabilizing by iteration 4-5; area figures 2.6/26.5/244.2/2197.4/19776.6/177989.8 across iterations 1-6; angle-sweep bbox widths 22.0-40.8 across 20-45 degrees; bush-vs-plant-rule area comparison at iterations 1-5) are direct output of the sandbox run, not estimated or sourced externally. Self-intersection counts were only verified up to iteration 3 (125 segments) — the O(n^2) check was explicitly skipped above that segment count as too slow for the sandbox, and that limitation is stated rather than silently omitted.
