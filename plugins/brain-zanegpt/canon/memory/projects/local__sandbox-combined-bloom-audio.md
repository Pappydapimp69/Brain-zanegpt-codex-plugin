## E8 — bloom reload realtime drain budget
- Date: 2026-07-13
- Project: local/sandbox-combined-bloom-audio
- Tags: [audio][dsp][realtime][state][determinism][testing]
- What: A persisted Bloom bit array reloaded with the wrong ambient seed can turn every previously inserted key into a false negative; if each false negative enqueues a repair message and the audio callback drains the queue until empty, the seed-persistence bug becomes a realtime budget failure.
- Why built: `brain train` aimed the next pass at the single-source edge between `sandbox-combined-audio-realtime` and `sandbox-combined-bloom-audio`. The interaction claim was that Bloom seed persistence is not only a deterministic replay concern: when its false negatives feed a realtime producer/consumer queue, it can multiply callback work past the audio budget.
- Design: Built `sandbox-bloom-realtime-drain.js`, a deterministic JavaScript model with: - 4096 inserted event keys. - A fixed-size Bloom filter with four deterministic seeded hash rounds. - A persisted bit array built with `OLD_SEED`. - A broken reload path that checks the same bit array with `NEW_AMBIENT_SEED`. - A realtime callback budget of 256 work units and per-message cost of 8 units. - Two consumer policies: drain-until-empty and capped drain at 32 messages per callback.
- Got right: The sandbox isolates the composed failure without clocks, RNG, threads, or wall-time measurements. The only variable between broken and fixed cases is the reloaded seed; the only variable between overrun and bounded cases is the callback drain policy.
- Where/why it failed: The broken reload produced 4096/4096 false negatives. Drain-until-empty processed all 4096 repair messages in one callback, costing 32768 units against a 256-unit budget, a 128x overrun.
- Fix: Persist and reload the Bloom seed with the bit array so the repair storm does not occur. Independently, cap realtime callback queue drains so any producer burst, including one caused by a state-persistence bug, is carried over across callbacks instead of consuming unbounded callback iterations.
- Why this fix: Seed persistence removes the specific false-negative storm: the fixed-seed case produced 0 false negatives and 0 overrun. The capped drain contains the broader producer-burst class: with the broken seed still producing 4096 false negatives, the capped consumer spread the work across 128 callbacks, with max 32 iterations and 256 units per callback, producing 0 overruns.
- Rule of thumb: State reload bugs that create producer bursts are realtime bugs when callbacks drain until empty. Persist deterministic seeds/state, and still cap callback queue work because producer correctness should not be the only thing enforcing the realtime budget.
- Provenance (verified/assumed): Verified first-hand on 2026-07-13 by running `node sandbox-bloom-realtime-drain.js` in `C:\Users\Kompooter\Documents\Brain`. Observed: broken seed reload + drain-until-empty = 4096 false negatives, 4096 max callback iterations, 32768 cost, 256 budget, 128x overrun; persisted seed + drain-until-empty = 0 false negatives and 0 overrun; broken seed reload + capped drain = 4096 false negatives, 128 callbacks, 32 max iterations, 256 max cost, 0 overruns.
- Composed: sandbox-combined-audio-realtime/E1, sandbox-combined-bloom-audio/E1, sandbox-combined-bloom-audio/E4
- Link: Sandbox: `sandbox-bloom-realtime-drain.js`

## E7 — genesis mix psg spectral comparison cannot verify lfsr tap
- Date: 2026-07-13
- Project: local/sandbox-combined-bloom-audio
- Tags: [audio][dsp][testing]
- What: Re-verifies the genesis-mix/genesis-psg edge from a new angle (already-filed angle: psg's real non-pow2 period causes mix's naive FFT to silently truncate data). New claim tested, from mix#E1's own second point ("compare on ABSOLUTE energy, not a per-buffer-normalized spectrum, because two different inputs can emit identical garbage"): does normalized-spectrum comparison specifically mask a wrong-tap LFSR bug that absolute-energy comparison would catch? That specific hypothesis was REFUTED — for most tested wrong taps (0x3, 0x5, 0x11), both absolute energy ratio and normalized-spectrum L2 distance correctly flagged a difference. But the sandbox surfaced a sharper, different bug while testing it: for taps 0x6, 0xB, and 0x21, BOTH absolute energy (ratio ~1.0-1.04) AND normalized-spectrum L2 distance (~0.016-0.017) were nearly indistinguishable from the correct tap (0x9) — even though their actual measured periods are wildly different (57337 for the correct tap vs 200000+, 23622, and 16383 respectively for the three "spectrally invisible" wrong taps).
- Why built: To check a specific mechanism (normalization hides real differences) suggested by mix#E1's own text; running it revealed the real risk is broader than that specific mechanism — spectral/energy comparison of ANY kind (normalized or not) is simply not a valid discriminator for LFSR tap correctness, for a meaningful subset of plausible wrong taps.
- Design: `lfsrSequence(tapMask, 4096)` reproduces psg#E1's own described LFSR mechanism for 6 different tap masks (1 correct, 5 plausible-wrong). Each sequence run through a radix-2 FFT (mix#E1's own algorithm) over a fixed 4096-sample (power-of-2) window; magnitude spectra compared both raw (absolute) and normalized (divided by total energy) against the correct tap's spectrum via L2 distance. Actual periods independently measured (psg#E1's own established method: count steps to state-repeat) to confirm the "spectrally invisible" wrong taps are genuinely, substantially different LFSRs, not coincidentally equivalent ones.
- Got right: mix#E1's absolute-vs-normalized distinction is real and correctly matters for SOME wrong-tap cases (0x3, 0x5, 0x11 all show clearly different energy ratios AND normalized distances) — the original finding isn't wrong, it's just not the full story for this specific composition.
- Where/why it failed: A short-window (4096-sample) FFT magnitude spectrum captures the LFSR's short-term statistical texture (roughly: how "white" the noise looks, its rough spectral tilt) — it does NOT capture the sequence's actual periodicity, which only becomes visible at a timescale approaching the true period (57337 samples, over 14x longer than the analysis window used here). Two LFSRs with completely different periods and completely different actual bit sequences can produce near-identical SHORT-WINDOW spectra purely because both look like "roughly white noise" at that scale — the spectral test is measuring the wrong property entirely for this validation task, a category mismatch, not a normalization-specific flaw.
- Fix: Verify LFSR/noise-generator correctness via the property that actually distinguishes implementations — measured PERIOD (psg#E1's own established, correct method) or exact bit-sequence comparison over a long-enough window to approach the period — never via spectral/FFT energy comparison at any window length short relative to the period, regardless of normalization.
- Why this fix: The fix isn't "use absolute energy instead of normalized" (mix#E1's own stated fix, correct for ITS finding) — for LFSR tap verification specifically, spectral comparison of either kind is the wrong tool, because periodicity is a TIME-domain property that a short-window frequency-domain measure structurally cannot see. This composition shows a specific, verified case where a validation technique correctly recommended in one context (comparing FFT outputs generally, per mix#E1) is the wrong tool entirely in a different, adjacent context (verifying a specific generator's period-defining tap), even after applying that context's own correctly-stated fix.
- Rule of thumb: Before reusing a validation/comparison TECHNIQUE (spectral analysis, statistical distance, any summary-statistic comparison) across two different verification tasks, check whether the technique actually measures the property that distinguishes CORRECT from WRONG in the new task — a technique's own documented fix (normalize vs. don't) can be exactly right for its original finding and still leave the technique fundamentally inapplicable to a different but superficially similar-looking verification problem, here because periodicity lives at a timescale a short spectral window cannot see at all.
- Provenance (verified/assumed): VERIFIED first-hand — computed FFT magnitude spectra (absolute and normalized) for 6 different LFSR tap configurations at a fixed 4096-sample window, and independently measured each tap's actual period via direct state-repeat counting: taps 0x6/0xB/0x21 (periods 200000+/23622/16383, versus the correct tap 0x9's 57337) all showed near-identical spectra (energy ratio 0.97-1.04, normalized L2 distance 0.016-0.017) to the correct tap, while taps 0x3/0x5/0x11 (energy ratios 0.23-0.43) were correctly distinguishable by both measures.

## E6 — bloom savemigrate idempotent migration preserves unknown fields
- Date: 2026-07-13
- Project: local/sandbox-combined-bloom-audio
- Tags: [state][testing][algorithm]
- What: Re-verifies bloom + savemigrate from a new angle (already-filed angle: bloom's seed must be persisted alongside its bits, or reload false-negatives). New claim tested: savemigrate#E2's own established idempotency discipline ("call the migrator twice in a row before trusting it in any pipeline that could retry or resume") applied to a save payload carrying a Bloom filter's fields (`seed`, `bits`, `m`, `k`) alongside the versioned data `migrate()` actually reshapes. Calling `migrate()` twice on the same save produced byte-identical output both times — the bloom-filter fields passed through completely untouched, and the version-gate correctly prevented re-reshaping `ki`/`mana`.
- Why built: To check whether savemigrate's own idempotency requirement (E2) — proven for its OWN reshape logic in isolation — still holds once a completely unrelated system's fields (bloom's seed/bits, which `migrate()` has no knowledge of) ride along in the same save payload, since a reshape step's `{...s, ki: ...}` spread pattern could plausibly interact badly with fields it doesn't recognize under repeated application.
- Design: `migrate()` (savemigrate#E1's version-dispatch pattern, gated on `version < 2`) applied twice in succession to a save containing both the version-1 `mana` field it reshapes and a Bloom filter object (`m, k, seed, bits`) it has no logic for at all. Compared full JSON output after 1 vs. 2 migrations.
- Got right: The version gate (`s.version < 2`) is exactly what makes this safe — once the first migration sets `version = 2`, the second call's gate condition is false, so the reshape body never re-executes, and the object spread (`{...s, ki: ...}`) that runs during a REAL reshape simply never touches unrelated fields it doesn't name, so they survive by construction, not by any special-casing.
- Where/why it failed: It didn't — this is a confirmatory result, filed because it answers a real, previously-untested question (does an idempotent migrator's safety guarantee extend to fields it has no knowledge of, under repeated/retried application) rather than assuming a general "idempotent for named fields" property automatically covers unrelated payload data.
- Fix: N/A — no bug found, no code change.
- Why this fix: N/A (no fix), but the reason this holds is structural and worth stating: an idempotent reshape gated on an explicit version check, implemented via non-destructive object spread rather than in-place field-by-field mutation, is safe for ANY unrelated field riding in the same payload — the gate prevents re-execution entirely, and the spread pattern never risks touching fields it doesn't name even if the gate were somehow bypassed. This is a stronger, more portable property than "this specific migrator is idempotent for the fields it reshapes."
- Rule of thumb: When verifying a migrator's idempotency (savemigrate#E2's own discipline), also test it against a save payload containing fields from a COMPLETELY UNRELATED system — a version-gated migrator using non-destructive spread should pass this for free, but confirm it rather than assume it, especially before combining that migrator with a new system whose persisted fields it was never written with in mind.
- Provenance (verified/assumed): VERIFIED first-hand — ran `migrate()` once and twice on an identical save payload containing both a version-1 field to reshape and unrelated Bloom-filter fields, confirming byte-identical output and untouched bloom-filter fields after both 1 and 2 applications.

## E5 — genesis fm audiorealtime feedback averaging also sticks
- Date: 2026-07-13
- Project: local/sandbox-combined-bloom-audio
- Tags: [audio][dsp][determinism]
- What: Closes the last untouched sandbox in the audio environment (`sandbox-genesis-fm`, never composed before). `combined-audio-realtime#E2` already proved a simple `y *= 0.9` decay gets permanently stuck at a nonzero subnormal (`0.9 * Number.MIN_VALUE === Number.MIN_VALUE` exactly) unless every sample is flushed to zero. genesis-fm#E1's own feedback mechanism is a DIFFERENT recurrence shape — averaging the last TWO operator outputs, then decaying (`fb = 0.9 * (prev1+prev2)/2`), not a single-pole multiply. Composed directly: without flush-to-zero, the feedback signal never reached exact `0` even after 30,000 samples, settling at a subnormal fixed point (`2.5e-323`, one of the smallest representable float64 values). With an explicit flush-to-zero guard, it correctly reached exact `0` at sample 9857 and stayed there.
- Why built: audio-realtime#E2's finding was demonstrated on the simplest possible decay shape; this checks whether the identical stuck-subnormal failure generalizes to genesis-fm's own, more complex two-term averaging feedback recurrence, or whether the averaging (which mixes in a still-larger prior term each step) might incidentally avoid the fixed point a pure single-pole decay hits.
- Design: `fb_n = 0.9 * (prev1 + prev2) / 2`, with `prev2, prev1` updated to the trailing two feedback values each step — reproducing genesis-fm#E1's own described feedback-averaging mechanism during a note-release decay, starting from `prev1=0.1, prev2=0.08`. Ran to 30,000 samples with and without a `Math.abs(fb) < 1e-300 -> fb = 0` flush-to-zero guard. (An earlier attempt at this same composition, in a prior session round, used only 5000 samples and incorrectly reported no distinguishable result — the two-term averaging converges noticeably slower per-sample than a simple `*0.9` multiply, needing roughly 9800+ samples to approach float64's subnormal range at all; this run uses a large enough sample budget to actually reach the regime audio-realtime#E2 is about.)
- Got right: The feedback-averaging recurrence itself converges correctly and monotonically toward zero in exact arithmetic — there is no oscillation or divergence, just the same IEEE-754 rounding fixed point audio-realtime#E2 already characterized, now confirmed to also trap a two-term-averaged decay, not only a single-pole one.
- Where/why it failed: The averaging step doesn't change WHERE the float64 rounding fixed point sits (a subnormal near `Number.MIN_VALUE` where further multiplication by 0.9 rounds back to the same bit pattern) — it only changes how many samples it takes to arrive there. Any recurrence whose steady-state behavior is "multiply something small by a sub-1 factor, repeatedly" converges to the identical stuck point regardless of the specific linear-combination shape feeding into that multiply, so a genesis-fm-style operator would carry a permanently nonzero (if inaudibly tiny) feedback signal through an arbitrarily long sustained silence unless explicitly flushed.
- Fix: Apply the same flush-to-zero guard audio-realtime#E2 already established (`if (Math.abs(fb) < threshold) fb = 0`), placed at the feedback-averaging step. Re-ran to 30,000 samples: reaches and stays at exact `0` starting at sample 9857.
- Why this fix: This is exactly audio-realtime#E2's own fix, unmodified, applied at a new recurrence shape — the fix targets the FLOATING-POINT REPRESENTATION problem (a small nonzero value that arithmetic can no longer reduce further), which is independent of which specific formula produces the shrinking value, so no genesis-fm-specific logic is needed beyond placing the existing guard at the feedback output.
- Rule of thumb: A stuck-nonzero-subnormal fixed point (audio-realtime#E2) is a property of FLOATING-POINT decay in general, not of any one specific decay formula — before assuming a DIFFERENT-shaped decay/feedback recurrence in the same project is safe from it, verify with a sample budget actually large enough to approach float64's subnormal range (tens of thousands of samples for a ~0.9-per-step-equivalent decay, not a few thousand) — an insufficient sample budget produces a false "no problem here" result that looks like evidence but is actually just an incomplete run, exactly what happened on the first attempt at this composition.
- Provenance (verified/assumed): VERIFIED first-hand — ran the feedback-averaging recurrence to 30,000 samples both with and without flush-to-zero, confirming the unflushed variant never reaches exact 0 (final value `2.5e-323` after 30,000 samples) while the flushed variant reaches exact 0 at sample 9857 and holds there through the remaining ~20,000 samples tested.
- Composed: sandbox-genesis-fm/E1, sandbox-combined-audio-realtime/E2

## E3 — genesis psg lfsr register must persist not reseed
- Date: 2026-07-13
- Project: local/sandbox-combined-bloom-audio
- Tags: [audio][state][determinism]
- What: Generalizes loop 1's pattern (persist a generator's full internal state, not just its output) to a new domain: psg#E1's noise LFSR, if a save/load (pause/resume) boundary re-initializes the register from its DEFAULT seed instead of persisting the actual current register value, produces an audible discontinuity — 7/20 mismatched samples immediately after resume versus the sequence that would have played uninterrupted. Persisting the actual register value at save time: 0/20 mismatches.
- Why built: Loop 1 found the identical shape of bug (persist derived output, omit the generator's live internal state) in a Bloom filter's seed. This checks whether the same class of mistake recurs in a completely different generator (an LFSR) with a completely different "hidden state" (a 16-bit register mid-sequence, not a construction-time seed) — confirming this is a recognizable PATTERN across generator types in this project, not a one-off Bloom-filter-specific issue.
- Design: psg#E1's own described LFSR (`reg = (reg>>1) | (parity(reg & tap)<<15)`) run 1000 steps from the default seed (`0x8000`), then continued 20 more steps either from that SAME default seed (naive reload) or from the actual register value after 1000 steps (fixed reload), compared against an uninterrupted 1020-step ground truth.
- Got right: The LFSR stepping logic itself is correct and reproduces psg#E1's own described mechanism exactly; the bug is entirely about what gets captured at the save boundary.
- Where/why it failed: A "seed" naturally reads as save-worthy configuration; a mid-sequence REGISTER VALUE reads as transient runtime state that's easy to assume "will just pick back up" — but for a stateful generator, the current register IS the only thing that determines correct continuation, exactly as the seed was for the Bloom filter.
- Fix: Persist the LFSR's current register value at save time, restore into the register (not the default seed) at load time. Verified: 0/20 mismatches.
- Why this fix: The LFSR's entire future sequence is a deterministic function of its CURRENT register value alone (not of how it got there) — restoring that exact value is both necessary and sufficient for exact continuation, with no need to also replay the 1000 steps that produced it. This mirrors loop 1's fix exactly: persist the minimal piece of live state a deterministic function actually depends on, not a derived summary of it.
- Rule of thumb: For ANY stateful sequence generator (LFSR, PRNG, Bloom filter, any iterator with internal state beyond its emitted output), a save/pause boundary must persist the generator's CURRENT internal state, not its original construction parameters — re-seeding from the default/construction-time value produces a discontinuity indistinguishable, at the save boundary, from simply forgetting to save at all.
- Provenance (verified/assumed): VERIFIED first-hand — 1000-sample pre-save run, compared 20-sample post-resume continuation against an uninterrupted 1020-sample ground-truth sequence: 7/20 mismatched with default-reseed, 0/20 with persisted-register reload.

## E2 — genesis psg fft noise period triggers silent garbage
- Date: 2026-07-13
- Project: local/sandbox-combined-bloom-audio
- Tags: [audio][dsp][testing]
- What: New audio-domain seam (psg, mix never composed before). psg#E1: the noise LFSR's measured period is 57337 — not a power of 2. mix#E1: a naive radix-2 FFT silently returns garbage (truncated output, no error) on non-power-of-2 input. Composed directly with psg#E1's own measured, non-synthetic period as the input length: feeding a 57337-sample PSG noise buffer through a naive-truncating radix-2 FFT silently discarded 24569 samples (43% of the buffer) with zero error raised.
- Why built: mix#E1's finding was demonstrated with a synthetic non-pow2 test case; this checks whether a REAL, already-measured data source in the same project (psg#E1's actual LFSR period) naturally triggers the identical failure — confirming the bug isn't a contrived edge case but a realistic one this project's own audio pipeline would hit.
- Design: A radix-2 FFT that, on non-power-of-2 input, truncates to the previous power of 2 (mix#E1's own described naive behavior) versus one that zero-pads to the next power of 2 or throws explicitly. Input: a full psg#E1-mechanism LFSR noise buffer of exactly 57337 samples (the measured period).
- Got right: The FFT's core radix-2 recursion is correct for power-of-2 inputs; the bug is entirely in how it handles the non-power-of-2 case (silent truncation) not in the transform math itself.
- Where/why it failed: Truncating to the previous power of 2 discards the tail of the buffer with no signal that anything was lost — exactly mix#E1's own finding, now shown to be triggered by an actual measured value (psg#E1's period) rather than an arbitrary test size.
- Fix: Zero-pad to the NEXT power of 2 (preserves all input data, 0 discarded) or throw explicitly if exact-length semantics are required. Verified: 0 discarded samples with padding; correct throw with explicit-mode.
- Why this fix: Padding preserves every input sample (the transform's frequency resolution changes slightly, but no data vanishes) while requiring zero change to the core radix-2 recursion; throwing is the right choice instead whenever the caller's contract requires an exact, non-padded length. Either is strictly better than the current default (truncate silently), which is the only one of the three options that loses data with no signal to the caller.
- Rule of thumb: When a project has an EXISTING, already-measured "irregular" value (a non-round period, an odd-sized buffer) from one sandbox, explicitly test it against every OTHER sandbox in the project with a size/shape assumption (power-of-2, fixed-length) — a real number from elsewhere in the project is a much sharper test than an arbitrary synthetic edge case.
- Provenance (verified/assumed): VERIFIED first-hand — fed psg#E1's actual measured period (57337) through a naive radix-2 FFT, confirmed 24569/57337 samples silently discarded; re-verified 0 discarded with zero-padding and correct throw with explicit-error mode.

## E1 — bloom savemigrate seed must persist not just bits
- Date: 2026-07-13
- Project: local/sandbox-combined-bloom-audio
- Tags: [algo][state][determinism]
- What: New environment (bloom, never in the graph before). bloom#E2: a Bloom filter's hash must be fixed, not process-randomized, or persisting the bit array across a process boundary causes silent false negatives. Composed with a JS save/load round trip: a filter seeded at construction from `Date.now()` (a realistic mistake, not Python's specific hash-randomization but the same class of bug) and persisted with only `{m, k, bits}` — omitting `seed` — produced 1000/1000 false negatives across 200 reload trials when reloaded with a different ambient seed. Persisting `seed` alongside `bits`: 0/1000.
- Why built: To check whether bloom#E2's rule ("fix the hash, don't rely on ambient randomness") holds when the SPECIFIC root cause differs (JS has no per-process hash randomization like CPython) but the general shape (a filter's correctness silently depends on state that isn't part of its persisted representation) recurs via a different, equally realistic mistake.
- Design: A JS Bloom filter (`m=1000` bits, `k=4` hashes, salted `stringHash`) seeded at construction from `Date.now()`. Save serializes `{m,k,bits}` (naive) or `{m,k,seed,bits}` (fixed); load reconstructs a fresh filter from the saved fields, using a NEW ambient seed for the naive path (simulating a process restart) and the persisted seed for the fixed path.
- Got right: The bit array itself round-trips correctly via JSON; the bug is entirely about which fields get included in the save payload, not about JSON serialization fidelity.
- Where/why it failed: The seed is load-bearing for every subsequent hash computation but isn't visually part of "the filter's data" the way `bits` obviously is — an implementer persisting "the important stuff" naturally reaches for the bit array and easily omits a construction-time parameter that looks like configuration, not data.
- Fix: Persist `seed` as part of the filter's saved state, load-time reconstruct with the SAME seed. Verified: 0/1000 false negatives.
- Why this fix: The hash outputs (and therefore every bit position ever set or queried) are a pure function of `(item, seed)` — omitting `seed` from the save payload means the load path can reconstruct a filter whose `add()`-time and `has()`-time hash functions disagree, which is indistinguishable from data corruption even though every individual byte round-tripped correctly. Including `seed` closes that gap with no other change.
- Rule of thumb: Any probabilistic/hash-derived structure (Bloom filter, consistent-hash ring, any structure whose correctness depends on a hash function's specific behavior) must persist EVERY parameter that determines its hash outputs, not just its resulting data — audit "what does `has()`/`add()` actually read" for hidden inputs before deciding what belongs in a save payload.
- Provenance (verified/assumed): VERIFIED first-hand — 200-trial reload sweep, 1000/1000 false negatives without persisted seed, 0/1000 with.
