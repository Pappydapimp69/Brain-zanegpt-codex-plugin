## E1 — derive label map instead of hand synced sidecar
- Date: 2026-07-09
- Project: local/collective-reference
- Tags: [tooling][process][testing]
- What: A GitHub Issue Form's field labels were mapped to internal field IDs via a hand-written sidecar JSON kept "in sync" with the `.yml` form by hand; an end-to-end test run caught that the two had already drifted, silently dropping a field.
- Why built: The intake pipeline parses a rendered Issue Form body (which uses the form's exact label text as section headers) into named fields. Something has to map "Tags (bracketed, lowercase, e.g. [browser][events])" (the label) back to `tags` (the internal id) to do that.
- Design: Originally a separate `labels.json` file listing every {label: id} pair, maintained by hand alongside the `.yml` form, and passed to the parser as a lookup table.
- Got right: The parser itself (label→value extraction, given a correct map) was solid and well-tested in isolation.
- Where/why it failed: Running the full pipeline end-to-end against a realistic rendered body (built from the real form's own labels) surfaced that the hand-written sidecar's label text no longer matched the form's actual label — the `tags` field silently vanished from the parsed output with no error, because a missing map entry just means that field never gets populated, not a crash. This is exactly the failure mode a from-first-principles code review wouldn't have caught, since the sidecar file *looked* internally consistent — it just no longer matched the object it was describing.
- Fix: Deleted the sidecar. Added `derive_label_map()`, which extracts the {label: id} map directly from the form `.yml`'s own text (a small tolerant scanner over its `id:`/`label:` lines, no YAML dependency needed for this narrow shape). The map is now always generated from the one file that actually defines the labels, so there is nothing to keep in sync.
- Why this fix: A hand-maintained duplicate of information that already exists in another file will drift eventually — not a maybe, a when. The only fix that actually closes the gap is removing the second copy, not writing a process to keep the two in sync more carefully.
- Rule of thumb: If two files must always agree (a form and its own field map, a schema and its own docs, a constant defined twice), don't maintain both by hand and hope — derive one from the other, or generate both from a single source. Catch this class of bug specifically with an end-to-end test built from the *real* upstream artifact (the actual form's real label text), not a hand-typed stand-in that can't reveal the drift it's supposed to catch.
- Provenance (verified/assumed): Verified first-hand — reproduced the silent field-drop with a synthetic sidecar, fixed it, then re-verified end-to-end with the real `.yml` form and a realistically-rendered body; full test suite (91 tests) green after the fix.
- Link: this session, `collective` reference-implementation scratchpad (`intake_steward.py::derive_label_map`, `test_intake_steward.py::TestLabelMapDerivation`)
