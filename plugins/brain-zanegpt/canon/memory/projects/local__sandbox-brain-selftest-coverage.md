## E1 — test coverage recency vs importance brain selftest
- Date: 2026-10-10
- Project: local/sandbox-brain-selftest-coverage
- Tags: [testing][process][tooling]
- What: A reproducible test of tension "test coverage tracks recency, not importance" on real data other than the game it was logged from. Unit = each of the 232 top-level functions of the Brain CLI at one pinned commit. Coverage = fraction of the function's statements executed when the repo's own selftest runs under a line tracer. Recency = median git-blame line date of the function. Importance = blast radius, the number of the 30 CLI commands whose static reference graph reaches the function (no git data used), with fan-in and a writes-or-deletes flag as alternates.
- Why built: The tension rests on one two-round mutation audit of one game. Supports pole A of tension 'test coverage tracks recency, not importance' (audit weighted toward the oldest code): on a second, unrelated codebase deliberate coverage follows age of code strongly, while importance explains much less. Built to check whether the effect is a one-repo accident and to split how much of it is a targeting choice.
- Design: Pin the commit, extract it into a temp dir, parse with ast, run the selftest in-process under sys.settrace, blame every line, build a reference graph from the command table. Report Spearman rank correlations, partial correlations, a seeded permutation null (2000 shuffles), thirds by age and by importance, and an old-and-important cell built to break the claim. Planted-truth controls (coverage generated from recency only, then from importance only, over the real features) check the statistic can tell the two apart. A post-hoc split (added after seeing the first results, flagged as such, not part of the verdict) separates functions the selftest names directly from functions that merely ran as callees.
- Got right: The measures were fixed in the sandbox header before the first run, and importance never touches git history while recency never touches the call graph, so the two cannot leak into each other (they correlate -0.07). The planted controls recover the right driver (partial 0.88 vs 0.08, and 0.75 vs 0.10) and the permutation null is centred on zero (sd 0.065), so the observed +0.43 is not a pipeline artefact. The run is deterministic: three runs gave identical output.
- Where/why it failed: Two of my four pre-registered predictions came out wrong, so the sandbox verdict is FAIL. I predicted importance would be near-uncorrelated with coverage (under 0.15) and that the old-and-important cell would be at most 20% covered. Observed: rho(coverage, blast radius) = +0.274 and the old-and-important cell is 37% covered (n=27). Importance is not ignored. Recency still dominates (+0.433 vs +0.274; partial +0.47 vs +0.34), and the oldest third of functions is 18% covered against 56% for the newest third (ratio 3.1).
- Fix: Do not state the tension as recency versus importance as if importance got nothing. The post-hoc split shows the mechanism: functions the selftest names on purpose track recency (rho +0.437) and not importance (+0.093; directly tested functions average a blast radius of 3.1 against 3.5 for all), while the 29 functions that were covered without ever being named average a blast radius of 7.8, so important helpers get covered only as callees of tested new code. Old functions that write or delete files, the selftest's own stated concern, are covered 6% (1 of 17) in the oldest third against 60% (3 of 5) in the newest third. Aim the audit at old, high-reach, unnamed functions, not simply at old ones.
- Why this fix: It is what the numbers separate. Targeted tests (named in the test file) follow recency and carry no importance signal; the importance signal that exists is incidental and therefore fragile, since it disappears when the caller's test changes. An audit list built as old AND high blast radius AND never named by a test is smaller and better aimed than old alone.
- Rule of thumb: Supports pole A of tension 'test coverage tracks recency, not importance', with a correction: what follows recency is DELIBERATE coverage, and importance reaches coverage only incidentally as callee reach. When a green suite looks reassuring, list functions that are old, reached by many entry points, and never named by any test, and audit those first. Measured on one Python CLI of 232 functions and 88 days of history; the age effect and the incidental-importance split are single-repo results, not a law.
- Provenance (verified/assumed): Verified first-hand by running the sandbox against the pinned Brain commit: every correlation, cell rate and count above is copied from its output. The T30 game audit numbers (1/12 vs 5/16) are taken from the tension text and were not re-run here. That the mechanism generalises beyond this repo, and that fan-in or reach is the right importance proxy, is assumed, not tested; the static reference graph over-approximates reach.
