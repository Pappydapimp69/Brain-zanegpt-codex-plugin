## E2 — movement stack occupancy set vanishes on json serialize
- Date: 2026-07-13
- Project: local/sandbox-combined-movement-stack
- Tags: [state][testing][architecture]
- What: Per `brain analyze seams`, composed astar-replan's occupancy grid (naturally modeled as a `Set` of blocked-cell keys for O(1) lookup) with `savemigrate#E3` (JSON round-trips silently drop `undefined` fields). Tested directly: `JSON.stringify({...state, occupied: new Set(["3,4","5,5","6,6"])})` produces `{"pos":...,"path":...}` — the entire `occupied` Set serializes to `{}` and is gone, not just one field. Post-reload, every previously-blocked cell reads as open with zero error or signal.
- Why built: savemigrate#E3 proved `undefined` vanishes silently on serialize; this checks whether a whole non-JSON-native collection type (Set/Map) suffers the same class of silent loss, which is worse in degree (total, not per-field) but identical in kind (invisible to any in-memory check, only visible in the persisted bytes).
- Design: Constructed a state object holding `occupied` as a `Set`, round-tripped it through `JSON.parse(JSON.stringify(...))`, and directly checked both the resulting shape and whether a replanner querying it post-reload would still treat previously-blocked cells as blocked.
- Got right: `pos` and `path` (plain array/object fields) survived the round-trip correctly — the loss is specific to non-JSON-native container types (Set, and by the same mechanism, Map), not a general serialization failure.
- Where/why it failed: `JSON.stringify` has no special handling for `Set`/`Map` — they serialize as their own enumerable-own-properties view, which for a Set is empty (`{}`), since Set's actual contents live outside the properties JSON.stringify walks. Every in-memory check (`occupied.has(x)`, `occupied.size`) works fine right up until the moment the state is actually persisted and reloaded, at which point the agent silently gains the ability to path through every cell that was blocked before the save — a correctness bug indistinguishable from "the map got easier," not an error.
- Fix: Serialize `occupied` explicitly as `[...occupied]` (an array of its entries) and reconstruct with `new Set(array)` on load, rather than relying on JSON's default object walk. Re-ran the round-trip: all 3 blocked cells survive and are correctly recognized as blocked post-reload.
- Why this fix: The loss isn't a savemigrate bug or an astar-replan bug — it's a composition gap where a system built to be JSON-serialized (savemigrate) was combined with a system that chose an in-memory representation (Set) for a completely valid, unrelated reason (fast lookup) with no idea it would ever be serialized. An explicit array<->Set conversion at the save/load boundary is the same "convert only at the boundary" pattern as `sandbox-combined-loop-combat#E1`'s integer-quantization fix — keep the efficient in-memory type everywhere else, convert only where it crosses the serialization boundary.
- Rule of thumb: Before composing ANY system that persists state via JSON with a system that uses `Set`/`Map`/`WeakSet`/`WeakMap`/`Date`/custom-class instances for its in-memory representation, check every such field explicitly — `JSON.stringify` silently produces `{}`/`{}`/wrong output for each of these with no warning, exactly like the `undefined`-drop savemigrate#E3 already found, but total rather than partial. "It looks right in memory" is never sufficient evidence a save/load round-trip is safe; always round-trip and re-check post-reload behavior, not just post-reload shape.
- Provenance (verified/assumed): VERIFIED first-hand — directly round-tripped a Set-holding state object through JSON.parse(JSON.stringify(...)), confirmed the Set became `{}` and a post-reload occupancy check silently returned "not blocked" for every previously-blocked cell, then confirmed the explicit array-conversion fix preserves all entries and correct post-reload blocking.
- Composed: sandbox-astar-replan/E2, sandbox-savemigrate/E3
- Link: session (query brain for "brain analyze groups and train on edges"), sandbox script sweep.mjs/sweep_fixed.mjs, no code change to a shipping project

## E1 — sandbox combined movement stack occupancy vs physical extent
- Date: 2026-07-12
- Project: local/sandbox-combined-movement-stack
- Tags: [algorithm][physics][gamedev]
- What: A new combined sandbox composed three already-proven-correct single-system lessons that a real game NPC needs together and that had never been tested in combination: an A*-replanner that never rejects the agent's own current cell as a valid start (astar-replan/E2), a swept-segment collision check built to catch fast-mover tunneling (collision/E1), and a dt-accumulator-driven animation FSM (anim/E2, E4). Ground-truth continuous-position sampling (64 substeps/tick) against each dynamic obstacle's actual sweep found real physical overlaps the grid-based pathfinder's occupancy view never flagged: 10 events across 3/20 seeds even at slow, sub-1-cell/tick speeds for both agent and obstacles, and 65 events across 20 seeds at NEAR-STATIC speed (0.05 cell/tick) — ruling out frame-skipping/tunneling-at-speed (the mechanism collision/E1 already covers) as the cause, since these overlaps happen even when nothing is moving fast enough to skip a frame.
- Why built: To check whether pathfinding-driven dynamic-obstacle avoidance (mark a cell "occupied" per tick, replan around it) is itself just a discrete per-tick collision check — and inherits collision/E1's known discrete-check failure mode — or whether composing it with a real swept-collision system surfaces a *different* interaction-seam bug that neither single system's own tests could see.
- Design: 24x24 grid, agent replans via A* to a fixed goal whenever its next waypoint cell is flagged occupied; occupancy is a per-tick snapshot of each dynamic obstacle's rounded grid cell. Agent and obstacles both have a small physical half-extent (0.4 cells) for the collision check. Every tick, both agent and obstacle segments (old position -> new position) are sampled at 64 substeps and checked for AABB overlap — this is the ground truth, independent of what the grid occupancy model believes.
- Got right: The anim-FSM composed cleanly — 0 leak events across every configuration tested (state transitions correctly reset frameIndex/clipAcc even under replan-driven, high-frequency direction churn), and the astar-replan E2 fix itself never caused a stuck/frozen agent (0 stuck ticks, 100% goal-reached across every seed and speed tested) — both prior fixes hold exactly as designed in isolation.
- Where/why it failed: Two distinct, separable mechanisms, isolated by directly instrumenting which grid cell the colliding obstacle occupied relative to the agent's current/target waypoint cell: (1) MAJORITY (7/10 traced events): A* over a 4-connected grid only forbids *entering* a flagged-occupied cell — it has no concept of clearance from a cell merely *adjacent* (orthogonal or diagonal) to the path. Once agent/obstacle physical half-extents approach half the grid spacing, an obstacle sitting in a neighboring, never-flagged cell can physically overlap the agent while it stands at or transits through its own waypoint — invisible to the pathfinder because "adjacent" and "occupied" are different predicates the grid never conflates, but "adjacent" and "physically touching" are the same predicate the collision system can't ignore. Confirmed by scaling the physical half-extent down: at half-extent 0.1 (combined touch distance 0.2, one-fifth of cell spacing) events dropped to a floor of 4; from half-extent 0.3 upward (combined touch distance approaching cell spacing) the adjacency-driven tail grows on top of that floor (10 events at 0.4, 12 at 0.45). (2) FLOOR (the remaining ~3-4 events, footprint-independent, present even at half-extent 0.1): astar-replan/E2's own fix — "never reject the agent's current cell as blocked, treat it as unconditional ground truth" — is exactly correct for its original purpose (don't freeze because of a stale occupancy flag) but composed with a *moving physical* obstacle it has no way to distinguish "my occupancy flag here is stale/irrelevant" from "a body has just physically moved onto the cell I'm standing in": both look identical (agent's own cell, occupied=true) to the grid, and the fix's job is specifically to keep planning through that regardless. The result is the replanner will happily keep validating a plan rooted at a cell a dynamic obstacle now shares, because occupancy-for-planning and overlap-for-physics were silently collapsed onto the same grid representation.
- Fix: Not implemented in this sandbox (decision/representation-layer investigation, matching the scope boundary set by sandbox-combined-integration/E3 and E4). The portable diagnosis: a discrete occupancy grid answers "where can a plan route through," a continuous collision system answers "am I touching something" — collapsing both onto the same per-cell flag loses the information the collision system needs (adjacency and exact-same-cell are not the same as physical overlap, and physical overlap is not confined to the agent's occupied *destination* cell). Either (a) keep the collision system authoritative and run it every tick regardless of what the pathfinder decided (never assume "the plan avoided occupied cells" implies "no physical contact will occur"), or (b) inflate the occupancy footprint used for planning by the agent+obstacle's combined physical half-extent (so grid-adjacency itself becomes the safety margin), and separately, don't let a "never reject my own start cell" planning fix silently stand in for "no collision system needs to run here" — the two checks answer different questions and neither should be inferred from the other passing.
- Why this fix: This is the same "boundaries are the recurring seam" pattern sandbox-combined-graph-editor/E2 already generalized (scope-growth, single-source-of-identity) applied to a new domain pair (pathfinding x physics): each system's own test suite fixed away the scope the other system imposes — astar-replan's tests used slow, schedule-driven occupancy toggles with no physical-extent concept at all; collision's tests used continuous physics with no discrete-planning concept at all. Neither could have found this bug alone, and unit-testing each in isolation (even exhaustively) structurally cannot, because "does my own occupancy-adjacent cell physically overlap me" and "did my own start-cell exception let me co-locate with a moving body" are questions that only exist once both systems share a grid.
- Rule of thumb: When a pathfinder's per-cell occupancy flag and a physics/collision system's per-tick overlap check are composed over the SAME grid, check both of these explicitly before trusting "the plan avoided occupied cells" as a collision guarantee: (1) does either mover's physical footprint make grid-ADJACENCY (not just same-cell) a collision risk — if so, inflate the planning footprint or don't rely on cell-occupancy for clearance; (2) does any planner-side "trust my own current position unconditionally" exception (a legitimate, previously-verified fix in its own right) now also mean "skip the collision check for my own cell" by implication — it shouldn't, and the two need to be verified as separately true, not assumed to compose.
- Provenance (verified/assumed): VERIFIED first-hand — ran the combined Node.js sandbox across 20 seeds x 200 ticks at four speed configurations (baseline/slow, two stress configs, near-static), ground-truth-sampled every tick's actual continuous overlap at 64 substeps independent of the grid model, traced which specific grid cell (relative to the agent's current/target waypoint, via Chebyshev distance) each of the first 10 real overlap events involved, and separately swept the physical half-extent from 0.1 to 0.45 to confirm the footprint-independent floor (~4 events, mechanism 2) versus the footprint-dependent tail (mechanism 1) as two distinct, separable causes rather than one.
