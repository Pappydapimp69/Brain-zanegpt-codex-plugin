## E1 — sandbox seam replan save silent corruption
- Date: 2026-07-13
- Project: local/sandbox-seam-replan-save
- Tags: [state][testing][gamedev]
- What: Combining two independently-verified fixes — `sandbox-astar-replan#E2` (a live replanner must never reject the agent's own current cell, treat it as unconditional ground truth) and `sandbox-savemigrate#E3` (JSON round-trips can silently corrupt state in ways invisible to in-memory checks) — surfaced a real blind spot: if agent position and the obstacle/occupancy grid are saved via two separate, non-atomic steps (a realistic pattern: two subsystems each with their own save()), realistic untargeted obstacle churn between the two saves put the agent's saved position inside a now-blocked cell in 29/5000 (0.58%) randomized trials. In every one of those 29 cases, the E2-fixed replanner ran normally with zero error or signal — by design, since E2's fix specifically removed the check that would have caught it.
- Why built: `brain analyze seams` ranked `sandbox-astar-replan` + `sandbox-savemigrate` as an untested pair sharing algorithm/state/testing tags, both already in the proven sandbox cluster.
- Design: Randomized grid + agent position, saved position via one snapshot, then ran 1-3 ticks of realistic UNTARGETED obstacle churn (one random cell toggles per tick, never specifically the agent's cell) before snapshotting the grid — modeling the real time gap between two independent subsystem saves, not a forced/contrived collision.
- Got right: An earlier version of this test forced the obstacle onto the agent's cell every single trial (100% hit rate) — recognized as too contrived to be a real finding and discarded before filing; the realistic untargeted-churn version, with a genuinely low and honest hit rate, is what makes this a real result rather than a tautology.
- Where/why it failed: E2's fix is correct for what it targets (a live-tick race where the agent's real-time position is the ground truth, never a rejectable hypothesis) — but it also means the replanner has NO remaining check that could notice "the world I just loaded is internally inconsistent." A non-atomic save that lets the position and grid drift out of sync (E3's territory: two related pieces of state saved separately) produces exactly the state E2 stopped checking for, and the combination means this class of corruption is undetectable by the replanner itself, at any rate, forever — not just rare, but structurally silent by construction.
- Fix: Not implemented — flagged as the finding. Two candidate directions, untested here: (a) make position+grid one atomic save unit rather than two independent subsystem saves, closing the gap E3-style corruption needs; or (b) add a ONE-TIME consistency check specifically at load time (not on every replan tick, to avoid reintroducing E2's live-tick bug) that flags — but does not reject — an agent whose loaded position reads as blocked in the loaded grid.
- Why this fix: N/A — diagnostic finding, no fix verified in this sandbox.
- Rule of thumb: When a fix removes a validity check because the check was WRONG for its actual use case (E2: don't treat live position as untrusted), audit whether that check was also silently serving as the only detector for a DIFFERENT problem (E3-style save/load corruption) — removing a check for the right reason can still delete your only signal for an unrelated failure mode, and the result is a bug that occurs at a low, honest, non-contrived rate and is then undetectable by construction, not just hard to catch.
- Provenance (verified/assumed): VERIFIED first-hand — ran the realistic (untargeted-churn) Node.js sandbox across 5000 seeded trials, directly counting inconsistent-after-load cases (29) and confirming all 29 ran through `replan()` with no error signal; a discarded prior version that forced the collision (100% rate) was explicitly not used as the basis for this finding.
