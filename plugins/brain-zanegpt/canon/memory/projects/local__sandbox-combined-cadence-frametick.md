## E2 — cadence gameloop endstate comparison hides real midrun desync
- Date: 2026-07-13
- Project: local/sandbox-combined-cadence-frametick
- Tags: [determinism][gamedev][testing]
- What: Re-verifies cadence-frametick + game-loop from a new angle. game-loop#E2's own stated methodology principle — "fingerprint PER TICK; end-state agreement hides a mid-run desync" — tested directly against cadence-frametick#E1's own specific bug (a float `cooldownMs -= dt` cooldown fires at different real-times under different frame schedules). Ran the float-cooldown cadence under two frame schedules (16ms and 20ms steps) over an identical 400ms total duration: END-STATE comparison (final fire count) reported "equal" (20 fires each, a false "looks fine" verdict) — but PER-TICK comparison (resampling both schedules onto a shared time grid and comparing running fire-count at each sampled instant) found real divergence at 4/24 sampled instants, meaning the two schedules genuinely fired the cadence event at different real times mid-run even though they happened to arrive at the same total count by the end.
- Why built: game-loop#E2's methodology point was stated as a general principle in its own entry; this checks whether it's concretely necessary for cadence-frametick#E1's specific bug, or whether that bug happens to always show up in the end-state total too (which would make per-tick fingerprinting a nice-to-have rather than load-bearing for this particular composition).
- Design: A float-driven cadence (`cooldownFloat -= dtMs`, firing and resetting to 20 when `<= 0`) run under two different fixed dt values (16ms, 20ms) for the same 400ms total. Fire count recorded cumulatively at every internal step, then resampled onto a shared coarser time grid (every 16ms) for a fair cross-schedule per-tick comparison, since the two schedules take a different number of native steps over the same duration.
- Got right: The end-state totals matching (20 and 20) is itself a real, reproducible artifact of this specific total-duration/cooldown-period combination — it is not a fluke of the test, which is exactly what makes it dangerous: a developer running only an end-of-run smoke test on this exact scenario would see a passing result and reasonably conclude the two frame schedules are equivalent.
- Where/why it failed: A float cooldown's firing TIME depends on the exact sequence of `dt` subtractions, which differs between a 16ms-step and 20ms-step schedule even over an identical total duration — the two schedules' cadence events land at different real times, but because both schedules process enough total time to complete the same INTEGER number of full cooldown cycles by 400ms, the final tallies coincide by arithmetic coincidence (400ms happens to be a common multiple-friendly duration relative to both step sizes and the 20ms cooldown period) while the actual moment-to-moment behavior genuinely diverges. A shorter or differently-timed test run, or one that only checks the end state, would report success on a live, reproducible desync.
- Fix: Compare per-tick (or per-sampled-instant) fingerprints across frame schedules, not only the run's final state — exactly game-loop#E2's own prescription, now demonstrated as load-bearing (not just a nice-to-have) for this specific class of frame-rate-dependent cadence bug, since the end-state check can and does produce a false pass on a real instance of it.
- Why this fix: An end-state-only check answers "did the two runs end up in the same place," which is neither necessary nor sufficient for "did the two runs behave identically" — for any bug whose symptom is TIMING (an event happening earlier or later, not a different final count), only comparing state at multiple points along the timeline can distinguish "genuinely identical behavior" from "coincidentally identical endpoint after different paths."
- Rule of thumb: When verifying frame-rate/schedule independence for any discrete, periodically-firing mechanism (cooldowns, cadence gates, periodic spawns), never trust an end-state-only comparison even when it passes — construct the comparison to sample intermediate states (per-tick, or at several representative instants across the run) specifically because a timing bug can produce a coincidentally-matching endpoint while genuinely diverging throughout the run, and a single passing smoke test at one specific duration proves nothing about other durations or ongoing gameplay.
- Provenance (verified/assumed): VERIFIED first-hand — ran a float-cooldown cadence under 16ms and 20ms fixed steps over an identical 400ms total, confirming end-state fire counts match exactly (20 vs 20) while per-tick resampled comparison at 16ms intervals found divergence at 4 of 24 sampled instants.

## E1 — compose input cadence with fixed timestep
- Date: 2026-07-13
- Project: local/sandbox-combined-cadence-frametick
- Tags: [determinism][gamedev][state]
- What: Composing an input-gated cadence (the-game-the-recursion/E16: a `cooldownMs -= dt` timer gating discrete steps) with a deterministic fixed-timestep loop (combined-game-loop/E2: same tick COUNT everywhere) shows the two are the fix for each other: the raw-float-dt cadence fires a frame-rate-DEPENDENT number of discrete steps for the same held duration, and moving the cadence onto the loop's integer tick lattice removes the dependence entirely.
- Why built: To close the untested recursion↔game-loop seam and confirm the composition reproduces.
- Design: Deterministic sandbox — hold an input for a fixed duration; count discrete steps under (a) `cooldown -= frame_dt`, one step/frame then reset, vs (b) a fixed 16ms tick accumulator stepping every N ticks; run each at 6ms and 33ms frame schedules.
- Got right: Reproduced. Float-dt steps: 6ms→20, 33ms→16 (frame-rate-dependent). Integer-tick steps: 6ms→19, 33ms→19 (identical). The cadence is fair/deterministic only on the tick lattice.
- Where/why it failed: The natural `cooldownMs -= dt` pattern silently makes the player's real action RATE depend on frame time (not just replay goldens) — a live fairness bug at low frame rates, invisible on the dev machine.
- Fix: Gate discrete input-driven cadences on the loop's integer tick count (game-loop/E2's integer time source), never on accumulated float dt; stress-test with multiple frame schedules over the same held duration and compare discrete-event counts.
- Why this fix: Transition rate must be a function of authoritative ticks, not wall-time-per-frame; only the integer lattice makes it frame-rate-independent.
- Rule of thumb: An input-gated cadence (movement step, attack, ability) must be driven by the loop's integer tick count, not a `cooldownMs -= dt` float — the float form makes the discrete-event RATE frame-rate-dependent (a live fairness bug, not just a replay concern); verify by counting events across multiple frame schedules for the same held duration.
- Provenance (verified/assumed): Verified first-hand — deterministic sandbox this session: float-dt 20 vs 16 steps across 6ms/33ms frames; integer-tick 19 vs 19. Built and observed.
