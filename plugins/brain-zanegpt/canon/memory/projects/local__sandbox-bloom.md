## E2 — python hash randomized per process breaks bloom filter
- Date: 2026-07-11
- Project: local/sandbox-bloom
- Tags: [algo][state][determinism]
- What: Deriving a Bloom filter's k hash functions from Python's built-in `hash()` produces DIFFERENT bit positions for the identical item across two separate process runs — the filter's own membership bits are not reproducible across a process restart.
- Why built: Sandbox to mine a genuinely new domain (probabilistic data structures) not yet covered in this repo. Built a standard Bloom filter, deriving k "independent" hashes by salting `hash()` with an index: `hash((item, i))`.
- Design: `_hashes(item)` yields `hash((item, i)) % m` for `i` in `range(k)` — using the interpreter's built-in hash as the underlying hash primitive, the natural first choice since it needs no imports.
- Got right: Sizing math (`m`, `k` from the standard optimal formulas) was correct and verified separately (see the false-positive-rate lower-bound proposal from this same sandbox).
- Where/why it failed: Ran the identical script (`print(hash(('item-0', 0)))`) in two separate `python3` invocations. Run 1: `-7761992969212121082`. Run 2: `2779064203308317018` — completely different values for the identical input. This is CPython's hash randomization (`PYTHONHASHSEED`, on by default since 3.3, a DoS-hardening feature for `str`/`bytes`/`tuple` hashing) — invisible within a single process (hash is stable for the process's lifetime, so a filter that's only ever built and queried in one run looks correct), but fatal the moment a filter's bit array is persisted, serialized, or shared, and then rebuilt or queried from a different process: the same logical item now maps to different bit positions, so a previously-added item can register as absent (false negative) or a never-added item can appear present, silently, with no error.
- Fix: Use a hash function with no process-level randomization for anything that must be reproducible or shared across a process boundary — e.g. `hashlib.blake2b`/`sha256` on a fixed encoding of the item, or Python's `hash()` only for structures that are guaranteed to be built AND fully consumed within a single process run.
- Why this fix: The bug is invisible in the exact test setup most people would naturally write first (build the filter and query it in the same script) — it only appears once the filter crosses a process boundary, which is usually a later, separate piece of work (persistence, a second worker, a restart) done by someone who has forgotten the filter was ever built with a randomized hash.
- Rule of thumb: Never use a language's ambient/default `hash()` for anything meant to be persisted, shared across processes, or reproduced later — check explicitly whether that hash is randomized per-process before relying on it, and prefer a fixed cryptographic or non-cryptographic hash (blake2b, xxhash, FNV) for anything crossing a process boundary. Directly parallels this repo's existing rule against ambient `Math.random()`/`Date.now()` in a simulation's authoritative state — same shape of bug, different language, different primitive.
- Provenance (verified/assumed): Verified first-hand — ran the identical script twice as two separate OS processes and directly observed the differing hash values printed above; not inferred from documentation.

## E1 — bloom filter fp formula is a lower bound not estimate
- Date: 2026-07-11
- Project: local/sandbox-bloom
- Tags: [algo][testing][process]
- What: The textbook Bloom filter false-positive formula `(1 - e^(-kn/m))^k` isn't an approximation that's merely "close" — it's a mathematically proven LOWER BOUND, and a real measured false-positive rate can exceed it by a large margin even when the bit array fills exactly as predicted.
- Why built: Same sandbox as the hash-randomization proposal — built a standard Bloom filter sized via the standard `m`/`k` optimal formulas for a 1% target false-positive rate.
- Design: Sized for n=5000 items, target p=0.01, giving m=47925 bits, k=7 hashes (both computed via the standard closed-form formulas).
- Got right: Measured the ACTUAL bit-fill fraction after inserting all real members and compared it to the theoretical expectation before trusting any false-positive measurement — it matched almost exactly (0.5158 actual vs 0.5182 expected), which is what made the false-positive discrepancy worth investigating rather than dismissing as noise.
- Where/why it failed: Queried 20,000 genuinely random (UUID) non-member strings against the filter. Target/naive-formula-predicted false-positive rate: ~0.01. Measured: 0.038–0.041 — roughly 4x worse, reproduced across two different non-member sample sets (sequential strings and random UUIDs, ruling out a string-pattern artifact). Bit-fill fraction was correct, so the bits themselves weren't over-set; the discrepancy is in the formula itself. Cross-checked against published literature (Bose & Guo, "On the False-Positive Rate of Bloom Filters"; Information Processing Letters 2010, "A new analysis of the false positive rate of a Bloom filter"): the standard formula computes false-positive rate as (mean fill fraction)^k, but the TRUE expected false-positive rate is E[(fill fraction)^k] — and since x^k is convex for k≥2, Jensen's inequality guarantees E[(fill fraction)^k] ≥ (E[fill fraction])^k always. The textbook formula is proven to underestimate, not just approximate.
- Fix: Never treat the standard formula's output as a guarantee — measure the real false-positive rate empirically against representative query data before shipping, and provision margin (a lower target p, or a larger m, than the formula's bare minimum) to absorb the gap. For small-to-medium filters especially (the regime this sandbox used), the gap can be large, not a rounding error.
- Why this fix: The formula being a proven lower bound (not a two-sided estimate) means "the math says 1%" can never be read as "the real rate is close to 1%, maybe a bit higher or lower" — it can only ever mean "the real rate is at least 1%, with no upper bound promised by this formula alone."
- Rule of thumb: When a design formula for an approximate/probabilistic structure gives you a target rate, check whether that formula is a two-sided estimate or a one-sided bound before trusting its number as a design budget — and when in doubt, measure the real rate against real data rather than trusting the closed-form math alone.
- Provenance (verified/assumed): Verified first-hand for the measurement (built the filter, measured bit-fill fraction and false-positive rate directly, twice, with two different non-member samples) — the Jensen's-inequality EXPLANATION for why is corroborated by external published sources (cited above), not independently re-derived from scratch in this session.
