## E1 — renderer swap transform ownership needs per frame set unless exclusive
- Date: 2026-10-09
- Project: local/sandbox-kernel-film-renderer-swap
- Tags: [film][rendering][canvas][structure][testing]
- What: Stress-test of the FILM kernel "a renderer swap is a cut" (two renderers, one owns the canvas at a time, handoff fade drawn by the incoming one) and its guard rail "whichever renderer draws first must set the transform explicitly". A mock 2D canvas (matrix plus save/restore stack) ran a side-on renderer A and a first-person renderer B through A->B->A, counting world draws whose device position differs from the position under the renderer's own intended camera.
- Why built: The kernel's guard rail is phrased about the FIRST drawer only, and its claim that the swap is "cheap and safe" rests on exclusivity. Both are checkable; the train pass asked for the boundary where the kernel stops holding.
- Design: Policies per renderer: set every frame, set inside save/restore, set once on takeover, set once ever (the guard rail read literally), never set. Helpers: a clean fade (save/reset/restore) and a leaky fade (resets to identity and never restores). Variants: exclusive swap, and a dual-renderer crossfade where both draw in one frame. A separate chrome pass tagged every op with its idiom and counted frames that mix idioms.
- Got right: Exclusive ownership with an explicit set per takeover or per frame gave 0 misplaced of 400 world draws. A renderer that inherits gave 160 of 160 misplaced. The chrome half of the kernel held: hiding the outgoing chrome and giving the incoming renderer its own gave 0 mixed-idiom frames, while leaving the outgoing chrome on, or borrowing the host HUD, gave 40 of 40 frames in B's span mixed.
- Where/why it failed: Four places the kernel's wording is too weak. (1) Set-once-by-the-first-drawer (init-once) is clean on the way in but A inherits B's camera on the swap BACK: 120 of 240 of A's draws misplaced. (2) Set-on-takeover is correct only while no helper leaks: with a leaky fade it produced 280 of 400 misplaced. (3) Setting every frame was predicted to cure that and did not: 80 of 400 misplaced, because the leaky fade resets the matrix AFTER the set and before the world draws (prediction wrong; this is the refuted part). (4) A dual-renderer crossfade breaks set-on-takeover (36 of 320) while set-every-frame gives 0, so the cheap rule is safe only because of exclusivity.
- Fix: Make each renderer own its transform at the point of use, not at the point of entry: set the base transform immediately before its world draws (post-hoc check: set-late with the leaky fade gave 0 of 400), or have every helper that touches the matrix save and restore it. Keep the handoff exclusive so a once-per-takeover set is enough; if a crossfade needs both renderers in one frame, switch to per-frame, post-helper sets.
- Why this fix: The failures all share one cause: the matrix is shared mutable state that outlives the renderer that wrote it. Ordering the set after the last possible writer, or bounding every writer with save/restore, removes the dependence on who drew before. It also matches the earlier finding that a full-screen helper must save and restore (the-game-wrong-sky/E1).
- Rule of thumb: In a renderer swap, "the first drawer sets the transform" is not enough: set it right before the world draws on every frame of every renderer, and make helpers restore what they reset; only a strictly exclusive handoff with clean helpers lets a once-per-takeover set suffice. Tested in 6 policy/helper/handoff combinations on a mock canvas, not a real browser.
- Provenance (verified/assumed): Verified first-hand: every number above comes from the sandbox run, which models only the 2D matrix state, the save/restore stack and tagged draw ops. The real browser canvas semantics (setTransform replaces, save/restore bounds changes) are taken from the cited memory entry and common API behaviour; the sandbox does not run a browser, and the kernel's own pond-film evidence is cited, not re-run.
