## E2 — shuffle scatter sort shuffle biases candidate order
- Date: 2026-07-13
- Project: local/sandbox-scatter
- Tags: [algorithm][state][gamedesign]
- What: New seam (`sandbox-shuffle` and `sandbox-scatter` shared no prior edge). shuffle#E1 proved `array.sort(() => Math.random()-0.5)` produces a measurably non-uniform permutation (up to 65% deviation on a 5-card deck) but that finding was abstract — never connected to a concrete downstream consumer. Composed directly: if scatter#E1's candidate-position rejection sampling randomizes its try-order via the same sort-comparator shuffle (a realistic implementation choice — "randomize which cell I try first" reads as an equally reasonable one-liner as the deck-shuffle case shuffle#E1 covered), the FIRST candidate position in the shuffled order — the one most likely to actually receive a prop under a tight attempt budget, exactly the budget-exhaustion scenario `sandbox-combined-wfc-keylock#E2` already found occurs in 8.8% of trials — showed a 91.7% deviation from uniform across 50,000 trials (one cell picked first ~19.2% of the time vs the fair 10%; another only ~5.9%).
- Why built: shuffle#E1 quantified the bias in isolation (a deck of cards, position-frequency histogram) but never connected it to a scenario where the bias translates into a game-visible, systematic content defect. This checks whether the abstract statistical bias becomes a concrete distributional problem once it's driving which map cells actually receive props/loot over many generated levels.
- Design: A 10-cell scatter candidate list run through sort-shuffle and Fisher-Yates 50,000 times each (different seed per trial), recording which cell landed FIRST in the shuffled order each time (a direct proxy for "which cell is most likely to receive a prop when the attempt budget is tight," since earlier-tried candidates succeed more often before either the budget or the min-distance constraint set thins the remaining options).
- Got right: Fisher-Yates confirmed clean at this new scale and context too — 2.2% max deviation, consistent with statistical noise, exactly matching shuffle#E1's own verified result transplanted into a new consumer.
- Where/why it failed: shuffle#E1 already explained the mechanism (a noisy sort comparator doesn't visit/compare all pairs equally, so most engines' sort implementations don't average out to uniform) — this seam's contribution is showing the CONCRETE, decision-relevant consequence for a system that consumes shuffle order as "try candidates in this sequence": across many generated levels, specific cells would be measurably over- or under-represented for props/loot — not a subtle statistical curiosity, but an ~2x skew (19.2% vs 5.9%) large enough to be noticeable as "this corner always seems to get more loot" in actual playtesting, exactly the kind of bug shuffle#E1's own "Where/why it failed" field warned is invisible by inspection and only shows up at scale.
- Fix: Use Fisher-Yates (shuffle#E1's own verified fix) for any candidate-order randomization inside a placement/scatter algorithm, not just for user-facing shuffles (card decks, playlists) — the risk isn't specific to the "shuffle" framing, it's any code path where `sort(random)` is used to randomize iteration/try order and the results of that order matter (which they silently do here, via the interaction with a limited attempt budget).
- Why this fix: This generalizes shuffle#E1's rule of thumb beyond its original framing ("never implement a user-facing shuffle via sort-comparator") to any INTERNAL ordering decision that indirectly affects an outcome distribution — the original entry's own fix needed no changes, only recognizing a second place it silently applies.
- Rule of thumb: shuffle#E1's fix ("never `sort(() => Math.random()-0.5)`, use Fisher-Yates") isn't limited to user-visible shuffles — audit for `sort(random)` inside ANY algorithm that randomizes try/candidate order (placement, sampling, retry sequencing, load balancing), since the resulting bias silently propagates into whatever outcome that order determines, and it's exactly as invisible-by-inspection there as in the original card-deck case, per shuffle#E1's own warning.
- Provenance (verified/assumed): VERIFIED first-hand — ran 50,000-trial histograms of "which of 10 candidates lands first" under both sort-shuffle and Fisher-Yates, confirming 91.7% max deviation for sort-shuffle (concrete numbers: one cell first-picked 9585/50000 times, another only 2966/50000) versus 2.2% for Fisher-Yates on the identical setup.

## E1 — naive scatter clumps use min distance rejection
- Date: 2026-07-05
- Project: local/sandbox-scatter
- Tags: [algorithm][gamedesign][state]
- What: Scattering N objects across a map by drawing each position independently and uniformly at random produces measurably clumpy results — overlapping/crowded pairs and uneven gaps — because independent draws carry no memory of where earlier objects landed; nothing prevents two draws from landing on top of each other.
- Why built: A sandbox comparing naive independent-random object placement against min-distance rejection sampling (a simplified Poisson-disk approach) for scattering 150 objects over a 100x100 area.
- Design: Naive: draw each of N points uniformly at random, independently. Min-distance rejection: draw a candidate point; if it's within a minimum distance of any already-placed point, discard it and draw again; otherwise keep it. Compare nearest-neighbor distance statistics between the two.
- Got right: For applications that genuinely want unclustered independent randomness (e.g. sampling for statistics), naive uniform draws are correct — the failure mode is specific to "scatter objects so they read as evenly, naturally spaced," which is a different requirement than statistical independence.
- Where/why it failed: "Looks random" and "looks evenly spaced" are different properties, and people conflate them. True independent uniform sampling *will* sometimes cluster several points close together — that's expected of true randomness, not a bug in the RNG — but it reads as broken/ugly when the actual intent was "objects spread out across the space."
- Fix: Min-distance rejection sampling (or a full Poisson-disk algorithm for performance at scale): reject any candidate closer than a chosen minimum distance to an existing point.
- Why this fix: It directly encodes the actual requirement (no two objects closer than X) instead of hoping independent random draws happen to satisfy it.
- Rule of thumb: When "scatter N objects across this space" is the requirement, plain independent uniform-random placement will clump — measure it with nearest-neighbor distance statistics (mean/stddev, or a count of pairs closer than your minimum spacing) rather than trusting a glance, since clumping is obvious in the numbers well before N is large enough to be obvious visually. Use min-distance rejection (or Poisson-disk) whenever "evenly scattered" is the actual design intent.
- Provenance (verified/assumed): Verified first-hand — 150 objects over a 100x100 area. Naive uniform placement: 57 pairs closer than the 4-unit minimum spacing, nearest-neighbor spacing coefficient of variation 0.575. Min-distance rejection at the same minimum: 0 violating pairs (by construction) and coefficient of variation 0.245 (more than 2x more even).
