## E1 — seed injection verification breaks replay based scrub determinism
- Date: 2026-07-20
- Project: local/sandbox-seed-vs-replay-verification
- Tags: [testing][harness][determinism]
- Composed: pappydapimp69__dog/E54, pappydapimp69__draft/E7
- What: `brain train edge` flagged `dog + draft` as the highest-value untested pair. dog#E54's eased-value verification technique (seed the value at an arbitrary point BETWEEN two candidate targets, then assert the SIGN of its movement over a few frames) assumes the tester can inject an arbitrary starting value directly into the accumulator. draft#E7's scrub-safe design makes `seek(t)` a deterministic REPLAY from a fixed initial condition (reset, then step every frame to `t`) specifically so continuous playback and scrubbing always agree exactly. Composing them: literally applying dog#E54's seed inside a draft#E7-style replay-only system injects a state no real replay from t=0 could ever reach, silently breaking the exact guarantee draft#E7 exists to provide. Sandbox-confirmed a working adaptation: run TWO full parallel replays from the SAME fixed initial condition (control target vs. treatment target), sample both at a shared time, and compare by sign — reproducing dog#E54's decisive, dt-invariant signal without ever injecting an artificial seed.
- Why built: dog#E54 was recorded from a live (non-scrub-safe, plain per-frame) game build with no seek/replay concept in scope; draft#E7 was recorded from a scrub-safe timelapse build with no eased-value hypothesis-testing scenario in scope. Neither session had reason to ask whether dog#E54's own seeding step is compatible with a system built to draft#E7's replay-determinism guarantee.
- Design: Deterministic Node script (`sandbox_seed_vs_replay_verification.mjs`), no RNG, no wall-clock. `replayTo(targetFn, tEnd)` mirrors draft#E7's `seek(t)` — always starts from the SAME fixed initial condition (v=0.5) and steps every frame via a `smooth()` ease to `tEnd`, never accepting an injected starting state. `seededProbe`/direct injection mirrors dog#E54's literal technique. Three scenarios: (A) compare an injected seed (0.30) against what a real replay from t=0 actually reaches by the same nominal time — confirming they don't match; (B) the adapted parallel-replay technique — two replays from the SAME fixed seed, differing only in target function, sampled at a shared time and compared by sign; (C) control — confirm the parallel-replay technique's sign result is stable across a 3x coarser dt, the same dt-invariance property that made dog#E54's original technique valuable.
- Got right: Scenario C confirms the adapted technique preserves dog#E54's core value (a decisive signal immune to headless clock jitter/dt variance) — it isn't a downgrade, just a reformulation compatible with replay-only access.
- Where/why it failed: Scenario A: a real replay from t=0 toward a constant target of 0.7 reaches 0.7000 by t=2.0 (fully converged); dog#E54's literal seed of 0.30 is nowhere near that trajectory at any real elapsed time for this target — confirming the injected seed is not a state any actual replay produces, meaning a test harness that pokes it directly into a draft#E7-style accumulator is testing a physically-impossible intermediate state, not a real moment in the system's own timeline.
- Fix: In a replay-based (scrub-safe, seek-from-fixed-initial-condition) system, adapt dog#E54's sign-test by running TWO parallel replays from the SAME shared initial condition — one per candidate scenario/target — and comparing their values at a shared sample time by sign, rather than seeding a single run's accumulator mid-flight. This requires the ability to run two independent replay instances (cheap for a pure function of a fixed start + target), not a shared mutable accumulator.
- Why this fix: The parallel-replay approach isolates exactly the same variable dog#E54's original technique isolates (which side of a reference point the target sits on) while respecting draft#E7's own invariant (nothing is ever a function of anything other than elapsed time from the fixed start) — it doesn't compromise either lesson's own reasoning, it finds the version of dog#E54's technique that's actually expressible inside draft#E7's constraint.
- Rule of thumb: Before applying a verification technique that requires injecting an arbitrary intermediate state (a seed, a mid-flight value) into a system, check whether that system's own state-access model actually supports injected states — a REPLAY-based (deterministic-from-a-fixed-start) system by construction only produces states reachable by real playback, and any test harness that pokes a value in directly is testing a state the system itself could never actually be in, silently invalidating the very determinism guarantee the replay design exists to provide. When the target system is replay-only, adapt a seed-and-compare technique into a parallel-replay-and-compare one instead.
- Provenance (verified/assumed): Verified first-hand — `sandbox_seed_vs_replay_verification.mjs` run to completion for all three scenarios, deterministic (no RNG, no wall-clock, closed-form `smooth()` ease stepped at fixed dt), each scenario's computed values and sign comparisons printed and checked programmatically (an `allPass` gate across all three; exits 1 and prints "CLAIM DID NOT REPRODUCE — do not file" if any scenario disagreed with the prediction — none did).
