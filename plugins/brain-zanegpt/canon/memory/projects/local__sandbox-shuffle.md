## E1 — naive sort shuffle is biased
- Date: 2026-07-05
- Project: local/sandbox-shuffle
- Tags: [algorithm][state]
- What: `array.sort(() => Math.random() - 0.5)` — a common one-liner "shuffle" — does not produce a uniform random permutation. It's measurably biased: some elements land in some positions far more or less often than a fair shuffle would, because `Array.prototype.sort`'s comparator contract assumes a consistent ordering and most engines' sort implementations (insertion/merge sort variants) don't visit/compare all pairs equally, so a noisy comparator doesn't average out to uniform.
- Why built: Card-battler-style deck shuffling in a sandbox game; the naive one-liner is the version most people reach for first (including well-known real-world instances of this exact bug shipping in production).
- Design: Compare a "shuffle" implemented via sort-with-random-comparator against Fisher-Yates (the standard in-place uniform shuffle) on the same deck size and trial count.
- Got right: Fisher-Yates itself is simple, well-known, and cheap (O(n), one pass) — there's no reason to reach for the sort trick other than unfamiliarity.
- Where/why it failed: The bias is invisible by inspection — a handful of manual test shuffles all *look* random, and even the a la carte "run it 10 times and eyeball the results" check won't catch it. It only shows up as a measurable skew across many trials (a position-frequency histogram), which most people never run before shipping a shuffle feature.
- Fix: Use Fisher-Yates: iterate `i` from the last index down to 1, swap element `i` with a uniformly random element in `[0, i]`. One line more than the sort trick, and it's provably uniform.
- Why this fix: Fisher-Yates is a direct, well-understood proof: at each step it places one element uniformly among the remaining unplaced slots, so induction gives a uniform permutation overall. The sort-comparator approach has no such guarantee — its distribution depends on the sort algorithm's internal comparison pattern, which is an implementation detail, not a contract.
- Rule of thumb: Never implement "randomize this order" via `sort(() => Math.random() - 0.5)` — use Fisher-Yates. If you inherit a shuffle you didn't write and aren't sure which it is, don't trust a visual glance: run it thousands of times and check the position-frequency histogram for skew before trusting it in anything where fairness matters (games, raffles, A/B ordering).
- Rule of thumb (verification pattern): to catch this class of bug in ANY "should be uniformly random" feature (shuffles, sampling, hashing distributions), run many trials and histogram the outcome — a bug that's invisible in a handful of samples is often glaring at scale.
- Provenance (verified/assumed): Verified first-hand — 200,000-trial simulation on a 5-card deck. Naive sort-comparator shuffle: max single-cell deviation from the uniform expectation was 65% (e.g. one card landed in one position ~32% of the time vs the fair 20%). Fisher-Yates on the identical test: max deviation 1.3%, consistent with statistical noise.
