## E6 — crowdsource aggregation count is not confidence and anonymity fights sybil
- Date: 2026-07-18
- Project: pappydapimp69/garden
- Tags: [architecture][data-integrity][privacy][security][process]
- What: External research (not reasoning alone) to ground Garden's crowdsourced plant-network design — an anonymized `species_observations` aggregate keyed by canonical species + zip only (no user_id, no GPS), a `species_insight` read gated by a min-sample threshold (>=3), and a `record_species_observation` writer that down-weights low-trust contributors via `trust_score`. Checked the design against how established citizen-science networks (iNaturalist, eBird) and the crowdsourced-data-quality literature actually handle trust, confidence, and geoprivacy.
- Why built: The plant-network + trust-weighting kernels were designed and MVP-built but never validated against real practice. Crowdsourced aggregation has well-known, non-obvious failure modes (spam, sybil, false confidence) that are cheap to get wrong and expensive to discover in production, so external grounding before hardening is worth more than another round of reasoning.
- Design: Compared four design choices against sources: (1) down-weight-not-reject via reputation, (2) min-sample publish gate, (3) coarse-location-not-GPS, (4) no reverse-lookup / no user_id.
- Got right (validated by external practice): (a) Down-weighting low-trust contributors without bans is exactly reputation-weighted truth-discovery ("filter guesses without bans, blend current-round weight with reputation") — the trust_score weighting matches the literature. (b) Coarse location beats GPS: iNaturalist obscures at-risk species to a random point in a ~0.2x0.2 degree (~400 km2) cell; Garden's zip-only-no-GPS-no-photo-no-user_id aggregate is arguably MORE private, because it closes all three of iNaturalist's documented obscuration-leak vectors at once (photo landmarks, description text, and same-user interpolation from nearby observations).
- Where/why it failed (two real gaps the research surfaced): (1) COUNT IS NOT CONFIDENCE. A 2024 study found 24.9% of iNaturalist "research-grade" observations (community-consensus-passed) were inaccurate or uncertain; confidence there is scored multi-dimensionally (species diagnosability, media quality, georeferencing accuracy), not by agreement count. Garden's min-sample>=3 gate treats raw count as truth and ignores the per-observation quality signals it already has (vision confidence; the trust-weighting kernel's own photo-vs-vision-disagreement flag). (2) ANONYMITY FIGHTS SYBIL RESISTANCE. The literature names sybil and reputation-reset attacks as the core crowdsource threat, defended by identity-linking (e.g. zkSNARK pseudonym binding). Garden's aggregate has NO user_id by design (privacy), which means it structurally cannot detect one user flooding a zip+species to skew "in your area" — the very property that makes it private removes the only signal that would catch a flood.
- Fix: (a) Gate/weight `species_insight` on per-observation quality (average vision confidence, photo-vs-vision agreement), not sample count alone — the 25%-wrong result is the cautionary case for "consensus count == truth". (b) Add an anonymous flood cap: store a one-way hash of (user_id, zip, species, day) as a dedup key on `species_observations` (unique or counted), capping one user's daily influence on a cell WITHOUT ever storing who they are — the middle path between full anonymity and sybil resistance.
- Why this fix: Each closes a gap the source design cannot see from the inside: raw-count confidence is the single most-documented citizen-science quality failure, and the anonymity/sybil tension is inherent — you cannot both refuse identity linkage and detect per-identity abuse, so the resolution is a linkage that is one-way and coarse (hashed, per-day) rather than either extreme.
- Rule of thumb: For a privacy-preserving crowdsourced aggregate: (1) publish confidence from per-observation QUALITY signals, never from agreement COUNT alone (community-consensus "research grade" was ~25% wrong in a real study); (2) coarse location + no user_id + no media in the aggregate is strong geoprivacy (beats coordinate-obscuration, which leaks via media/text/same-user interpolation); (3) full anonymity structurally defeats sybil/flood detection — reintroduce the MINIMUM linkage needed as a one-way, coarse-grained (e.g. hashed per-user-per-cell-per-day) dedup key, not raw identity.
- Provenance (verified/assumed): VERIFIED first-hand — fetched and read the cited external sources this session, and confirmed Garden's SCHEMA.sql crowdsource layer first-hand as the reviewed baseline. Verification method is external-source corroboration (a literature-grounded design review), the appropriate standard for a design-validation finding. Sources read first-hand: Ackland et al. 2024 "A Method for Conveying Confidence in iNaturalist Observations" (PMC11461752 — the 24.9%-of-research-grade-inaccurate figure and the multi-dimensional confidence scoring); iNaturalist Geoprivacy documentation (the ~0.2deg / ~400km2 obscuration cell and its documented leak vectors); "Establishing Trust in Crowdsourced Data" (arXiv 2511.03016), Hunter et al. 2013 (Wiley), and Data Quality in Citizen Science (Springer) for reputation-weighted truth-discovery and sybil/reset threats. The claims are about real-world citizen-science practice (corroborated across sources), a domain established by literature rather than by a code sandbox.

## E5 — verify supabase sql on ephemeral local postgres stub auth uid
- Date: 2026-07-18
- Project: pappydapimp69/garden
- Tags: [testing][verification][supabase][postgres][process]
- What: Building the E1 sanitization trigger + the crowdsource RPCs (species_observations / record_species_observation / species_insight) for Garden meant writing security-critical Postgres — a BEFORE INSERT trigger, two SECURITY DEFINER functions, RLS with no policies — that could not be exercised against the live Supabase project from the dev sandbox. Rather than ship it "reviewed but unrun", verified it against a throwaway local Postgres.
- Why built: Garden is a client-direct Supabase app; its security boundary lives entirely in DB objects (RLS, triggers, DEFINER functions). "Looks correct" is exactly the confidence level these bugs hide behind — a trigger that silently keeps a key, an RPC that trusts client input. The SCHEMA.sql header even says "run this in the Supabase SQL editor", i.e. it is never executed in CI.
- Design: Docker wasn't running, but the postgresql-16 server package was installed. Ran `initdb` + `pg_ctl` as a non-root user into a temp datadir on a custom port/socket (no container needed). Then a small harness stubs the Supabase-only surface: `create schema auth; create table auth.users(...); create function auth.uid() returns uuid as $$ select nullif(current_setting('test.uid', true),'')::uuid $$`, plus a `create role authenticated`. The migration's own SQL is then applied verbatim, and assertions set `test.uid` per-transaction (SET LOCAL needs a txn block) to simulate different JWT subjects.
- Got right: Testing the SECURITY properties, not just "does it parse" — asserted the trigger strips injected keys (user_id/email/`<script>` → gone) and rejects unknown action_type; asserted the RPC contributes nothing for an opted-out user, sources the zip server-side (client never passes it), weights by trust_score, and gates the read at the min-sample threshold. Each is a property an attacker would probe.
- Where/why it failed (the trap this avoids): Supabase SQL reads as plain Postgres but depends on objects that don't exist in a vanilla cluster — `auth.uid()`, `auth.users`, the `authenticated`/`anon` roles, `current_setting` GUCs. Naively piping SCHEMA.sql into local PG fails on those, which tempts you to skip local verification entirely and trust the SQL editor at deploy time. The unlock is that all of them are cheaply stubbable — `auth.uid()` is just a function returning a GUC you set per test.
- Fix: Keep a tiny reusable auth-stub harness (auth schema + uid()-via-GUC + roles) and run security-critical Supabase DDL/functions against an ephemeral local Postgres before deploying. `SET LOCAL test.uid` inside a transaction to role-play each user. Assert the adversarial cases (stripped keys, rejected types, opt-out, server-sourced fields, threshold gating), not just successful inserts.
- Why this fix: It converts "reviewed" into "verified" for exactly the layer where client-direct apps put their trust boundary, at ~zero infra cost (no container, no cloud project, no credentials). A DEFINER function or trigger that's wrong is invisible in normal-shaped output; a couple of adversarial assertions against real Postgres surface it before users can.
- Rule of thumb: You can verify Supabase RLS/trigger/RPC security locally without Docker or the cloud project: `initdb` a scratch Postgres, stub the Supabase surface (an `auth` schema + `auth.uid()` reading a `current_setting` GUC + the `authenticated`/`anon` roles), apply the real migration, and assert the ADVERSARIAL cases (injected keys stripped, unknown inputs rejected, opt-out honored, privileged fields sourced server-side, read thresholds enforced) with `SET LOCAL` role-play. Don't ship security-critical DB objects "reviewed but unrun".
- Provenance (verified/assumed): VERIFIED first-hand — this is the method used to verify Garden's E1 trigger and crowdsource RPCs this session; all assertions passed against Postgres 16.13 (payload stripped, unknown action rejected, opt-out contributes nothing, zip server-sourced, weight 0.5 from trust 50, insight enough:false@2 / true@3). The only stubbed pieces were auth.uid()/auth.users/roles; the migration SQL itself ran unmodified.

## E4 — file url blocks es module imports serve over http to verify
- Date: 2026-07-18
- Project: pappydapimp69/garden
- Tags: [testing][verification][javascript][browser][process]
- What: To verify the new longitudinal-insight card and the plant-network insight framing, I loaded a tiny harness page in headless Chromium (Playwright) that did `import { generateInsight } from '.../src/state/insights.js'` — running the REAL shipped module, not a copy. Loading the harness via a `file://` URL failed: the module fetch was blocked with "Access to script … from origin 'null' has been blocked by CORS policy: Cross origin requests are only supported for protocol schemes: chrome, chrome-untrusted, data, http, https", so `window.__render` was never defined and the assertions timed out.
- Why built: The whole point was to verify the actual source module's behavior against real RPC output shapes / real journal data, so that the test can't drift from what ships. That requires the browser to `import` the real file, i.e. ES module loading.
- Design: Serve the harness over HTTP instead of `file://`. Copied the module next to the harness, `python3 -m http.server` in that dir, loaded `http://127.0.0.1:<port>/harness.html`, and (critically) bypassed the sandbox's HTTPS proxy for localhost via `NO_PROXY=127.0.0.1 HTTP_PROXY= HTTPS_PROXY=` so the browser could actually reach the local server.
- Got right: Insisting the browser import the real module rather than a hand-copied snippet — which then correctly rendered the exact shipped text ("Herb Box has dropped from 8 to 2 tagged plants across your last 4 check-ins."), and let me verify dismiss→persist→stays-quiet end-to-end.
- Where/why it failed: A `file://` document has an opaque ('null') origin, and Chromium refuses ES module (`import`) fetches from opaque origins — even for a sibling file in the same directory. A plain classic `<script>` from file:// works, so the failure only appears the moment you use `type="module"` / `import`, which is easy to mis-attribute to a bad path. Separately, in a proxied sandbox, even the HTTP server is unreachable until localhost is excluded from HTTPS_PROXY.
- Fix: To exercise a real ES module in a headless browser, serve the page over http:// (any static server), not file://. Inline-copying the module to dodge the import is the tempting wrong turn — it verifies a copy, not the shipped code. In a proxied environment, unset/NO_PROXY localhost so the browser can reach the local server.
- Why this fix: It keeps the verification honest (real module, real code path) while satisfying the browser's origin rules. The alternative (test a pasted copy of the logic) is exactly the drift that makes a green test meaningless when the real module changes.
- Rule of thumb: Headless-browser verification that must import the REAL ES module has to be served over http:// — `file://` has an opaque origin and Chromium blocks module imports from it ("origin 'null' … CORS"), while classic scripts still load, so the break shows up only when you switch to `type="module"`. Spin up `python3 -m http.server`, and in a proxied sandbox exclude localhost from HTTP(S)_PROXY. Don't "fix" it by inlining a copy of the module — that tests a copy, not what ships.
- Provenance (verified/assumed): VERIFIED first-hand this session — reproduced the exact `file://` CORS error and the `window.__render undefined` symptom, then confirmed the same harness works when served over http:// with localhost excluded from the proxy (card rendered the real module's text, dismiss persisted the key, repeat stayed quiet).

## E3 — serverless quota gate must be atomic not check then insert
- Date: 2026-07-17
- Project: pappydapimp69/garden
- Tags: [security][architecture][serverless][supabase][concurrency]
- What: Garden's `vision-proxy` Supabase edge function is the declared "sole source of truth" for the per-user vision quota (10/day UTC, 100/lifetime) that the project owner's Anthropic key pays for. It enforces the cap by (1) running two `count` queries against a `vision_api_calls` ledger, (2) returning 429 if over limit, (3) inserting a new ledger row, (4) forwarding the request to api.anthropic.com. The check and the insert are not one atomic operation, AND the insert is fire-and-forget (`admin.from(...).insert(...).then(...)` — never awaited) with an explicit "if the insert fails we still forward" fallback.
- Why built: A covered-usage tier so users can try the app without bringing their own key. The edge function holds the server-side key and is meant to bound how much of it any one user can spend. The insert was placed "first" (per the code comment) specifically to stop a user cancelling a slow Anthropic response to dodge the counter.
- Design: RLS on the ledger is actually correct as a *reset* defense — there is no UPDATE or DELETE policy, so a client cannot delete its own rows to zero the counter (RLS default-denies operations with no policy). The bypass is not through the ledger's integrity; it's through the gate's non-atomicity.
- Got right: The read-side (RLS owner-only select) and the no-delete-policy choice genuinely prevent the obvious "delete my rows to reset quota" attack. Auth is verified manually (`admin.auth.getUser(jwt)`) even though the function is deployed `--no-verify-jwt`, so unauthenticated calls are rejected.
- Where/why it failed: Check-then-act across a network round-trip is a TOCTOU race. N concurrent invocations at count=9 all read a below-limit count, all pass the gate, all forward — the 10/day and 100/lifetime caps are defeated by concurrency, letting one user run the owner's API key far past the intended ceiling (a direct cost/DoS on your own credential). The fire-and-forget, non-awaited insert widens the window (the forward starts before the row is committed) and the "forward even if insert fails" branch burns uncounted calls. The comment's stated protection ("insert first") is contradicted by the code never awaiting it.
- Fix: Make check-and-record ONE atomic operation and await it, and refuse (don't forward) when it reports over-limit. Two proven shapes: (a) a Postgres `SECURITY DEFINER` RPC that takes a per-user advisory lock (`pg_advisory_xact_lock(hashtextextended(user_id,0))`) then does count-guarded insert in a single transaction, returning allowed/blocked; (b) Supabase's own documented recommendation — an atomic Redis `INCR` (Upstash) keyed on user+day, which is a single indivisible op by construction. Either replaces the two-query-then-async-insert pattern.
- Why this fix: A quota is a load-bearing rule whose whole value is that it holds under adversarial, concurrent load — exactly the condition a check-then-act gate fails. Atomicity has to live at the counter (DB transaction or Redis INCR), not be approximated by ordering two independent statements. Awaiting the record and refusing on over-limit closes the "forward first, count later" gap.
- Rule of thumb: In a serverless/multi-instance backend, a per-user rate/quota gate implemented as "SELECT count → compare → INSERT" is bypassable by concurrent requests, and any fire-and-forget counter increment makes it worse. Enforce the limit atomically at the counter — a single DB transaction (advisory lock or count-guarded insert) or an atomic store INCR — await it, and refuse rather than proceed when it reports over-limit. RLS that forbids the client from deleting the ledger is necessary but NOT sufficient; it stops resets, not races.
- Provenance (verified/assumed): VERIFIED first-hand by reading `supabase/functions/vision-proxy/index.ts` and `SCHEMA.sql` — the insert is demonstrably not awaited, the gate is a separate count-then-compare, and the ledger has no UPDATE/DELETE policy (reset is blocked). ASSUMED (not exploit-demonstrated in a live sandbox): that concurrent invocations interleave to actually exceed the cap — this is standard TOCTOU behaviour for independent serverless invocations and is near-certain, but I did not run a concurrent-request proof against a deployed instance. External-research addendum (2026-07-17): Supabase's official edge-function rate-limiting guide recommends atomic Upstash Redis increments precisely because they eliminate the check-then-act window; Supabase RPCs are noted as running atomically in one DB round-trip.

## E2 — key hiding proxy must pin request not forward raw body
- Date: 2026-07-17
- Project: pappydapimp69/garden
- Tags: [security][architecture][llm][proxy][api]
- What: Garden's `vision-proxy` edge function exists to hide the owner's Anthropic key: the browser sends a request with its Supabase JWT, the function attaches the server-side key and forwards to api.anthropic.com. It forwards the client's request body VERBATIM (`body = await req.text()` → passed straight through). The client is *supposed* to send a fixed shape (`model: claude-sonnet-4`, `max_tokens: 2000`, a vision message), but the function validates none of that.
- Why built: A thin pass-through proxy is the simplest way to keep the key off the client while still letting the real Anthropic Messages API do the work — the app just wants "call vision on my behalf."
- Design: The proxy authenticates the caller (JWT) and meters call COUNT via the quota ledger, but treats the request BODY as opaque and trusted.
- Got right: Keeping the key server-side at all (vs shipping it, or the BYOK path which uses the user's own key) is the correct instinct — the key never reaches the browser on the covered path.
- Where/why it failed: Counting calls is not the same as bounding cost or scope. Because the body is unvalidated, an authenticated user (not bound by the app's client code) can POST any body the proxy will sign with the owner's key: the most expensive model, `max_tokens` at the ceiling, or arbitrary non-vision prompts — turning the endpoint into a general-purpose Anthropic relay for the owner's account, capped only by call count (and see the sibling lesson: that count cap is itself racy). "10 calls/day" with an unpinned body can mean 10 max-cost completions of the attacker's choosing.
- Fix: Construct the upstream request server-side from a strict allow-list. Pin `model`; clamp/replace `max_tokens` to the app's real ceiling; accept only the fields the feature needs (e.g. the image + a fixed system/instruction) and drop or reject everything else. Never forward `await req.text()` unparsed to a paid upstream you hold the credential for.
- Why this fix: The client request is attacker-editable UX, not a control surface — the moment your server signs it with a secret, every field the client controls is a field the attacker controls at your expense. Reconstructing the upstream call from server-owned constants makes the cost/scope of a covered call fixed regardless of what the client sends.
- Rule of thumb: A credential-hiding proxy must PIN and reconstruct the upstream request from server-side constants (model, token cap, allowed fields), not forward the client's raw body. Metering request COUNT does not bound per-request COST or SCOPE — an unvalidated forwarded body lets a caller spend your key on the priciest model/params, or repurpose the endpoint entirely, within whatever count limit exists.
- Provenance (verified/assumed): VERIFIED first-hand — `vision-proxy/index.ts` reads `await req.text()` and forwards it unmodified with the server key; no model/token/field validation is present. The abuse (expensive model / arbitrary prompts on the owner's key) follows directly from that and from the Anthropic Messages API accepting those fields; I did not run a live abusive request against the deployed function. External-research addendum (2026-07-17): multiple hardened LLM-proxy projects and a documented gh-aw-firewall issue ("proxy forwards all requests regardless of validity") converge on the same rule — validate/pin the request server-side; hiding the key is necessary but not sufficient.

## E1 — client side sanitization is not enforcement for a writable table
- Date: 2026-07-17
- Project: pappydapimp69/garden
- Tags: [security][data-integrity][supabase][rls][postgres]
- What: Garden dual-writes each user action to a private `user_action_log` (full payload, owner-only RLS) and an anonymized `global_action_log` used for crowdsourced aggregation. The client function `sanitizeForGlobal()` strips the global payload to an allow-list of numeric/categorical fields (`plant_count`, `zone_type`, `confidence`, `category`, `amount`) before inserting. The table's RLS insert policy is `with check (auth.uid() is not null)` — any authenticated user may insert any row.
- Why built: The global log is meant to power privacy-preserving aggregate insights across users, so it accepts inserts from everyone but (via the client sanitizer) only "safe" fields, and has no SELECT policy so only the service role can read it back.
- Design: Sanitization and the field allow-list live in client JavaScript (`src/data/actionsLog.js`); the database only checks that the caller is logged in.
- Got right: No SELECT policy on the global table is correct — clients can write but never read others' rows, so it's not a data-exfiltration surface. The private/global split (full payload stays in an owner-only table) is a sound separation.
- Where/why it failed: The allow-list runs only on the honest client. Because Garden talks directly to PostgREST with the anon key + a user JWT, a malicious authenticated user bypasses the app entirely and POSTs arbitrary `action_type` + arbitrary `payload` straight to `/rest/v1/global_action_log` — the RLS check (`auth.uid() is not null`) waves it through. That injects unsanitized, attacker-chosen, possibly PII-bearing or aggregate-poisoning rows into the exact table the crowdsource feature trusts. Client-side sanitization is UX, not a boundary.
- Fix: Enforce the shape server-side. Best: a `BEFORE INSERT` trigger (`SECURITY DEFINER`) on `global_action_log` that whitelists `action_type` against known values and rewrites `payload` to only the safe keys (dropping everything else) — so even a raw PostgREST insert is normalized. Alternatively route all global logging through an edge function / RPC that is the only grantee of INSERT, and revoke direct insert from the `authenticated` role. Keep client `sanitizeForGlobal()` too (cheap, reduces honest traffic), but never rely on it.
- Why this fix: With a client-direct architecture the database IS the trust boundary; anything not enforced in RLS/triggers/grants is unenforced. A trigger or a sole-writer RPC makes the sanitization run regardless of who calls or how, closing the gap between "the app's code" and "what the endpoint accepts."
- Rule of thumb: In a client-direct (PostgREST/Supabase) app, any table with a permissive insert policy (`auth.uid() is not null`) accepts whatever an authenticated attacker sends straight to the REST endpoint — client-side sanitization/allow-listing is decorative. Enforce field/value whitelisting in a BEFORE-INSERT trigger or a sole-writer SECURITY DEFINER RPC (and revoke direct insert), especially for shared/aggregate tables where one poisoned row corrupts everyone's view.
- Provenance (verified/assumed): VERIFIED first-hand — `SCHEMA.sql` shows `global_action_log` with `for insert with check (auth.uid() is not null)` and no trigger; `src/data/actionsLog.js` shows the allow-list is client-only and the app inserts via the shared PostgREST client with the anon key. The raw-insert bypass follows directly from PostgREST exposing the table to the `authenticated` role; I did not execute the bypass against the live project. FIX NOW IMPLEMENTED + VERIFIED (this session): added the BEFORE INSERT trigger to SCHEMA.sql and verified against an ephemeral local Postgres 16 that a raw insert with extra keys (user_id/email/`<script>`) is stripped to the safe set and an unknown action_type is rejected. Composes with collective/E5 (a user-supplied path is attacker-editable; enforce server-side, default-deny).
- Composed: collective/E5
- Link: this session (Garden audit + fix); `SCHEMA.sql` (global_action_log, sanitize_global_action_log trigger), `src/data/actionsLog.js`
