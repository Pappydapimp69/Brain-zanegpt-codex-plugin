## E2 — pathmetrics heuristic diagonal corner guard weight independent
- Date: 2026-07-13
- Project: local/sandbox-combined-pathmetrics
- Tags: [algorithm][gamedev][testing]
- What: New environment/group seed (`sandbox-pathfinding-astar-heuristic` and `sandbox-pathfinding-diagonal` shared no prior edge). astar-heuristic#E1 found weighted A* (weight 1.5-3) cuts 56-58% of node expansions with 0% path-length cost. diagonal#E1 found naive 8-directional movement corner-cuts through wall gaps in 100% of solvable paths (179/179) unless explicitly guarded. Composed directly: does heuristic weighting (which biases search toward greedier, more diagonal-favoring paths) interact with the corner-cutting guard, either bypassing it or requiring stronger guarding at high weight? Across weights {1, 1.5, 3, 5, 10} and two wall densities (0.30, 0.35), the guard held at 0/95 corner-cuts in every configuration; a control run with the guard disabled reproduced diagonal#E1's near-100% rate exactly (90/90).
- Why built: To check whether a fix verified against ONE search behavior (plain admissible A*, diagonal#E1's own test) continues to hold once a DIFFERENT search behavior (greedy/weighted A*, deliberately favoring shortcuts) is composed with it, since a corner-cutting guard applied at the wrong point in the algorithm (e.g. only checked for the admissible path, not every candidate move regardless of weight) could plausibly be bypassed by weighting.
- Design: The corner-cutting guard (diagonal move rejected if either flanking orthogonal neighbor is a wall) is implemented at the neighbor-GENERATION step, before any cost or heuristic value is computed or compared — structurally independent of weight. Ran 100+40 trials across weight/density combinations with the guard on, plus a guard-off control.
- Got right: The guard's placement (gating candidate moves at generation time, not after cost comparison) is exactly why it composes safely with any downstream weighting scheme — weighting only affects WHICH valid candidates get explored first, never which candidates are valid in the first place.
- Where/why it failed: It didn't; this is a confirmatory result. Filed because the composition was untested and the guard's weight-independence was a structural property worth verifying directly rather than assuming from the code's shape, especially given weighted A* is explicitly recommended as a default optimization by astar-heuristic#E1 itself.
- Fix: N/A — no bug found; no code change needed in either system.
- Why this fix: N/A (no fix), but the reason no fix is needed is itself the useful content here: a validity guard applied at candidate-GENERATION time is invariant to anything that happens AFTER generation (cost weighting, tie-breaking, search order) by construction — the class of guard that stays composable is the one checked before the decision it's meant to constrain, not layered on top of a specific search variant's output.
- Rule of thumb: When composing a movement/geometry VALIDITY guard (corner-cutting, collision, occupancy) with a SEARCH OPTIMIZATION (heuristic weighting, tie-breaking, pruning), check where the guard is applied in the algorithm — if it gates candidate generation (before cost/heuristic computation), it is structurally weight/optimization-independent and composes safely without re-verification per optimization variant; if it gates something applied later (post-hoc path validation, a final check), it can be bypassed by a search variant that explores differently, and needs explicit re-verification per variant.
- Provenance (verified/assumed): VERIFIED first-hand — ran weighted A* (weights 1, 1.5, 3, 5, 10) across 100+40 trials at two wall densities with the corner-cutting guard active, confirming 0 corner-cuts in every configuration, and confirmed a guard-off control reproduces diagonal#E1's near-100% baseline rate (90/90) on the identical map generator.

## E1 — pathmetrics distance difficulty masked by working pathfinder
- Date: 2026-07-13
- Project: local/sandbox-combined-pathmetrics
- Tags: [gamedesign][algorithm][testing]
- What: Grew the pathmetrics environment (loop 1's group) with `sandbox-distance` (new pairing). distance#E1: Euclidean distance from spawn badly misrepresents actual maze/corridor difficulty (a cell can be Euclidean-close but require a long walk). astar-heuristic#E1 also uses Euclidean distance, but as an ADMISSIBLE HEURISTIC — a role where underestimating true cost is not just safe but required. Composed directly: A* using the Euclidean heuristic found the TRUE-optimal path length in 100/100 trials (zero visible pathfinding failure, exactly as expected since Euclidean is always <= true grid-path distance). Meanwhile, using that SAME Euclidean value to tier difficulty/loot by distance-from-spawn was wrong by >50% relative error in 234/1602 (14.6%) of sampled cells, max error 86% — reproducing distance#E1's own finding, but now alongside a pathfinding consumer that reports zero problems.
- Why built: distance#E1 and astar-heuristic#E1 both consume "distance from spawn," computed the same way (Euclidean), for two DIFFERENT purposes with different correctness requirements (heuristic: must underestimate, any degree of underestimation is fine; difficulty pacing: must approximate true walking distance closely). Checking whether a project that reuses a single cached "distance" value for both purposes gets any warning signal from the working consumer (the pathfinder) that the value is unsafe for the other, non-working consumer (difficulty tiering) — since if a developer wired A* first and it worked perfectly, that's exactly the kind of false confidence that would delay noticing the difficulty-gradient bug distance#E1 already found.
- Design: A 25x25 grid (wall density 0.28) with BFS-computed TRUE path distance from spawn as ground truth. A* run with an Euclidean heuristic to a random goal per trial, comparing its found path length against true BFS distance (pathfinding correctness check). Separately, for 20 sampled open cells per trial, Euclidean distance vs. true BFS distance compared directly (difficulty-tiering correctness check) — same map, same "distance from spawn" concept, two different consumers.
- Got right: A*'s use of Euclidean distance is not just "not obviously wrong" but PROVABLY always safe here — grid walls can only make true path distance greater than or equal to straight-line distance, never less, so Euclidean is unconditionally admissible for this class of map and A* remained 100/100 optimal regardless of wall configuration or goal placement.
- Where/why it failed: The two consumers of "distance from spawn" have inverted tolerance for the SAME error direction. Euclidean underestimating true distance is exactly what makes it a valid heuristic (helpful, required even) — and exactly what makes it a bad difficulty signal (a cell reported as "close" that's actually a long walk gets under-tiered, the opposite of distance#E1's own finding but the identical mechanism). Because the heuristic's use case rewards the same property the difficulty use case is harmed by, a project sharing one distance value across both will see the pathfinder succeed constantly while the difficulty system silently drifts wrong — the working system provides zero signal about the broken one, because "does the heuristic work" and "does the difficulty gradient work" are unrelated questions that happen to consume the identical input number.
- Fix: Keep the two consumers on separate distance sources — A*'s heuristic continues using cheap Euclidean distance (correct and necessary for performance); difficulty/loot tiering uses the already-computed BFS true-path distance (the same value astar-heuristic's own ground-truth check already required, so no new computation is needed, only not discarding it after the pathfinding check). Re-verified: with difficulty tiering driven by true BFS distance, mismatches drop to 0/1602 by construction.
- Why this fix: This is not "Euclidean distance is broken" (it's provably correct for its actual job) nor "always use BFS distance" (needlessly expensive for pure pathfinding heuristics) — it's that a SHARED "distance" abstraction hides two different contracts (lower-bound-is-fine vs. must-approximate-actual-cost) behind one name and one value, and the fix is to stop sharing the value once the contracts diverge, using whichever source each specific consumer's correctness requirement actually needs.
- Rule of thumb: Before reusing a single computed value (distance-from-spawn, or any derived metric) across multiple consumers, check whether each consumer's correctness requirement is actually the SAME direction of approximation error — a value that's safe to underestimate (an admissible heuristic) and a value that must closely approximate ground truth (a difficulty/pacing gradient) are different contracts even when computed identically, and a working instance of the tolerant consumer provides NO evidence the strict consumer is also correct. Verify each consumer against its own ground truth independently, don't infer from one succeeding.
- Provenance (verified/assumed): VERIFIED first-hand — ran 100 trials confirming A* with a Euclidean heuristic finds the true-BFS-optimal path length in 100/100 cases, and separately sampled 1602 cell/trial pairs confirming 234 (14.6%) have >50% relative error between Euclidean and true BFS distance (max 86%), then confirmed 0/1602 mismatches once difficulty tiering is switched to the already-available true BFS distance.
