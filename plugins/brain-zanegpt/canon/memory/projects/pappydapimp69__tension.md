## E2 — t11 cheap 3d visual checks detection vs false alarm
- Date: 2026-10-10
- Project: Pappydapimp69/Tension
- Tags: [testing][harness][gamedev][3d]
- What: Measured, on a REAL headless-Chromium WebGL render (raw WebGL, readPixels, SwiftShader), which of the four defect classes named in tension T11 (wrong material, z-fighting, inverted normal, broken shader) cheap automated checks can catch, and the false-alarm rate on benign changes. 23 injected defect variants, 10 benign variations (anti-aliasing toggle, sub-pixel camera shifts, light and ambient tweaks of 3 to 5 percent, tessellation change, clear colour), 1 intentional content change. Checks: a "no errors" null check, channel-mean pixel stats, golden-image diff (exact bytes and mean-absolute-error thresholds), and a lighting-invariant suite (per-object chroma ratios, lighting correlation against a reference normal pass, decal-footprint fraction plus camera-jitter stability, sanity).
- Why built: T11 says a wrong material, z-fighting, an inverted normal or a broken shader all pass a "no errors" test and that perceptual diff against a golden image is brittle, but never measured either claim. Supports pole B of tension 'automated 3D verification has a ceiling (logic, not looks)' in part: cheap checks DO cover most of the four named classes in a purpose-built calibration scene, while the true ceiling is narrower and differently shaped than stated (luminance-only material changes, marginal z-fighting, and the requirement for a white-box reference scene). Pole A (a ceiling exists) is also supported for the null check and for golden diff.
- Design: One calibration scene (ground, a decal quad triangulated differently from the ground so it can fight, a lit sphere, a lit cube, per-face cube normals, one directional light plus ambient, output gamma applied once). Each case renders twice (second render has the camera yawed 0.004 rad) and gets one trusted reference pass (object ids in alpha, true normals in rgb, decal drawn at a safe offset). Defects: 6 material (swap, big/mid/subtle hue, luminance-only x0.8, default white), 5 z-fight (decal offsets 0 to 3e-3 at two camera distances), 5 inverted-normal (sphere, cube, cube top face only, sphere upper half, everything), 7 shader (compile error, NaN output, missing normalize, red/blue swap, light uniform unset, gamma twice, gamma missing). The invariant checks use quantities independent of light intensity and albedo scale: ln(R/G) and ln(B/G) equal ln(albedo ratio)/2.2 at any light level, and Pearson correlation of luminance with max(0, N.L) from the reference normals.
- Got right: Control renders are byte-identical when repeated (SwiftShader is deterministic here), so exact golden diff has no noise floor to hide behind. Null check caught 1/23 defects (the compile error), 0/10 false alarms: it catches no material, no z-fight, no normal defect. The lighting-invariant suite caught 18/23 (material 4/6, z-fight 3/5, inverted normal 5/5, shader 6/7) with 0/10 false alarms on benign variations and 0/1 on the content change, and caught the cube-top-only inverted normal that golden diff at MAE>1.0 missed (MAE 0.92). Single-light correlation against reference normals is a better inverted-normal detector than a mirrored-light pair, which is blind to a face whose lit amount is symmetric under the mirror.
- Where/why it failed: Golden diff by mean-absolute-error cannot be tuned to separate defects from benign changes: at MAE>1.0 it caught 17/23 defects with 5/10 false alarms; at MAE>2.0 it has 0/10 false alarms but only 15/21 visible defects (71%); the smallest visible-defect MAE (0.42, a far-camera z-fight) is below the largest benign MAE (1.97, a 5 percent light change). Exact-byte golden (the fingerprint pattern) catches 23/23 but false-alarms 10/10 benign variations. The invariant suite missed 5: the luminance-only albedo change (same hue, x0.8), a subtle hue shift, the missing-normalize shader (changes shading by about 0.03 MAE), and two marginal z-fights (under about 1 percent of pixels fighting) that stay below the footprint and jitter thresholds. Pre-registered prediction P2 (golden catches at least 20/23) was refuted: 17/23. A first-run harness flaw (object-level checks alarming where only one cube face was visible) was fixed and logged, not hidden.
- Fix: Do not rely on a "no errors" run or on a single golden threshold for 3D. Add (1) a purpose-built calibration scene with a reference id/normal pass, (2) invariant checks: chroma ratios against design albedo, luminance-vs-N.L correlation per object, decal footprint fraction plus a camera-jitter stability test for z-fighting, a flat/black sanity check, and (3) the compile/link status plus GL error check as the cheap shader gate. Mark an object-level check N/A (not an alarm) when the reference shows no shading variation. Keep screenshot capture for human review only for the residual class: luminance-only material changes, marginal z-fighting, and subtle shader drift.
- Why this fix: Invariants (log chroma ratio, correlation) remove the nuisance variables that make pixel diff brittle (light level, ambient, albedo scale), so tolerance can be tight where it matters; the camera-jitter test turns z-fighting from a look into a stability measurement. The price is a white-box scene: these checks need known geometry and design colours, so they cover a calibration scene, not arbitrary game content.
- Rule of thumb: Supports pole B of tension 'automated 3D verification has a ceiling (logic, not looks)', with a narrower ceiling: in a calibration scene with a reference pass, cheap invariant checks caught 18/23 injected defects (78 percent, 0/10 false alarms), versus 1/23 for a no-errors check and 17/23 with 5/10 false alarms for golden-diff at MAE>1.0, but luminance-only material changes, marginal z-fighting, subtle shader drift and anything outside a known calibration scene remain beyond them; treat these numbers as one renderer and an author-chosen defect and benign set, not a population rate.
- Provenance (verified/assumed): Verified first-hand: every number above comes from running the sandbox on headless Chromium with SwiftShader (24-bit depth buffer), twice with identical results; the checks, thresholds and the defect and benign sets were written by me.

## E1 — a resolution that narrates its transition reads as open
- Date: 2026-09-12
- Project: Pappydapimp69/Tension
- Tags: [tooling][process][testing]
- What: Two tension entries that had been explicitly resolved kept reporting as OPEN on every `brain query`, because the status reader scans a whole entry body for the first status marker in a fixed priority order and a resolution block narrates its own transition — "🔴 open -> 🟢 resolved" contains the red marker, so it classifies red forever.
- Why built: The ledger's own footer says "if you resolve it, flip the status to 🟢 and link the decision", and the established shape for that is an appended `### UPDATE ·` or `### <id> · RESOLUTION ·` block stating the transition. Writing the transition out is the natural and honest way to record it.
- Design: `entry_status(b)` is `next((m for m in STATUS_MARKS if m in b), "")` with `STATUS_MARKS = ("🔴","🟡","🟢","⚪")`. It is a substring scan over the ENTIRE block, ordered by severity rather than by position, and `brain query` warns `⚠ open fork` for anything it returns red.
- Got right: Measured the blast radius before touching the parser. Across 56 blocks in the ledger, switching the reader from first-mark to last-mark changes exactly ONE classification — and that one entry is genuinely open. So the reader was right and the prose was wrong; the fix belongs in the writing convention, not the code.
- Where/why it failed: Silently, and in the direction that costs most. A stale open fork is not a crash — it is a warning that keeps appearing, so the next agent either surfaces a settled decision to the user as if it were live, or learns to ignore the warnings. The pre-commit gate compounds it: `brain gate` refuses commits whose diff matches an open fork's keywords, so a resolved contradiction keeps demanding `BRAIN_ACK=` on every future commit that mentions its vocabulary. Both effects were observed first-hand in one session.
- Fix: Resolution blocks carry their own `Lean: 🟢 resolved (evidence, <date>)` line and never spell the red marker — "Status: open -> 🟢 resolved" rather than "Status: 🔴 open -> 🟢 resolved". The original entry's `Lean:` line is flipped to green in place with a pointer to the resolution block, and its original reading is kept verbatim below as the record.
- Why this fix: A severity-ordered scan is the RIGHT default for a document where an entry may carry several markers and the worst one should win — it fails safe. Making it positional to accommodate one prose habit would break that property for every entry that legitimately mentions a lesser status first. Changing the prose costs nothing and keeps the conservative reader.
- Rule of thumb: When a status field is mined from prose by substring scan rather than parsed from a designated line, narrating a state TRANSITION in that prose re-asserts the old state. Check what the reader actually does before assuming a status line is authoritative — and when a tool and a document disagree, measure how many entries a parser change would reclassify before reaching for the parser.
- Provenance (verified/assumed): Verified first-hand. Read `entry_status` in the Brain CLI, reproduced the misclassification on both entries, confirmed the fix by re-running `brain query reachability` and `brain query tutorial` (both warned before, neither warns after), and measured the 56-block reclassification count directly. The gate behaviour was hit in this session: one commit was refused against the already-resolved fork and another against its own resolution block.
