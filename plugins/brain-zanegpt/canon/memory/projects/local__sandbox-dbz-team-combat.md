## E5 — sandbox dbz team combat symmetric control catches turnorder bias
- Date: 2026-07-12
- Project: local/sandbox-dbz-team-combat
- Tags: [testing][gamedev][state]
- What: While verifying the defense-mitigation fix's effect on team balance, a symmetric 2v2 fight (two IDENTICAL rosters, same stats, same AI) was run as a control — expected outcome ~50/50 regardless of any balance parameter, since both sides are literally the same. At the baseline (no defense mitigation), the result was 25/15 in favor of one team — a real, measurable ~62.5%/37.5% split despite fully identical stat sheets on both sides.
- Why built: A sanity/control test, run specifically because a prior finding (a percent-max-HP cap producing 30/30 deterministic outcomes) raised the general question of whether the combat sandbox's own turn-order/targeting code might have hidden structural biases independent of the game-design parameters actually under test.
- Design: `makeSymmetricTeam('A')` and `makeSymmetricTeam('B')` construct byte-for-byte identical character rosters; turn order is computed each round via `Array.sort` on effective speed, and target selection resolves ties via `Array.sort` on HP percentage — both stable sorts, meaning exactly-tied values preserve original array/insertion order rather than being randomized.
- Got right: Running the control test at all (rather than assuming a "symmetric" setup is automatically bias-free) is what caught this — the effect wasn't visible from inspecting the code, only from actually running many trials and comparing the aggregate win rate against the null-hypothesis expectation (50/50).
- Where/why it failed: With identically-speed-valued characters, JavaScript's stable `Array.sort` preserves whichever team's characters were concatenated first in the turn-order array construction (`[...alive(teamA), ...alive(teamB)]`), giving team A a small but real first-strike advantage on every speed tie, which compounds over a multi-round fight into a measurable win-rate skew even between fully identical rosters.
- Fix: Not fixed in this sandbox (documented as a discovered artifact, not yet corrected) — the general fix for this class of bug is to break speed/priority ties with an explicit tie-breaker that doesn't correlate with turn/array order (e.g., a small deterministic per-character jitter derived from a seeded RNG, or alternating which team wins ties round-to-round) rather than relying on whatever order characters happen to be concatenated in.
- Why this fix: N/A — flagged as an open finding rather than a verified fix, since applying and re-verifying a specific tie-breaking scheme was out of scope for this round.
- Rule of thumb: When building any multi-agent/multi-character simulation with tie-prone sortable priority (speed, initiative, threat score), run a symmetric control test (identical participants on both "sides") BEFORE trusting an asymmetric test's results — a symmetric control should be statistically indistinguishable from 50/50, and if it isn't, the simulation's own tie-breaking/ordering code has a hidden bias that will silently distort every asymmetric result run through the same code path, not just the control.
- Provenance (verified/assumed): VERIFIED first-hand — ran the actual Node.js symmetric 2v2 sandbox across 40 seeds x 2 runs each (determinism check), directly measuring the win-rate split with identical rosters on both sides at DEFENSE_K=0.

## E4 — sandbox dbz team combat mitigation doesnt transfer across team size
- Date: 2026-07-12
- Project: local/sandbox-dbz-team-combat
- Tags: [gamedesign][gamedev][state]
- What: Having found a working pre-cap defense-mitigation fix for a lopsided 3v1 team fight (the companion E3 entry: DEFENSE_K~5 restores competitive uncertainty, 13 boss-deaths/17 team-wipes out of 30), this sandbox tested whether that SAME K value generalizes to a different attacker-count ratio — the same boss, the same two of three player characters, in a 2v1 fight instead of 3v1. It does not: at K=5 (competitive at 3v1), the 2v1 fight becomes heavily boss-favored (5 boss-deaths/25 team-wipes out of 30). Re-tuning specifically for 2v1 found K~3 restores a comparable competitive balance (12 boss-deaths/18 team-wipes) — a fully different value from the 3v1 sweet spot.
- Why built: A parameter found to "fix" a specific test configuration (3v1) risks being reported as solved when it may only be solved for that specific shape of encounter; this sandbox checked that assumption directly before treating the defense-mitigation fix as a general answer.
- Design: Reused the exact same character archetypes, boss stats, and mitigation formula from the 3v1 test, only changing which/how-many player characters were included (`makeTeamA2()` drops the Technician from `makeTeamA3()`), holding K fixed at the 3v1 sweet spot first, then re-sweeping K specifically for the 2v1 configuration.
- Got right: Testing the SAME K before re-tuning (rather than jumping straight to re-tuning) is what made the failure to generalize directly visible and measurable (5/30 vs the expected ~13/30), rather than just assuming re-tuning would obviously be needed and never actually confirming the magnitude of the mismatch.
- Where/why it failed: A fixed mitigation strength interacts with total attacker-side action economy and aggregate throughput, both of which scale with attacker count — the same K that exactly offsets 3 attackers' combined output overcorrects against only 2 attackers' combined output, because there is proportionally less raw damage for the SAME mitigation strength to reduce down to a competitive level. A static, single-value "defense" stat baked into a boss's stat sheet therefore cannot be simultaneously correct across every group size that boss might be fought at.
- Fix: Not resolved in this sandbox as a general implementation pattern — the concrete numeric result (K~5 for 3 attackers, K~3 for 2 attackers) suggests two directions worth trying in a real implementation, neither yet verified: (a) per-encounter-authored defense values, tuned individually for each specific fight's expected attacker count, accepting the design overhead; or (b) a dynamically-scaling mitigation term that reads the CURRENT number of living opposing attackers each round (directly available to the combat resolver already, since it's needed for other team-fight logic) rather than a single static defense stat.
- Why this fix: Both candidate directions are flagged rather than verified because this sandbox only characterized the FAILURE to generalize, not tested either fix — recording the open question honestly is more useful to a future session than asserting an untested resolution.
- Rule of thumb: A balance parameter (damage-cap fraction, mitigation strength, or similar) verified to work in one specific encounter shape (a specific attacker:defender ratio) should not be assumed to transfer to a different encounter shape without re-verification — re-test the SAME parameter value first (to measure the actual size of the mismatch) before re-tuning, since the mismatch magnitude itself is useful data about how sensitive the system is to encounter shape.
- Provenance (verified/assumed): VERIFIED first-hand — ran the same Node.js combat sweep (30 seeds x 2 runs each) comparing 3v1 and 2v1 configurations at matched K values and at re-tuned K values, directly measuring the shift in boss-death/team-wipe rate.

## E3 — sandbox dbz team combat defense mitigation fix
- Date: 2026-07-12
- Project: local/sandbox-dbz-team-combat
- Tags: [gamedesign][gamedev][state]
- What: Following up on the prior finding that neither scaling a percent-max-HP damage cap by attacker count nor matching action economy fixes a deterministically lopsided 3v1 team fight (boss loses 30/30 seeds either way), this sandbox tested the fix flagged as "next thing to verify": wiring the previously-unused `defense` stat into the damage formula as a PRE-CAP mitigation term (`mitigatedDamage = rawDamage * attackerPower / (attackerPower + defenderDefense * K)`, a standard armor-formula shape), holding the original safe 0.2 cap fraction fixed. Unlike the two previously-tried fixes, this one worked: sweeping the mitigation strength K found a real transition from "team always wins" (K=0-3: 30/30 boss deaths) through a genuine competitive zone (K=4: 24 boss-deaths/6 team-wipes; K=4.5: 21/9; K=5: 13/17; K=5.5: 13/17) to "boss now favored" (K=6: 9/30 boss-deaths, 21 team-wipes).
- Why built: The prior round's two fix attempts (cap-scaling, action-economy parity) both failed for the same underlying reason — a percent-of-defender-max-HP cap structurally rewards attacking high-max-HP targets with bigger absolute hits — and this sandbox tested whether decoupling tankiness from raw HP pool size (via a genuine pre-cap mitigation stat) fixes what raw-HP-based approaches couldn't.
- Design: `mitigated = rawDamage * (attackerPower / (attackerPower + defenderDefense * DEFENSE_K))`, applied before the existing `min(mitigated, defenderMaxHP * 0.2)` cap; K swept from 0 to 6 in increments, 30-seed sweeps with per-seed determinism verification at each K value.
- Got right: Sweeping a continuous parameter (K) rather than testing one fixed value made the SHAPE of the fix visible — it's not a step function or a shallow gradient, it's a real transition zone spanning roughly K=3 to K=6 in this specific stat configuration, which is the kind of detail a single before/after test would have missed entirely.
- Where/why it failed: N/A for this entry — this documents a working fix, not a failure. (See the companion entry filed alongside this one for where the fix's generalization DOES fail.)
- Fix: Wire `defense` into a pre-cap mitigation formula rather than leaving it unused (as the prior round's E2 entry documented) or relying on raw HP-pool size for tankiness (which the prior round's E1 entry showed backfires under a percent-max-HP cap).
- Why this fix: Pre-cap mitigation reduces the RAW damage value before the percent-max-HP cap ever sees it, so it operates on a different axis than the cap (which bounds a hit's damage RELATIVE to the target's max HP) — the two mechanisms are complementary rather than redundant: mitigation determines how much of an attacker's raw output actually becomes "raw damage," and the cap then bounds how much of THAT can land in one hit relative to the target's own HP. Neither mechanism alone can do the other's job (confirmed by the prior round's cap-scaling and action-economy tests both failing).
- Rule of thumb: When a percent-max-HP damage cap makes a high-HP "tank" character take proportionally bigger hits (a real, verified failure mode from the companion E1 entry), the fix is a genuine pre-cap mitigation/defense stat, not further tuning of the cap fraction itself or the attacker/defender action count — but expect the mitigation strength to have a real, possibly narrow, transition zone that needs to be found by sweeping the parameter, not assumed from a single guessed value.
- Provenance (verified/assumed): VERIFIED first-hand — ran the actual Node.js 3v1 combat sweep across 30 seeds x 2 runs each (determinism check) for 8 distinct K values (0, 1.5, 3, 4, 4.5, 5, 5.5, 6), directly measuring boss-death rate and team-wipe rate at each.

## E2 — sandbox dbz team combat unused stat axis
- Date: 2026-07-12
- Project: local/sandbox-dbz-team-combat
- Tags: [state][gamedev]
- What: A combined sandbox modeled a multi-axis character stat system (power/speed/technique/defense, each with per-transformation-tier multipliers) specifically to test whether decoupling axes preserves a lower-power character's ability to win specific exchanges via a niche stat (the "multi-axis progression" idea from prior research). The `defense` axis was fully modeled — it had a base value, a per-tier multiplier, and participated in `effectiveStats()` — but was never actually read by the damage-resolution code; the combat loop's `rawDamage` calculation used only `stats.power`, so every character's `defense` value had zero effect on any fight outcome despite looking fully wired up.
- Why built: N/A — this was discovered as a side effect of investigating why a "tank" boss character (high defense stat, high max HP) still lost 30/30 team-fight simulations; the investigation into WHY revealed defense wasn't being consumed anywhere.
- Design: `effectiveStats(c)` computes `{power, speed, technique, defense}` from base stats and the character's current transformation tier multiplier, returning all four fields — the object looks complete and every field is populated with plausible, tier-scaled numbers. The damage-dealing code path (`takeAction()`) destructures `stats.power` only and never references `stats.defense`.
- Got right: N/A (this is the bug report, not a success).
- Where/why it failed: A stat object that returns all four expected fields with correct-looking, tier-scaled values gives no signal that one of those fields is dead code — there is no missing-field error, no NaN, no crash, just a stat that silently never influences outcomes. This is exactly the kind of gap that survives casual code review (the field is declared, computed, and even printed in debug output) and only surfaces through behavioral investigation (e.g., "why doesn't giving this character more defense change anything") rather than static inspection.
- Fix: Not yet applied in this sandbox (documented as the next thing to verify, not yet re-tested) — the general fix is to explicitly wire `defense` into the damage-resolution formula (e.g., `rawDamage = attackerPower - defenderDefense * mitigationFactor`, applied before any damage cap) and, more generally, to add a unit-level check that every declared stat axis is actually referenced somewhere in the resolution path before treating a "multi-axis" stat system as complete.
- Why this fix: A stat axis's mere existence in a data structure provides no functional guarantee it affects gameplay — only an explicit read-site in the resolution logic does, and the more axes a stat system has (this one has four), the easier it is for one to be added to the data model, threaded through tier-multiplier computation, and never actually connected to an outcome.
- Rule of thumb: When building or reviewing a multi-axis stat system, don't trust that a stat "exists and looks populated" as evidence it's load-bearing — grep the actual damage/outcome-resolution code for each stat name specifically and confirm each one is read somewhere, especially for axes (like defense/mitigation) that are easy to compute and display but easy to forget to apply at the point damage is actually calculated.
- Provenance (verified/assumed): VERIFIED first-hand — found by grepping the sandbox's own damage-resolution code (`grep "rawDamage = stats.power"`) after a team-fight simulation raised the question of why a high-defense boss character still lost every trial; confirmed `defense` never appears on the right-hand side of any damage calculation in the sandbox.

## E1 — sandbox dbz team combat cap doesnt generalize
- Date: 2026-07-12
- Project: local/sandbox-dbz-team-combat
- Tags: [gamedesign][gamedev][state]
- What: A prior sandbox (local/sandbox-power-scaling) verified that capping per-hit damage at a fixed percentage of the DEFENDER's max HP fixes the 1v1 one-shot problem across DBZ-typical power ratios (flat 5-turn fights from 1x to 100,000x). This sandbox extended the same fixed 20%-of-max-HP cap, unchanged, to a 3-vs-1 team fight (three player characters vs one boss, the canonical "everyone attacks the overwhelming threat together" DBZ scenario) and found it produces a DETERMINISTICALLY lopsided outcome: the boss lost 30/30 seeds, with near-zero variance in fight length (stddev 0.49 rounds) — not a close fight with some randomness, a guaranteed loss every time.
- Why built: The 1v1 fix was verified sound in isolation; this sandbox tested whether it survives the natural next step of a real DBZ-style game (group fights are common — "everyone pile on Frieza/Cell" is a recurring trope), rather than assuming a fix verified in one configuration generalizes to a structurally different one.
- Design: `simulateFight()` runs a turn-based 3v1 combat loop (speed-sorted turn order, sticky target selection per the earlier flee-AI hysteresis lesson, ki-gated transformations, ki-blast vs melee action choice) with the SAME `resolveDamage()` percent-max-HP-cap function from the prior sandbox. Two follow-up variants were tested to find a fix: (a) dividing the cap fraction by the number of living opposing attackers each round, and (b) giving the boss extra actions per round to match the team's total action count (restoring 1:1 action-economy parity), both while holding the original "safe" 0.2 cap fraction.
- Got right: Isolating the two candidate fixes (cap-scaling vs action-economy parity) and testing each in controlled sweeps (30 seeds x 2 runs each for determinism) against the same fixed boss/team stat baseline made the actual mechanism visible rather than just observing "team fights are unbalanced" as an unexplained fact.
- Where/why it failed: Neither candidate fix restored genuine competitive uncertainty at the original safe cap fraction. Dividing the cap by attacker count (0.2/3) just slowed the SAME deterministic loss (mean fight length 5.6->8.0 rounds, boss deaths still 30/30, variance if anything LOWER at 0.18 stddev) — because the real driver is action-economy asymmetry (3 actions/round vs 1), not per-hit damage magnitude, so scaling per-hit damage down proportionally just stretches out an equally-certain outcome. Restoring action-economy parity (boss gets 3 actions/round to match 3 living attackers) also failed to fix it (still 30/30 boss deaths, mean round only inching to 6.8) because of a DEEPER structural issue: a cap defined as a percentage of the DEFENDER's OWN max HP means a higher-max-HP "tank" character (the 1800-HP boss) has a per-hit damage ceiling 3.6x-5.1x LARGER in absolute terms than the squishier 350-500 HP player characters, purely because 20% of a bigger number is a bigger number — so giving a boss more HP to feel "tankier" perversely makes every attacker's capped hit against it larger too, undermining the intended tankiness. Only substantially RAISING the cap fraction (0.5-0.65, well above the "safe" 1v1 value) reintroduced real uncertainty (25/30 and 26/30 boss deaths, team wipes appearing, stddev jumping to ~1.75) — at the direct cost of reintroducing bigger individual swings/one-shot risk for the smaller-HP-pool player characters, the exact problem the cap was built to prevent in the first place.
- Fix: Not resolved in this sandbox — flagging as an open problem rather than a false "fixed." The three approaches tried (flat cap, attacker-count-scaled cap, action-economy parity) all failed to produce competitive uncertainty at a "safe" cap fraction; only raising the cap fraction worked, and only by reintroducing the original risk for other participants. A real fix likely needs to decouple "how tanky does a defender feel" from "how much raw max HP does it have" (e.g., a defense/mitigation stat applied BEFORE the cap, so tankiness comes from damage reduction rather than a bigger HP pool that paradoxically invites bigger capped hits) — untested in this round, flagged as the next thing to verify.
- Why this fix: N/A — this entry documents a verified negative result (three plausible fixes tried and empirically falsified) plus the root-cause mechanism, not a working fix, because shipping a false "fixed" claim here would be worse than an honest "still open."
- Rule of thumb: A combat-balance fix verified in one configuration (1v1) does not automatically transfer to a structurally different configuration (N-vs-1) — verify separately rather than assuming, and when re-verifying, distinguish between damage-MAGNITUDE fixes (scaling a cap) and ACTION-ECONOMY fixes (matching turn counts), because they address different mechanisms and neither alone fixed this case. Separately: a percentage-of-DEFENDER's-own-max-HP damage cap has a structural blind spot — it rewards attacking high-max-HP targets with proportionally bigger absolute hits, which actively fights against "give the tank more HP" as a tankiness lever; if a game's damage system uses this kind of cap, tankiness should come from a pre-cap mitigation/defense stat, not from raw HP pool size.
- Provenance (verified/assumed): VERIFIED first-hand — ran the actual Node.js 3v1 combat sandbox across 30 seeds x 2 runs each (determinism check) for the baseline and both candidate fixes, directly measuring boss-death rate, team-wipe rate, mean fight length, and fight-length variance for each variant; the tank-punishment mechanism (3.6x-5.1x cap-ceiling asymmetry) was confirmed directly by arithmetic from the sandbox's own stat values, not estimated.
