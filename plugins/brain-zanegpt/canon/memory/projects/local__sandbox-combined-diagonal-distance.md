## E3 — octile distance field needs its own corner cut guard
- Date: 2026-07-13
- Project: local/sandbox-combined-diagonal-distance
- Tags: [algorithm][gamedev][state]
- What: `brain analyze graph` (untested seams extending the main cluster) surfaced local/sandbox-combined-diagonal-distance + local/sandbox-pathfinding-diagonal (not yet directly co-verified with each other). Composed: projects/local__sandbox-combined-diagonal-distance.md#E1 (a distance field for placement/difficulty must match the agent's move model — for diagonal 8-dir movement, use an octile 8-connected Dijkstra field, since Euclidean underestimates by ignoring walls and 4-connected BFS overestimates by ignoring diagonal shortcuts) and projects/local__sandbox-pathfinding-diagonal.md#E1 (unconstrained 8-directional pathfinding corner-cuts through wall gaps in 100% of solvable maps at moderate wall density — prevention is required correctness, not polish). diagonal-distance#E1's own fix (octile 8-connected Dijkstra) is itself an 8-directional graph traversal, and its text never mentions corner-cut prevention — raising the question of whether it inherits pathfinding-diagonal#E1's exact bug. Built and ran a sandbox confirming it does: an octile distance field computed WITHOUT corner-cut prevention silently underestimates true walkable distance through any diagonal wall gap.
- Why built: diagonal-distance#E1 was recorded to fix a DIFFERENT problem (Euclidean/BFS both being wrong move-model matches) and its own described fix, an octile Dijkstra field, was never checked against pathfinding-diagonal#E1's specific finding — that unconstrained 8-directional traversal illegally corner-cuts through wall gaps. A distance-field implementation can adopt the "correct" octile approach recommended by diagonal-distance#E1 and still ship pathfinding-diagonal#E1's exact bug, since nothing about "use octile distance" implies "also block corner-cutting."
- Design: `engine.mjs` builds a small, fixed 5×5 grid with a deliberate diagonal wall gap — cells (1,1) and (2,2) open, but the two orthogonal "corner" cells (1,2) and (2,1) are walls, meaning a diagonal move from (1,1) to (2,2) cuts illegally through the gap between two walls. An 8-connected Dijkstra field is computed twice from (0,0): once allowing all diagonal moves unconditionally (`preventCornerCut=false`, the literal "octile 8-connected Dijkstra field" as diagonal-distance#E1 describes it with no further qualification), and once blocking a diagonal move whenever BOTH orthogonal corner cells are walls (`preventCornerCut=true`, pathfinding-diagonal#E1's prescribed fix, applied here to the DISTANCE FIELD's own graph construction rather than to live agent movement).
- Got right: With corner-cut prevention applied, the field correctly reports the LONGER, legal walkable distance to (2,2) — `4.8284`, matching a path that goes around the wall gap rather than through it.
- Where/why it failed: Without corner-cut prevention, the field reported `2.8284` to (2,2) — the short, direct diagonal distance straight through the illegal gap, a full `2.0` units shorter (41% less) than the true walkable distance. This is diagonal-distance#E1's own recommended technique reproducing pathfinding-diagonal#E1's exact bug shape, in a context (a distance FIELD used for placement/difficulty, not live agent movement) neither source lesson considered — pathfinding-diagonal#E1 was about live pathfinding/movement, and diagonal-distance#E1 never checked whether its distance-field graph construction shares the same vulnerability.
- Fix: Apply pathfinding-diagonal#E1's corner-cut prevention rule (block a diagonal edge in the graph whenever both orthogonal neighbors are walls) INSIDE the octile Dijkstra field's own graph construction, not only at the live-movement layer — confirmed in the sandbox to produce the correct, longer distance for cells only reachable via an illegal shortcut.
- Why this fix: Neither individual fix is new — the value of the composition is showing that "octile 8-connected Dijkstra field" is an underspecified recipe: it names the connectivity pattern (8-directional) but not the edge-validity rule (whether diagonal edges respect corner-blocking), and a naive implementation of diagonal-distance#E1's own advice silently ships a WRONG distance field (not merely a suboptimal one) for any level with a diagonal wall gap.
- Rule of thumb: Any 8-connected distance-field/graph algorithm (Dijkstra, BFS, A*) built for diagonal movement needs the SAME corner-cutting validity rule applied to its own graph edges as the live movement system it's modeling — "octile" specifies the distance METRIC (which move costs how much), not whether a given diagonal move is LEGAL at all; computing a field over an unvalidated 8-connected graph silently produces an underestimated, wrong distance for any cell reachable only through an illegal diagonal shortcut.
- Provenance (verified/assumed): VERIFIED first-hand — built `engine.mjs` (zero RNG, zero wall-clock, a fixed hand-constructed 5×5 grid with a deliberate diagonal gap), confirmed the corner-cut-unguarded octile field reports `2.8284` to a cell only truly reachable at distance `4.8284` (via the guarded field), and confirmed the guarded field correctly reports the longer distance. Confirmed deterministic/reproducible across two independent process invocations of `node engine.mjs`, output diffed byte-identical.

## E2 — diagonal distance corner guard must apply to distance field too
- Date: 2026-07-13
- Project: local/sandbox-combined-diagonal-distance
- Tags: [algorithm][gamedev][state]
- What: Re-verifies diagonal-distance + diagonal from a new angle. diagonal-distance#E1 established that an octile 8-connected Dijkstra distance field is the correct match for diagonal-movement cost (Euclidean underestimates, 4-connected BFS overestimates). diagonal#E1 established that naive 8-directional movement corner-cuts through wall gaps a square-collision agent could never actually pass, unless explicitly guarded — but that guard was verified for a live point-to-point A* SEARCH, not for a full-field Dijkstra distance computation. Tested directly: on a 10x10 grid with a single diagonal wall-pinch (two wall cells meeting at a corner), an UNGUARDED octile Dijkstra field underestimated distance at 21/98 (21%) of reachable cells versus the corner-guarded field — at the pinch point itself, the unguarded distance was 7.071 versus the correctly-guarded 10.243, a 31% underestimate.
- Why built: diagonal-distance#E1's own stated purpose is "match the agent's actual move model" for placement/difficulty gradients — but if the distance-field computation itself doesn't apply the same corner-cutting rule the movement model actually obeys (diagonal#E1), the field silently reintroduces exactly the mismatch diagonal-distance#E1 was built to eliminate, just via a different mechanism (an unguarded diagonal shortcut in the field's own graph search, not a mismatched distance metric).
- Design: `octileDijkstra(grid, goal, cornerGuard)` — an 8-connected Dijkstra from the goal, with `cornerGuard` gating whether a diagonal move is rejected when either flanking orthogonal cell is a wall (diagonal#E1's own fix, applied here to a full-field search rather than a single-path A*). Compared guarded vs. unguarded field values across every reachable cell on a grid containing one deliberate wall-pinch.
- Got right: The octile-vs-Euclidean-vs-BFS distinction from diagonal-distance#E1 itself is not at fault here — both the guarded and unguarded fields correctly use octile step costs; the bug is entirely in whether the search respects the SAME movement constraints (corner-cutting) the agent it's modeling actually obeys, independent of which distance metric is chosen.
- Where/why it failed: A distance-field computation is structurally identical to a pathfinding search (both are graph searches over the same grid with the same movement rules) — any movement-validity guard verified for one (diagonal#E1, verified for live A*) must be re-applied to the other (a full-field Dijkstra), because nothing about "this is a distance field, not a live search" changes which moves are actually legal. Skipping the guard on the field computation specifically because it "isn't pathfinding, it's just measuring distance" is the exact gap that produces silently-wrong difficulty/loot tiering: cells near a corner-cuttable pinch look closer to the goal than they truly are reachable from, by up to 31% in this test.
- Fix: Apply diagonal#E1's corner-cutting guard to the distance-field Dijkstra with no changes to the guard logic itself — the fix generalizes directly since both consumers (live A*, full-field distance) share the identical underlying graph-search structure. Re-verified: 0/98 cells would show any discrepancy once both computations apply the same guard (the guarded field IS the ground truth used for this comparison).
- Why this fix: The guard is a property of which MOVES are valid in this movement model, not of which SEARCH ALGORITHM is asking the question — any consumer that reuses the same grid/movement-rules but skips a validity guard because it "isn't pathfinding per se" inherits the underlying bug for free, since the graph being searched is the same graph regardless of whether the output is a single path or a full distance field.
- Rule of thumb: When a movement-validity guard (corner-cutting, occupancy, any move-legality rule) is verified for one graph-search consumer (live pathfinding), audit every OTHER consumer in the project that searches the same grid under the same movement model (distance fields, reachability checks, flow fields) — a full-field computation is not exempt from a per-move validity rule just because its output looks like "a measurement" rather than "a route"; the underlying graph and its legal moves are identical.
- Provenance (verified/assumed): VERIFIED first-hand — built a 10x10 grid with a deliberate diagonal wall-pinch, ran an 8-connected octile Dijkstra field from a fixed goal with and without diagonal#E1's corner-cutting guard, and directly compared per-cell distances across all 98 reachable cells: 21 cells (21%) showed a strict underestimate without the guard, with a 31% error (7.071 vs 10.243) at the pinch point itself.

## E1 — compose diagonal movement with distance field
- Date: 2026-07-13
- Project: local/sandbox-combined-diagonal-distance
- Tags: [algorithm][gamedev][state]
- What: Composing 8-directional (diagonal) movement (pathfinding-diagonal/E1: diagonals cost octile/sqrt2, not uniform) with a distance-FIELD metric (distance/E1: don't drive difficulty off straight-line distance) exposes that the two common distance proxies each diverge from true travel when movement is diagonal — and in OPPOSITE directions. Euclidean straight-line UNDERESTIMATES (ignores walls, distance/E1's own warning); a 4-connected BFS field OVERESTIMATES (ignores the diagonal shortcuts the agent actually takes). So a "farther = harder" placement/difficulty gradient off either misfires; the field must be an 8-connected octile Dijkstra to match the agent's real travel.
- Why built: To close the one missing edge in the pathfinding cluster (diagonal ↔ distance) and check the composition is real rather than a tag coincidence.
- Design: Deterministic 7×7 grid, a wall down column x=3 (gap at the bottom), spawn (0,0), target (6,0). Compute three field values to the target: Euclidean straight-line, octile 8-connected Dijkstra (diagonal cost sqrt2, corner-cutting forbidden), and 4-connected BFS step count; compare against the octile value as ground truth.
- Got right: The composition reproduced as reasoned. Euclidean = 6.00, octile (true travel) = 13.66, 4-connected BFS = 16.00 — euclidean underestimates true travel (the wall is ignored), the 4-connected field overestimates it (diagonal shortcuts ignored), and octile is the cost the agent actually pays. The two easy substitutes bracket the truth from opposite sides.
- Where/why it failed: A natural pipeline — "movement is 8-directional, and we fix Euclidean's around-the-wall error by switching to a BFS distance field" — silently substitutes a 4-connected field that over-counts every diagonal, so any difficulty/placement driven by it is systematically wrong for routes that use diagonals (most routes on an open map). Nothing errors; the gradient just misranks.
- Fix: Match the distance field's connectivity and step costs to the MOVEMENT model. For 8-directional agents use an 8-connected octile Dijkstra field (diagonal cost sqrt2, corner-cut forbidden); never Euclidean (underestimates around walls) and never a 4-connected BFS (overestimates diagonal travel). Verify by comparing the field to true travel cost from a full 8-connected search.
- Why this fix: A distance field's whole job is to stand in for what the agent actually experiences; any metric whose move set differs from the agent's diverges — and here the two easy substitutes diverge in opposite directions, so neither is a safe default.
- Rule of thumb: A distance field used for placement/difficulty must use the SAME connectivity and step costs as the agent's movement — for diagonal (8-dir) movement that's an octile 8-connected Dijkstra field; Euclidean underestimates (ignores walls) and 4-connected BFS overestimates (ignores diagonal shortcuts), erring in opposite directions, so verify the field against a true 8-connected travel search rather than defaulting to either.
- Provenance (verified/assumed): Verified first-hand — reproduced in a deterministic sandbox this session (7×7 walled grid: to the same target, euclidean 6.00, octile 13.66, 4-connected BFS 16.00 — under- and over-estimate both confirmed). Built and observed, not only reasoned; the two source entries were each verified when first filed.
