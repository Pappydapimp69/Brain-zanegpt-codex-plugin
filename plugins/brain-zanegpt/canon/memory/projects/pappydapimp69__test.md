## E24 — playwright frame edge invisible to per frame sampling
- Date: 2026-07-13
- Project: pappydapimp69/test
- Tags: [testing][determinism][gamedev][harness]
- What: `brain train combined` surfaced dog + the-game-prologue as an untested seam (shared: browser, determinism, gamedesign, gamedev, harness, input, process, state, testing, tooling, ui). Composing their recorded lessons — not a new build — projects/pappydapimp69__dog.md#E22 (a headless rAF slowdown ratio is not a stable constant, and a virtual-clock API can fire rAF callbacks correctly on a trivial loop while still failing to drive a real engine's own `Clock.getDelta()`/dt bookkeeping) and projects/pappydapimp69__the-game-prologue.md#E2 (Playwright's instant keypresses have zero real duration, so a press shorter than one frame is invisible to code that only samples held-key state once per frame) turn out to be the SAME defect shape applied to two different per-frame assumptions.
- Why built: Neither lesson's own single-system tests could see the higher-order pattern — dog#E22 was found testing timing/clock code with no keyboard input path in scope, and the-game-prologue#E2 was found testing input handling with no dependency on a virtual/mocked clock. Only reasoning about them together, as the seam brain train flagged, surfaces that they're one bug class, not two unrelated ones.
- Design: Both lessons describe something the engine's per-frame update loop implicitly assumes is "sampled every frame, therefore always observed": a currently-held key (the-game-prologue#E2) or the passage of real time (dog#E22). Playwright doesn't move through frames the way a human at a real keyboard or a real un-mocked browser clock does — it can fire a keydown+keyup pair with zero elapsed real time between them (falling entirely between two sampled frames), and its `page.clock` virtual-clock API can advance its OWN reported time while never actually driving the engine's internal dt accumulator, because "fires rAF" and "advances the engine's own delta-time bookkeeping" are only coupled if the engine's Clock class is wired to read from that same virtual source.
- Got right: Each lesson's own fix is already correct in isolation and composes without conflict: dog#E22's fix (poll for the actual state transition; verify a virtual clock drives the engine's own dt with a cheap per-frame probe before trusting it) and the-game-prologue#E2's fix (capture presses at event time into a pending queue, not by sampling held state) touch different subsystems (clock vs. input) and can both be applied to the same game without one undermining the other.
- Where/why it failed: Composed, the shared root cause is that an automated headless harness (Playwright specifically) is not just "faster" than a human tester — it violates the frame-granularity assumption itself, either by acting between frames (instant keypress) or by decoupling reported time from the engine's real tick source (mocked clock that doesn't actually drive `getDelta()`). A test suite that only guards ONE of these two edges (e.g. queued input, but still trusting `page.clock` at face value, or vice versa) still has an untested frame-boundary blind spot, because the two lessons were recorded from two different systems that never shared a test run.
- Fix: When writing a Playwright-driven determinism/regression test for any per-frame game system, treat BOTH frame-boundary edges as guilty until proven innocent in that specific harness: (1) input — capture presses via an event-time queue (projects/pappydapimp69__the-game-prologue.md#E2), never per-frame held-state sampling, whenever the test may synthesize a keypress; (2) time — before trusting a virtual/mocked clock to drive a timing-sensitive assertion, add a minimal per-frame probe confirming the engine's OWN dt/frame counter actually advances under it, not just that rAF fires (projects/pappydapimp69__dog.md#E22).
- Why this fix: Neither fix is novel — each was already verified correct on its own project. The value of composing them is knowing to apply BOTH checklist items together the first time a Playwright test touches a new project's input+timing code, instead of discovering the second one only after a second, independent flaky-test investigation.
- Rule of thumb: A Playwright-driven test for a real-time game loop must distrust the frame boundary in both directions at once — an instantaneous synthetic keypress that can occur and release inside a single simulated frame, and a virtual/mocked clock whose reported time may diverge from the engine's own accumulated dt — and add an explicit probe for each before trusting a new headless timing-sensitive test.
- Provenance (verified/assumed): ASSUMED — this is a reasoned composition of two independently VERIFIED first-hand lessons (dog#E22, the-game-prologue#E2), rather than a fresh first-hand test in its own right; the higher-order claim (both are the same defect shape) is a reasoned synthesis that remains untested against a concrete case where both edges were mishandled together in one test run.

## E23 — discrete seek sweep blind to fractional frame scrub
- Date: 2026-07-13
- Project: pappydapimp69/test
- Tags: [testing][animation][determinism][gamedev]
- What: `brain train edge` (draft + test, shared=12 tags). Composed: projects/pappydapimp69__test.md#E13 (verify a time-based renderer with a FULL SEEK-SWEEP, not a few sample frames — reused draw helpers silently diverge on shared constant names) and projects/pappydapimp69__draft.md#E7 (scrub-safety needs specific state to be a PURE FUNCTION OF ELAPSED TIME, bit-identical under scrub vs continuous playback). Sandbox-confirmed test#E13's "full seek-sweep," when implemented as a sweep over discrete FRAME INDICES (the natural, common implementation), can pass with zero mismatches while draft#E7's guarantee still fails at a fractional-frame scrub position — a real elapsed time a player can genuinely reach that the discrete sweep never tests.
- Why built: test#E13 doesn't specify what "full" means for the sweep — the natural, cheap implementation is "every frame index 0..N," which sounds exhaustive but only covers elapsed times that are exact multiples of the frame duration. draft#E7's actual guarantee is about ANY elapsed time (continuous), since a real scrub UI (a transport bar, a seek-to-timestamp API) isn't constrained to land exactly on frame boundaries.
- Design: `sandbox.py` — zero RNG, zero wall-clock. `pure_rotation_buggy(elapsed)` looks like a draft#E7-style pure function but internally rounds elapsed time to the nearest frame index before computing (`frame_index = round(elapsed/FRAME_DT); quantized_elapsed = frame_index*FRAME_DT`) — invisible at exact frame boundaries, where the rounding is a no-op. `pure_rotation_continuous(elapsed)` is the true continuous version with no quantization. Ran a test#E13-style full sweep over 10 discrete frame indices (0..9) comparing both functions, then evaluated both at one deliberately non-frame-aligned time (`3.5 * FRAME_DT`, halfway between frame 3 and frame 4).
- Got right: The discrete seek-sweep is not USELESS — it did correctly verify agreement at all 10 tested frame-aligned points, and would have caught any bug that broke agreement AT frame boundaries specifically (the class of bug test#E13 was originally filed against — reused draw helpers diverging on shared constants).
- Where/why it failed: The full frame-index sweep reported zero mismatches (`[]`) — a clean pass — while the fractional-frame scrub at `t≈0.1167` returned `buggy=12.0` vs `continuous=10.5`, a real divergence the sweep never had a chance to detect because it only ever evaluated exact multiples of the frame duration.
- Fix: Not applied to any shipping code (composition/flagging entry). test#E13's "full seek-sweep" needs an explicit note: sweeping discrete frame indices verifies frame-boundary agreement only — if the scrub UI (or any consumer) can reach non-frame-aligned elapsed times, the sweep must ALSO sample at least one fractional/off-boundary point per tested interval, not just the frame indices themselves.
- Why this fix: test#E13 and draft#E7 were each correct for what they described — test#E13's sweep is real, additional coverage over "a few sample frames," and draft#E7's pure-function requirement is the right design goal. The gap is only that "full" sweep coverage was never defined precisely enough to guarantee draft#E7's continuous-time claim, so a future session implementing "full seek-sweep" per test#E13 could reasonably (and incorrectly) implement exactly the frame-index-only version this sandbox shows is insufficient.
- Rule of thumb: A "full seek-sweep" verification (test#E13) that only samples discrete frame indices verifies frame-boundary correctness, not draft#E7's actual continuous-time guarantee — if scrub/seek can reach non-frame-aligned elapsed times, the sweep must include at least one fractional/off-boundary sample per interval, not just the frame indices, or a quantization bug invisible at every tested boundary can still reach players.
- Provenance (verified/assumed): Verified first-hand — built `sandbox.py` (zero RNG, zero wall-clock, 10-frame discrete sweep plus one deliberately fractional scrub point), confirmed the discrete sweep passes with zero mismatches while the fractional-frame scrub diverges (12.0 vs 10.5). Confirmed deterministic/reproducible across two independent process invocations of `python3 sandbox.py`, output diffed byte-identical.

## E22 — wrong iframe window invisible to incidental fingerprint
- Date: 2026-07-13
- Project: pappydapimp69/test
- Tags: [testing][determinism][gamedesign]
- What: `brain train edge` (untested seams) surfaced pappydapimp69/test + pappydapimp69/the-game-wrong-sky (shared=9 tags: determinism, gamedesign, gamedev, harness, input, mobile, process, state, testing). Both projects independently arrived at the identical i-frame architecture (withhold the command, don't flag the state) — a strong REINFORCING composition — but wrong-sky#E9 adds an untested claim neither project's own text demonstrates concretely: that the replay/determinism fingerprint specifically CANNOT catch a wrong i-frame window length. Built and ran a sandbox verifying that claim precisely, rather than accepting it on the strength of the architectural reinforcement alone.
- Why built: test#E4 records the architecture (withhold, don't flag) without commenting on test coverage; wrong-sky#E9 asserts the fingerprint blind spot but doesn't show a concrete case where a WRONG window survives a real playthrough-style fingerprint. Simply noting "these two lessons say the same thing" would be a weak composition — the sandbox instead tests wrong-sky#E9's strongest, least obvious claim directly.
- Design: `engine.mjs` implements the shared architecture as a pure reducer (`reduce(state, command)`: `ENEMY_STRIKE` always applies -10 hp if dispatched, no invuln flag anywhere in `state`) plus a presentation-layer seam (`seamDecide`) that withholds `ENEMY_STRIKE` during an i-frame window after a dodge. Two window lengths are compared: `INTENDED_WINDOW=5` vs. a bug, `BUGGY_WINDOW=3`. Scenario A replays a fixed, "incidental" playthrough script that attempts strikes at ticks 2 and 8 (before the dodge fully registers, and long after even the correct window has expired) — the kind of script an ordinary smoke-test playthrough would produce. Scenario B replays a DELIBERATE, targeted seam-level probe at tick 5 (distance 3 from the dodge start at tick 2) — chosen specifically because distance 3 falls inside the intended 5-tick window (withheld, no damage) but outside the buggy 3-tick window (3 is not `< 3`, so the strike is dispatched, damage applied).
- Got right: The shared architecture itself is confirmed sound in both scenarios — whichever window length is in effect, the reducer stays a pure function of dispatched commands with no invuln flag anywhere in state, exactly as both test#E4 and wrong-sky#E9 independently specify.
- Where/why it failed: In Scenario A, the correct-window and buggy-window fingerprints were IDENTICAL (`e3db4e78` both) and both reported `final hp: 90` — the 3-tick-vs-5-tick bug is completely invisible to this fingerprint, not because the fingerprint is broken, but because neither of the script's two strike-attempt ticks (2, 8) happens to fall in the disputed distance-3-to-5 range. A team relying on this incidental playthrough script as their determinism/regression coverage would ship the wrong i-frame window with a fully green fingerprint. In Scenario B, targeting exactly that disputed range (tick 5, distance 3) produced DIFFERENT fingerprints (`f5fdbcb6` vs `1c850a00`, hp 100 vs 90) — confirming the bug is real and catchable, just not by an incidental script.
- Fix: wrong-sky#E9's own prescription, now concretely demonstrated rather than merely asserted: a command-withholding i-frame architecture (test#E4 + wrong-sky#E9's shared, independently-verified design) needs a DEDICATED seam-level timing test that specifically probes the boundary tick(s) of the intended window, in addition to (not instead of) the general determinism fingerprint — the fingerprint only tests whatever commands the existing script happens to dispatch, and provides zero assurance about window correctness unless the script happens to probe exactly the disputed range.
- Why this fix: Neither test#E4 nor wrong-sky#E9 individually demonstrates this gap with a constructed counterexample — the value of the sandbox is turning wrong-sky#E9's asserted claim ("test timing at the seam since the fingerprint won't") into a concrete, reproducible demonstration, strengthening what was previously just an assertion in the source lesson's own text into a verified finding.
- Rule of thumb: A command-withholding i-frame/invulnerability architecture (verified independently by two projects as the right way to keep an authoritative reducer replayable) is NOT automatically test-covered by a general determinism/playthrough fingerprint — the fingerprint's coverage of window-timing correctness depends entirely on whether the specific script happens to probe the disputed boundary ticks; add a dedicated seam-level test that deliberately targets those boundaries (distance = window−1 should withhold, distance = window should not) rather than trusting an incidental playthrough script to happen to catch it.
- Provenance (verified/assumed): VERIFIED first-hand — built `engine.mjs` (zero RNG, zero wall-clock, fixed tick counts and command schedules), confirmed an incidental 2-probe script (ticks 2, 8) produces identical fingerprints for a correct 5-tick window and a buggy 3-tick window (bug invisible), and confirmed a deliberate single-probe script (tick 5, chosen for distance-from-dodge=3) produces different fingerprints for the same two windows (bug caught). One implementation bug was found and fixed during sandbox iteration (an initial probe tick was accidentally chosen at a distance both window lengths already excluded, producing a false "not caught" result until corrected to a distance inside the disputed range) — corrected before treating the result as verification. ## E21 — stale derived state is one shape two boundaries
- Date: 2026-07-13
- Project: pappydapimp69/test
- Tags: [gamedev][state][process]
- What: `brain train group` (untested seams extending the main cluster) surfaced pappydapimp69/test + pappydapimp69/the-game-prologue (shared: determinism, gamedesign, gamedev, harness, input, process, state, testing, tooling). Composed: projects/pappydapimp69__test.md#E8 (when a source-of-truth object is replaced at runtime — world reload, archetype switch — rebuild ALL derived/mirrored state through ONE shared clear+respawn path; per-call-site partial cleanup duplicated villagers and froze enemies bound to stale entity ids) and projects/pappydapimp69__the-game-prologue.md#E10 (in a data-driven game, deliberately choose whether a save SNAPSHOTS content or REFERENCES it — snapshotting gives save stability but means a save can never receive a content hotfix; pair it with a version stamp that fails safe to New Game). Built and ran a small deterministic sandbox confirming both lessons describe the SAME underlying shape — derived/saved state silently going stale when the content it was built from changes — at two different boundaries: a runtime world-reload (test#E8) and a save persisting across a content hotfix (the-game-prologue#E10).
- Why built: test#E8 was recorded purely at the runtime-reload boundary (in-memory derived caches, no save/persistence angle in scope) and the-game-prologue#E10 purely at the save/load boundary (persisted content snapshots, no runtime-reload angle in scope). Neither lesson's own text states the general shape both are instances of, so a developer who fixes one (say, adopts the-game-prologue#E10's version-stamp discipline for saves) has no signal that the identical failure shape can also occur purely at runtime, with no save involved at all.
- Design: `engine.mjs` models a content source with two versions (`contentV1`/`contentV2`, the second simulating a hotfix). Mechanism A (test#E8): a naive runtime reload updates one derived cache (`meshCache`) but a second, independently-authored call site (`aiCache`) is never rebuilt, versus a fixed variant routing both through one shared `rebuildAll` function. Mechanism B (the-game-prologue#E10): a naive save/load silently returns pre-hotfix content forever with no detection, versus a versioned variant comparing the save's stamped `schemaVersion` against current content and failing safe (returning current content, flagging `staleDetected`) on mismatch.
- Got right: Each fix, applied to its own mechanism, is confirmed to fully resolve it in isolation — the shared rebuild path leaves no derived cache behind (both `meshCache` and `aiCache` correctly reflect the new content), and the version stamp correctly detects the hotfix and fails safe rather than silently serving stale data.
- Where/why it failed: In the naive runtime-reload case, `aiCache` remained `{}` (empty/stale) after the world reloaded with `villagerHp: 20` content, while `meshCache` correctly updated — exactly test#E8's "duplicated villagers... froze enemies bound to stale entity ids" shape, reproduced from a minimal two-cache case. In the naive save/load case, `effectiveHp` remained `10` (the pre-hotfix value) even though current content had moved to `20`, with `staleDetected=false` — nothing in the naive path ever notices the save is now stale, exactly the-game-prologue#E10's "a save can never receive a content hotfix" concern, but shown as an ACTIVE silent-staleness bug (wrong value served) rather than only a passive limitation.
- Fix: Both mechanisms confirm the same general remedy shape, applied at their own boundary: route every consumer of a mutable content source through ONE explicit, shared resync path (test#E8's shared rebuild function; the-game-prologue#E10's version-stamp check performing the equivalent role at load time) rather than trusting ad-hoc, independently-authored per-consumer update logic.
- Why this fix: Neither individual fix is new — the value of the sandbox is confirming that "rebuild all derived state through one shared path" (test#E8) and "version-stamp the save, fail safe on mismatch" (the-game-prologue#E10) are the SAME architectural principle (centralize resync of anything derived from a changeable source) independently discovered at two boundaries, which strengthens both as a general rule rather than two unrelated project-specific fixes.
- Rule of thumb: Any state derived from, or persisted from, a content source that CAN change after the derivation/persistence happened (a runtime data reload, a shipped content hotfix, a schema migration) needs an explicit, single, shared resync mechanism — not per-consumer ad-hoc updates — whether that state lives in-memory (test#E8) or on disk in a save file (the-game-prologue#E10); the failure mode (some consumers silently see stale data, undetected) is identical at both boundaries.
- Provenance (verified/assumed): VERIFIED first-hand — built `engine.mjs` (zero RNG, zero wall-clock), confirmed the naive runtime-reload leaves one of two derived caches stale while the shared-rebuild-path fix resolves it, and confirmed the naive save/load silently serves pre-hotfix content while the versioned fix detects and fails safe. Confirmed deterministic/reproducible across two independent process invocations of `node engine.mjs`, output diffed byte-identical.

## E20 — two orthogonal phantom e2e failure mechanisms
- Date: 2026-07-13
- Project: pappydapimp69/test
- Tags: [testing][harness][process]
- What: `brain train group` (untested seams extending the main cluster) surfaced pappydapimp69/test + pappydapimp69/the-game-the-waiting-city (shared: determinism, gamedesign, gamedev, harness, input, mobile, process, state, testing, tooling). Composed: projects/pappydapimp69__test.md#E9 (headless browser testing: give each concurrent Playwright/http.server run its OWN port — a shared port causes phantom "logic" failures that pass on re-run — and gesture-initialize WebAudio or audio is silently dead under autoplay policy) and projects/pappydapimp69__the-game-the-waiting-city.md#E2 (a browser e2e test that drives the LIVE running game with a fixed-coordinate scripted command sequence breaks the instant any entity gains real-time autonomous movement; re-read entity positions live before each interaction instead of reusing a pure-replay test's static coordinates). Both describe a test that FAILS in a way indistinguishable from a real game-logic bug, from two structurally unrelated causes. External research (not reasoning alone) checked whether Playwright's own tooling protects against test#E9's mechanism: per Playwright's official parallelism and best-practices docs (playwright.dev/docs/test-parallel, playwright.dev/docs/best-practices), each worker gets its own OS process and browser context, but server-side state and fixed ports are explicitly NOT isolated by Playwright itself — confirming test#E9's port-sharing hazard is a real, documented gap, not a one-off observation. Built and ran a small deterministic sandbox confirming the two mechanisms are orthogonal: fixing either one gives zero protection against the other.
- Why built: test#E9 was recorded from a pure-infrastructure angle (concurrent test processes, no live-AI/scripted-coordinate concern in scope) and the-game-the-waiting-city#E2 from a pure-game-logic angle (autonomous entity movement, no concurrent-process concern in scope). Both produce the identical developer-facing symptom — "the test reported a failure, and it looked like a game bug, but the game actually works" — so a developer debugging a phantom E2E failure for the first time has no structural way to know which of (at least) two causes to check first without already having both lessons.
- Design: `engine.mjs` models Mechanism A (test#E9) as two "workers" starting a mock server at either a shared or isolated port key in a Map, with a fixed, deterministic startup order (no real threading/timing race — the interleaving itself, not nondeterministic timing, is the hazard being isolated), and Mechanism B (the-game-the-waiting-city#E2) as a deterministically-moving entity (`entityPositionAtTick`) where a scripted command either reuses a coordinate captured once at script-authoring time or re-queries the entity's live position immediately before firing. A cross-check section applies EACH mechanism's fix while leaving the OTHER mechanism's bug present, to test whether either fix has any effect on the other's failure mode.
- Got right: Each fix, applied to its own mechanism, is confirmed to fully resolve it in isolation: isolated ports eliminate mechanism A's read corruption (worker A correctly reads its own content); live position re-querying eliminates mechanism B's miss (target and real position match).
- Where/why it failed: The cross-check is the actual composed finding — with ports isolated (mechanism A fixed) but coordinates still captured once and reused (mechanism B's bug present), the interaction still misses (`hit=false`); with coordinates live-requeried (mechanism B fixed) but the port still shared (mechanism A's bug present), the server read is still corrupted (`corrupted=true`). Neither fix has ANY effect on the other mechanism's failure — they are fully orthogonal, confirmed by construction rather than assumed from the fact that they're "different kinds of bugs."
- Fix: Both mechanisms must be independently guarded against in a Playwright-driven browser-game test suite: isolate ports/server-side state per concurrent worker (test#E9, confirmed a real documented Playwright gap by external research) AND re-query any interactive-target entity's live position immediately before a scripted command that depends on it (the-game-the-waiting-city#E2) — treating either as a substitute for the other leaves a real, reproducible false-failure class unguarded.
- Why this fix: Neither individual fix is new — the value of the sandbox is confirming, rather than assuming, that a team which has already fixed ONE phantom-failure class (say, because a bug report from mechanism A already got investigated and resolved) has learned literally nothing that helps diagnose mechanism B when it next appears, and vice versa; the shared SYMPTOM (a passing-on-retry or seemingly-game-logic-shaped test failure) is not a useful signal for which mechanism is at play.

- Where/why it failed: wfc-keylock#E1 and #E3 show that a procgen technique built entirely from local predicates can pass every local check it was designed to satisfy (0% contradiction; every individual move destination-cell-walkable) while still failing the property a level actually needs (globally reachable, globally traversable) — and the failure rate was severe (96% of maps, 500/500 paths), not a rare edge case, precisely because nothing in either local check was ever responsible for the global property in the first place.
- Fix: When choosing or auditing a procgen connectivity algorithm, classify its core guarantee before trusting it: if it is GLOBAL BY CONSTRUCTION (a spanning tree / union-find over the full region graph, as in the-game-the-recursion#E6's chosen approach), no separate connectivity pass is needed — the guarantee is structural. - Why this fix: Each of the three source fixes was already independently verified correct in its own project; the value of composing them is a single classification rule (local vs. global-by-construction) that predicts, before building or auditing a NEW procgen connectivity step, whether an explicit extra pass is required — rather than discovering it the way wfc-keylock did, by measuring a 96%-unreachable-region or 500/500-disconnected-path failure after the fact.
- Rule of thumb: A procgen connectivity algorithm's completeness guarantee is either GLOBAL BY CONSTRUCTION (a spanning-tree/union-find structure over the full region graph — trust it) or LOCAL (adjacent/pairwise constraint satisfaction — trust it for nothing beyond the pair, and add an explicit separate global-connectivity pass); 0% local contradiction or "every move destination is walkable" is not evidence of the global property and has been measured to fail on the large majority of outputs when treated as if it were.

- Project: Pappydapimp69/Test

- Project: Pappydapimp69/Test

## E2 — deterministic rng as save and coop seam
- Date: 2026-06-30
- Project: Pappydapimp69/Test
- Tags: [gamedev][state][coop]
- What: Building the authoritative simulation core for a 3D RPG vertical slice ("Echoes of the Shattered Realm"). Decided that all randomness in the sim must flow through a single seeded RNG whose entire state is a `{seed, count}` pair stored *inside* the saved world object — `Math.random()` is banned in the sim layer.
- Why built: Needed save/load, and wanted to keep lockstep co-op possible later without a rewrite. Both wants turned out to be the *same* requirement: a reproducible random stream.
- Design: One mulberry32 generator; `nextFloat` advances `rng.count`; the world holds `rng:{seed,count}`. Save = `JSON.stringify(world)`; load = `JSON.parse`. Content (items/enemies/quests) is NOT serialized — it is reloaded from data and rebound, so content can be patched under old saves.
- Got right: A mid-run save/load round-trip is asserted in the headless demo — after reload, `rng.count` is preserved and the next roll is identical to the un-saved timeline. One discipline bought three things: exact save/load, replay-from-seed for repro bug reports, and the lockstep-co-op option.
- Where/why it failed: The non-obvious trap is everything that *silently* breaks determinism and won't show up until a save desyncs or two clients diverge: an ambient `Math.random()`, a `Date.now()`/`new Date()` leaking into game logic, or unordered iteration over a hash map affecting outcome order. None of these error — they just quietly make the stream irreproducible.
- Fix: Route every roll through the one seeded RNG; ban `Math.random()` in the sim (a lint rule is the cheap enforcement); keep wall-clock time out of the sim (advance an in-world clock via commands instead); iterate entities in a stable id order when order affects outcomes.
- Why this fix: Determinism is a global property — a single ambient call anywhere in the sim voids it. Centralizing the entropy source and forbidding ambient sources is the only way to keep the guarantee provable rather than hoped-for.
- Rule of thumb: If you want save/load to round-trip exactly OR lockstep multiplayer later, store the RNG state inside the saved state and forbid ambient `Math.random()`/`Date.now()` in the simulation. The constraint it forces — float-nondeterministic physics must stay OUT of the authoritative layer — is the tell that you're doing it right.

## E1 — data driven content needs a validation ladder
- Date: 2026-06-30
- Project: Pappydapimp69/Test
- Tags: [gamedev][gamedesign][tooling]
- What: Made the RPG fully data-driven — items, enemies, quests, NPCs, archetypes all live in `src/data/*.json`; the code knows only *shapes* (an item has a slot; a quest has typed objectives), never specific content. Adding content is a JSON edit, not a code change.
- Why built: To keep authoring cheap and unbounded and to keep the dangerous surface (new mechanics) small and in reviewed code. The deliberate code/content boundary sits at *types*: a new quest is data; a new *kind* of objective is one reducer case.
- Design: A loader builds id-keyed maps from the JSON; cross-file references are by id (`loot[].itemId`, quest `giver`, `rewards.items`, archetype `startingItems`).
- Got right: Authoring a new enemy or quest needs zero code and is referenceable immediately; the small mechanic surface stays reviewable.
- Where/why it failed: Going data-driven silently trades away compile-time safety. A single typo in an item id ships a quest whose `collect` objective can never be satisfied — and nothing errors at load. The failure moves from the compiler (where you'd catch it instantly) to the player (who hits an uncompletable quest). With hand-edited JSON this is a *when*, not an *if*.
- Fix: Build a validation ladder, cheapest-first: (1) JSON Schema per content type to catch malformed records; (2) a referential-integrity + completability check — every referenced id resolves, and every quest is actually completable (its kill/collect targets exist and spawn/drop somewhere); (3) run a headless end-to-end smoke playthrough in CI that exercises the live content graph and fails loudly on a broken reference.
- Why this fix: The compiler used to be the validation step; once content leaves code, you must rebuild that safety net deliberately or it doesn't exist. A headless smoke test is the highest-value rung because it catches semantic breakage (uncompletable quest) that schema/ref checks alone miss.
- Rule of thumb: The moment you make content data-driven, you have opted out of compile-time safety for that content — add a validation step (schema → referential integrity → headless smoke playthrough) in the same change, or breakage relocates from the compiler to the player.
