## E1 — sandbox pathfinding diagonal corner cutting is the default not the edge case
- Date: 2026-07-11
- Project: local/sandbox-pathfinding-diagonal
- Tags: [algorithm][gamedev][state]
- What: An 8-directional grid A* was built to check how often naive diagonal movement (allowing a move from (x,y) to (x+1,y+1) even when both flanking orthogonal cells (x+1,y) and (x,y+1) are walls) actually produces a physically-impossible path — one that clips a wall corner a square-collision agent could never really walk through. On 200 randomly-generated maps at wall density 0.30, EVERY SINGLE solvable path (179/179, 100%) contained at least one such corner-cut, averaging nearly 16 per path.
- Why built: A pathfinding-algorithm sandbox to check whether corner-cutting is a rare edge case worth a defensive check "just in case," or a near-certain default outcome worth treating as a real requirement — since the two call for very different engineering priorities.
- Design: Standard 8-directional A* (octile-distance heuristic) with a toggleable corner-cut policy: `allowCornerCut: true` permits a diagonal move even when one or both flanking orthogonal cells are walls; `false` disallows it, requiring both flanking cells to be open. Separately tested diagonal MOVEMENT COST: `uniform` (every direction costs 1, a classic and easy bug) vs `octile` (diagonal moves cost sqrt(2), matching real Euclidean distance).
- Got right: Measuring corner-cuts actually PRESENT IN THE FINAL RECONSTRUCTED PATH (not just theoretically possible during search) is what makes the 100% figure meaningful — it's not "corner-cutting is theoretically reachable," it's "the A*-chosen shortest path routes through a wall corner in literally every solvable test map at this wall density."
- Where/why it failed: Corner-cutting isn't a rare edge case that "probably won't come up much" — on a wall-density-0.30 map, it is the DEFAULT outcome of unconstrained 8-directional movement, because a shortest-path search will always find and use any diagonal shortcut available, and moderately-dense wall layouts create many opportunities for exactly this shortcut. Separately, the uniform-diagonal-cost bug (treating a diagonal step as costing the same as an orthogonal one, instead of sqrt(2)) isn't purely cosmetic either — it changed the actual CHOSEN route (not just its reported cost number) in 16.8% of maps where both cost models found a solution, meaning a game running this bug is measurably routing agents differently than intended, not just mislabeling distances.
- Fix: Not applicable — no bug in a shipping project, this is a characterization result. The verified, portable takeaway: treat both corner-cut prevention (checking both flanking orthogonal cells before permitting a diagonal move) and correct diagonal cost (sqrt(2), or the octile-distance heuristic convention) as REQUIRED baseline correctness for any 8-directional grid pathfinder meant to represent a square-collision agent, not optional polish — disallowing corner-cuts made every affected path measurably longer (100% of the time, mean +9.23 cost units), confirming this is a genuine physical constraint with a real cost, not a free correctness fix.
- Why this fix: A pathfinder that finds a "shorter" path by cutting a wall corner is not actually finding a shorter path for the agent it represents — it's finding a shorter path for a point-agent with no collision radius, and reporting that as if it were valid for the real agent. The gap between the two (100% corner-cut incidence, 9.23 average extra cost when corrected) is large enough that this is a correctness bug in most games, not an aesthetic nitpick.
- Rule of thumb: When building 8-directional grid pathfinding for any agent with real collision geometry (i.e., not a mathematical point), corner-cut prevention is not optional — verify it explicitly rather than assuming it's a rare case, since on a moderately-walled map it will affect essentially every generated path, not a small fraction of them. Separately, always use octile/Euclidean diagonal cost (sqrt(2)), not uniform per-direction cost — the uniform-cost shortcut is an easy bug to introduce (it looks harmless, all directions "just cost 1") but it measurably changes chosen routes, not just their reported length.
- Provenance (verified/assumed): VERIFIED first-hand — ran the actual 8-directional A* implementation (Node.js sandbox) across 200 random maps per experiment, directly counting corner-cuts present in the reconstructed final path (not a theoretical estimate) and directly comparing chosen-route step counts between cost models.
