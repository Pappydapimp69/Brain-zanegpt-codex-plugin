## E8 — three faults one symptom mobile tap
- Date: 2026-09-25
- Project: Pappydapimp69/dark-goblin
- Tags: [gamedev][input][mobile][phaser][process]
- What: "Tapping the button does nothing" on a real Android phone turned out to be THREE independent faults stacked in series — viewport units, pointer mapping, and the framework's hit test. Each fix was necessary, none was sufficient, and the symptom was byte-identical after each one.
- Why built: A Phaser game scaled with FIT so one design size covers every screen, verified by a headless browser driver.
- Design: Standard Phaser: `100%` viewport heights, the Scale Manager mapping pointers into game space, and controls made interactive with `setInteractive(rect, Rectangle.Contains)` on a Container.
- Got right: Refusing to ship a guess, and measuring instead. A probe on the title screen counted the same tap at every layer it crosses and printed the numbers on screen, so a person with no console and no debugger could read them back. Each round it eliminated exactly one hypothesis, which is why three stacked faults got resolved at all rather than one fix being reverted for "not working".
- Where/why it failed: (1) `100%`/`100vh` size to the chrome-collapsed viewport, so the layout is wrong whenever the address bar shows. (2) Phaser maps a pointer with `displayScale = gameSize / canvasBounds`, and BOTH halves are cached; `updateBounds()` refreshes the rectangle and leaves the scale stale, so a tap on a control at x=360 reported x=455 — y correct, x scaled by 1.27. Only `refresh()` recomputes the scale, but refresh emits RESIZE and on WebGL drops and rebuilds textures, throwing on `glTexture` when called per tap. (3) With the mapping finally correct, a tap reported at 354,858 against a control spanning x 60-660, y 808-892 — inside by any reading, press and release both seen, nothing cancelled — still never reached the handler. Phaser's Container hit test was refusing a point inside its own hit area, on that device only.
- Fix: `100dvh` with `vh` fallback; measure the canvas rectangle on every touch in the CAPTURE phase and call `scale.refresh()` only when it has actually changed; and replace the framework hit test with one scene-level dispatcher that holds each control's rectangle and does the four comparisons itself.
- Why this fix: The third is the load-bearing one and the one worth generalising. Containment is four comparisons. A framework's hit test adds transforms, camera space, container-local space and a device-dependent path to a calculation that has one correct answer, and when it disagrees with arithmetic on one device there is nothing to debug from the outside. Owning it removes a whole class of device-specific input faults permanently, at the cost of implementing priority and press/release pairing by hand — about twenty lines.
- Rule of thumb: When a control is confirmed to be under the pointer and the framework still says it was not hit, stop diagnosing the framework and take the hit test — containment is arithmetic and arithmetic does not vary by device. And when several faults are stacked in series, the symptom does not change as you fix them one at a time: treat "the symptom is identical after my fix" as no evidence at all about that fix, and keep a probe that can distinguish the layers, or correct changes will be reverted for looking useless.
- Provenance (verified/assumed): Verified — every number quoted was read off the affected device, each fix was deployed and re-measured, and the final state was confirmed working by the reporter. The `glTexture` regression was reproduced locally. Assumed — why Phaser's Container hit test fails on that device specifically; it was replaced rather than root-caused.

## E7 — render the whole space and look at it
- Date: 2026-09-21
- Project: Pappydapimp69/dark-goblin
- Tags: [gamedev][visualdesign][testing][content]
- What: A composed art system generating forty-two characters from six builds, six head coverings, twelve props and five tones. Nine of the forty-two came out with no face at all. A contact sheet of the whole cast showed it in one glance; thirteen unit tests over the same system had just gone green.
- Why built: A cast of forty-two cannot be forty-two drawings, and it should not be: a town is eight people dealt from the roster, so what must read is individual and trade, not portraiture. Composition also keeps the set consistent for free.
- Design: Each figure is built by layering — body, then neck, then skull, then the two marks that serve as eyes, then the head covering, then the carried object.
- Got right: The composition premise held completely, and so did leaning on silhouette rather than hue (two independently chosen palettes can land on the same colour-vision confusion axis at matching luminance, and then only outline separates them). Assets as generated source rather than image files is also what made every fix a one-line change applied to all forty-two at once.
- Where/why it failed: The covering was drawn as a single shape OVER the skull, and a headscarf and a hood both enclose a head — so they painted over the eyes. Every figure wearing one was faceless. This is structural, not a typo: in a layered composition the occluding element is nearly always the one that defines the silhouette, and the identifying feature is nearly always underneath it. The per-item tests could not see it — they assert that a spec resolves, that the document is well-formed, that no coordinate is NaN. None of those is "this looks wrong", and nothing in a single figure's markup is wrong.
- Fix: Split every covering into a mass drawn BEHIND the skull and a near edge — brim, drape, fringe — drawn in front, always clear of the eye line. Then build a contact sheet: one SVG tiling every figure in the set with its id beneath it, written by the same tool that writes the assets.
- Why this fix: The behind/front split is the general shape of the bug's fix, not a patch on scarves: any occluder in a composition system needs an explicit z-relationship to the feature that identifies the thing, or it will eventually cover it. The contact sheet is the cheaper half. The same sheet immediately surfaced two more problems no test would have raised — an attribute dealt by hash-modulo had produced thirteen figures of one build against three of another, so every randomly dealt town looked like the same town, and one bespoke garment was drawn wider than the body it sat on, reading as a column rather than an apron.
- Rule of thumb: Any system that GENERATES a population — sprites, avatars, procedural levels, synthetic records — needs an artefact that renders the whole space at once, produced by the same tool that produces the assets so it cannot drift. Per-item validation answers "is this well-formed", never "is this right", and for anything visual the second question is the only one that matters. And in layered composition, give every occluder an explicit split around the feature that identifies the subject, rather than trusting draw order to stay correct as parts are added.
- Provenance (verified/assumed): Verified first-hand — the faceless figures, the 13-vs-3 build distribution and the oversized garment were all read off the rendered contact sheet, all three fixed, and the corrected sheet re-rendered and checked. The thirteen passing tests are the suite state at that moment. Assumed — nothing.

## E6 — phaser load svg atob data uri
- Date: 2026-09-21
- Project: Pappydapimp69/dark-goblin
- Tags: [phaser][gamedev][browser][rendering]
- What: Handing Phaser's `load.svg` a percent-encoded `data:image/svg+xml,...` URI throws `Failed to execute 'atob' on 'Window'` and kills the game before its first scene renders. Nothing draws, and the error names a function the calling code never used.
- Why built: The art is generated SVG source rather than files on disk, so there is nothing to fetch — the natural move is to hand the loader a data URI.
- Design: `toDataUri` percent-encodes rather than base64-encoding, because percent-encoding behaves identically in the browser and in Node (a tool writes the same assets out to files) and sidesteps base64's unicode handling.
- Got right: Percent-encoding is genuinely the better encoding for the job, and it works perfectly with an `Image` element. The problem is entirely in what Phaser's loader assumes.
- Where/why it failed: Phaser's SVG file loader treats a data URI as base64 and calls `atob` on the payload. A percent-encoded body is not base64, so it throws during load, before any scene exists. The symptom is maximally unhelpful: a blank canvas, no scenes active, and an `atob` error referring to code you did not write.
- Fix: Skip the loader. Build an `Image` from the data URI, draw it into a canvas at the exact pixel size wanted, and register that with `textures.addCanvas`. Done before the game is constructed, so scenes can use the textures immediately with nothing to wait on.
- Why this fix: Base64 would also have satisfied the loader, but it leaves the work inside a code path that clearly did not anticipate this use. Going through a canvas is fewer moving parts, works with either encoding, and adds the thing the loader does not give you: exact control of raster size, which matters for vector art with heavy outlines — a mismatch between the SVG's own dimensions and the drawn size shows up immediately as soft edges on ink that should be crisp.
- Rule of thumb: When a framework loader dies on a data URI with an encoding error, do not reach for the other encoding — rasterise it yourself through `Image` plus canvas and register the texture directly. It is a handful of lines, it is encoding-agnostic, and for generated vector art it is strictly better because you choose the raster size. More generally: a blank screen plus an error naming a builtin you never called means a framework made an assumption about your input, so look at what it thinks your input is before looking at your own code.
- Provenance (verified/assumed): Verified first-hand — the failure and its exact message observed in a headless Chromium run of the built game, and the canvas path fixed it with no other change. Assumed — that the loader's base64 assumption is unconditional for data URIs; I read the behaviour, not Phaser's source.

## E5 — every harness encodes a world that moves
- Date: 2026-09-21
- Project: Pappydapimp69/dark-goblin
- Tags: [testing][harness][process][gamedev]
- What: Three separate instruments broke during one build, in three different phases, for three apparently unrelated reasons — and all three were the same defect: a harness encoding an assumption about a system that is free to change underneath it. Each failure looked like a finding about the game rather than a fault in the tool.
- Why built: A simulated-player bot for balance, and a headless browser driver for the render seam. Both were good ideas that earned their keep: the driver found three real bugs the unit suite structurally could not see, and the bot surfaced the only reachability problem anyone found.
- Design: The bot modelled attachment by returning to its most-visited character. The driver clicked at computed screen coordinates after sleeping for fixed wall-clock durations, and read the scene by iterating each scene's top-level children.
- Got right: Both tools were cheap and both were kept. Exposing a handle to the running game on `globalThis` is what made every one of these diagnosable in a single evaluate call instead of by staring at screenshots.
- Where/why it failed: (1) The bot's attachment was an argmax over a visit counter — a ratchet, since the first character met is the maximum forever. It reported the headline content chain completing in 0% of lives; the true figure was 12%. (2) The driver's fixed sleeps assumed in-game time tracks wall-clock, but a slow headless renderer plus an engine's frame-delta clamp ran scheduled callbacks at a third speed, so a timed text reveal looked dead. Its coordinate clicks assumed a fixed layout, but the cast is dealt randomly each run, so a panel holding four people instead of two moved every target. (3) Nesting buttons in a container for an animation hid them from a tree walk that only looked at top-level children, and made their coordinates local rather than world. Every one of these produced a plausible-looking claim about the game. The 0% was the most dangerous: a reachability test that returns exactly the failure it was built to detect is trivially believed.
- Fix: Make each instrument observe rather than assume. Probabilistic stickiness instead of an argmax. Poll the live scene for the transition instead of sleeping. Find controls by label and ask each object for its world transform instead of computing where it ought to be. Where a rule is checkable mechanically, check it mechanically rather than by discipline — collecting every string the game draws and failing on any digit turned "no numbers are ever shown to the player" from a standing intention into a gate.
- Why this fix: The common root is that a harness is written once against a snapshot, while the system keeps moving: content grows, layouts reflow, scene graphs gain a level, render speed varies by machine. Any constant in a harness — a coordinate, a duration, a depth, a hard max — is a claim about that snapshot, and it decays silently. Observation does not decay. The cost is a handle into the live system, which is a small price and useful for far more than tests.
- Rule of thumb: Treat every measuring instrument as code under test with its own failure modes, and audit it for constants: fixed coordinates, fixed waits, assumed nesting depth, an argmax in a behavioural model. Each is an assumption about a world that will move. The specific tell that you are looking at an instrument fault rather than a finding is a suspiciously clean result — 0%, 100%, "completely broken" — especially when it confirms the exact thing the instrument was built to look for. Check the instrument before you believe it, and give yourself a live handle into the running system so that check costs one call.
- Provenance (verified/assumed): Verified first-hand — all three failures observed in this build, each diagnosed against live state, each fixed, and the corrected figures measured over the same seeds and content. Assumed — nothing beyond the generalisation itself, which is drawn from these three instances plus the two prior entries it composes.

## E4 — phaser delta clamp confirms headless time lesson
- Date: 2026-09-21
- Project: Pappydapimp69/dark-goblin
- Tags: [testing][harness][gamedev][determinism]
- What: A Phaser scene's timed text reveal looked completely broken under a headless browser — the character was on screen, the line never appeared. In-game time was running at roughly a third of wall-clock. dog#E22 already documents this hazard from a different engine; this is the second live instance, with the specific mechanism and a cheap observable.
- Why built: A smoke driver that plays the built game through a whole loop in Chromium and fails on any console error, so that bugs living at the render seam get caught. It already had a good record: it had found three real bugs the unit suite could not see.
- Design: The driver clicked, slept for a generous fixed duration, screenshotted, and moved on. The scene under test pauses 1.4 seconds in silence and then types a line out at 34ms a character.
- Got right: Keeping a game handle on `globalThis` so the driver could read the live scene graph instead of guessing from pixels. That is what turned a mystery ("the goblin is mute") into a measurement in one pass: dumping the scene's clock and its pending timer events showed a timer with `delay: 1400` whose `elapsed` had only reached 1383 after 4.1 seconds of wall-clock, while `Clock.now` tracked real time exactly.
- Where/why it failed: Phaser's TimeStep clamps frame delta to `deltaMax` (50ms by default) to stop a stalled tab from teleporting the world. Headless Chromium on a software renderer was producing frames of roughly 150ms, so every frame contributed 50ms instead of 150 and all `Time.addEvent`/`delayedCall` scheduling ran at about a third speed. `Clock.now` is wall-clock and looks correct, which is exactly why the lag is hard to spot: the clock agrees with reality while everything scheduled against it does not. This is the identical hazard dog#E22 found, arriving through a different mechanism (a delta clamp rather than an rAF slowdown ratio) in a different engine.
- Fix: The driver polls the live scene for the state it actually cares about — this scene active, this text settled — with a generous ceiling, instead of sleeping. No timing constant anywhere in it.
- Why this fix: The ratio is not a constant to calibrate against. It varies with the renderer, the machine, the scene's own draw cost and whatever else the box is doing, so any fixed wait tuned today is a flake tomorrow. Polling for the transition is correct regardless of how slowly time runs. Note the game itself needed no change: on a device hitting 60fps the delta never reaches the clamp, so this is purely an instrument fault — the thing under test was right the whole time.
- Rule of thumb: In any engine with a frame-delta clamp, a slow renderer silently divides the rate of every scheduled callback while the wall-clock reads correct — never sleep a fixed duration in a harness, poll for the transition. When timed behaviour looks dead under a headless browser, compare a pending timer's `elapsed` against the clock's `now` before suspecting the code: they diverging IS the diagnosis, and it takes one evaluate call if the harness can reach the live scene graph. Keep a handle to the running app exposed for exactly that reason.
- Provenance (verified/assumed): Verified first-hand — the timer dump is quoted above (`1400@1383` at `clockNow 6175`, click at ~2025), and switching the harness from sleeps to polling made the same build pass with no change to the game. Assumed — that `deltaMax` of 50ms and ~150ms frames are the exact numbers; the ratio was measured, the frame time was inferred from it.

## E3 — pure core moves bugs to the render seam
- Date: 2026-09-21
- Project: Pappydapimp69/dark-goblin
- Tags: [testing][architecture][gamedev][harness]
- What: A game built as a pure engine plus a thin Phaser shell had 91 green unit tests over the engine and three real bugs in the built game, all found within one scripted browser playthrough and none findable by the suite.
- Why built: The spec mandated a pure-TypeScript engine with zero rendering imports, rendering dispatching actions and never mutating state. That is a good architecture and it did what it promised: every rule in the spec has a test, and the rules were all correct.
- Design: Engine as a pure reducer; a store as the single seam; scenes read state and dispatch. Unit tests cover the engine exhaustively — scoring tables, attribution, determinism fingerprints, content validation.
- Got right: The architecture itself, and the discipline tests. Greping the engine directory for rendering imports, and asserting the store replaces state rather than mutating it, are cheap and they hold the seam's shape. The engine genuinely had no bugs.
- Where/why it failed: A pure core does not remove bugs, it RELOCATES them to the core-to-shell contract, and a suite that only exercises the core is blind there by construction. All three bugs lived in that gap. (1) Content placed eight characters at a location string the renderer's own hardcoded list did not contain: they were instantiated, selected into the active set, and drawn nowhere — present and unreachable, with nothing throwing. (2) An availability guard was asymmetric: it hid a broken character's ordinary options but never hid the option that was supposed to REPLACE them, so a post-catastrophe line was offered before the catastrophe. The engine test asserted the "after" case and never the "before" case. (3) A modal overlay was transparent enough to read the screen behind it. None of the three is a rule, so no rule test could see any of them.
- Fix: A ~60-line headless browser script that drives the BUILT artifact through one complete loop, screenshots each beat, and exits non-zero on any console error. Then each bug it found was pushed back down into something permanent: the renderer's private list of locations became a declared field in content with a validator rejecting anyone outside it, and the asymmetric guard became one condition with a regression test for the "before" case.
- Why this fix: The screenshots are what actually found bugs 1 and 3 — a human glance at a rendered frame catches "seven people where eight should be" and "I can read the street through this" instantly, and no assertion was ever going to be written for either. The console-error exit code makes it a gate rather than a ritual. Crucially the driver is cheap enough to keep: no page objects, no selectors, just coordinates into a canvas and a fixed viewport so the scale is 1:1. Silencing the incidental favicon 404 mattered more than it sounds — a check with a permanently non-empty error list stops being read.
- Rule of thumb: The cleaner the core-shell split, the more the remaining bugs live exactly at the seam, and unit tests over the core are blind there by construction — budget for a smoke driver over the built artifact from the first UI commit, not as a polish-phase luxury. Two specific shapes to look for: any enumeration the renderer keeps privately (locations, categories, sprite keys) that content can reference by string, which strands data silently rather than failing; and any "A replaces B" rule implemented as two independent guards, which leaves the before-case untested. And keep the smoke check's baseline at zero errors, or it decays into noise.
- Provenance (verified/assumed): Verified first-hand — all three bugs observed in screenshots of the built game, all three fixed, and the two that could be are now covered by regression tests that fail against the old code. The 91-tests-green figure is the suite state at the moment the browser run found them. Assumed — nothing; this is a straight account of one session.

## E2 — pkill f matches its own shell
- Date: 2026-09-21
- Project: Pappydapimp69/dark-goblin
- Tags: [tooling][process][harness]
- What: `pkill -f "vite preview"` run at the head of a long compound shell command killed the shell running it, discarding the file writes and the commit that were queued behind it.
- Why built: Tidying up a dev server started earlier in the session before committing, as one step of a single combined command.
- Design: One `bash -c` doing cleanup, then a heredoc append to a file, then `git add`, `git commit` and `git push`, chained with `&&`.
- Got right: The work itself was recoverable — the earlier steps had already written their files, so only the tail of the chain was lost, and `git status` showed exactly how far it got.
- Where/why it failed: `pkill -f` matches against each process's FULL command line, and the invoking shell's own command line contains the pattern, because the pattern is an argument to `pkill` within it. So the shell matches its own search string and kills itself. The command exits with a signal status (144 here) and everything after the `&&` silently never runs — which reads like a mysterious failure of an unrelated later step rather than a self-inflicted kill.
- Fix: Do not use `pkill -f` with a pattern you have just typed into the same command line. Target the process another way — by port (`fuser -k 4173/tcp`, `lsof -ti:4173 | xargs kill`), by a saved PID from when it was started, or by `pkill -f` in its own separate invocation where nothing after it can be lost.
- Why this fix: The self-match is structural, not a race — any `pkill -f <pattern>` is a process whose command line contains `<pattern>`. Killing by port or stored PID addresses the thing you actually mean. Isolating the call at minimum contains the blast radius to the cleanup itself.
- Rule of thumb: `pkill -f <pattern>` always matches its own invoking command line — never chain real work behind it with `&&`. More generally, put a self-referential or destructive cleanup in its own invocation, so a surprising exit cannot swallow the steps that mattered; and when a compound command dies with a signal exit status (128+n) and the later steps produced nothing, suspect the earlier step killed the shell before suspecting the later ones.
- Provenance (verified/assumed): Verified first-hand — the command exited 144, the heredoc append and the commit both did not happen, the files written by earlier steps survived, and re-running the tail without the `pkill` succeeded unchanged.

## E1 — measuring bot argmax faked a design finding
- Date: 2026-09-21
- Project: Pappydapimp69/dark-goblin
- Tags: [testing][gamedesign][simulation]
- What: A simulated "realistic player" bot, written to judge whether a narrative game's authored content is reachable, reported that the game's headline chain completes in 0% of lives. The 0% was a bug in the bot, not a property of the game.
- Why built: The spec's own four bots are policies over hidden scoring tags, and one of them looks ahead by trial-applying a move to see what it unlocks. Neither is available to a person playing: every number is hidden and nobody gets to take a move back. So the balance question — can a normal player reach the content? — needed a bot that plays on what the screen actually shows.
- Design: The bot models attachment: it returns to whoever it has been spending time with rather than re-deciding from scratch each turn. That was implemented as an argmax — pick among the most-visited people, ties rolled.
- Got right: The premise held up completely. The four spec bots reported the design was fine; the fifth was the only one that varied by seed at all, and it was the only one that surfaced any reachability problem. Giving it its own RNG stream, separate from the world's, meant its deliberation never perturbed the thing it was measuring.
- Where/why it failed: An argmax over a visit counter is a ratchet. The first person visited has one visit and everyone else has zero, so that person is the argmax forever — the bot never met anyone else. That is obsession, not attachment. It read as a credible design finding ("a realistic player finishes nothing") because a too-narrow player is exactly the failure a reachability test is looking for, so the result confirmed what the test existed to detect.
- Fix: Make the stickiness probabilistic — a 0.6 chance of returning to the familiar, otherwise drift to whoever else is in front of you. One number, one extra draw on the bot's own stream.
- Why this fix: Attachment is a tendency, not a constraint. A ratchet cannot be softened by tuning the counter because the bug is the argmax itself; only making the preference probabilistic lets the model spread attention the way a person does. The corrected instrument moved the headline chain from 0% to 12% and a secondary chain from 16% to 62% — same game, same content, same seeds. The real finding survived (12% is still low, and worth reporting to the designer), but it is now a finding about the game rather than about the bot.
- Rule of thumb: A bot you use to judge a design is code under test, and it needs its own tests before its output is evidence. Treat an argmax inside a behavioural model as a defect on sight — human tendencies are probabilistic, and a hard max over an accumulating counter is a ratchet that collapses the model to one branch. And when a measuring instrument confirms exactly the failure it was built to look for, sanity-check the instrument before believing the result: 0% and 100% are instrument readings far more often than they are world readings.
- Provenance (verified/assumed): Verified first-hand — both figures measured over the same 100 seeds and the same content, with only the focus rule changed (argmax: 0% / 16%; stickiness 0.6: 12% / 62%). Assumed — that 0.6 is a good stickiness constant; it is a plausible number, not a calibrated one, and no human play data exists to fit it against.
