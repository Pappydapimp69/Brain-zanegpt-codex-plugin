## E1 — validation ladder and no dupe keys lint both miss a spread vs explicit key collision
- Date: 2026-07-20
- Project: local/sandbox-validation-ladder-vs-key-collision
- Tags: [testing][tooling][gamedev]
- Composed: pappydapimp69__test/E1, pappydapimp69__draft/E1
- What: `brain train edge` flagged `draft + test` as the highest-value untested pair. test#E1's validation ladder for data-driven content (schema → referential-integrity/completability → headless smoke playthrough) is meant to catch a broken content entry before it ships. draft#E1 found a specific failure shape a general ladder doesn't anticipate: a JS object literal that spreads a source template AND sets a derived key under the SAME name has the later key silently win, losing the original reference. My first hypothesis — that a source-level lint check mirroring ESLint's `no-dupe-keys` would catch this — was WRONG and corrected by external research before filing: `no-dupe-keys` explicitly does not detect a collision between a spread's runtime contents and an explicit literal key, because the spread's contents aren't statically visible to the linter. Sandbox-confirmed: neither test#E1's ladder (as described) nor the standard lint mitigation catches a draft#E1-shaped collision — only a smoke-test path that happens to dereference the shadowed property does, and only a dedicated spread-vs-explicit-key diff check catches it deterministically.
- Why built: test#E1 was recorded from a missing/typo'd content-id investigation with no object-construction-hazard in scope; draft#E1 was recorded from a single incident with no systematic check proposed. Neither entry asks whether a general validation ladder or standard tooling actually covers the other's failure shape — composing them (and correcting my own first guess about lint coverage via real research rather than assuming) is what surfaced the gap.
- Design: Deterministic Node script (`sandbox_validation_ladder_vs_key_collision.mjs`), no RNG, no wall-clock. `buildUnitBuggy(template)` reproduces draft#E1's shape exactly (`{...template, id: template.id, def: template.attack*1.5}` where `template.def` already exists, same key, different meaning — deliberately chosen numbers so the collision isn't numerically masked by coincidence). `buildUnitFixed` uses a distinct key name. Four scenarios: (A) schema + referential-integrity checks against the buggy unit; (B) a shallow smoke test (never reads `def` meaningfully) vs. a deep smoke test (dereferences it in a mitigation calculation) against both buggy and fixed units; (C) a minimal, honest model of `no-dupe-keys` (flags only literal duplicate keys among a literal's own EXPLICIT properties, cannot see inside a spread — matching real ESLint's documented behavior) run against the buggy literal's explicit key list; (D) a dedicated check that diffs a literal's explicit keys against its spread source's keys.
- Got right: Scenario D confirms a real, working mitigation exists — the failure isn't "this class of bug is uncatchable," it's specifically that the two mitigations someone would reach for FIRST (test#E1's ladder, standard lint) both miss it, while a less obvious, purpose-built check (spread-vs-explicit-key diffing) catches it deterministically.
- Where/why it failed: (A) schema check passed (`def` is a number) and referential-integrity check passed (the id is valid) on a unit whose `def` was silently wrong (10.5 instead of the real 12) — both ladder rungs gave a clean bill of health on genuinely broken data. (B) The shallow smoke test never crashed and gave no signal either way; only the deep smoke test (which happened to dereference `def` in a damage-mitigation calculation) produced a visibly different result (9.5 mitigated vs. 8 on the fixed unit) — confirming detection is entirely a function of which runtime path a smoke test happens to cover, exactly draft#E1's own observed shape ("throws only where the lost reference is dereferenced"). (C) The `no-dupe-keys`-style check found zero duplicates among the literal's own explicit keys (`id`, `def`) — because the actual collision is with the SPREAD's runtime contents, invisible to a check that only inspects a literal's own explicit property list.
- Fix: Add a fourth, purpose-built rung to a validation ladder for any codebase that constructs objects via `{...source, explicitKey: ...}`: for each such construction site, statically or at build-time diff the explicit keys against the spread source's known key set (a type system, a schema, or a runtime dev-mode assertion), flagging any explicit key that already exists in the source. This is a different check than either "does the resulting DATA look valid" (schema/referential-integrity) or "does the SOURCE contain a literal duplicate key" (`no-dupe-keys`) — it specifically checks the relationship BETWEEN a spread and the literal's own keys.
- Why this fix: test#E1's ladder operates entirely on the resulting DATA (is this object well-formed, do its ids resolve) and standard lint operates entirely on a literal's own SOURCE TEXT (are there two identical keys written out) — neither layer has visibility into "does this explicit key silently override something the spread already provided," which is a property of the RELATIONSHIP between the two, not of either one in isolation.
- Rule of thumb: A validation ladder and standard static lint together still leave a real gap for any `{...source, key: derivedValue}` construction where `key` might already exist on `source` — this is invisible to schema checks (the result IS well-typed), referential-integrity checks (nothing references a missing id), AND `no-dupe-keys`-style lint (the collision is with a spread's runtime contents, not a literal duplicate). If your codebase constructs objects this way, add an explicit spread-vs-explicit-key diff check at each construction site, or (per the external research) consider a static type system whose compiler is positioned to catch a subset of these at the type level.
- Provenance (verified/assumed): Verified first-hand — `sandbox_validation_ladder_vs_key_collision.mjs` run to completion for all four scenarios, deterministic (no RNG, no wall-clock), each scenario's checks and computed values printed and checked programmatically (an `allPass` gate across all four). My initial hypothesis (that `no-dupe-keys` would catch this) was checked against the real ESLint documentation and community-confirmed limitation before writing scenario C, rather than assumed or reasoned about in isolation — the sandbox models the ACTUAL documented behavior (no-dupe-keys ignores spread contents), not a guessed one.
