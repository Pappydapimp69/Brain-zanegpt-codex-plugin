## E6 — megagroup stress shared history must undo top of stack only
- Date: 2026-07-13
- Project: local/sandbox-combined-rpg-progression
- Tags: [architecture][state][testing]
- What: A whole-mega-group stress test — one live simulation running EVERY already-verified-and-fixed sub-system in this project's largest emergent cluster simultaneously (procgen-CA + connectivity-fixup shared dungeon, astar-replan movement, dbz-combat/power-scaling shared boss, loot-pity shared loot table, savemigrate periodic round-trips, undo-redo) under concurrent load from 6-10 NPCs sharing ONE global command history. Every prior undo/redo verification in this project (rpg-progression#E1/E2/E4/E5, the group-merge#E2) used a SINGLE acting agent — this is the first test with more than one. A natural but wrong implementation — each NPC tracks its own "my last command's index" and calls `undo` by jumping directly to that index's preimage, rather than always popping the actual top of the shared stack — corrupted world state in 20/20 seeds (200 ops, 6 NPCs). The correct implementation (undo/redo only ever operate on the literal top of the ONE shared stack, regardless of which NPC is "currently acting") held at 0/20 (6 NPCs, 200 ops) and 0/20 at a larger config (10 NPCs, 400 ops).
- Why built: To check whether every fix already verified in this project's mega group (deep-copy snapshots, atomic cascading transactions, presentation-state exclusion, the top-of-stack redo-invalidation rule) actually holds once genuinely NEW scale — multiple concurrent agents on one shared timeline — is introduced, since N=1 (every prior test) structurally cannot distinguish "undo my last action" from "undo the globally most recent action" — they're the same operation until a second agent exists.
- Design: `makeGlobalHistory()` provides `undoTopOfStack`/`redoTopOfStack`, always operating on `undoStack[undoStack.length-1]` regardless of caller. The naive alternative (`lastCmdIndexByNpc[npcId]`) records each NPC's own most recent command's stack position and, on that NPC's "undo," restores THAT command's preimage directly via `Object.assign`, without first rolling back any commands other NPCs pushed afterward. Both compared against an independent ground-truth replay (a single linear undo/redo log, the only semantically coherent contract for one shared timeline) across 20+20 seeds.
- Got right: Every OTHER already-verified fix in the mega group held under this multi-agent load with zero regressions — the correct-implementation run (0/20, both configs) exercises loot-pity's dup-protection, astar-replan's occupancy handling, savemigrate's version-dispatch, and the atomic-salvage-transaction fix simultaneously across many concurrent agents and many ticks, with no divergence from ground truth on any of them. The bug found here is entirely new, isolated to the undo-targeting logic, not a regression in anything previously fixed.
- Where/why it failed: A shared command history is a single LINEAR timeline by construction — "undo" can only ever mean "revert the single most recent event on that timeline," because the state at any point in the stack is only valid relative to everything that came before it up to the top. Restoring a preimage from partway down the stack while silently keeping every state change that happened AFTER it (from other agents) produces a Frankenstein state that was never actually valid at any real point in the session's history — not "an older but internally consistent state," but bytes from two different times spliced together. This is invisible in a single-agent test because with one agent, "my last command" and "the top of the stack" are always the same index by construction, so the bug has no way to manifest until a second agent's command can land on top of the first agent's.
- Fix: Undo/redo on a shared history must operate ONLY on the literal top of the stack, never on a per-agent recorded index — if per-agent "undo my own last action, regardless of what else happened since" is a genuinely desired feature, it requires a fundamentally different design (per-agent sub-histories with a merge/rebase strategy, or rejecting the undo if the agent's last command isn't on top), not a shortcut on top of one shared linear stack. Verified: 0/20 divergences with top-of-stack-only undo at both tested scales.
- Why this fix: This generalizes rpg-progression#E5's original single-agent finding ("redo stack invalidated on any new edit") to its true multi-agent form: a shared linear history has exactly ONE valid "undo" operation at any moment (revert the top), and any design that tries to expose a per-agent view of "your last action" onto that same single stack without accounting for interleaving is reintroducing the exact class of bug a linear undo/redo stack exists to prevent — just one level higher, at the multi-agent composition layer instead of the single-command layer.
- Rule of thumb: Before sharing ONE undo/redo history across multiple independently-acting agents (players, NPCs, concurrent editors), explicitly verify that undo/redo semantics only ever target the literal top of the shared stack — any implementation that lets an agent "undo my own last action" via a remembered index, rather than the current stack top, will silently corrupt state the first time another agent's action lands on top of it. This bug is invisible at N=1 by mathematical necessity (index == top always), so single-agent testing — no matter how thorough — cannot surface it; it only exists to find once real concurrent-agent load is applied, which is exactly what a whole-group stress test (as opposed to pairwise seam testing) is for.
- Provenance (verified/assumed): VERIFIED first-hand — ran a 6-NPC, 200-op-per-seed simulation across 20 seeds composing procgen-CA+fixup, astar-replan, dbz-combat/power-scaling, loot-pity, savemigrate, and undo-redo simultaneously, comparing both undo strategies against an independent ground-truth replay: 20/20 divergences (naive per-agent-index), 0/20 (top-of-stack-only); re-verified the correct strategy at 10 NPCs / 400 ops / 20 further seeds, 0/20 divergences.

## E5 — teamcombat undo redo by rerunning breaks replay fidelity
- Date: 2026-07-13
- Project: local/sandbox-combined-rpg-progression
- Tags: [determinism][gamedev][testing]
- What: New seam (`sandbox-dbz-team-combat` and `sandbox-undo-redo` shared no prior edge) in the mega group. dbz-team-combat#E5: a symmetric fight (identical rosters, identical AI) still shows a real ~62.5/37.5 outcome split from TURN-ORDER bias alone. Composed with an undo/redo command history: a realistic "redo" implementation that RE-RUNS the fight simulation from a continuing live RNG stream (rather than replaying the captured per-round log) produced 0/300 mismatches in final WINNER — but 300/300 mismatches in the full round-by-round turn-order log, and 135/300 (45%) mismatches in final HP values. The winner-only check is misleadingly reassuring: it passes because the fixed 12-vs-10 damage asymmetry structurally determines who tends to win regardless of the exact turn sequence, while the actual replayed fight — round count, HP trajectory, combat log — is a completely different fight 100% of the time.
- Why built: rpg-progression's undo/redo pattern is already verified deterministic for simple state mutations (E1/E2's deep-copy snapshots). A full combat SEQUENCE is different: it's not one atomic state change but a multi-step simulation driven by randomness, and "redo" for a simulation invites the shortcut of "just re-run it" rather than "replay what was recorded" — this checks whether that shortcut is actually safe, using dbz-team-combat's own already-proven-sensitive-to-turn-order mechanic as the test signal.
- Design: `simulateFight(rng)` runs up to 20 rounds of a symmetric 2v2-style exchange (12 dmg to whoever is hit first each round, 10 to the other, coin-flip turn order each round via the shared rng), recording a per-round `log` of "who went first." `redoByReRunning(rng)` calls `simulateFight` again on the SAME (already-advanced) rng object. `redoByReplayingLog(log)` re-derives final state by replaying the captured log with no randomness consumed.
- Got right: Nothing about dbz-team-combat#E5's own finding needed revisiting — the turn-order bias it identified is exactly the mechanism that makes this seam's bug measurable at all (a mechanic where turn order doesn't matter to the outcome couldn't have surfaced replay divergence this clearly).
- Where/why it failed: "Redo by re-running the simulation" silently assumes the ORIGINAL random draws are irrelevant to reproducing the original outcome — true only for the narrow, coincidental property that this particular mechanic's WINNER is largely determined by the fixed damage asymmetry rather than the specific turn sequence. Every other observable property of the fight (which round it ended on, exact final HP, the full turn-order log a combat-log UI or a mid-fight achievement would need) diverges completely, because re-running consumes entirely fresh randomness continuing from wherever the live stream happened to be after the original fight — not a replay of what actually happened, a DIFFERENT fight that happens to often end the same way.
- Fix: `redo()` must replay the CAPTURED log (or command sequence) exactly, consuming no new randomness — `redoByReplayingLog`. Re-verified: 0/300 mismatches in final HP and 0/300 in winner across the identical 300-seed sweep, confirmed on every dimension, not just the misleadingly-passing winner check.
- Why this fix: This generalizes rpg-progression#E1/E2's deep-copy-snapshot principle from single atomic mutations to multi-step, randomness-driven sequences: a command's postimage (or, for a sequence, its full recorded log) is the source of truth for redo, never a live re-derivation — re-deriving from a continuing random stream is a different bug shape from the shallow-copy aliasing bug E1/E2 already fixed, but the same root cause: something that LOOKS like state (a captured outcome) actually depends on external, uncaptured state (the rng stream's current position) that the redo path doesn't control.
- Rule of thumb: When testing whether "redo" (or replay, or reconstruction) of a randomness-driven sequence is correct, checking only the FINAL/SUMMARY outcome (who won, did the test pass) can pass while the full reconstructed sequence is completely different — a coincidental structural bias in the underlying mechanic can make final winner converge even when replay fidelity is totally broken. Verify replay against the FULL recorded trajectory (every intermediate state/log entry), not just a summary statistic, especially for any mechanic already known (per dbz-team-combat#E5) to be sensitive to the exact sequence of random draws.
- Provenance (verified/assumed): VERIFIED first-hand — ran 300 seeded fights, confirming redo-by-re-running matches the original winner in 300/300 cases while diverging in the full round-log in 300/300 and final HP in 135/300 (45%), then confirmed redo-by-replaying-the-captured-log matches on every dimension (HP, winner) in 300/300 cases.

## E4 — rpg progression deallocation through history needs same transaction
- Date: 2026-07-13
- Project: local/sandbox-combined-rpg-progression
- Tags: [architecture][state][testing]
- What: Per `brain analyze seams`, applied `sandbox-combined-graph-editor#E1` ("every structural mutation must flow through the ONE history stack, including ALLOCATION") to a NEW deallocation case in the already-satisfied RPG-progression sandbox: an inventory-cap auto-salvage (drop the oldest item once inventory exceeds a cap) that a realistic implementer would treat as passive "cleanup," not a player action. Three variants tested against an independent ground truth across 20 seeds x 40 ops (pull/undo/redo): (1) salvage mutates `inventory`/`salvageLog` directly, bypassing history entirely -- 10/20 seeds diverged, confirming graph-editor#E1's lesson transfers to this domain; (2) salvage routed through `history.do()` but as its OWN, separate command from the pull that triggered it -- 20/20 seeds diverged, WORSE than bypassing history at all; (3) salvage folded into the SAME `history.do()` transaction as the triggering pull -- 0/20 seeds diverged.
- Why built: To check whether graph-editor#E1's rule ("route mutation through history") is sufficient as stated, or whether it under-specifies something that only shows up when the mutation is deallocation TRIGGERED BY another action rather than a standalone player command.
- Design: `CAP = 6`. On every `pull`, if `inventory.length > CAP`, the oldest item is auto-salvaged (`shift()`) into `salvageLog`. Variant 1: salvage runs as plain code after `history.do(pull)` returns. Variant 2: salvage runs as its own `history.do(salvage)` call immediately after. Variant 3: the salvage check lives INSIDE the pull's `history.do()` callback, so pull-and-cap-triggered-salvage is one atomic command.
- Got right: Variant 1 reproducing graph-editor#E1's exact failure shape (partial divergence, not total -- 10/20, matching "passes many cases, fails once state and undo history interact badly") confirms the lesson is domain-general, not specific to node-graph allocation. The naive fix (just wrap it in `history.do()`, variant 2) is the interesting result: it did NOT reduce divergence, it INCREASED it (10/20 -> 20/20), because "is it in the history system" and "is it the RIGHT granularity in the history system" are different questions -- variant 2 correctly stopped aliasing/omission bugs but introduced an ATOMICITY bug (a single player-perceived action, "pull [that happens to trigger a salvage]," became two separate undo-stack entries, so one `undo` only unwound the salvage half, leaving the pull in place -- a state ground truth never produces, since ground truth always treats pull+auto-salvage as one unit).
- Where/why it failed: graph-editor#E1 says allocation must go through the ONE stack; it doesn't say what counts as ONE command when an allocation triggers a cascading, same-tick deallocation. Treating them as two separate commands is a natural reading of "route it through history" and is provably worse than not routing it at all here, because it turns one user-perceived undo into a two-step unwind the user never asked for and the UI never signaled.
- Fix: The cap-triggered salvage must execute inside the SAME `history.do()` closure as the pull that can trigger it, not as a subsequent call -- one player action, one command, one undo/redo unit, matching exactly how `sandbox-combined-rpg-progression#E1`'s already-proven pattern works for a command with multiple internal effects.
- Why this fix: Undo/redo granularity should match the unit the PLAYER perceives as one action, not the unit that's convenient to implement -- "pull an item" is one action even when it cascades into a forced salvage, so it must be one command. Verified by isolating exactly one variable (where the salvage call sits) across three otherwise-identical runs: bypass (10/20), separate-command (20/20, worse), same-transaction (0/20).
- Rule of thumb: When extending "route all mutation through the history stack" (graph-editor#E1) to a NEW deallocation that is triggered BY another action (a cap eviction, a cascading delete, an auto-consume) rather than requested directly by the player, the fix is not "also call history.do() for the deallocation" -- it is "include the deallocation inside the SAME history.do() transaction as its trigger." Test this explicitly: routing a cascading mutation through history as a separate command can measurably regress correctness versus not routing it at all, because it trades an aliasing/omission bug for an atomicity bug that's just as invisible until undo/redo interleaves with it.
- Provenance (verified/assumed): VERIFIED first-hand -- ran the identical 20-seed x 40-op sequence through all three variants against an independent structuredClone ground truth, comparing both `inventory` and `salvageLog` after every run: 10/20, 20/20, and 0/20 divergences respectively, isolating the transaction-boundary change as the only variable between the second and third runs.

## E3 — rpg progression anim presentation state must be outside history
- Date: 2026-07-13
- Project: local/sandbox-combined-rpg-progression
- Tags: [animation][architecture][state]
- What: Per `brain analyze seams`, folded `sandbox-anim`'s FSM (idle/walk/attack clips, anim/E4's transition-reset fix) into the already-satisfied RPG-progression sandbox (reusing its command history, not rebuilding), driven by the existing `move`/`cast` commands. Naively including the `anim` object in the SAME state blanket-deep-copied by every command's preimage/postimage (the exact mechanism rpg-progression#E1/E2 proved correct for `inventory`/`weightTable`/`pos`) produced 109/218 (50%) of undo/redo operations across 20 seeds visibly changing the animation clock — including undos of commands like `pull` that have nothing to do with movement or combat and should never touch it.
- Why built: rpg-progression#E2 established that a blanket structural-clone copy strategy generalizes to new mutable fields "for free." This tests whether that generalization has a limit — specifically whether it holds for PRESENTATION state, not just additional authoritative state.
- Design: `anim = {clip, frameIndex, accumulator, done}`, ticked by a continuous per-frame `tick(dt)` call (advancing frameIndex/accumulator between discrete commands) and updated on transition by `move`/`cast` via anim/E4's own verified `play()` reset. Two variants: (a) `anim` folded into the same object undo/redo already deep-copies; (b) `anim` held in a separate object never touched by `history.do/undo/redo`.
- Got right: anim/E4's transition-reset fix (frameIndex/accumulator/done all reset on `play()`, guarded by a same-clip no-op) worked exactly as designed in both variants — no leak-across-clips bug reappeared. rpg-progression#E1/E2's aliasing fix also held in variant (a): the animation state was never CORRUPTED (no stale-reference bugs), it was correctly reverted to an EARLIER value on every undo -- structurally working exactly as designed, which is precisely the problem.
- Where/why it failed: rpg-progression#E1/E2 proved a blanket copy strategy is safe against ALIASING (a field silently shared/corrupted across commands). It says nothing about SCOPE (which fields belong in the undo-tracked snapshot at all). `anim`'s frame/accumulator/done are exactly the kind of state `sandbox-combined-game-loop#E1` already named and drew a hard boundary around in a different project: presentation/feel state that must be split from authoritative (undo-fingerprinted) state. Folding anim into the authoritative blanket copy means every undo -- even of an unrelated `pull` -- snaps the animation clock back to whatever it was at that command's preimage capture, a real, player-visible defect (the sprite visibly rewinds mid-walk-cycle on an inventory undo).
- Fix: Move `anim` out of the state object the command history captures entirely. It is ticked and mutated directly by `tick(dt)`/`play()`, never wrapped in `history.do()`, and therefore structurally cannot be reverted by undo/redo. Re-ran the identical 20-seed op sequence: 0/218 undo/redo operations changed anim state.
- Why this fix: This is `sandbox-combined-game-loop#E1`'s authoritative/presentation split, generalized: the question "does this field belong in the undo-tracked snapshot" is independent of "is the copy strategy safe" -- a perfectly-implemented blanket deep-copy will faithfully replay a scope mistake with zero corruption and zero errors, which is exactly why this class of bug is easy to miss: nothing crashes, nothing looks structurally wrong in a diff, the bug is only visible as an unwanted temporal side effect (state changing on an undo that shouldn't have touched it).
- Rule of thumb: A blanket/structural-clone copy strategy for a command history (rpg-progression#E1/E2's fix) generalizes automatically to new AUTHORITATIVE fields, but you must still explicitly decide, per new field, whether it IS authoritative -- presentation/feel/cosmetic state (animation clock, particle timers, camera shake) must live outside the captured state entirely (game-loop#E1's split), or every undo will silently rewind it too. "The copy strategy is safe" and "this field belongs in the snapshot" are two separate questions; verify both when a new system joins a group, not just the first one.
- Provenance (verified/assumed): VERIFIED first-hand -- ran the identical 20-seed, 45-op sequence (move/cast/pull/undo/redo/tick) against both variants, directly comparing `JSON.stringify(anim)` before/after every undo/redo call: 109/218 changed in the folded-in variant, 0/218 in the split-state variant.

## E2 — sandbox combined rpg progression group merge copy strategy generalizes
- Date: 2026-07-13
- Project: local/sandbox-combined-rpg-progression
- Tags: [state][architecture][testing]
- What: Per `brain analyze seams`, two independently-satisfied emergent groups (movement/pathfinding: astar-replan+collision+anim+combined-movement-stack; and RPG/combat: dbz-combat+loot-pity+power-scaling+savemigrate+undo-redo+combined-rpg-progression) share a direct bridge node (astar-replan <-> undo-redo, astar-replan <-> dbz-combat). - Why built: To test whether "satisfied" (0/20 divergences) actually transfers when a group is EXTENDED rather than re-verified in isolation — per the group-training plan, adding systems should reuse the proven sandbox and re-run old diagnostics as a regression check, not just hunt for new bugs in the new part alone.

- Got right: The undo-redo aliasing fix from rpg-progression#E1 (switch preimage/postimage capture from a hand-picked shallow spread to a BLANKET `JSON.parse(JSON.stringify(state))`) required zero additional code to cover the new `pos` field -- it is a whole-state structural clone, not a per-field allowlist, so it generalized automatically the moment a new system introduced a new mutable field. - Where/why it failed: It didn't -- this is a confirmatory/negative result, not a bug report, and is being recorded because a clean group-merge result is exactly the signal that tells `brain analyze groups` this bridge edge is now safe (a positive edge), which is itself decision-relevant data for future group-training, not just an absence of news.
- Fix: N/A (no bug found). The design choice worth keeping: DO NOT special-case which fields a command's preimage copies. A copy strategy that clones the whole state structurally, rather than a curated field list, is future-proof against systems added later introducing their OWN new mutable fields -- the alternative (an allowlist of "fields the undo system knows about") would have required a matching code change every time a new system joined the group, and would fail exactly the way rpg-progression#E1's original shallow-copy bug failed: silently, only under composition, invisible to either system's own tests.
- Why this fix: A structural/blanket copy strategy trades a small, constant runtime cost (serialize the whole state every command) for eliminating an entire class of aliasing bugs at every future group-merge, not just the one that was already found -- verified here by extending the group and getting a clean result on the first try, with no additional aliasing-specific code written for the new field.
- Rule of thumb: When merging two independently-satisfied groups by adding one as a layer onto the other's already-proven sandbox (rather than building a new one from scratch), the regression check that matters most is: does the OLD group's fix (not just its passing tests) generalize to the NEW group's mutable state, or did it only work by accident of which fields existed at the time it was written? A copy-strategy fix (or any fix phrased as "handle this class of field," not "handle these specific fields") is the version that survives a merge for free; verify this explicitly rather than assuming it, since the failure mode (an allowlist silently missing a new field) produces the exact same kind of invisible-until-composed bug the original fix existed to catch.

## E1 — sandbox combined rpg progression undo redo aliases shared mutable state
- Date: 2026-07-13
- Project: local/sandbox-combined-rpg-progression
- Tags: [state][architecture][testing]
- What: A 5-system RPG sandbox composed dbz-combat's resource-cost binding (E4), power-scaling's %-max-HP damage cap (E2), loot-pity's floor-based dup-protection (E1) and non-zero-weight fallback (E2), savemigrate's version-dispatch round-trip (E1), and undo-redo's command-history pattern (E3/E4/E5) — five systems verified correct in isolation, never run together. Driving 40 mixed pull/cast/save/undo/redo ops (independent RNG streams for op-selection vs loot-draw, so outcomes are directly comparable) against an independent structuredClone ground-truth model found 20/20 seeds diverging from ground truth when the undo-history's command preimage captured loot-pity's `weightTable` and the `inventory` array by REFERENCE (a realistic, easy-to-write implementation) instead of by deep copy. Switching only the copy strategy to deep-copy (`JSON.parse(JSON.stringify(...))`) dropped divergences to 0/20 with no other change.
- Why built: To test whether undo-redo's own already-verified aliasing fix (E3: "an undo history is only trustworthy if every entry [is] deep-copied") actually gets applied everywhere it needs to once a SECOND system (loot-pity) contributes its own separately-verified, separately-correct design choice: mutating a shared table in place on every pull. Neither sandbox's own tests could see this, since undo-redo's tests never had an in-place-mutated shared object to alias, and loot-pity's tests never had an undo/redo system replaying stale snapshots of its table.
- Design: `weightedPickWithPity` mutates `state.weightTable` in place every pull (loot-pity's own verified, correct behavior). `makeHistory(copyStrategy)` captures a command's preimage/postimage via either `{...state, inventory: state.inventory, weightTable: state.weightTable}` (shallow — top-level spread, but the two mutable fields are left as bare references) or full `JSON.parse(JSON.stringify(state))` (deep). Both variants were run against the identical 40-op sequence per seed (20 seeds) and checked against a ground-truth replay using `structuredClone` at every boundary.
- Got right: `ki` (resource cost binding, dbz-combat E4) and `dummyHp` (power-scaling's capped damage, E2) matched ground truth in EVERY seed under BOTH copy strategies — primitives captured by value are immune to this class of bug by construction, and the save/migrate round-trip (`version` field survives a `save` op mid-sequence) never itself caused a divergence. The bug is confined exactly to the two fields that are objects/arrays, confirming it is an aliasing-of-shared-mutable-state bug specifically, not a general fragility of the composition.
- Where/why it failed: undo-redo/E3 already established the general rule ("deep-copy every history entry") from ITS OWN single-system tests, which used command state shapes where nothing was mutated by code outside the command itself. loot-pity's `weightedPickWithPity` is designed to mutate its weight table in place — a correct, already-verified design for a system with no undo concept. Composed, a command's captured "preimage" for pull #1, if taken by reference, is not actually a snapshot of the past — it is a live view of `state.weightTable`, which pull #2's in-place mutation silently rewrites before pull #1 is ever undone. Undoing pull #1 then restores whatever the table currently looks like (post-pull-#2, post-pull-#3, ...), not what it looked like before pull #1 — corrupting both the weight table's decay/floor state (defeating loot-pity/E1's own dup-protection invariant after an undo/redo cycle) and the inventory contents (since the array reference has the same problem). This reproduced in 20/20 seeds, not an edge case.
- Fix: Deep-copy (or an equivalent structural clone) any field captured into an undo/redo command's preimage/postimage, with no exception for fields that "feel like" shared config/state rather than per-command data — `weightTable` looked like global system state, not something a single pull command owns, which is exactly why it was easy to leave un-copied.
- Why this fix: undo-redo/E3's rule was already correct and sufficient; the gap here was applying it inconsistently once a second system introduced a mutable structure that the undo system's author didn't think of as "command state." Verified by isolating the ONLY variable (copy strategy) across an otherwise-identical 40-op x 20-seed sweep: 20/20 divergences with shallow, 0/20 with deep, with `ki`/`dummyHp` unaffected in both — the fix is precisely targeted at the actual mechanism, not a coincidental improvement.
- Rule of thumb: When composing an undo/redo command system with ANY other system that mutates a shared structure in place as part of its own correct, verified design (a weighted table, a pool, a cache, a counter object) — re-audit every field an undo command captures and confirm it is copied, not referenced, with special attention to fields that look like "global system state" rather than obviously-per-command data. A field being outside the undo system's own mental model of "what a command touches" is exactly the case its own single-system tests would never have exercised.
- Provenance (verified/assumed): VERIFIED first-hand — ran the identical 40-op x 20-seed sweep under both copy strategies against an independent structuredClone ground-truth replay, confirmed 20/20 divergence with shallow-reference capture and 0/20 with deep-copy, and confirmed the two resource/primitive fields (ki, dummyHp) never diverged under either strategy, isolating the bug to the two shared-mutable-object fields specifically rather than a general composition fragility.
