## E1 — sandbox pathfinding astar weighted heuristic sweet spot
- Date: 2026-07-11
- Project: local/sandbox-pathfinding-astar-heuristic
- Tags: [algorithm][gamedev][state]
- What: A grid A* implementation was swept across heuristic weights (a common "weighted A*" speed/optimality tradeoff technique, where multiplying the admissible heuristic by a weight >1 trades path optimality for fewer node expansions) to characterize the actual shape of that tradeoff, rather than assuming it's linear. On a pinned 30x30 test map, weights of 1.5, 2, and 3 all found the mathematically OPTIMAL path (0% longer than weight=1's ground truth) while cutting node expansions by 56-58% versus the admissible baseline — but weights beyond that (5, 10, 50) bought almost no further expansion reduction (only ~5% more) while path length kept degrading (3.1% longer at weight=5, 9.4% longer at weight=10, capping there even at weight=50).
- Why built: A pathfinding-algorithm sandbox to characterize weighted A*'s speed/quality tradeoff curve empirically, since the common assumption ("higher weight = proportionally faster, at some quality cost") wasn't obviously going to hold and was worth measuring directly rather than trusting intuition.
- Design: Standard A* with Manhattan-distance heuristic, weight applied as `f = g + weight * h`. Swept weight in {0, 1, 1.5, 2, 3, 5, 10, 50} across multiple random 30x30 grid maps (wall density ~0.25-0.28), recording node-expansion count and resulting path length at each weight, plus a ground-truth optimal path (weight=1) for comparison.
- Got right: Measuring BOTH expansion count and path length across the same weight sweep (not just one metric) is what surfaced the actual shape of the curve — either metric alone (just "expansions go down" or just "path length goes up") would have looked like an unremarkable monotonic tradeoff and hidden the real finding.
- Where/why it failed: The tradeoff curve is NOT linear or even close to it — it has a steep initial drop then a hard flattening. Going from weight=1 (admissible, 347.4 mean expansions across 7 solved maps) to weight=1.5 (106.1 mean expansions) is a ~70% reduction for ZERO path-length cost on the pinned test map. Going from weight=1.5 all the way to weight=10 (a further 6.7x increase in weight) only reduced expansions a further ~12% (106→93) while path length degraded steadily the whole way. A naive "pick a big weight for max speed" instinct wastes almost all of the extra weight budget on essentially nothing, while paying steadily worsening path quality for it.
- Fix: Not applicable — no bug, this is a characterization result to inform future tuning decisions. The verified, portable takeaway: when tuning weighted A* for a real-time game (enemy pursuit, NPC movement), start the weight sweep in the 1.5-2 range and measure — that band is where nearly all of the available speedup lives while often still finding the exactly-optimal path; treat weights above ~3 as needing explicit justification (a genuine expansion-count crisis) since they're very unlikely to buy meaningful additional speed relative to the quality they cost.
- Why this fix: The proven theoretical bound (a weighted-A* path is at most `weight × optimal` in cost) is a worst-case guarantee, not a description of typical behavior — this sandbox measured the TYPICAL behavior directly (0/50 trials violated the weight=2 bound, and typical suboptimality at weight=2 was 0%, far under the theoretical worst case), which is the number that actually matters for tuning a real system, not the worst-case bound alone.
- Rule of thumb: When adding a heuristic weight to A* for a speed/quality tradeoff, don't assume the relationship between weight and speedup is linear or even monotonically useful across its whole range — sweep and measure both node-expansion count and path-length on representative maps first. For grid-based games with moderate wall density, expect almost all the useful speedup to be available already at weight ≈1.5-2, with diminishing-to-zero further returns and steadily worsening path quality beyond that.
- Provenance (verified/assumed): VERIFIED first-hand — ran the actual A* implementation (Node.js sandbox) across a weight sweep on both an aggregate multi-map test (10 random maps per weight) and a single pinned map for exact before/after comparison; the theoretical-bound spot-check (0/50 violations at weight=2) was also run directly, not assumed from the proof alone.
