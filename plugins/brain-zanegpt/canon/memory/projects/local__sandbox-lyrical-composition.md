## E9 — rich rhyme vs repetition needs word identity not just phonemes
- Date: 2026-09-28
- Project: local/sandbox-lyrical-composition
- Tags: [lyrical-composition][rhyme][testing]
- What: A phoneme-only rhyme detector cannot distinguish a RICH rhyme (same sound, different word — "night"/"knight") from plain word REPETITION ("night"/"night") — both compare phoneme-equal under the same check. Craft treats these oppositely (rich rhyme is a deliberate technique; exact repetition is usually not counted as a rhyme at all, sometimes penalized as lazy). Telling them apart needs an explicit word-identity (`a != b`) check layered on top of the phoneme comparison, not implied by it.
- Why built: `lyrics`/`rhyme` domains were near-empty in memory canon; this is the smallest possible case that separates "sounds the same" from "counts as a rhyme," since it isolates word-identity as the one variable that changes between the two example pairs while phoneme content stays fixed.
- Design: Deterministic Python (`sandbox_lyrical_rhyme.py` loop 12), a toy lexicon entry for night/knight (identical phoneme tuple by construction, both /naɪt/), compared via a phoneme-equality function against both the night/knight pair and the night/night pair.
- Got right: The phoneme-equality check is correct in the narrow sense — it accurately reports that the two words sound identical in both cases, which is true.
- Where/why it failed: "Sounds identical" and "is a rhyme" are not the same predicate the moment word identity enters the picture, and a detector built only from the phonetic representation has no access to word identity at all unless it's given the words as well as their sounds — which a purely phoneme-keyed lookup (a natural simplification once you have a pronunciation dictionary) discards by construction.
- Fix: Layer a `word_a != word_b` check on top of the phoneme match before classifying something as a (rich) rhyme; when they're equal, classify as repetition instead, a distinct category from any rhyme type.
- Why this fix: The two categories are craft-opposite (rich rhyme rewarded, repetition often flagged as lazy), so silently merging them isn't a minor labeling slip — a rhyme-density or rhyme-quality metric built on the phoneme-only check would count every repeated word as if it were a deliberate rich rhyme.
- Rule of thumb: A phonetic/sound-based match is not automatically a rhyme classifier — "same word repeated" and "different word, same sound" both satisfy sound-equality and need to be told apart by an orthogonal, cheap check (word identity) before the sound-equality result is used for anything craft-relevant.
- Provenance (verified/assumed): Verified first-hand — sandbox built and run; the printed True/True match under phoneme-only comparison for both pairs is observed output, and night/knight's shared phoneme transcription is verified against real CMUdict via the `pronouncing` package this session (`phones_for_word` returns `N AY1 T` for both), replacing an earlier hand-transcription this entry originally shipped with.

## E8 — rhyme scheme closure distance operationalizes emotional motion
- Date: 2026-09-28
- Project: local/sandbox-lyrical-composition
- Tags: [lyrical-composition][rhyme][gamedesign][testing]
- What: Operationalizes the existing idea kernel `[SONGWRITING / rhyme / rhyme-scheme-shape-sets-a-songs-emotional-motion / aabb-stops-often-abba-stays-open-and-wistful]` as a STRUCTURAL measurement, not an aesthetic claim: define a scheme's "closure distance" per rhyme pair as the number of intervening lines between a line and its most recent same-letter partner. Measured across six schemes (AABB, ABAB, ABBA, AAAA, ABCB, AABC), AABB's every pair closes at distance 1 (adjacent), ABBA's outer pair closes at distance 3 (as far apart as a 4-line scheme allows), and — the one genuinely non-obvious result — AAAA (maximum possible letter repetition) still caps at distance 1, because each repeated line closes on the PREVIOUS occurrence of its letter, not the first; repetition count and closure distance are independent quantities.
- Why built: The idea kernel asserts a real craft distinction (AABB "stops," ABBA "stays open") in purely aesthetic language, which is exactly the kind of claim T22 says needs a sandbox before it's trusted, and exactly the kind of claim that CAN'T be fully closed by one (whether a scheme "feels" open is a human judgment). What a sandbox CAN settle is whether there is a structural correlate underneath the aesthetic language, measurable without appeal to feeling — closure distance is that correlate, and it needed to be checked against more than the two named examples to see if it holds generally or was cherry-picked.
- Design: A deterministic Python function (`sandbox_lyrical_structure.py` loop 4) computing, for each letter occurrence in a scheme string, the line-distance to that letter's previous occurrence (no distance recorded for a letter's first occurrence, since it has no partner yet). Run across six schemes chosen to include the two named cases, a maximal-repetition edge case (AAAA), and two irregular schemes with no closing pair at all (ABCB has one pair; AABC has one pair).
- Got right: AABB and ABBA reproduce the kernel's claim exactly at the structural level (distance 1 vs distance 3) — the aesthetic language has real structure under it, at least for these two named schemes.
- Where/why it failed: The one case that would have been wrong to assume by analogy: AAAA is the scheme with the MOST repetition of any tested, and a naive "more repeats = further apart on average, more expansive" intuition would guess AAAA's closure distance grows with each additional A. It doesn't — every A closes on the IMMEDIATELY PRECEDING A, so AAAA's max closure distance is 1, identical to AABB's, despite four same-letter lines instead of two. Repetition count is not a proxy for closure distance; they're independent axes that happen to correlate in the two originally-cited examples only because those examples both have exactly two rhyming lines per letter.
- Fix: When operationalizing an aesthetic craft claim into a metric, don't stop at the cited examples — sweep the metric across the general case (here, all short standard scheme shapes) specifically looking for a case where an intuitive proxy (repeat count) and the actual defined metric (closure distance) would diverge, before trusting the metric generalizes past the two anecdotes that motivated it.
- Why this fix: The kernel's own two examples cannot distinguish "closure distance" from "repeat count" as the real driver, because both examples happen to have exactly 2 occurrences per letter — AAAA is the cheapest possible test that separates the two candidate explanations, and it settles which one the metric actually is.
- Rule of thumb: An aesthetic craft claim backed by exactly two contrasting examples may have MULTIPLE structural metrics consistent with both — before generalizing one of them, find the case in the domain's own state space (here: the scheme with maximum letter repetition) that would separate the candidate metrics, and check it before trusting either.
- Provenance (verified/assumed): Verified first-hand — sandbox built and run; the six schemes' printed closure-distance lists (AABB:[1,1], ABAB:[2,2], ABBA:[1,3], AAAA:[1,1,1], ABCB:[2], AABC:[1]) are observed output. Scope note, not a hedge on the above: this entry's claim is limited to the STRUCTURAL measurement (closure distance as defined and computed). Whether a human listener actually perceives closure distance as the mechanism behind the kernel's "stops vs stays open" language is a separate, perceptual question that stays a human judgment call — outside what this or any sandbox measures, and outside what this entry asserts (ties to the existing T11-style limit already on record for other domains: automated verification has a ceiling at "logic," not "feel").

## E7 — rhyme letter assigner needs an explicit matching scope
- Date: 2026-09-28
- Project: local/sandbox-lyrical-composition
- Tags: [lyrical-composition][rhyme-tooling][algorithm][state]
- What: Two sandbox loops (loops 1 and 5) verify the existing idea kernel `[SONGWRITING / rhyme-tooling / two-pass-letter-assignment-keeps-schemes-legible]` (previously asserted, not sandbox-verified) and find a second, independent way a rhyme-scheme letter-assigner's matching SCOPE can be wrong. (1) A single-pass, vowel-only letter assigner processing day/way/gaze in order collapses all three into one letter (AAA) because it has no way to prefer a PERFECT match (day/way, same vowel+coda) over an ASSONANCE-only one (gaze, same vowel, different coda) once both are candidates for the same line — a two-pass assigner that resolves perfect rhymes first and reserves their letter correctly separates them (AAB). (5) A letter assigner with no notion of SECTION (verse vs chorus) will match a chorus line's rhyme_class against an EARLIER VERSE line sharing the same class purely by coincidence, producing a scheme (`ABABACAC`) that visually claims the chorus rhymes with the verse; a section-aware assigner scoping its search to the current section only produces the intended `ABABCDCD`.
- Why built: The `rhyme-tooling` idea kernel asserted the two-pass claim without a sandbox citation; `brain train new-domain` on `lyrics`/`rhyme` showed 0 memory entries backing any rhyme-tooling claim with an actual run. Built the smallest algorithm that could exhibit the claimed failure, then asked whether the same assigner has other scope blind spots — section boundaries were the first candidate, since nothing about a rhyme_class match inherently respects song structure.
- Design: Two small deterministic Python letter-assigners (`sandbox_lyrical_structure.py` loops 1, 5), no RNG. Loop 1 represents words as (vowel, coda) pairs so "perfect" and "assonance" are independently checkable (a flat rhyme_class id, tried first, could not represent the conflict at all and had to be rebuilt). Loop 5 tags each line with a section label and compares a section-blind assigner against a section-aware one on an 8-line verse+chorus construction with a deliberately coincidental cross-section rhyme_class match.
- Got right: Both two-pass and section-aware variants produce exactly the intended scheme in their respective test, with no side effects on the lines that were never in conflict (the day/way pair keeps its shared letter in both variants; the within-chorus C-rhymes are unaffected by section-awareness).
- Where/why it failed: Both failures are the same root cause wearing different clothes: the assigner's candidate search has an implicit, UNBOUNDED scope (every earlier line, no type or section filter) when the correct scope is narrower and TYPED (perfect-rhyme candidates take priority over assonance candidates; same-section lines only, absent a deliberate cross-section callback). An assigner that searches "everything before this line, first match wins" will find A match, just not necessarily the RIGHT one.
- Fix: Make the candidate search's scope an explicit, ordered set of filters rather than a single flat lookup: (a) perfect-rhyme candidates resolved and their letters reserved before any assonance-only candidate is considered, and (b) candidates restricted to the current section unless a cross-section link is explicitly intended. Both are two-pass in spirit — a first pass to claim the higher-priority scope, a second pass for what's left.
- Why this fix: "First match in reading order" is a scope choice disguised as no choice at all — it silently treats "the first candidate line found" as authoritative, which is only correct when candidates never compete by type or by section. Since rhyme type and song structure are exactly where lyric composition tools are asked to be precise (a scheme letter that means something to a songwriter reading it), the unbounded scope's convenience cost is paid in the tool's most-used feature.
- Rule of thumb: A "find the earliest/nearest match" assigner has an implicit search SCOPE — before trusting its default (usually: everything seen so far, first hit wins), ask what two things it will now conflate that should stay separate (rhyme type; song section; any other typed boundary the domain has), because the assigner cannot know a boundary exists unless it is told to respect one.
- Provenance (verified/assumed): Verified first-hand — both sandboxes built and run; the printed schemes (single-pass AAA vs two-pass AAB; section-blind ABABACAC vs section-aware ABABCDCD) are observed output, not estimates, and the day/way/gaze rhyme judgments (day/way perfect, gaze assonance-only) are verified against real CMUdict via the `pronouncing` package this session (day=D EY1, way=W EY1, gaze=G EY1 Z — day/way share the empty coda, gaze's Z coda is the only difference), replacing an earlier hand-transcription this entry originally shipped with.

## E6 — eye rhyme spelling matcher can hit total false positive rate
- Date: 2026-09-28
- Project: local/sandbox-lyrical-composition
- Tags: [lyrical-composition][rhyme][testing]
- What: A spelling-suffix rhyme matcher ("do the last N letters match?") run on the classic English through/rough/though/cough set — all four spelled with "-ough" — flags all 6 pairs as rhyming. Phonetically, none of the four words shares a vowel sound with any other (UW / AH / OW / AA respectively), which is a prerequisite for even the weakest defined rhyme category (assonance); the false-positive rate on this set is exactly 100%, not merely elevated.
- Why built: `lyrics`/`rhyme` domains were near-empty in memory canon. Spelling-suffix matching is the cheapest possible rhyme heuristic (no phonetic dictionary needed) and a plausible first implementation for anyone building rhyme-aware tooling without a pronunciation lookup; the through/rough/though/cough set is the standard linguistics example for English spelling-to-sound irregularity, so it's a strong, well-known adversarial input rather than a constructed edge case.
- Design: Deterministic Python (`sandbox_lyrical_rhyme.py` loop 11), phonetic transcriptions for the four words looked up from real CMUdict via the `pronouncing` package (through=UW, rough=AH+F, though=OW, cough=AA+F — CMUdict's first of two listed pronunciations for cough, AO+F being the other; both are disjoint from UW/AH/OW either way), compared against simple suffix string matching over all 6 pairs.
- Got right: The spelling check does exactly what it's built to do — matches the literal suffix — and is not itself buggy; the failure is entirely in treating spelling as a stand-in for sound.
- Where/why it failed: 6/6 pairs pass the spelling check; 0/6 share a vowel phoneme. This isn't a matcher being slightly too permissive — it is maximally wrong on this input, because English orthography and English phonology diverge completely for this particular letter sequence (a known, extreme case, not a tail probability).

## E4 — scanning scope determines whether pov and rhyme signals are seen
- Date: 2026-09-28
- Project: local/sandbox-lyrical-composition
- Tags: [lyrical-composition][testing][state]
- What: Two sandbox loops (9, 17) show the same principle from opposite directions: a scanner's default SCOPE (which tokens it looks at, and where) determines whether a real lyrical signal is seen, independent of whether the scanner's per-token logic is correct. ## E2 — fixed slant rhyme threshold is not proportionally consistent
- Date: 2026-09-28
- Project: local/sandbox-lyrical-composition
- Tags: [lyrical-composition][rhyme][testing]
- What: A fixed "at most K phonemes differ" slant-rhyme threshold (K=2) is not proportionally consistent across word length: it ACCEPTS a 3-phoneme pair (cat/bad) that differs in 2 of 3 phonemes (67% different) while it REJECTS a 7-phoneme pair that differs in 3 of 7 phonemes (43% different) — the pair judged MORE similar by proportion is the one the fixed threshold refuses.
- Why built: Fixed absolute thresholds recur across the shared canon as a known hazard in other domains (a numeric epsilon, a distance cap); slant/near-rhyme detection is a natural place for the same pattern to reappear, since "how many phonemes may differ" is exactly the kind of knob a rhyme tool would expose, and nothing about a fixed K makes it scale-aware by default.
- Design: A standard Levenshtein edit-distance implementation over phoneme-token lists (deterministic, no RNG), applied to a hand-built short pair (3 phonemes, edit distance 2) and a hand-built long pair (7 phonemes, edit distance 3), with a single fixed threshold K=2 applied to both.
- Got right: The edit-distance computation itself is straightforward and behaves as expected (correctly returns 2 and 3 for the constructed pairs); the bug is entirely in what a FIXED threshold means once word length varies, not in the distance metric.
- Where/why it failed: K=2 is calibrated (implicitly) against the short pair's scale, where 2 differing phonemes out of 3 is already the maximum meaningful distance before the words share nothing; the same absolute budget on a 7-phoneme word is a much smaller proportional allowance, and the boundary lands exactly backwards — the short pair (67% different) passes, the long pair (43% different, genuinely closer in proportion) fails.
- Fix: Scale the threshold by word length — accept when `edit_distance / max(len_a, len_b) <= P` for some proportion P, rather than `edit_distance <= K` for a fixed K. This is the standard fix for the same failure mode wherever it recurs (a distance budget needs a denominator matching the thing it's being compared against).
- Why this fix: A fixed K implicitly assumes the words being compared are roughly the same length as whatever pair K was chosen against; lyric words vary from 1 to 5+ syllables in the same passage, so that assumption fails routinely, not rarely.
- Rule of thumb: Any "at most K units differ" acceptance threshold needs a denominator — ask what K means as a proportion of the SMALLEST and LARGEST plausible input before fixing it as an absolute, or verify directly (as here) that the threshold's accept/reject boundary doesn't invert relative to proportional similarity.
