## E1 — json big id rounding is runtime specific and needs an exact bigint guard
- Date: 2026-10-10
- Project: local/sandbox-kernel-serialization
- Tags: [serialization][json][javascript][verification][testing]
- What: Re-verified the kernel ideas:SERIALIZATION/json/parse-silently-rounds-integers-past-2^53 on a real Node runtime driven from a Python harness, and pushed it until it stopped holding. The headline holds (parse of 9007199254740993 yields 9007199254740992, no error), but the defect lives in the number-typed consumer, not in the JSON text, and the kernel's wording "integers past 2^53" is wider than the truth.
- Why built: The kernel was never applied by any memory entry. Its claim is one first-hand example; the open questions were how much of an id range actually corrupts, whether the usual safeguards (round-trip test, equality check, digit-count guard, quoting) catch it, and where the quote-as-string fix itself breaks.
- Design: Python (stdlib only) pipes id literals into a real Node process, and also uses Python json.loads and float() as contrasting substrates. Sweeps of 1000 consecutive ids at 2^53 and 2^54, a mixed set of exactly representable large ids, and 16-digit safe ids. Checks: plain parse, parse-stringify-parse, string transport, string transport followed by Number(), reviver with source text plus BigInt, and two corruption detectors (compare printed form vs compare BigInt values).
- Got right: Python json.loads keeps 9007199254740993 exactly while Node rounds it, so the claim is a property of double-typed consumers and must be tested on the real runtime (sandbox-kernel-verification-method/E1 was the reason to drive Node instead of only modelling it). Corruption is exact arithmetic of the double grid: 500 of 1000 ids corrupt at 2^53 (spacing 2), 750 of 1000 at 2^54 (spacing 4), and the 2^54 block collapses 1000 ids into 251 distinct values, so two different ids can become one key.
- Where/why it failed: Three of my own expectations and the kernel wording broke. (1) I predicted 500 distinct values in the 2^53 block and observed 501, because the last odd id ties to even and rounds up out of the block; the corrupted count was right. (2) The wording "any integer larger than 2^53 is rounded" is false for half of them: the even ids in the 2^53 block, and large exactly representable ones such as 2^60 and 2^62, survive unquoted, so the rule is "ids that are not exactly representable". (3) Two natural guards fail: a parse-stringify-parse test passed 1000 of 1000 while 500 differed from the truth (mirage/E8 again: a round trip proves self-agreement), and a detector comparing String(Number(lit)) to the literal raised 2 false positives on exact ids like 2^60 because the printer emits shortest digits, not the exact digits.
- Fix: Quote the id at the producer, and make the consumer treat it as an opaque string (Number(str) on the consumer re-corrupted exactly the same 500). Where numbers must stay numeric, parse with a reviver that reads the source text and builds a BigInt (0 of 1000 corrupted on Node 22), and guard with BigInt(Number(lit)) !== BigInt(lit), which had 0 false negatives and 0 false positives. Do not guard by digit count: 16-digit ids such as 9007199254740991 are exact and a >15-digit rule flagged 3 of 3 of them.
- Why this fix: The loss happens at the number-typed boundary and cannot be undone downstream, so the only exact fixes are to keep the digits as text or as an arbitrary-precision value across that boundary. The BigInt comparison tests the actual property (is the double equal to the integer) instead of a proxy (printed length, printed text). JSON.stringify of a BigInt throws a TypeError, so the write side is loud while the read side is silent, which is why the read side needs the explicit guard.
- Rule of thumb: Test an id-precision claim on the real consuming runtime, not on a different language's JSON parser. In a JS-style consumer, an integer id is only safe unquoted if the double represents it exactly, so quote or BigInt-parse every id that can exceed 2^53 and detect loss with an exact value comparison, never with a round-trip test, a printed-text comparison or a digit count. Narrowed to what was run: 2^53 and 2^54 sweeps, one mixed set and one runtime version, not every magnitude. The money-in-cents example is remote: 2^53 cents is about 90 trillion units, so it only bites at that scale or with very fine fixed-point scales.
- Provenance (verified/assumed): Verified first-hand by running the sandbox against a local Node runtime (version 22 line) and Python 3 json; all numbers above are from that run. The kernel's real-world examples (snowflake and database ids) are carried over from the kernel text as assumed context.

- Polarity: compatible
