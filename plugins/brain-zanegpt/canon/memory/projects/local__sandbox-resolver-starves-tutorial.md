## E2 — seed tutorial starvation is a pipeline property
- Date: 2026-07-13
- Project: local/sandbox-resolver-starves-tutorial
- Tags: [tutorial][testing][gamedev]
- What: `brain train new-domain tutorial` (0 entries tagged, despite two already-sandboxed real findings about tutorial-starvation never carrying the tag). Composed: `local__sandbox-resolver-starves-tutorial.md#E1` (a single-action-resolver's priority ranking can silently starve an entity-pinned tutorial trigger) and `local__sandbox-capture-layer-starves-tutorial.md#E1` (a closed-vocabulary capture layer can silently drop the event before the resolver ever sees it). Both are the SAME shape at different pipeline positions: an entity-pinned tutorial trigger sits at the end of a chain of independent layers (capture → resolver → trigger), and each layer is an independent silent-starvation point. Sandbox-confirmed an endpoint-only audit (does the raw input fire?) reports healthy while the tutorial never fires, because the failure is internal to the pipeline, not at either endpoint.
- Why built: Both source entries were filed as isolated, project-specific bugs (a resolver-priority bug in one sandbox, a capture-vocabulary bug in another) — neither generalizes to "this is a property of any layered pipeline feeding an entity-pinned trigger," so a THIRD layer added later (e.g. a cooldown gate, an accessibility remap, a network-authority check) has no standing expectation that it too needs auditing.
- Design: `sandbox.py` — zero RNG, zero wall-clock. A 3-layer pipeline (`capture_vocab_gate`, `resolver_priority_gate`, `tutorial_entity_pin`) mirroring the two real bugs' actual pipeline shape, each layer a pure boolean gate. Ran with the resolver layer deliberately failing (mirroring `sandbox-resolver-starves-tutorial#E1`'s exact bug) while the capture and pin layers pass, then compared an endpoint-only check ("does the raw input fire?") against the pipeline's real end-to-end result.
- Got right: Both source entries' own root-cause analysis is correct and stands — this seed doesn't revise either finding, only names the shared shape between them.
- Where/why it failed: endpoint check (`input fires`) reported `True` while `tutorial actually fires` reported `False` — the trace (`[True, True, False]`) shows the pipeline succeeded through the capture layer, then failed specifically at `resolver_priority_gate`. An audit that only checks "did the input fire" (matching the shape of dog#E27's device-only checklist, already composed elsewhere against draft#E9's specific instance of this) cannot localize — or even detect — a mid-pipeline drop.
- Fix: Not a code fix — a domain-tagging + generalization seed. Any entity-pinned tutorial/onboarding trigger built on a multi-layer input pipeline needs a PER-LAYER check (does THIS layer forward the signal for this specific entity/verb/zone?), not just an input-fires / tutorial-fires pair — the same discipline both source bugs independently arrived at, now stated as a pipeline property instead of two unrelated incidents.
- Why this fix: The value of composing these two already-verified findings is generalization, not new detection — future tutorial/onboarding work in this codebase family has at least two known concrete layer types (vocabulary gates, priority resolvers) that can silently starve a trigger, and should treat any NEW layer inserted into that pipeline as a candidate third.
- Rule of thumb: An entity-pinned tutorial/onboarding trigger sitting behind a chain of independent pipeline layers (capture → resolver → trigger, or any equivalent) has one silent-starvation candidate PER LAYER, not one for the pipeline as a whole — verify each layer forwards the specific signal (not just that raw input fires and the tutorial eventually completes some OTHER way), and treat every new layer added to the chain as a new candidate to audit, not an assumed pass-through.
- Provenance (verified/assumed): Verified first-hand — built `sandbox.py` (zero RNG, zero wall-clock, a 3-layer deterministic pipeline mirroring the two real bugs' actual shapes), confirmed the endpoint-only check passes while the true pipeline result fails, and confirmed the trace correctly localizes the failure to the middle layer. Confirmed deterministic/reproducible across two independent process invocations of `python3 sandbox.py`, output diffed byte-identical. The two composed source entries were themselves already independently sandbox-verified in their own filings; this entry cites them and adds the pipeline generalization on top.

## E1 — single action resolver priority can starve an entity pinned onboarding trigger
- Date: 2026-07-20
- Project: local/sandbox-resolver-starves-tutorial
- Tags: [ui][gamedesign][input]
- Composed: pappydapimp69__dog/E20, pappydapimp69__the-game-prologue/E15
- What: `brain train` flagged `dog + the-game-prologue` as a high-value untested seam. Composed dog#E20 ("resolve what can happen right now through ONE function returning at most one action, drive every UI surface off that single value") with the-game-prologue#E15 ("teach a game's verbs with a passive observer overlay... pin each teaching trigger to a SPECIFIC entity id") and found a real interaction neither entry names alone: if a higher-priority verb is simultaneously valid on the same entity as the tutorial's target verb, the resolver never surfaces the tutorial verb as the ONE chosen action — the player is never actually offered it, so the onboarding step pinned to that (entity, verb) pair never fires, with no error from either system, because both are individually behaving exactly as designed.
- Why built: dog#E20 and the-game-prologue#E15 were each recorded from single-subsystem investigations (a UI-input-resolver design and a tutorial-trigger design, in different projects) with no scenario in scope where both applied to the same entity at once. External research (game-UX contextual-prompt design guidance) confirmed this composition is a live, recognized design tension in the field — not a strawman: contextual/single-action prompts are deliberately built to surface only one recommended action at a time specifically so they don't overwhelm the player, which is the same mechanism that can silently starve a lower-priority but tutorial-relevant verb.
- Design: Deterministic Node script (`sandbox_resolver_starves_tutorial.mjs`), no RNG, no wall-clock. `resolveAction(target, availableVerbs, priorityOrder)` mirrors dog#E20 exactly — sorts available verbs by a fixed priority list and returns only the top one. `makeTutorialTracker(steps)` mirrors the-game-prologue#E15 — marks a step done only when its pinned `(entityId, verb)` pair is actually executed. Three scenarios, 500 simulated frames each: (A) tutorial verb permanently outranked by an always-available competing verb on the same entity; (B) control — the competing verb becomes temporarily unavailable, tutorial verb should then fire; (C) control — priority reversed (tutorial verb ranked highest), should never starve.
- Got right: Scenarios B and C behaved exactly as the claim predicts when the interaction ISN'T present (verb frees up, or tutorial verb already wins) — confirming the starvation in scenario A is specifically about simultaneous availability + relative priority, not a general defect in either the resolver or the tracker considered alone.
- Where/why it failed: Scenario A ran 500 frames with the tutorial's target entity interacted with every single frame, and the resolver's chosen action was `throw_ball` on all 500 — `pet` was never once the executed verb, so the tutorial step pinned to `(dog_e1, "pet")` stayed permanently un-done. Neither dog#E20's resolver nor the-game-prologue#E15's tracker malfunctioned: the resolver correctly always picked the higher-priority verb (that's its entire contract), and the tracker correctly never marked a step done for a verb that was never executed (that's its entire contract) — the bug exists only in the COMPOSITION, in the gap between "an action is available" and "an action was ever the one chosen and shown."
- Fix: The onboarding system needs a signal distinct from "this verb was executed" — either (a) the resolver exposes the full ranked/available verb set (not just the winner) so a tutorial system can detect "target verb is valid but currently outranked" and surface a nudge (temporarily boost its priority, or hint the player to change context so it wins), or (b) tutorial-pinned verbs get a scoped priority override while their step is active and undone, so the resolver's normal ranking is only overridden exactly when — and for as long as — onboarding genuinely needs it to be.
- Why this fix: Both options fix the actual gap (visibility into "available but unchosen," or a scoped priority carve-out) rather than changing either system's own correct, independent contract — matching the same shape as the already-recorded composition `draft#E9` (a resolver's "new verb = no new wiring" claim breaking against a closed-vocabulary capture layer beneath it): the fix belongs at the SEAM between the two systems, not inside either one.
- Rule of thumb: When composing a single-choice resolver (exposes only the ONE winning option per target) with anything that needs to detect "was X ever offered" (a tutorial, an analytics funnel, an accessibility hint), audit whether "executed" is being used as a proxy for "was available" — the resolver's whole job is to hide the losers, so anything downstream that only observes the winner cannot tell "correctly never available" from "available but permanently outranked," and needs its own explicit visibility into the full candidate set to tell them apart.
- Provenance (verified/assumed): Verified first-hand — `sandbox_resolver_starves_tutorial.mjs` run to completion for all three scenarios, deterministic (no RNG, no wall-clock, fixed 500-frame loops), each scenario's full executed-verb log and tutorial-step completion state printed and checked programmatically (an `allPass` gate across all three; exits 1 and prints "CLAIM DID NOT REPRODUCE — do not file" if any scenario disagreed with the prediction — none did). External research (not internal reasoning alone) checked whether the composed scenario reflects a real, recognized design concern rather than a fabricated edge case: game-UX guidance on contextual/single-action prompts (nngroup.com contextual-menus-guidelines, acagamic.com contextual-prompts) confirms single-visible-action prompt design is standard practice specifically because it deliberately shows only one recommended action, the same mechanism this sandbox shows can starve a differently-prioritized tutorial target.
