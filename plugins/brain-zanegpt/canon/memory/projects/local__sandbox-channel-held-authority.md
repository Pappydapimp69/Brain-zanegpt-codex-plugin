## E1 — channel held authority vs believed sender field
- Date: 2026-10-09
- Project: local/sandbox-channel-held-authority
- Tags: [multi-agent][architecture][testing][security]
- What: A deterministic toy model of an agent message channel compares three ways of authorizing a privileged action (a deploy): believing the self-asserted sender field, a written rule applied only when the receiver looks, and a channel that stamps identity from the port the message arrived on and checks a capability table it holds. Out of 120 forged privileged messages, belief executed 120, the look-1-in-4 rulebook executed 90, and the port-stamping channel executed 0.
- Why built: Gap pass on the unapplied kernel MULTI-AGENT/governance/trust-is-not-enforcement (hold the channel, do not grant authority). The claim was only stated in prose; this makes it a number and adds controls that try to break it. This is a model of a channel, not a measurement of any real multi-agent deployment.
- Design: 480 messages (120 rounds x 4: honest read, legitimate owner deploy, forged deploy from a low-privilege port claiming to be the owner, honest-but-unauthorized deploy). Gates: belief, rulebook (applies the capability check to the real port on every 4th privileged message, otherwise believes the field), channel (port only). Negative controls: a prophet relay that has been granted authority and believes persuasive text, an envelope channel that reads a sender-written label, and a stolen owner port. Symmetric control: identical all-honest traffic through belief, rulebook and channel.
- Got right: Legitimate owner deploys executed 120/120 under every gate, so the channel gate costs nothing on honest traffic. Honest-traffic outcome hashes were identical across the three gates (7ffdb95906), so any difference on the main run comes from the forgeries and not from gate bookkeeping. The honest-but-unauthorized sender was refused by all gates, so only forgery separates them.
- Where/why it failed: The channel guarantee is narrow. A prophet relay holding granted authority executed 120/120 forgeries, an envelope channel that reads a label the sender writes executed 120/120, and a stolen owner port executed 120/120. The rulebook leaked 90/120 even though the rule was correct and written down, because applying it depended on the receiver looking.
- Fix: Put identity at the transport (stamped from the connection, never from message content), keep the capability table inside the channel, give relays no authority of their own beyond what the port carries, and treat a stolen credential as a separate problem needing revocation and least privilege per port.
- Why this fix: It removes the need for any component to hold an opinion about another's honesty, which is the kernel. The negative controls show the same hole reappears the moment authority is granted to a believing component or identity is read from sender-written text, so the benefit comes from where the check lives, not from adding a checker.
- Rule of thumb: Hold the channel, do not grant authority: stamp sender identity from the transport and check capabilities there, because in this model belief leaked 120/120, a written rule applied 1-in-4 leaked 90/120, and a believing relay or sender-written label leaked 120/120 while the port-stamped channel leaked 0/120; it bounds the blast radius to the port, and a stolen port still gets everything that port is allowed.
- Provenance (verified/assumed): Verified first-hand by running the sandbox: the counts 120/90/0/120/120/120 and the identical honest-control hashes. The model is a toy with a fixed message mix and a deterministic attention schedule; the 1-in-4 attention rate is a parameter I chose, so 90 is a property of that parameter, and the claim about real deployments is an extrapolation.
