## E1 — refusal names the rule not the bucket but never the secret operand
- Date: 2026-10-10
- Project: local/sandbox-refusal-rule-not-bucket
- Tags: [governance][refusal-design][security][testing][tension]
- What: A deterministic model of a guard with 12 rules in 3 classes, refusing in two formats: CAT (names only the class) and RULE (names the rule, the offending item and an exact acknowledgement token). A repair loop that can only use the message was run against single offences, double offences, false positives, a secret numeric threshold and a rule gated on a hidden flag.
- Why built: The kernel ideas:GOVERNANCE/refusal-design/a-refusal-that-names-a-category-teaches-nothing says a refusal should return the rule and the remedy, never the bucket. It was backed by one session anecdote and no model, and it sits next to mirage/E5 (a refusal is an observation), which suggests that more specific refusals may leak more. I wanted the point where the kernel stops holding.
- Design: Formats CAT and RULE; three actors (careful category-only that drops one candidate and restores it when the message does not change, hurried category-only that sweeps the whole class window, rule-level that removes the named item). S1 40 single-offence actions, S2 20 two-offence actions in different classes, S2b 20 in the same class, S3 20 legit-but-lexically-matching items, S4 a prober recovering a secret threshold 0..127 under four message formats (matched values printed, rule named without values, class only, byte-identical acknowledgement), S5 a rule that fires only when a hidden flag is set, S6 an actor that ignores message content.
- Got right: Rule-level needed 80 guard calls against 140 for the careful category-only actor (ratio 0.571) on S1, with zero legit items dropped; the hurried category-only actor matched the rule-level call count (80) only by sweeping 120 legit slots (3.0 per action). On S2b the careful category-only actor stalled on 20 of 20 because removing one offender leaves the identical class message, while rule-level resolved all in 60 calls. On the 20 false positives rule-level produced 20 acknowledgements whose receipt names the rule; category-only ended with 15 deleted-legit-content outcomes and 5 receiptless human overrides (this split follows from the modelled 3-retry budget, so read it as a direction, not a rate). The control actor that ignores messages made 5 calls under both formats, so the gain depends on the actor acting on the content.
- Where/why it failed: The kernel does not hold as an unqualified rule. S4: printing the matched value and threshold gave 1 probe to recover a secret threshold, against 8 worst and 7.61 mean for both the rule-named-without-values format and the class-only format; the two latter were identical, so naming the rule costs zero extra leakage over naming the class. S5: listing ALL matched rules produced 2 distinct outputs across the hidden flag values, while class-only and first-matched-rule produced 1; a message enumerating a state-dependent rule is a readout of the state. The fully byte-identical acknowledgement left 128 of 128 candidates, but it also removes the remedy from the legitimate actor, so it is a pure-oracle-defence format, not a refusal design.
- Fix: Split the refusal into parts by who is entitled to them. Return the rule identity, the remedy and the acknowledgement token (all of which carry no information about secret operands). Withhold matched values and thresholds when the operand is secret or derived from hidden state; report only the first public rule rather than every match when any match is state-dependent. Make the override require the rule token so the receipt names what was overridden.
- Why this fix: It keeps the measured gain (0.57x calls, 20/20 named receipts, no collateral) because that gain comes from rule identity plus remedy, and it removes the two leaks that were measured (value printing 8x faster recovery, enumerating all matches reveals the flag). Rule-without-values was shown to leak exactly as much as class-only, so the fix is free on the leak axis.
- Rule of thumb: Return the rule and the remedy, not the bucket (0.57x guard calls, 20/20 named-rule receipts in this model), but return the rule's NAME, never its secret OPERANDS: values and thresholds cut secret recovery from 8 probes to 1, and a list of every matched rule leaks a hidden flag. Decide per field whether the refused party is entitled to it. Scope: tested with a window of 4 plausible items per class, so the 0.57 ratio is a property of that setting.
- Provenance (verified/assumed): Verified first-hand by the sandbox run (all checks passed, last line RESULT: PASS). The kernel's own session anecdote (four category-only refusals) was not re-observed here, and the actor behaviours and the 3-retry budget in S3 are modelling choices of this sandbox.
