## E1 — spatial marker projection flips direction behind camera and independent clamp distorts angle
- Date: 2026-07-20
- Project: local/sandbox-offscreen-marker-projection
- Tags: [ui][gamedev][algorithm]
- Composed: N/A
- What: `ideas/UI-UX/four-ui-types` names "a floating waypoint marker" as the canonical SPATIAL UI example, but doesn't cover the projection math needed to render one for an off-screen or behind-camera target. External research on off-screen indicators documents two real, independent failure modes for a naive implementation: (1) a perspective-divide by the raw signed view-space `z` silently mirrors the marker to the WRONG side of the screen once the target passes behind the camera, and (2) clamping screen X and Y independently (two separate `Math.min/max` calls) doesn't preserve the true source→target direction, distorting the indicator's angle. Built a from-scratch camera/projection sandbox and confirmed both.
- Why built: The SPATIAL UI-type kernel establishes WHAT a waypoint marker is (a UI category) but not HOW to project one correctly; this fills that gap with the concrete, sandbox-verified math, since a design taxonomy entry alone doesn't catch an implementation bug.
- Design: Deterministic Node script (`sandbox_offscreen_marker_projection.mjs`), no RNG, no wall-clock. A from-scratch camera (position + forward/up, right derived via cross product, tan-half-fov) with two projection functions: `naiveProject` (raw signed-z perspective divide, then independent X/Y `Math.min/max` clamp to screen bounds) and `fixedProject` (divide by `Math.abs(z)` instead of signed `z`, plus a single uniform SCALE factor applied to both axes together, derived from whichever axis needs it most, rather than two independent clamps). Three scenarios on a square screen (removes aspect-ratio as a confound on angle comparisons): (A) a target behind the camera, checking which screen half each method points to against a convention-independent ground truth (the view-space x sign); (B) a target requiring both-axis clamping, checking projected screen-angle-from-center against the true (unclamped) direction angle; (C) control — an on-screen target needing no clamping, confirming both methods agree when neither failure mode is in play.
- Got right: Scenario C confirms the two projection methods are identical (to the pixel) for an ordinary on-screen target — the divergence in A and B is specifically caused by the behind-camera and clamping-distortion mechanisms, not a general difference between the two implementations.
- Where/why it failed: Scenario A: for a target at view-space `x=+5, z=-50` (behind, true bearing is "positive-x side"), the naive method projected to `sx=330.7` (screen-LEFT of center, x=400) — the wrong side — while the fixed method projected to `sx=469.3` (screen-right, correct). Scenario B: for an in-front target needing both-axis clamping, the true direction angle from screen-center was 36.87°; naive's independent clamp produced 45.00° (8.13° of distortion); the fixed method's single uniform-scale clamp reproduced 36.87° exactly (0.00° error). My own FIRST attempt at the "fixed" implementation also failed to reproduce the claim on the first sandbox run — it divided by `Math.abs(z)` (correct) but then ALSO applied an unconditional sign-flip for behind-camera targets, double-correcting and reproducing the same wrong-side bug as naive; the sandbox catching this before filing is itself the point of the mandatory-verification rule (a plausible-looking fix that "should" work is not the same as one that measurably does).
- Fix: (1) Project using `x / |z|` (and `y / |z|`) instead of `x / z`, never conditionally re-flipping afterward — dividing by the absolute value alone is the complete fix; adding an extra flip on top of it re-introduces the exact bug it's meant to prevent. (2) Clamp to the screen edge with a single uniform scale factor computed from whichever axis is closer to its bound (`min(1, maxX/|dx|, maxY/|dy|)`), applied to both axes together, never two independent `Math.min/max` clamps.
- Why this fix: Both naive failure modes share a root cause — treating the two axes (or the sign of z) as independently correctable when they're actually coupled through the true direction vector; any correction that doesn't preserve that coupling (an extra conditional flip on one axis, or clamping X and Y separately) reproduces a version of the same bug in a new spot, which is exactly what happened during this session's own first attempt at the fix.
- Rule of thumb: When projecting a SPATIAL UI marker (or any off-screen/behind-camera indicator) to screen space, (a) divide by the absolute value of view-space depth, never the signed value, and don't layer a second directional correction on top of that — verify with a literal behind-camera test case, not just "does it compile"; (b) when clamping a 2D screen position to stay in-bounds, clamp with one uniform scale factor derived from the tightest axis, never two independent per-axis clamps, or the indicator will silently point in the wrong direction under exactly the conditions (steep off-center targets) it exists to handle correctly.
- Provenance (verified/assumed): Verified first-hand — `sandbox_offscreen_marker_projection.mjs` run to completion for all three scenarios, deterministic (no RNG, no wall-clock, closed-form geometry), each scenario's projected coordinates and derived angles printed and checked programmatically (an `allPass` gate across all three; the first version of this script exited 1 with "CLAIM DID NOT REPRODUCE" twice in a row — once from a camera-basis handedness bug in the test harness itself, once from the double-correction bug in the "fixed" implementation described above — both diagnosed and fixed before the final passing run). External research (not internal reasoning alone) confirmed both failure modes are real, documented problems in shipped off-screen-indicator implementations, not a fabricated edge case.
