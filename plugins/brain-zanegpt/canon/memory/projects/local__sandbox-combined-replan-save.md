## E2 — frontier drop bug only visible to structural checks
- Date: 2026-07-13
- Project: local/sandbox-combined-replan-save
- Tags: [determinism][algorithm][state]
- What: `brain analyze graph` (untested seams extending the main cluster) surfaced local/sandbox-combined-replan-save + local/sandbox-savemigrate (not yet directly co-verified). Composed: projects/local__sandbox-combined-replan-save.md#E1 (an amortized computation inside a deterministic loop must survive a save/restore of its IN-FLIGHT state — a mid-computation checkpoint must resume to the no-save baseline; a frontier dropped by naive JSON diverges) and projects/local__sandbox-savemigrate.md#E3 (a migrated field can look fully present in memory — `'y' in obj'` → true — while `JSON.stringify` silently drops it because its value is `undefined`; only a round-trip through the actual persistence format reveals this). replan-save#E1's own text names the SYMPTOM ("a frontier dropped by naive JSON diverges") without stating the mechanism; savemigrate#E3 supplies exactly that mechanism, and a BFS/Dijkstra frontier's start-node entry — with a legitimately-undefined `parent` field, since the start node has no parent — is a completely natural, not artificially injected, instance of savemigrate#E3's exact vulnerable shape. Built and ran a sandbox confirming this, and along the way corrected a flawed first attempt that revealed a sharper, more precise version of the claim.
- Why built: Neither source lesson states that an in-flight search frontier is a NATURAL occurrence of the undefined-field-drop pattern (savemigrate#E3 was recorded from a schema-migration context; replan-save#E1 names "naive JSON" as the culprit without identifying which specific field or why). The value is pinning down precisely which field drops, why it's a normal (not edge-case) part of frontier state, and — discovered only after an initial sandbox attempt failed — precisely WHAT KIND of check can and cannot observe the drop.
- Design: `engine.mjs` constructs the natural first frontier entry a BFS from a start node produces: `{node: 0, dist: 0, parent: undefined}` (the start node legitimately has no parent). This entry is round-tripped two ways: `naiveRoundTrip` (plain `JSON.parse(JSON.stringify(entry))`, savemigrate#E3's vulnerable pattern) and `fixedRoundTrip` (explicitly normalizing `undefined` to `null` before serializing). A `structuralFingerprint` function (sorted key-value pairs, JSON-stringified) models the kind of check a real save/restore verification test uses to confirm "the restored state matches the pre-save state" — matching replan-save#E1's own described verification method (checkpoint resumes to the no-save baseline).
- Got right: An initial version of this sandbox attempted to demonstrate the divergence by re-running a full BFS after a naive mid-computation restore and comparing the final `visited` results against a no-restore baseline — this FAILED to show any divergence, and investigating why led to a real, precise, useful finding rather than a shrug: in JavaScript, `obj.parent` reads as `undefined` identically whether the key is present-with-value-`undefined` or entirely absent, so ORDINARY property-read logic (`if (node.parent === undefined)`, path-reconstruction walking parent pointers, etc.) literally cannot observe savemigrate#E3's drop — confirmed explicitly in this sandbox (`original.parent === undefined` and `naiveRestored.parent === undefined` both `true`). Only a presence check (`'parent' in obj`), a `Object.keys()` count, or — critically — a structural/serialization fingerprint comparison can see it.
- Where/why it failed: The naive round-trip's structural fingerprint (`[["dist",0],["node",0]]`) does NOT match the original's fingerprint (`[["dist",0],["node",0],["parent",null]]`) — confirming replan-save#E1's "diverges" claim is real, but specifically as a STRUCTURAL/serialization-level divergence, not a behavioral one from ordinary reads. This matters practically: a save/restore correctness test built around "does the game still play correctly after reload" (behavioral testing) would NOT catch this bug at all, since nothing that merely reads `.parent` behaves differently; only a test built around "does the restored structure match the pre-save structure byte-for-byte" (a structural fingerprint, exactly replan-save#E1's own prescribed verification method) catches it.
- Fix: Normalize `undefined` to `null` (or an equivalent explicit sentinel) before serializing any in-flight state that may legitimately contain undefined fields — confirmed in the sandbox to produce a structural fingerprint that exactly matches the original, unlike the naive round-trip.
- Why this fix: Neither individual fix is new — the value of the composition, sharpened by a genuine correction mid-sandbox, is identifying that (a) an in-flight search frontier's start-node entry is a completely ordinary, not contrived, instance of savemigrate#E3's vulnerable shape, and (b) the specific verification METHOD matters enormously: a behavioral test (does downstream logic still work) gives false confidence, since ordinary property reads can't distinguish "field absent" from "field present but undefined" — only a structural/fingerprint-based save/restore verification (which is what replan-save#E1 actually used) can catch this class of bug at all.
- Rule of thumb: When verifying that an in-flight computation's save/restore is lossless, a behavioral test ("does the resumed computation still produce correct results") is not sufficient to catch an undefined-field-drop bug, because ordinary JS property reads cannot distinguish an absent key from a present key holding `undefined` — verify with a STRUCTURAL fingerprint (key set + values) comparing pre-save state to post-restore state, and normalize any legitimately-undefined field (a frontier's start-node parent pointer, or any similar "doesn't apply yet" field) to an explicit sentinel like `null` before persisting.
- Provenance (verified/assumed): VERIFIED first-hand — built `engine.mjs` (zero RNG, zero wall-clock, a fixed BFS-shaped frontier entry), confirmed ordinary `=== undefined` reads cannot distinguish the naive-restored entry from the original, confirmed a structural fingerprint DOES diverge for the naive restore and matches exactly for the fixed restore. An initial sandbox design (re-running a full BFS and comparing final results) produced a false "no divergence" result; investigating why revealed the precise "ordinary reads can't see this, only structural checks can" finding, which is a sharper and more useful result than the original hypothesis — corrected before treating anything as verified. Confirmed deterministic/reproducible across two independent process invocations of `node engine.mjs`, output diffed byte-identical.

## E1 — amortized work must survive midflight save
- Date: 2026-07-13
- Project: local/sandbox-combined-replan-save
- Tags: [determinism][algorithm][state]
- What: An amortized computation (an A* replan) running inside a deterministic fixed-timestep loop (combined-game-loop) must survive a save/restore of its IN-FLIGHT state (savemigrate), not just its settled state. Verified from an integration angle: a mid-replan save that correctly serializes the frontier resumes identically to the no-save baseline, while a naive save that drops the frontier (the savemigrate class of bug — a Set/heap silently becoming {} under JSON) resumes to a WRONG result.
- Why built: To raise independence on the single-source edges astar-replan↔game-loop and astar-replan↔savemigrate by re-verifying them together, and to record that saving settled state does not cover saving mid-computation.
- Design: Deterministic grid; run A* to completion (baseline: 84 expansions, path len 23). Re-run with a checkpoint at expansion 15 saved+restored two ways — correct (frontier kept) and naive (frontier dropped) — and compare each resumed run to the baseline.
- Got right: Reproduced. Correct save/restore == baseline (84 expansions, len 23). Naive save (frontier lost) → no path found (diverges). The composed replan+loop+save is deterministic across a save boundary only if the in-flight frontier is serialized.
- Where/why it failed: A save taken while a computation is mid-flight silently loses any complex in-memory structure JSON can't represent (a Set/heap frontier → {}), so the resumed deterministic loop diverges — invisible to a save test that only checkpoints settled state.
- Fix: Test save/restore at a MID-COMPUTATION checkpoint, serializing all in-flight structures explicitly; assert the resumed run reproduces the no-save baseline (path and expansion count), not just that the file round-trips.
- Why this fix: Determinism across a save boundary requires the entire live state, including transient search structures; only a mid-flight save test exercises them.
- Rule of thumb: An amortized computation (A* replan, incremental rebuild) running inside a deterministic loop must survive a save/restore of its IN-FLIGHT state — verify a mid-computation checkpoint resumes identically to the no-save baseline (correct frontier serialization matches; a frontier dropped by naive JSON diverges); saving settled state alone misses it.
- Provenance (verified/assumed): Verified first-hand — deterministic integration sandbox this session (baseline 84 expansions/len 23; correct save == baseline; naive save → no path). Built and observed.
