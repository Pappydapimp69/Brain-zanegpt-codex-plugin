## E1 — adaptive music horizontal vs vertical lag and cut tradeoff
- Date: 2026-10-08
- Project: local/sandbox-adaptive-music-horizontal-vs-vertical-lag-and-cut-tradeoff
- Tags: [music][audio][design][state]
- What: A tick-based sandbox of 16 bars compares quantized horizontal segment switching, unquantized switching, 4-bar and 1-bar vertical layer fades, and a combined scheme, on a binary combat trace and a slow continuous ramp. It applies the horizontal-vs-vertical kernel together with the bar-quantization and separate-intensity-director kernels.
- Why built: No memory entry had applied the adaptive-scoring kernels; I wanted to see which architecture wins on which state shape, and where the kernel's tradeoff stops holding.
- Design: A separate intensity director maps a threat score to tiers 0-3. Horizontal switches to one authored segment per tier, either at the next bar line (queued) or immediately. Vertical moves one layer level toward the tier at a rate set by the fade length. Metrics: worst ticks to reach target after a tier change, audible one-step jumps, mid-bar cuts, distinct segments. Hand-made traces, no RNG.
- Got right: On the binary trace quantized horizontal reached the new state within 3 ticks with 0 mid-bar cuts, unquantized switching made 2 mid-bar cuts, and a 4-bar vertical fade lagged 26 ticks. On the ramp, horizontal gave 3 audible jumps against 0 for vertical and combined, and vertical uses one harmonic bed against 4 segments.
- Where/why it failed: My first run modelled horizontal as a two-state switch and failed my own prediction: it gave only 1 cut on the ramp. Horizontal only produces many cuts when it has one authored segment per tier, so the cut count depends on authored branch count, not on the state shape alone. A 1-bar vertical fade lagged just 6 ticks, so vertical is slow for sharp states only when the fade is long.
- Fix: Treat the architecture choice as three tunable numbers, quantize grid, fade length and number of authored branches, rather than a binary pick; use horizontal for piece selection and a short vertical fade for intensity.
- Why this fix: The lag of a vertical scheme is its fade length and the cut count of a horizontal scheme is its branch count, so each scheme's weakness can be tuned away at a cost, which the kernel's either-or phrasing hides.
- Rule of thumb: Horizontal queued to bar lines bounds reaction lag to one bar with no mid-phrase cuts but cuts audibly once per authored branch crossed; vertical never cuts but lags by its fade length, so a 1-bar fade closes most of the sharp-state gap; verified in a tick model only, not by listeners.
- Provenance (verified/assumed): Verified first-hand by running the sandbox twice; the first run failed because of my model choice and the second is the filed result. Listener perception of cuts is the kernel's claim and is not tested here.
