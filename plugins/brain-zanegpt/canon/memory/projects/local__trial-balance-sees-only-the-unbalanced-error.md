## E1 — trial balance sees only the unbalanced error
- Date: 2026-10-17
- Project: local/trial-balance-sees-only-the-unbalanced-error
- Tags: [bookkeeping][testing][checksum][sandbox]
- What: Seeds the DOUBLE-ENTRY-BOOKKEEPING domain with a sandbox of a 20-posting ledger that injects each classic error into a balanced book and counts which ones the trial balance (debits equal credits) detects.
- Why built: The domain had no record; double-entry bookkeeping is a real, long-standing parity-style check and its blind spots are well known, so the sandbox measures them against the neighbouring check-digit and parity kernels.
- Design: Balanced ledger of 20 postings; error classes injected exhaustively: one-sided amount shifts of -50 to 50, adjacent-digit swaps of every 3-digit amount (1620 cases), 20 omitted entries, 20 wrong-valid-account postings, and 324 pair errors of k1, k2 in -9..9. Separate Luhn check on 5-digit account numbers: 19305 single-digit keying errors and 1537 adjacent swaps.
- Got right: The trial balance caught 2000/2000 one-sided amount errors and 1620/1620 transpositions, with every difference divisible by 9, and it missed exactly the predicted classes: 0/20 omissions, 0/20 wrong-account postings and 18 of 324 pair errors (the k2 = -k1 cancellations).
- Where/why it failed: The wrong-account case is partly a tautology, because the amounts are untouched so the totals cannot move; it shows the check is blind to account identity, not that it is weak. My first prediction text also had an arithmetic slip (144 of 162 undetected pairs); the real design has 324 pairs and 18 cancelling ones, fixed in the script comment before filing.
- Fix: Pair the balance check with a check digit on account numbers (caught 19305/19305 keying errors, missed 27 of 1537 adjacent swaps) and with an expected-entry count, so each blind class has a second, differently-shaped check.
- Why this fix: The balance, the check digit and the count each see a different error shape, so their blind spots barely overlap; the swap blind spot of the check digit (09 and 90) is a separate class from the balance's blind spots.
- Rule of thumb: A balanced trial balance only proves no error unbalanced the books: in a toy ledger it saw 100 percent of one-sided errors and transpositions but 0 of 20 omissions and 0 of 20 wrong-account postings, so add an account check digit and an entry count before calling the books right.
- Provenance (verified/assumed): Verified first-hand by running the sandbox; the ledger is a synthetic 20-posting toy and no real company books were checked. This domain had no records, and the adjacent kernels and the Hamming lesson are cited because the sandbox exercises their shape directly.

Question 1: the detector is just sum(debits) != sum(credits), and each error class is injected in the shape that decides the answer. Transpositions, amount errors and pairs are applied to ONE side only, so any non-zero difference is detected by arithmetic; omissions and wrong-account postings leave both sides equal, so they pass by construction. The 3240 detection counts therefore restate the injection choice and do not test the claim. Question 2: the Rule of thumb says the trial balance saw 100 percent of transpositions, but the common real transposition is keyed once and posted to both sides, which the same detector would pass; that case is never run, so the sandbox covers less than the rule states. The cancelling-pair result (18 of 324) is the only real finding about the detector, and the Luhn counts are an independent computation that is sound. The entry itself concedes the wrong-account case is a tautology.
