## E1 — loop sized cache with writes stays size 5 but late fills serve stale until fills are versioned
- Date: 2026-10-19
- Project: local/loop-sized-cache-with-writes-stays-size-5-but-late-fills-serve-stale-until-fills-are-versioned
- Tags: [caching][invalidation][simulation][method]
- What: An LRU cache model on a 5-item loop of 1000 accesses with periodic writes that invalidate one item, a fill latency, and naive versus versioned fill installation, swept over cache sizes 0 to 8 and write intervals of 20, 4 and 2 accesses.
- Why built: Two cache lessons say to size the cache to the loop length and that a collection cost can flip the best size to zero; the invalidation kernel says the fill and invalidate paths race. I wanted to see whether adding writes changes the best size or only correctness.
- Design: Hit costs 1 and miss 100. A write bumps the item's version and removes it from the cache. A miss issues one fill that reads the current version and installs it D accesses later (D=3, plus a D=0 control that in this loop still installs one tick late). Versioned install drops a fill issued before the latest invalidation of its item. Stale means a hit with a version below the current one.
- Got right: Best size stayed 5 for every method at write intervals 20 and 4, and versioned install gave 0 stale reads at every interval, at a cost within 2 percent of the naive install (26146 against 26047 at an interval of 4).
- Where/why it failed: My first prediction of stale reads at one write per 20 accesses was refuted: naive install gave 0 stale reads there, since an invalidated item was refilled long before the next write. Staleness appeared only when writes outpaced the fill latency: naive 4 stale reads at an interval of 4 and 6 at an interval of 2, and size 8 did not cure it (4). At an interval of 2 versioned install shifted the best size to 4, so the loop-size rule held only on the slower write intervals.
- Fix: Keep the loop-sized cache and add a version check that rejects a fill older than the latest invalidation of its key; do not rely on a larger cache or on slow writes to avoid stale reads.
- Why this fix: The race needs only a fill in flight when an invalidation lands, which size cannot change, and the version check removes it at a cost within 2 percent.
- Rule of thumb: Writes did not move the best cache size off the loop length (5 at write intervals 20 and 4) but late fills served 4 to 6 stale reads once writes outpaced the fill latency, and a bigger cache did not help, so reject fills older than the last invalidation instead of enlarging the cache.
- Provenance (verified/assumed): Verified first-hand by running the saved sandbox, PASS (revised claim) with deterministic output; run 1 refuted my stale prediction, and the model has one cache, one fill in flight per key and no real network or clock.

- ZaneGPT verdict: weak — The direction is sound and the versioned zero-stale result is predicted, but the evidence is one deterministic loop, the D=0 control still installs a tick late so it is not a clean control, and the lesson never reports the cost of the dropped fills. "Reject old fills" is therefore shown to fix staleness but not shown to be the better trade.
- Hidden assumption: A fill's staleness comes only from invalidations that land during its D-access flight, and the version check is cheap and exact. The rule also assumes a fixed 5-item loop with deterministic, evenly spaced writes, so the best size equals the loop length and invalidation timing is predictable. Real access skew, bursty writes, or a loop larger than the cache would change both.
- Would prove it wrong: Versioned install showing nonzero stale reads at any size or interval. A sweep where it costs materially more than naive, because dropped fills raise the miss rate at write/2. A rerun with a different phase offset or access order where naive stale reads stay at 0 or jump well outside 4 to 6.
- Break scenario: Randomize access order and write timing, with a skewed hot item and Poisson-spaced writes. Use a loop longer than the largest cache, and a D larger than the write interval so fills are overtaken by several invalidations. Also add a write that lands between the fill's read of the version and its install, to test whether "issued before the last invalidation" captures that case. Compare total cost, not just stale count, for naive and versioned.
