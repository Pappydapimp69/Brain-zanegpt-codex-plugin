## E2 — seed map design spanning tree guarantees connectivity not loops
- Date: 2026-07-13
- Project: local/sandbox-maze
- Tags: [gamedesign][map-design][algorithm]
- What: `brain train gap` (topic "map design" — `brain query` returned zero records, the signal to seed it). `local__sandbox-maze.md#E1` fixes dungeon/map connectivity by using a spanning-tree carve, verified via flood-fill. External research (WebSearch) confirms this is exactly right for the MINIMUM guarantee, but also that a pure spanning tree is a known, named limitation in real dungeon-gen practice: it "contains no cycles and there is only a single path from one room to any other room" — established implementations (e.g. Delaunay-triangulation-based generators) add back a small percentage of extra edges (12.5% cited) from the full candidate graph on top of the guaranteed-connected tree specifically to add loops/multiple paths, since adding edges to an already-connected graph can only preserve or increase connectivity, never break it.
- Why built: sandbox-maze#E1 states its fix purely in terms of the connectivity property (does a flood-fill reach every cell) and doesn't record that a spanning tree is also the WORST case for loop-free, single-path, maximum-backtracking map structure — a real design cost the entry doesn't flag as a tradeoff of its own fix.
- Design: `sandbox.py` — zero RNG, zero wall-clock. A fixed 4x4 grid graph (16 rooms, all orthogonal neighbor edges, deterministic sorted order). Built a spanning tree via union-find over the fixed edge list (no randomness — first-valid-edge order), verified connectivity via the same flood-fill method sandbox-maze#E1 itself uses, and counted cycles (`edges - nodes + 1` for a connected graph). Then added back a deterministic first-N slice (12.5% of all candidate edges, the cited real figure) of the edges NOT in the tree, and re-checked both connectivity and cycle count.
- Got right: sandbox-maze#E1's core claim holds exactly as stated — the spanning-tree carve does guarantee full connectivity (flood-fill reached all 16 rooms), matching its own verification method.
- Where/why it failed: N/A — not a bug, a recorded gap. The spanning-tree-only maze had exactly 0 cycles (15 edges, 16 rooms) — confirming there is genuinely only one path between any two rooms, matching the external sources' description precisely. After adding back 3 extra edges (12.5% of the 24 total candidate edges), connectivity remained True (flood-fill still reached all 16 rooms) while cycle count rose to 3 — real loops, added without ever touching or re-deriving the connectivity guarantee.
- Fix: Not applied to any shipping code (seed entry, no source to modify). Record the missing second half of sandbox-maze#E1's recipe: build the spanning tree for the connectivity GUARANTEE, then deliberately add back a small fraction of the remaining candidate edges for loops/player-experience — connectivity is provably preserved by construction (adding edges cannot disconnect an already-connected graph), so this costs nothing against the original guarantee.
- Why this fix: sandbox-maze#E1 solved the correctness half of map generation (never generate an unsolvable/disconnected map) but silently left the map generator producing worst-case-for-player-experience mazes (a single mandatory path, no shortcuts, maximum forced backtracking) as its default output — a real design cost worth flagging even though nothing about it is a bug.
- Rule of thumb: A spanning-tree carve is the correct MINIMUM structure for guaranteed map connectivity, but it is also, by construction, the topology with zero loops and exactly one path between any two rooms — the worst case for backtracking and route variety. Treat "connected" and "well-structured" as two separate goals: verify connectivity via flood-fill (sandbox-maze#E1's method, unchanged), then deliberately add back a small fraction of the discarded candidate edges for loops — doing so cannot break the connectivity guarantee, since adding edges to an already-connected graph never disconnects it.
- Provenance (verified/assumed): Verified first-hand — built `sandbox.py` (zero RNG, zero wall-clock, fixed 4x4 grid, deterministic edge ordering), confirmed the spanning-tree-only maze is connected with exactly 0 cycles, and confirmed adding back a deterministic 12.5% slice of remaining edges keeps it fully connected while raising cycle count to 3. Confirmed deterministic/reproducible across two independent process invocations of `python3 sandbox.py`, output diffed byte-identical. External claims (MST-for-connectivity, loops-added-back-at-cited-percentages, single-path limitation of a pure tree) verified via live WebSearch results describing real dungeon-generator implementations, cross-consistent across independent sources; direct WebFetch to those sources was not attempted given this session's confirmed org egress-policy block on general web hosts.

## E1 — maze connectivity needs construction not density
- Date: 2026-07-05
- Project: local/sandbox-maze
- Tags: [algorithm][state][process]
- What: A procedural maze/dungeon generator that independently rolls each wall segment open at some fixed probability ("density") has no guarantee of full connectivity — even at a density tuned so its *expected total number of open passages* exactly matches a known-connected generator, it can (and in this test, always did) leave large portions of the map unreachable from the start.
- Why built: A dungeon-generation sandbox comparing a recursive-backtracker (spanning-tree) maze generator against a naive independent-wall-removal generator at matched openness.
- Design: Recursive backtracker: randomized DFS that carves into unvisited neighbours and backtracks when stuck, producing exactly `cells - 1` passages with no cycles (a spanning tree). Naive: for every wall segment in the grid, independently open it with probability `density`.
- Got right: Choosing `density` to match the backtracker's average total openness was the right control — it isolates the actual variable (does the *arrangement* of open passages guarantee connectivity, not just the *count*).
- Where/why it failed: Independent per-wall coin flips don't coordinate with each other at all — nothing in the naive generator's process cares whether the open passages it rolls actually chain together into a connected structure. Matching the *average* total openness of a spanning tree says nothing about whether THIS instance's passages are arranged to connect everything; they can easily cluster into disconnected regions purely by chance, even though "enough passages exist on average."
- Fix: Use a generation algorithm whose process structurally guarantees the property needed — a spanning-tree carve (recursive backtracker, Kruskal's/Prim's maze variants) is connected by construction, not by luck.
- Why this fix: A spanning tree over N cells has exactly N-1 edges and, by definition, one path between any two nodes — connectivity isn't a probabilistic outcome to hope for, it's baked into what "spanning tree" means.
- Rule of thumb: When a procedural generator must guarantee a global property (full connectivity, solvability, reachability), don't reach for "generate loosely at a density and hope the numbers work out" — pick (or verify) a construction whose process *guarantees* the property, and regression-test it with the actual check (a flood-fill from the start) over many seeds, not a glance at one rendered map.
- Provenance (verified/assumed): Verified first-hand — 500-trial simulation, 20x20 grid. Recursive backtracker: fully connected (all 400 cells reachable) in 500/500 trials. Naive independent-wall-removal at a density matched to the backtracker's average passage count: fully connected in 0/500 trials, with the worst trial reaching only 1 of 400 cells from the start.
