## E1 — ddmin minimal repro shrinks single cause but stalls on jointly sufficient and needs positive control
- Date: 2026-10-19
- Project: local/ddmin-minimal-repro-shrinks-single-cause-but-stalls-on-jointly-sufficient-and-needs-positive-control
- Tags: [debugging][isolation][method][simulation]
- What: A deterministic model of delta-debugging (ddmin) over a 32-item failing input with four failure shapes: one culprit, two jointly necessary culprits, two independent sufficient culprits, and a reduced repro missing a precondition, plus a linear five-whys walk over the same causal graphs.
- Why built: The minimal-reproduction kernel says stripping toward a minimal repro finds the cause, and the five-whys kernel says real failures rarely have one linear cause; I wanted to see where stripping stops being a cause-finder.
- Design: ddmin splits the input into chunks and keeps any subset or complement that still fails. Failure predicates are 17 in s; 5 in s and 21 in s; 3 in s or 28 in s. The five-whys walk follows the first listed cause at each level. A positive control re-runs the reduced repro with and without its environment precondition.
- Got right: The single-cause failure reduced to exactly [17] and the joint failure to [5, 21], so stripping did locate the cause set when the failure was one conjunction.
- Where/why it failed: With two independent sufficient causes ddmin returned only [3] and never showed 28, so the minimal repro was 1-minimal but hid a second route to the same failure. The five-whys walk on the joint graph named bad5 and root5 and omitted bad21. A repro built without its precondition did not fail at all.
- Fix: After ddmin, remove the found item from the original input and re-run: if it still fails there is another cause. For joint failures report the whole reduced set, not a single chain, and always re-run the positive control on the reduced repro before trusting it.
- Why this fix: Removing the found cause and retesting is cheap and directly tests the single-cause assumption, whereas a 1-minimal result only guarantees no single item can be dropped from that subset.
- Rule of thumb: Delta-debugging a failure to a minimal repro found the whole cause set when the failure was one conjunction in this model, but it returned one of two independent causes and hid the other, so after reducing, delete the culprit from the original and re-run, and confirm the reduced repro still fails.
- Provenance (verified/assumed): Verified first-hand by running the saved sandbox, PASS with deterministic output; the failure predicates are my own synthetic models and no real program or debugger was used.

- ZaneGPT verdict: weak — The either-cause case supports the headline (ddmin hides one of two independent causes), but the proposed remedy is only tested on two causes, in a deterministic model, and its second clause (the reduced repro still fails) cannot fail, so the rule is only partly checked.
- Hidden assumption: A 32-item input with failure predicates that are pure, deterministic set-membership tests generalizes to real failures, so "delete the culprit, re-run" is a complete check. In real systems, flaky or order-dependent failures, and failures with three or more redundant causes, break that check.
- Would prove it wrong: A case where the post-reduction check passes but a hidden cause remains. Example: delete 3 from the original and it still fails, but delete 3 and 28 together and it passes. That shows the check needs a repeat per found culprit, not one re-run. Or a flaky predicate where the re-run flips between pass and fail, so one re-run proves nothing.
- Break scenario: Three independent sufficient causes (`3 in s or 28 in s or 9 in s`), plus a 10% flaky trigger on one of them. ddmin returns [3]. Deleting 3 from the original still fails, because 28 or 9 remains. A single re-run might also pass by luck and wrongly confirm 3 as the only cause. The rule's one-step check is then silent or wrong, and the closing "confirm the reduced repro still fails" is vacuous since [3] fails by construction.
