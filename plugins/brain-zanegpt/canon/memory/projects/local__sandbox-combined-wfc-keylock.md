## E6 — wfc keylock ca fixup and scatter fix both generalize
- Date: 2026-07-13
- Project: local/sandbox-combined-wfc-keylock
- Tags: [gamedesign][algorithm][procgen]
- What: Grew group 1 (wfc-keylock environment) with `sandbox-procgen-ca` (new pairing) — the third generator tested against this project's connectivity-fixup pass, and the second against scatter's floor-only-candidate fix. procgen-ca#E1: CA cave smoothing produces MULTIPLE roughly-equal-sized regions (largest-region fraction 43.5-61.6% across seeds), structurally different from maze/WFC's one-dominant-region-plus-small-islands shape. Composed with the connectivity-fixup (already generalized from WFC to a density-based maze, `sandbox-combined-wfc-keylock#E4`): 237/500 CA maps disconnected before fixup (avg 1.74 regions/map), 0/500 after — the fixup's region-agnostic design (operate on final region topology, sort by size, carve smallest to nearest) handles the more-balanced multi-region case with zero changes. Composed with scatter's floor-only-candidate fix (originally verified on WFC maps, `sandbox-combined-wfc-keylock#E2`): 0/3000 wall placements on CA maps, and notably 0/500 attempt-budget exhaustions (versus 8.8% on the sparser WFC maps), since CA's more open/spacious caves give min-distance rejection sampling more room to succeed.
- Why built: To continue the pattern of checking whether fixes verified for one specific generator's failure shape are genuinely generator-agnostic or were incidentally tuned to that generator's particular disconnection/sparsity profile — CA's structurally different region-count distribution (2-3 roughly-equal regions vs. WFC/maze's 1-dominant-plus-many-tiny-islands) was chosen specifically because it stresses the fixup's "sort by size, carve smallest first" logic differently (more, larger carves needed) than either prior generator did.
- Design: `generateCA()` reproduces procgen-ca#E1's own described mechanism (45% fill probability, 6 iterations of 4-5 rule smoothing) exactly. Both the connectivity-fixup and scatter-candidate-filtering functions are the literal, unmodified code already verified against WFC and maze.
- Got right: Both fixes held with zero modification across a third, structurally distinct generator. This strengthens the earlier generalization claims (wfc-keylock#E2, #E4) from "works for two generators with a similar disconnection shape" to "works across generators whose disconnection/sparsity profiles differ meaningfully" — the fixup and the candidate-filter are each doing their job at the correct level of abstraction (final grid topology; final walkable-cell set), never anything specific to how a particular generator produces that grid.
- Where/why it failed: It didn't; this is the third consecutive confirmatory generalization result for these two fixes, filed because each additional generator checked is real, decision-relevant evidence toward "these fixes are safe to apply to any future discrete-grid generator in this project without re-verification," not just repetition of the same finding — the specific numbers (237/500 vs. maze's 1000/1000, 0/500 exhaustion vs. WFC's 8.8%) show the fixes handle meaningfully different underlying distributions, not just the same one twice.
- Fix: N/A — no bug found, no code change to either fix.
- Why this fix: N/A (no fix), but the reason zero changes were needed across three generators is the load-bearing content here: both fixes were designed to operate on the OUTPUT REPRESENTATION (a discrete walkable/blocked grid; a set of floor cells) rather than on any property specific to how that representation was produced, which is precisely the design property that makes a fix reusable across generators instead of needing a bespoke version per generator.
- Rule of thumb: Once a fix for a discrete-grid procedural-generation problem (connectivity repair, candidate-space filtering) has been verified generator-agnostic across two OR MORE structurally different generators (different disconnection shapes, different wall/floor ratios, different region-count distributions), treat it as safe to apply to any NEW generator producing the same grid representation without re-verification — but the generalization claim strengthens with each additional, meaningfully-different generator checked, so prefer testing against generators that stress the fix differently (as CA's multi-region shape did here) over testing near-identical generators that would just repeat the same confirmation.
- Provenance (verified/assumed): VERIFIED first-hand — ran 500 trials of an independently-implemented CA cave generator (matching procgen-ca#E1's described parameters) through the unmodified connectivity-fixup (237/500 disconnected before, 0/500 after) and, separately, through the unmodified scatter floor-only-candidate filter (0/3000 wall placements across 500 maps x 6 props, 0/500 attempt-budget exhaustions).

## E5 — wfc keylock lsystem endpoint rasterization fragments connectivity
- Date: 2026-07-13
- Project: local/sandbox-combined-wfc-keylock
- Tags: [procgen][algorithm][state]
- What: Grew group 1 (wfc-keylock environment) with `sandbox-procgen-lsystem` (new pairing). lsystem#E1: segment count grows 5x/iteration but bounding-box area grows ~9x/iteration — higher-iteration L-system output is measurably SPARSER (more spread out per segment). keylock#E1's reachability-gate requires a discrete grid (a flood-fill BFS over cells), but an L-system's native output is CONTINUOUS turtle-graphics line segments, which must be rasterized onto a grid before keylock's logic can run at all. Composed directly: rasterizing by marking only each segment's two ENDPOINTS (a plausible first-pass implementation — "these are the points the turtle visited") fragmented a SINGLE, fully-connected turtle path (by construction, one continuous walk with branches) into 14 disconnected components at iteration 2, 62 at iteration 3, and 306 at iteration 4 — worsening exactly in step with lsystem#E1's own sparsity-increases-with-iteration finding. Rasterizing the FULL line (sampling points along each segment's length, not just its ends) produced exactly 1 connected component at every iteration tested, correctly reflecting the true topology.
- Why built: Neither system's own tests ever needed this conversion — lsystem#E1 tested continuous geometry (bounding box, segment count) with no grid involved at all; keylock#E1's maze was ALREADY a discrete grid, generated directly as one, with no rasterization step in its pipeline. The composition is the first time an L-system's output has to cross the continuous-to-discrete boundary before another system (keylock's reachability gate) can consume it, and lsystem#E1's own "gets sparser at higher iterations" finding directly predicts this boundary would get worse, not better, as detail increases — which is exactly what was measured.
- Design: Standard L-system turtle (`F -> F[+F]F[-F]F`, 25 degree turns, matching lsystem#E1's own described rule) expanded 2-4 iterations, walked to produce line segments with step length 3 units. Two rasterization strategies onto a unit grid: endpoints-only (mark each segment's two endpoint cells) versus full-line (sample points along each segment's length at sub-cell intervals, marking every cell traversed). Connected-component count measured (8-connected) for both.
- Got right: The L-system generator and turtle-walk themselves are correct — the full-line rasterization's 1-component result at every iteration confirms the underlying path really is fully connected by construction (a single continuous walk with branches can never actually be disconnected); the bug is entirely in the rasterization step, not in either system's core algorithm.
- Where/why it failed: A line segment whose length exceeds roughly one grid cell (step length 3 vs. cell size 1, here) passes THROUGH multiple intermediate cells that endpoint-only rasterization never marks — so two segments that are geometrically continuous (segment A's endpoint equals segment B's start point) can still look disconnected to a cell-adjacency check if the segment between them "jumped over" cells the discrete grid never recorded as visited. This gets structurally worse exactly where lsystem#E1 already found detail increases — more, and longer relative to grid resolution, segments spread over a disproportionately growing bounding box — so the fragmentation observed (14 -> 62 -> 306 components) is not a fixed-cost bug but one that scales with exactly the property lsystem#E1 already flagged as growing.
- Fix: Rasterize the FULL extent of every line segment (supercover/line-sampling — mark every cell a segment's length passes through, not just its two endpoints), sampling at an interval fine enough relative to grid cell size (here, twice per cell width) to guarantee no gap. Re-ran the identical 2/3/4-iteration sweep: 1 connected component in every case.
- Why this fix: This generalizes the exact continuous-to-discrete boundary lesson already established for Set/JSON serialization in this project (`sandbox-combined-movement-stack#E2`: convert explicitly at the boundary, don't rely on a naive default) to a geometric case — a discrete grid consumer needs the FULL swept extent of continuous geometry, not just its sampled control points, and the gap between "looks connected as continuous geometry" and "looks connected as a rasterized grid" grows exactly as fast as the geometry's own segment-length-to-grid-resolution ratio does.
- Rule of thumb: Before feeding ANY continuous-geometry generator's output (L-systems, splines, procedural line art) into a discrete-grid consumer (a pathfinder, a reachability check, anything cell-based), verify the rasterization step marks each segment's FULL swept path, not just its endpoints or control points — endpoint-only rasterization silently fragments connectivity whenever a segment's length exceeds roughly one grid cell, and the fragmentation gets WORSE, not better, as the generator's own detail/iteration count increases if the generator (like an L-system) produces proportionally longer or sparser segments at higher settings.
- Provenance (verified/assumed): VERIFIED first-hand — expanded an L-system 2/3/4 iterations, rasterized the resulting turtle-graphics segments onto a grid via both an endpoints-only and a full-line-sampling strategy, and directly counted connected components via flood-fill: 14/62/306 components (endpoints-only, worsening with iteration count exactly as lsystem#E1's sparsity finding predicts) versus 1/1/1 (full-line, at every iteration tested).
- Composed: sandbox-procgen-lsystem/E1, sandbox-keylock/E1, sandbox-combined-wfc-keylock/E1

## E4 — wfc keylock connectivity fixup generalizes to density maze
- Date: 2026-07-13
- Project: local/sandbox-combined-wfc-keylock
- Tags: [gamedesign][algorithm][procgen]
- What: Grew group 1 (wfc-keylock environment) with `sandbox-maze` (new pairing). maze#E1: a density-based generator (roll each wall segment open at a fixed probability) has no connectivity guarantee and, in that sandbox's own test, ALWAYS left portions unreachable. `sandbox-combined-wfc-keylock#E1` already built a generic connectivity-fixup pass (flood-fill regions, carve a corridor from each isolated region's nearest cell to the main region) to fix the SAME class of failure for a different generator (WFC's local-constraint satisfaction). Composed directly: does the fixup, verified only against WFC's disconnection mechanism, also repair a density-rolled maze's disconnection? Ran 1000 trials of a density-based generator (matching maze#E1's own described mechanism): 1000/1000 disconnected before fixup (worse than, but directionally consistent with, maze#E1's own finding), 0/1000 after applying the unmodified fixup.
- Why built: To check whether a connectivity fix built and verified for one generator's specific failure mode (WFC's local-vs-global gap) is actually GENERATOR-AGNOSTIC as its own design implied, or whether it was accidentally tuned to WFC's particular disconnection shape (small isolated pockets from a random-walk-style carve) and would need rework for maze#E1's different mechanism (independently-rolled wall segments, potentially producing much larger or more numerous disconnected regions).
- Design: `generateDensityMaze()` independently rolls each cell open at a fixed density (0.55), reproducing maze#E1's described generator exactly. The connectivity-fixup function used is the literal, unmodified code from `sandbox-combined-wfc-keylock#E1`.
- Got right: The fixup's core design — operate purely on the FINAL grid's region structure (flood-fill, sort by size, carve shortest path to the largest region) — never referenced anything about HOW the grid was produced, which is exactly why it required zero changes to work on a structurally different generator. This confirms the fixup is a genuinely generic, reusable connectivity-repair layer, not an incidental fix for WFC specifically.
- Where/why it failed: It didn't; this is a confirmatory/generalization result. Filed because "does fix X, verified for problem Y, actually generalize to problem Y' (same class, different mechanism)" is exactly the kind of unstated assumption combined-sandbox training exists to check rather than assume, and a clean generalization is valuable, reusable information for any future generator (L-system, cellular automata, or anything else in this project) that might exhibit the same local-vs-global connectivity gap.
- Fix: N/A — no bug found, no code change to the fixup.
- Why this fix: N/A (no fix), but the underlying reason the fixup generalizes cleanly is worth stating precisely: any procedural generator that produces its output as a discrete grid of walkable/blocked cells presents the SAME post-hoc repair surface (a set of disjoint regions to reconnect) regardless of the generation mechanism that produced those regions — the fixup operates one layer of abstraction above the generator, on the grid's region topology alone, so it is correct for any generator that terminates in that same representation.
- Rule of thumb: A connectivity-repair pass built for one procedural generator's disconnection failure should be evaluated for reuse across every OTHER generator in the same project that shares its output representation (a discrete walkable/blocked grid) before assuming a new generator needs its own bespoke fix — verify the reuse explicitly (as here) rather than either assuming it transfers for free or rebuilding a redundant, generator-specific repair pass.
- Provenance (verified/assumed): VERIFIED first-hand — ran 1000 trials of an independently-implemented density-based maze generator (matching maze#E1's described mechanism) through the unmodified `sandbox-combined-wfc-keylock#E1` connectivity-fixup function, confirming 1000/1000 disconnected before and 0/1000 disconnected after.

## E3 — astar replan wfc cell based pathfinding blind to socket edges
- Date: 2026-07-13
- Project: local/sandbox-combined-wfc-keylock
- Tags: [algorithm][procgen][gamedev]
- What: Bridges the two live emergent groups directly (`astar-replan` in the movement/RPG cluster, `procgen-wfc` in the dungeon-gen cluster; `brain analyze seams` flagged this pair explicitly). astar-replan's occupancy model is CELL-based (`occupied.has(cell)` — a cell is walkable or not). WFC/E1's tiles are SOCKET-based — two adjacent tiles are only actually connected if their facing sockets match, which is an EDGE property, not a cell property. Composed directly: astar-replan planned a path across a socket-incompatible edge (two individually-walkable cells that are NOT connected to each other per the tile generator's own semantics) in 500/500 trials where a path was found.
- Why built: astar-replan's own sandbox and every prior composition (movement-stack, seam-loop-movement, the save/Set seam) used a plain walkable/wall grid with no directional-tile concept, so "is the neighbor cell non-wall" was always a sufficient traversability check. procgen-wfc's tiles were never fed into a pathfinder before — this is the first time astar-replan's implicit assumption (cell walkability fully determines traversability) meets a generator where it doesn't.
- Design: An 8x8 grid of 3 tile types (`ns`: sockets open only North/South; `ew`: sockets open only East/West; `open`: all four sockets open), placed independently per cell. `edgeConnected(a, b, dir)` checks both tiles' facing sockets match. astar-replan's original move-gate checks only destination-cell non-wall status; the fixed version additionally requires `edgeConnected` between the current and candidate cell before allowing the move.
- Got right: astar-replan's core search (open-list ordering, g/h-score bookkeeping, path reconstruction) needed zero changes — the bug is entirely in what counts as a valid MOVE, not in how the search explores or optimizes.
- Where/why it failed: A cell-walkable check answers "can I stand here"; it says nothing about "can I get here FROM my current cell" when the connectivity model is edge-based rather than purely cell-based. astar-replan's own verified fix (E2: never reject the agent's own start cell) and every prior composition in this project only ever needed the cell-level question, so nothing forced the edge-level question to be asked — it's invisible until a generator that encodes directional/socket connectivity is on the other end of the seam.
- Fix: Gate every candidate move by `edgeConnected(currentTile, neighborTile, direction)` in addition to (not instead of) the existing wall/occupancy check. Re-ran the identical 500-trial sweep: 0/N violations (N was small — see caveat below — but zero of the paths that were found crossed an incompatible edge, versus 500/500 before the fix).
- Why this fix: The correct move-validity check for an edge-based connectivity model must be evaluated per EDGE (a function of both endpoints and direction), not per destination CELL alone — this generalizes the same "check the actual dependency, not a proxy for it" pattern as `sandbox-combined-movement-stack#E1` (grid-adjacency isn't clearance) applied to a different kind of grid-representation mismatch.
- Rule of thumb: Before feeding a cell-based pathfinder (walkable/wall per cell) a map from any generator whose connectivity model is EDGE- or SOCKET-based (WFC-style tilesets, directional doors, one-way passages), check explicitly whether "neighbor cell is non-wall" is actually sufficient to mean "reachable from here" — it silently is NOT for any generator where two individually-valid cells can still be mutually unconnected. A pathfinder verified correct on a plain walkable/wall grid carries this assumption invisibly forward into any composition with a richer connectivity model.
- Caveat (own limitation, stated honestly): this sandbox's tile placement is independent-per-cell random assignment, not real constraint-propagated WFC, so post-fix only 3/500 grids had ANY valid path at all (most random tile arrangements are locally disconnected almost everywhere) — the fix's correctness (0 violations) is fully verified, but the LOW connectivity rate is an artifact of this simplified generator, not a claim about real WFC output, which uses propagation specifically to keep the compatible-neighbor rate high.
- Provenance (verified/assumed): VERIFIED first-hand — ran 500 trials of the original cell-only astar-replan against socket-typed tiles, confirming every found path (500/500) crossed at least one socket-incompatible edge; re-ran with the edge-gated fix confirming 0 violations among the (fewer, due to the stated generator caveat) paths found.

## E2 — wfc keylock scatter candidate space must exclude walls
- Date: 2026-07-13
- Project: local/sandbox-combined-wfc-keylock
- Tags: [gamedesign][algorithm][procgen]
- What: A 4-system combination (procgen-wfc generation, the connectivity-fixup pass from `sandbox-combined-wfc-keylock#E1`, keylock's map, and `sandbox-scatter#E1`'s min-distance-rejection prop placement) tested whether scatter's fix — verified in its own sandbox on an open continuous plane with no invalid regions — still works once the candidate space is a WALLED, mostly-non-walkable grid. Scattering 6 props per map (500 trials, min-distance 2.0) using scatter's original candidate space (every cell in the grid) placed props on wall tiles 2271 times across 500 trials — an average of ~4.5 of every 6 requested props landing somewhere the player can't stand or see them meaningfully.
- Why built: scatter#E1's min-distance rejection fix solves clumping among VALID candidate positions; it was never tested against a candidate space that includes structurally INVALID positions (walls), because its own sandbox's map was fully walkable by construction. This combination sandbox is the first time scatter's candidate space is a real dungeon grid rather than an open plane.
- Design: Generate a WFC-style map, connectivity-fixup it (E1's own fix), then scatter N=6 props with `minDist=2.0` using rejection sampling — first over the entire W×H grid (every cell, matching scatter#E1's original candidate contract), then restricted to floor-only cells.
- Got right: scatter#E1's min-distance rejection logic itself is not at fault — of the props that DID land on floor tiles, none violated the minimum-distance constraint; the bug is entirely about which cells are eligible candidates in the first place, not the spacing algorithm.
- Where/why it failed: scatter#E1's fix answers "how do I avoid placing two props too close together," implicitly assuming every candidate position is a legal placement. On an open plane that assumption is free — every cell is walkable. Composed with a WFC+keylock dungeon where most cells are wall, the same rejection-sampling loop happily draws wall cells as candidates, checks only the min-distance constraint (which walls trivially satisfy, since nothing else is near them), and accepts them — silently producing a level where most decorative/loot props are inside solid geometry, invisible and unreachable, with no error or signal.
- Fix: Restrict the candidate list to floor-only cells before running scatter#E1's rejection sampling — `candidates = allCells.filter(walkable)`, unchanged otherwise. Re-ran the identical 500-trial sweep: 0 wall placements. Secondary effect observed, not itself a bug: 44/500 (8.8%) of trials now exhaust their attempt budget without placing all 6 props, because a small walkable floor area combined with a fixed min-distance can genuinely run out of room — a capacity interaction between map size and prop count/spacing that scatter#E1 never had to consider on an unbounded-feeling open plane.
- Why this fix: The correct scope for "which positions are candidates" is a property of the MAP (walkable vs not), not of the placement algorithm — scatter#E1's rejection sampling is correctly generic and needed zero logic changes, only a correctly-filtered input. This is the same "convert/filter only at the composition boundary" pattern as `sandbox-combined-loop-combat#E1` (quantize at the write boundary) and `sandbox-combined-movement-stack#E2` (convert at the save boundary) — each single system stays untouched, the seam gets one targeted filter/conversion.
- Rule of thumb: Before reusing a placement/scatter algorithm verified on an open or fully-valid space inside a system that has STRUCTURALLY INVALID positions (walls, out-of-bounds, occupied-by-something-else), explicitly filter the candidate set to valid positions first — never assume a spacing/rejection algorithm's own correctness implies its candidate space is safe; those are separate questions, and an algorithm that's perfectly correct over its actual inputs will silently produce nonsense if fed invalid ones with no way to tell the difference.
- Provenance (verified/assumed): VERIFIED first-hand — ran 500 trials scattering 6 props onto WFC+connectivity-fixed maps with the naive whole-grid candidate space, counting 2271 wall-placement instances, then re-ran identically with floor-only-filtered candidates confirming 0 wall placements and separately noting the 44/500 attempt-budget-exhaustion rate as a distinct, expected capacity effect.

## E1 — wfc keylock local constraint doesnt guarantee global connectivity
- Date: 2026-07-13
- Project: local/sandbox-combined-wfc-keylock
- Tags: [gamedesign][algorithm][procgen]
- What: New group seed (previously untested: `sandbox-procgen-wfc` and `sandbox-keylock` share no prior edge). Composed WFC-style local-constraint level generation with keylock/E1's reachability-gated key placement fix. Hypothesis was that the fix itself would fail on WFC output; instead it held perfectly (0/2000 softlocks) — because it was never actually challenged: 1917/2000 (96%) of generated maps contained floor tiles the player can never reach AT ALL, so no door/key ever gets placed there in the first place. The real finding is upstream of keylock's fix: 0% local contradiction rate (procgen-wfc#E1's own verified result) says nothing about GLOBAL connectivity of the walkable area.
- Why built: keylock#E1's fix was verified on a recursive-backtracker maze, which is a spanning tree and therefore fully connected by construction — every cell is reachable from every other cell before any lock is even placed. procgen-wfc#E1 never tested a generator whose local satisfaction could produce a globally disconnected walkable area, because its own metric (contradiction rate during collapse) doesn't measure that. Composing them was the first time either sandbox's assumption ("the map is one connected region") was actually checked against the other's generator.
- Design: A WFC-style generator (random-walk floor carving + scattered isolated floor cells — deliberately reproducing the realistic WFC failure mode where local tile-compatibility satisfaction leaves disconnected pockets) feeds directly into keylock#E1's exact reachability-gate logic (flood-fill from start, door edge removed, key sampled from the gated-reachable set).
- Got right: keylock#E1's fix is provably ROBUST to a disconnected map — because it only ever samples door/key placements from cells already flood-fill-reachable from the start, a disconnected "island" region simply never gets a lock or key placed in it, so it can't cause a softlock. This is a genuinely useful, previously-unstated robustness property of the fix, not just an absence of a new bug.
- Where/why it failed: The maze generator keylock#E1 was originally verified against guarantees full connectivity as a structural side effect of being a spanning tree; nothing about keylock#E1's fix or its own tests ever had to state that assumption, because it was always true. Swap in a generator family (WFC, and by the same local-vs-global gap, any purely-local constraint-satisfaction or noise-threshold generator) where that guarantee doesn't hold, and the practical consequence isn't the softlock keylock#E1 solved — it's a much larger, silent content-waste bug: the vast majority of generated levels ship with rooms/areas nothing in the game will ever route the player to, key/lock or not.
- Fix: Run an explicit connectivity-fixup pass (flood-fill regions, carve a corridor from every isolated region's nearest cell to the main region — the same pattern already verified for CA-based generation in this project's own `procgen-ca` connectivity step) on WFC output BEFORE any door/key placement logic runs. Re-ran the identical 2000-trial sweep post-fixup: 0/2000 maps had more than one connected region.
- Why this fix: A local-constraint-satisfaction generator's own success metric (contradiction rate) is orthogonal to global connectivity by construction — no amount of tuning WFC's propagation logic fixes this, because propagation only ever reasons about adjacent-tile compatibility, never about whether two satisfied regions are mutually reachable. A separate, generator-agnostic connectivity pass is the correct layer to enforce it, exactly mirroring how `procgen-ca`'s own cave generator already needed the same fixup for the same underlying reason (cellular-automaton smoothing is also a purely local rule).
- Rule of thumb: Before trusting any "is this level solvable" or "can the player reach X" verification (keylock#E1's own reachability-gate pattern, or any downstream logic that assumes one connected walkable region), check whether the generator that produced the map actually GUARANTEES global connectivity as a structural property (a spanning tree does; a purely local constraint-satisfaction or cellular-automaton process does not, regardless of how low its own local-failure metric is) — a 0% "contradiction"/"local violation" rate is not evidence of global connectivity and must never be read as such.
- Provenance (verified/assumed): VERIFIED first-hand — ran 2000 trials of WFC-style generation composed directly with keylock#E1's own reachability-gate logic, counted 1917/2000 maps with a disconnected floor region and 0/2000 actual softlocks (confirming the fix's robustness), then applied an explicit connectivity-fixup pass and re-ran the identical 2000 trials confirming 0/2000 maps remained disconnected.
