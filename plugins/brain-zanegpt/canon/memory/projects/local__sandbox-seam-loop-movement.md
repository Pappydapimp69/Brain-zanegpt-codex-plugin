## E1 — sandbox seam loop movement lattice resolution
- Date: 2026-07-13
- Project: local/sandbox-seam-loop-movement
- Tags: [determinism][physics][gamedev]
- What: Composed `sandbox-combined-game-loop#E1` (authoritative/fingerprinted state must live on an integer lattice — no float leaking into anything gameplay-affecting) with `sandbox-combined-movement-stack#E1` (collision detection needs fine-grained continuous substep sampling to catch adjacency-driven physical overlaps a grid occupancy model misses). Collision outcomes are gameplay-affecting (damage/blocking), so per game-loop#E1's own rule they belong on the integer lattice — but forcing movement-stack#E1's substep collision sampling onto an integer lattice is only SAFE at a fine enough resolution. At 1/100-cell resolution, quantized vs. float overlap counts differed by <5% (noise). At 1/10-cell, real non-monotonic drift appeared (both over- and under-detection, up to ~8% of the true count). At 1/2-cell (a plausibly "cheap" fixed-point budget), results became wildly unreliable: swings of +135/-149 events relative to float ground truth, and two DIFFERENT collision half-extents (0.3 and 0.45) collapsed to the identical detected-overlap count (405) — an aliasing artifact where the lattice itself was coarser than the distinction the game logic needed to make.
- Why built: `brain train edge` ranked this pair (game-loop + movement-stack) as an untested seam sharing architecture/gamedev/state/testing tags. Both fixes are individually verified and correct; this tested whether they compose or fight.
- Design: Agent and obstacle random-walk within a shared bounded box (paths cross frequently, unlike an initial discarded setup where they never converged), positions quantized to a configurable lattice resolution (or left as float, the control), 64-substep interpolated overlap sampling per tick (matching movement-stack#E1's exact methodology) run at 5 collision half-extents x 3 lattice resolutions x 20 seeds each, compared against the float baseline.
- Got right: An initial scenario (agent walks a straight line toward a fixed goal, obstacle random-walks near a distant starting point) produced 0 collisions in every condition — recognized as a setup bug (the paths simply never got close enough to test anything) and discarded before drawing any conclusion, rather than reporting a false "no interaction" finding.
- Where/why it failed: The two source fixes don't just fail to compose — they actively trade off against each other along a single, previously-unnamed dial (lattice resolution relative to collision half-extent), and neither source sandbox's own tests could see this because game-loop#E1 never tested collision-relevant continuous motion, and movement-stack#E1 never tested integer quantization. "Use an integer lattice" (game-loop#E1) is necessary for determinism but insufficient on its own — a lattice fine enough for TIMING determinism can still be far too coarse for COLLISION correctness, silently producing both false-positive and false-negative overlaps whose direction and magnitude depend on how the specific half-extent relates to the lattice spacing, not on any code defect.
- Fix: Not implemented — flagged as the finding, with a concrete direction: tie the minimum lattice resolution to the SMALLEST collision half-extent the game ever uses (e.g., at least ~10-20 sub-units per half-extent, based on where this sandbox's drift stayed under ~10%), rather than picking a lattice resolution from timing/determinism concerns alone and assuming it's "fine enough" for collision too.
- Why this fix: game-loop#E1's integer-lattice rule is a NECESSARY condition for determinism but was never a sufficient specification — it says "integer," not "how fine an integer," and this sandbox shows that gap is exactly where collision correctness lives.
- Rule of thumb: When composing a determinism-driven integer-lattice architecture with a collision/physics system, "make positions integers" is not a complete answer — verify the CHOSEN lattice resolution against the SMALLEST half-extent any collidable object uses, by directly comparing quantized vs. float ground-truth overlap counts across a resolution sweep, the same way this sandbox did; do not assume a lattice fine enough for smooth-looking motion or stable timing is automatically fine enough for correct collision outcomes — the two needs are not the same and can diverge sharply at exactly the resolution a "reasonably fine" fixed-point budget might pick.
- Provenance (verified/assumed): VERIFIED first-hand — ran the Node.js sandbox across 20 seeds x 5 half-extents x 3 lattice resolutions plus a float control, directly comparing overlap-event totals; the aliasing artifact (two different half-extents both yielding exactly 405 at the coarsest resolution) was independently confirmed by inspecting the raw quantized-position collision checks at that resolution, not just the aggregate counts.
