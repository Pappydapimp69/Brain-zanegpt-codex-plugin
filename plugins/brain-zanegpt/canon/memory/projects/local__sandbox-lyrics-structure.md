## E6 — word frequency drift detector flags a second vocabulary track
- Date: 2026-09-29
- Project: local/sandbox-lyrics-structure
- Tags: [lyrics][testing]
- What: A per-line "topic drift" detector scoring each line by the fraction of its words that are below-median frequency in the song's overall vocabulary flags an extended metaphor's VEHICLE words (storm/lightning/clouds/flood imagery, used consistently through a heartbreak song) as MORE off-topic (avg score 0.66) than the metaphor's TENOR words (heart/breaking/leaving/alone, avg score 0.33) — despite the vehicle imagery being just as deliberate and consistently used a device as the tenor vocabulary, not an accident.
- Why built: `lyrics` had no memory entries on lyric-quality/consistency checking; a naive word-frequency-based drift or outlier detector is a plausible first implementation for "does this song stay on topic," and extended metaphor (a single consistent secondary vocabulary track alongside the literal one) is exactly the craft technique such a detector would need to NOT flag.
- Design: Deterministic Python (`sandbox_lyrics_structure.py` loop 8), a 6-line constructed lyric using two disjoint word sets (5 tenor words, 6 vehicle words) each appearing multiple times across the passage, `collections.Counter` for the frequency profile, and a below-median-frequency fraction as the per-line drift score, averaged separately over lines classified as pure-tenor vs pure-vehicle.
- Got right: Both vocabulary tracks are internally consistent by construction (each word recurs across the passage) — the detector isn't wrong that these words are less individually frequent than the dominant track; it's wrong that lower relative frequency means off-topic.
- Where/why it failed: A single-frequency-profile drift detector implicitly assumes the song has ONE topic vocabulary and everything else is noise — an extended metaphor is structurally TWO consistent vocabulary tracks running in parallel (literal + figurative), and whichever track is used in the minority of words (here, the vehicle words, slightly outnumbered by tenor words in this passage) reads as "the outlier" purely from being the smaller of two legitimate tracks, not from being actually inconsistent.
- Fix: Before flagging a low-frequency word cluster as drift, check whether it forms its OWN internally-consistent, recurring cluster (the vehicle words co-occur with each other across multiple lines, the same way the dominant vocabulary does) rather than treating "not the dominant vocabulary" as synonymous with "inconsistent" — a simple version: cluster words by co-occurrence first, and only flag a cluster that appears ONCE (no repetition) as genuine drift.
- Why this fix: The detector's actual, useful signal (repetition/consistency) is being computed correctly per-word but interpreted at the wrong grain (dominant-vs-not, a single axis) for a song that has two consistent axes running at once — re-grain the check to "does this word's cluster recur" rather than "is this word individually common," and both the tenor and vehicle tracks pass for the right reason.
- Rule of thumb: Any single-frequency-profile outlier/drift/consistency detector implicitly assumes ONE consistent population — before trusting a low-frequency flag, check whether the flagged content is itself a second, internally consistent cluster (a deliberate secondary vocabulary, a code-switch, a scene change that recurs) rather than genuine one-off noise; this generalizes past songwriting to any content with a legitimate secondary register.
- Provenance (verified/assumed): Verified first-hand — sandbox built and run; the printed per-line drift scores and the tenor/vehicle averages (0.33 vs 0.66) are observed output from the actual word-frequency computation, not estimated.

## E5 — section tags are labels not content aware editing metadata
- Date: 2026-09-29
- Project: local/sandbox-lyrics-structure
- Tags: [lyrics][bracket-tags][tooling][testing]
- What: Two sandbox loops (4, 9) show a bracket-tag section parser only ever knows about the TAGS, never about what the lyric TEXT says about its own structure — in both directions. (4) A loose substring section-tag detector (does this line contain "verse"/"chorus"/"bridge"?) misfires on ordinary lyric content: "you're my whole universe" gets flagged as a section tag because it contains "verse", something an anchored `^\[...\]$` bracket pattern correctly ignores. (9) The reverse problem: a tag-only auto-renumbering tool (relabel every "[Verse N]" by encounter order after an edit) is blind to prose the lyric ITSELF uses to reference its own structure ("like I said in verse one," "remember verse two?") — inserting a new section between two verses leaves those self-references correct by luck (nothing was reordered), but REORDERING two verses (promoting verse 2 to slot 1) leaves the new [Verse 1]'s own lyric still saying "verse one," a stale, now-wrong self-reference the tag-only tool has no way to see or flag.
- Why built: `bracket` returned only 1 shared memory entry (a TTS silent-no-op finding, a different failure class) and `section` returned 45 ideas but 0 lyrics-specific memory; bracket-tag parsing is the substrate every Suno-adjacent structural tool (duration, scheme, renumbering) is built on, so its own failure modes are worth establishing directly rather than only as a side effect of testing something built on top of it.
- Design: Two deterministic Python constructions (`sandbox_lyrics_structure.py` loops 4, 9), no RNG. Loop 4 compares a loose keyword regex against an anchored bracket regex on a 5-line mixed sheet. Loop 9 builds a 4-section sheet with in-lyric callbacks to earlier verse numbers, applies a straightforward "renumber every [Verse N] tag by encounter order" function first to an insert-only edit (tags stay correct by luck) and then to a reorder (tags stay internally consistent with each other, but the self-referencing PROSE goes stale).
- Got right: The anchored regex correctly ignores the false-positive lyric line in loop 4; the renumbering function is not itself buggy in either loop 9 case — every [Verse N] tag it produces is internally consistent with the others, exactly what "renumber the tags" was asked to do.
- Where/why it failed: Both failures are the same category from opposite sides: the tool's model of "what a section is" stops at the bracket tag, but the lyric text the tag is attached to can (a) accidentally look like a tag itself (loop 4) or (b) contain a claim ABOUT a tag's number that the tool never reads or updates (loop 9). A tool that only ever touches brackets cannot know that "verse" inside prose isn't a tag, or that "verse two" inside prose is a reference THAT WOULD NEED UPDATING if verse two moved.
- Fix: For tag detection, always anchor to the bracket syntax itself (`^\[...\]$`), never a bare keyword search over line content. For renumbering, either scan lyric content for a small set of self-referential patterns ("verse N", "chorus", ordinal callbacks) and flag them for review post-reorder (renumbering can't safely auto-rewrite prose meaning) rather than silently leaving them, or treat any REORDER (as opposed to a pure insert/append) as needing a human pass over content, not just tags.
- Why this fix: The two loops show the SAME underlying gap (tag-only structural awareness) causing OPPOSITE-looking bugs (false positive in one direction, false negative — a stale reference the tool doesn't even notice exists — in the other), which is a strong signal the gap is structural rather than two unrelated bugs: any tool built on "just parse the brackets" inherits both failure directions for free.
- Rule of thumb: A bracket/tag-based structural parser's contract ends at the brackets — before trusting it for anything that touches the SURROUNDING text (detection: could real content look like a tag? mutation: could a tag change invalidate a claim the content makes about it?), check both directions explicitly, since fixing one doesn't imply the other was ever addressed.
- Provenance (verified/assumed): Verified first-hand — both sandboxes built and run; the printed hits (loose regex flagging 3 lines vs anchored regex flagging 2; the reorder case's `[Verse 1]` lyric still literally containing the string "verse one") are observed output.

## E4 — non scheme lines must be excluded not defaulted
- Date: 2026-09-29
- Project: local/sandbox-lyrics-structure
- Tags: [lyrics][rhyme-tooling][state][testing]
- What: Two sandbox loops (3, 5) show a line-based rhyme-scheme/metric scanner breaking whenever a lyric sheet contains lines that carry no scheme intent at all — ad-libs and spoken bridges — unless those lines are EXCLUDED, not merely defaulted. (3) A naive scheme scanner that includes bracketed ad-lib lines ("(yeah)", "(uh)") in its line sequence inflates the measured line-distance between a real rhyme pair from 1 (their true, adjacent gap among lyric lines) to 2 (counting the intervening ad-lib as if it were a real line) — which would silently corrupt any closure-distance-style metric (cf. the prior session's E8) computed over the raw line list. (5) A letter-assigner that represents "no rhyme intended" (a spoken bridge line) with the same `None` sentinel its matching logic uses for "not yet computed," without an explicit exclusion check, matches two UNRELATED spoken bridge lines to each other by coincidence (both get letter 'B' in a scheme AABBA) purely because `None == None`, producing a scheme relationship the writer never intended.
- Why built: The prior session's line/word-level sandboxes always worked over lyric-only sequences by construction; a real lyric SHEET routinely interleaves ad-libs and spoken sections with sung/rhymed ones, and neither loop's failure would appear until a tool was run on a full, real sheet rather than a hand-curated lyric-only fixture.
- Design: Two deterministic Python constructions (`sandbox_lyrics_structure.py` loops 3, 5), no RNG. Loop 3 builds a 7-line sequence (4 real lyric lines, 3 ad-libs interleaved) and compares a naive letter-assigner that includes every line against one that filters ad-libs first, measuring the rhyme-pair line-gap both ways. Loop 5 builds a 5-line sequence (3 verse lines sharing rhyme_class "A", 2 spoken bridge lines with rhyme_class `None`) and compares an assigner using ordinary equality (which treats `None == None` as a match) against one that explicitly excludes `None` from ever matching.
- Got right: Both naive variants correctly handle the REAL rhyme relationships in each fixture (the true A/A and B/B pairs still land correctly) — the bug only shows up in what happens to the non-scheme lines, not in whether real rhymes are found.
- Where/why it failed: Both are the same mistake in different clothes: a sentinel meaning "this line doesn't participate in the scheme" (an ad-lib's absence of a rhyme_class; a bridge line's `None`) gets treated as ordinary DATA subject to the same equality/counting logic as real scheme-bearing lines, rather than being excluded from the population the logic operates over. `None == None` is TRUE in Python, so two "doesn't apply" sentinels silently equal each other exactly like two real matching values would.
- Fix: Filter out non-scheme-bearing lines (ad-libs; explicitly `None`-tagged spoken lines) BEFORE any position-, gap-, or equality-based scheme logic runs, not after — and represent "does not participate" with a value (or an explicit skip) that the matching logic is hard-coded to never treat as equal to itself, rather than relying on a sentinel that happens to also satisfy the language's default equality.
- Why this fix: Any "compare for equality" step over a field that can be legitimately absent needs its NOT-APPLICABLE case handled as a control-flow branch (skip it), not as a data value flowing through the same comparison — Python's `None == None` (and the equivalent null-equals-null pattern in most languages) will always resurface this exact bug for any metric built the same way, not just rhyme schemes.
- Rule of thumb: Before running an equality- or gap-based scan over a line sequence, ask what represents "this line doesn't count" — if that's the SAME sentinel the code separately uses for "not computed yet" or defaults to under normal equality, two unrelated non-participating lines will match each other, and the fix is exclusion before the scan, not a smarter comparison inside it.
- Provenance (verified/assumed): Verified first-hand — both sandboxes built and run; the printed gap values (1 true vs 2 inflated) and scheme strings (naive AABBA vs correct AA--A) are observed output.

## E3 — near title drop needs content word subsequence matching
- Date: 2026-09-29
- Project: local/sandbox-lyrics-structure
- Tags: [lyrics][testing]
- What: A "does the title appear in the lyrics" checker using exact substring match catches only 1 of 3 deliberate title-drops in a constructed hook (the verbatim repeat), missing a pronoun-and-word-inserted variant ("I'm gonna hold THAT line forever") and a tense-shifted variant ("we HELD the line"). An order-preserving subsequence matcher over the title's CONTENT words only (dropping function words like "the"/"a"/"that" from the requirement, and stemming simple tense shifts) catches all 3.
- Why built: `lyrics` canon had no memory entries on hook/title-drop detection specifically, and exact-substring is the obvious first implementation for "check the title appears" — worth establishing how much it actually misses on realistic, not pathological, variation.
- Design: Deterministic Python (`sandbox_lyrics_structure.py` loop 6), a 3-way hook-line fixture (exact repeat; word-inserted + pronoun swap; tense-shifted), compared under literal substring containment vs a hand-built order-preserving word-subsequence matcher with a small stem table and a stopword exclusion list, tuned once on the exact-match control line (which initially failed the fuzzy matcher too, from an un-stripped trailing comma on a token — fixed by stripping punctuation before comparison, a reminder that the "obvious" positive control is itself worth running, not assumed to pass).
- Got right: Once punctuation-stripped and function-words excluded from the requirement, the fuzzy matcher correctly passes the exact-repeat control AND both near-drop variants, with no false positive introduced on this fixture.
- Where/why it failed: Exact substring match requires the title to appear byte-for-byte; the first near-drop replaces "the" with "that" (a function-word substitution, extremely common when a line needs to scan differently) and the second replaces "hold" with "held" (an ordinary tense shift for a hook that's now describing something that already happened) — both are unremarkable songwriting choices, not edge cases, and both defeat literal substring containment completely.
- Fix: Require only the title's CONTENT words (excluding a short stopword list) to appear in the line, in order, allowing a small gap between them and a small stem/tense-normalization step — not a fuzzy/edit-distance match on the whole title string, which would risk false positives on unrelated lines that happen to share a few common words.
- Why this fix: An order-preserving subsequence match over content words specifically targets what makes something feel like "the title, varied for the line" (the same key words, the same order) while remaining strict about accidental overlap (a line using the title's content words out of order, or with too much drift between them, still fails) — the stopword exclusion is what makes it robust to the specific, common substitution class (function-word swaps) this loop found, without loosening the content-word requirement at all.
- Rule of thumb: A "does X appear" checker built on exact substring containment should be assumed to miss most REAL variation a human would still call "the same thing, said slightly differently" — function-word substitution and simple tense/inflection shifts are the first two variation classes to test against, since they're also the most common ones a writer produces without thinking about it.
- Provenance (verified/assumed): Verified first-hand — sandbox built and run; the printed hit counts (exact: 1/3, fuzzy: 3/3 after fixing the punctuation-stripping bug the positive control itself surfaced) are observed output.

## E2 — lyric sheet duration estimation fails three independent ways
- Date: 2026-09-29
- Project: local/sandbox-lyrics-structure
- Tags: [lyrics][duration][testing]
- What: Three sandbox loops (`brain train lyrics`, loops 1, 2, 7) each break a plausible song-duration estimator in an independent way. (1) Estimating duration from the count of DISTINCT section TYPES (4: Verse/Chorus/Bridge as a set) instead of section OCCURRENCES (7, counting each repeated tag) undercounts by exactly `(occurrences - types) * avg_section_seconds` — on a 7-section sheet with 4 distinct types, that's 60s of 140s, a 43% undercount. (2) Estimating duration from VISIBLE lines on the page undercounts whenever a writer used a repeat marker ("[Chorus] x2") instead of writing a section out twice — the marker is an instruction, not decoration, and a line-counting estimator that doesn't parse it treats the chorus as playing once. (3) Estimating duration from ONE global syllables-per-second rate misestimates any section performed at a genuinely different pace (a double-time rap bridge vs sung verses) by a large margin at the SECTION level (+9.03s on a 12s section, a 75% error) even when the SONG-level total error mostly cancels out (+0.00s here) — a total-duration-only sanity check would hide a per-section error this size.
- Why built: `lyrics` had 0 memory entries despite `duration` returning 17 (all from unrelated domains — timers, animation, audio). Song duration estimation from a lyric sheet is a natural first feature for any Suno-adjacent tool (matching a generated track's length, or estimating before generation), and each of the three obvious "count something on the page" approaches has its own independent failure mode.
- Design: Three small deterministic Python functions (`sandbox_lyrics_structure.py` loops 1, 2, 7), no RNG. Loop 1 compares `len(sections)` vs `len(set(sections))` on a 7-section sheet with a double+triple chorus tail. Loop 2 compares a raw line count against a repeat-marker-aware expansion on a 4-section sheet where one chorus carries an "x2" marker and is also spelled out once more elsewhere. Loop 7 gives 5 sections true (syllable-count, true-pace) pairs, calibrates one "global" rate from the true total, and re-estimates each section's duration from that single rate, isolating the bridge's error specifically.
- Got right: All three estimators are exactly correct in the DEGENERATE case each was probably first tested against (a sheet with no repeated section types, no repeat markers, uniform pacing) — which is exactly why each would ship before the failure surfaces on a normal song.
- Where/why it failed: All three share one shape: each estimator uses an AGGREGATE or DEDUPLICATED signal (distinct types; visible lines; one global rate) as a stand-in for something that is actually PER-INSTANCE or PER-SECTION (how many times each section plays; how many lines actually sound; how fast THIS section is performed) — dropping the per-instance information is exactly the input a typical song provides (repeated choruses, repeat markers, mixed pacing), not an edge case.
- Fix: (1) Count section occurrences, not distinct types, for duration; reserve distinct-type counts for a separate "structural complexity" metric and never let the two share a variable name. (2) Parse and expand repeat markers before counting lines, the same way any templating/macro-expansion step must run before a size estimate. (3) Estimate duration per-section, using that section's own pacing signal (a per-section rate hint, or a content-derived cue like a "rap"/"sung" tag) if available, and sum; check total-duration accuracy at the section level, not only the song level, since compensating errors hide there.
- Why this fix: In each case the aggregate signal is a lossy compression of the input the estimator actually needs (occurrence sequence; expanded line list; per-section pace) — the fix is to stop compressing before estimating, not to correct the estimate after the fact, and per-section validation is required because song-level totals can and did cancel out a real, large per-section error.
- Rule of thumb: Before trusting a "count X" duration or size estimator, ask whether the real quantity is actually PER-INSTANCE (how many times does this play) rather than per-distinct-thing or per-visible-unit — and validate any aggregate estimator at the sub-unit level too, since a compensating error is invisible at the total.
- Provenance (verified/assumed): Verified first-hand — all three sandboxes built and run; the printed numbers (140s vs 80s occurrence/type split; 12 vs 14 expanded lines; the bridge's +9.03s per-section error against a +0.00s song-level total) are observed output, not estimates.

## E1 — dedup lifetime kernel third domain repeat markers vs authored variants
- Date: 2026-09-29
- Project: local/sandbox-lyrics-structure
- Tags: [lyrics][state][algorithm][testing]
- What: A THIRD independent confirmation, in a third representation, of the dedup-key-lifetime kernel (`[SYSTEM / state / a-dedup-keys-lifetime-must-match-the-invariants-scope]`, sourced from sandbox-hitbox-window, then confirmed transferring to lyric-hook text dedup in sandbox-lyrical-composition/E1) — this time on the SECTION-repeat-marker axis rather than the hook-TEXT axis. A repeat-marker expander that mechanically duplicates a section's FIRST occurrence N times for "[Chorus] x2" has no way to know that a separately-written, evolved second chorus appearing right after it ("[Chorus - final]", with one line changed) was meant to REPLACE the marker's second duplicate rather than sit alongside it — naive concatenation produces 3 chorus plays (2 mechanical duplicates plus the authored final) where exactly 2 were intended, because the marker's "how many times" and the authored variant's "what the Nth time actually says" are two different sources of truth for the SAME repeat instance, and nothing reconciles them.
- Why built: The prior two confirmations of this kernel (physics/timing hitboxes; lyric hook TEXT) both concerned dedup of literal content instances. Repeat-marker expansion is structurally the same invariant ("this section plays N times") expressed as a COUNT plus a template, rather than as repeated literal text — worth checking whether the kernel's failure shape (a key/count that's authoritative on its own conflicts with authored content that should have been the same source of truth) survives the shift from "count occurrences of matching text" to "expand a declared count."
- Design: Deterministic Python (`sandbox_lyrics_structure.py` loop 10), no RNG. A 2-section sheet: `[Chorus] x2` (2 lines, the marker), followed immediately by `[Chorus - final]` (2 lines, one word changed — the intended, evolved SECOND play of that same chorus). A naive expander reads the `x2` marker and duplicates its 2 lines twice, then independently appends the separately-tagged "final" chorus, with no logic connecting the two.
- Got right: The marker parsing itself is correct in isolation — `x2` really does mean "this text, twice," and the expander produces exactly that if the "final" chorus block didn't also exist; the bug is purely in the INTERACTION between the two ways of expressing "the second chorus play," not in either mechanism alone.
- Where/why it failed: Same shape as both prior confirmations: an invariant ("chorus plays exactly N times, and the Nth time is THIS specific text") has its count half satisfied by a mechanical marker and its content half satisfied by separately-authored text, and nothing in the expander's model represents them as the SAME instance — so it happily satisfies the count requirement (duplicate twice) and the content requirement (append the final version) independently, producing N+1 total plays.
- Fix: When a marker declares a repeat count, the expander must treat any subsequently-tagged variant of the same section (a `[Chorus - final]`, `[Chorus 2]`, or similarly-named block) as OVERRIDING one of the marker's mechanical duplicates, not adding to them — concretely, expand the marker to N slots first, then fill the LAST slot from an explicitly-tagged variant if one exists, rather than expanding and appending independently.
- Why this fix: This is the same fix shape both prior confirmations used — mint one id for the invariant's real scope (here: "chorus play #2 of this repeat block") and let every source of information about that scope (the marker's count, the variant's authored text) write into the SAME slot, rather than letting each source independently produce its own output that then gets concatenated.
- Rule of thumb: (Unchanged from the original kernel — a third domain confirms it generalizes past "repeated text" specifically to "a repeat expressed as count + template," which is a strictly different mechanism sharing the same invariant shape.) Composing this with the original and the lyric-hook-text confirmation should raise `brain analyze graph`'s independence count for the kernel to 3 sources across 2 unrelated domains (physics/timing; two distinct sub-mechanisms within lyrics).
- Provenance (verified/assumed): Verified first-hand — sandbox built and run; the printed expansion (6 lines = 3 chorus plays from a sheet where 2 were intended) is observed output, not an estimate.
