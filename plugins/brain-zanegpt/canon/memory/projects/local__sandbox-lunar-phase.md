## E1 — lunar mean phase is a proxy for true new moon
- Date: 2026-10-09
- Project: local/sandbox-lunar-phase
- Tags: [astronomy][lunar-phase][verification][timekeeping]
- What: Seeds the new ASTRONOMY domain. A moon-phase routine that counts whole synodic months from a fixed new-moon epoch (period 29.530588861 d) was compared with 17 published new-moon instants (2000, 2017, 2023, all 13 of 2024, 2026) and with the same routine plus Meeus-style anomaly, latitude-argument and node terms and a TT-to-UTC shift.
- Why built: Phase code is typically written as a modulo on a constant period and then trusted for date-keyed events (eclipse day, tide table, a "new moon tonight" game event). Needed to measure how far that proxy sits from the true instant and whether tuning it can close the gap.
- Design: Deterministic stdlib sandbox. Mean model = 2451550.09766 + 29.530588861k. Corrected model adds 15 periodic terms (dominant -0.4072 sin M') in days, then subtracts delta-T (64-69 s). Scenarios: mean vs 17 references; corrected vs the same; dominant term alone; 7th-decimal period edit and a naive 29.5 d period; UTC calendar-date classification of 38 moons (2024-2026); fixed -8 h offset vs the real Los Angeles zone over 2000-2050.
- Got right: Corrected model agrees with all 17 references within 1.2 minutes (max), so both the model and the recalled references corroborate each other. The mean model is off by up to 11.9 h (2017-08-21 +11.88 h, 2024-08-04 +10.30 h) and puts 9 of 38 new moons on the wrong UTC calendar date.
- Where/why it failed: Two instinctive repairs failed. Tuning the mean period at the 7th decimal moved the true error by only 0.0021 h, and the naive 29.5 d period drifted 231 h by 2026. Keeping only the dominant anomaly term still left 4.42 h worst case. A fixed -8 h offset vs the real Los Angeles zone flipped 0 local dates in 2024-2026 (a clean-looking sample) but 8 moons over 2000-2050, all inside the 07:00-08:00 UTC window.
- Fix: Treat mean-period phase as a proxy gauge and read the true instant beside it: compute the anomaly-corrected time, keep it as a UTC instant, and derive local calendar dates per IANA zone at the edge. Use the mean model only for "roughly which week", never for a date or hour decision.
- Why this fix: The error is a periodic equation-of-the-center effect (about +/-10 h), not a drift, so no constant can remove it; only the anomaly terms do, and they cost a dozen sines. The date flips are a separate mechanism, so zone handling has to be fixed independently.
- Rule of thumb: In the cases run (17 reference moons, 38 date classifications, 2000-2050 zone sweep), a mean-period lunar phase misses the true new moon by up to about 12 h and the miss cannot be tuned away; compute the corrected instant, store UTC, and localise per IANA zone, and check a long span because a short sample can show zero zone flips.
- Provenance (verified/assumed): Verified first-hand: the sandbox run and every number above. The 17 reference instants were recalled from published almanac and eclipse tables (minute resolution), not fetched during this run; their agreement with the independent model within 1.2 min is the evidence they are right. Meeus constants entered from memory and checked only through that agreement.
- Composed: ideas:ZEN/verification/finger-is-not-the-moon-proxy-gauge/true-cost-readout-beside-the-proxy, sandbox-proxy-gauge/E1, ideas:TIMEKEEPING/timezones/a-utc-offset-is-not-a-time-zone-so-future-events-must-store-the-iana-zone-id
- Polarity: compatible
