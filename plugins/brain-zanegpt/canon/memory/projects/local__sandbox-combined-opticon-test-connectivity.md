## E1 — opticon test connectivity predicate vs algorithm
- Date: 2026-07-31
- Project: local/sandbox-combined-opticon-test-connectivity
- Tags: [determinism][gamedesign][procgen][testing][pathfinding]
- What: `brain train combined` surfaced Pappydapimp69/Opticon#E6 (a pathfinder's walkability check disagreed with the move resolver's "interact-in-place" semantics — stepping toward a SWITCH tile toggles it but never relocates the mover there, so BFS found "reachable" tiles gameplay could never actually reach) composed with pappydapimp69/test#E17 (a procgen connectivity guarantee is either GLOBAL BY CONSTRUCTION — e.g. a spanning tree/flood-fill over the full region graph, trust it structurally — or LOCAL — adjacent/pairwise checks only, trust it for nothing beyond the pair). A deterministic sandbox composing both: opticon#E6's exact bug shape (a reachability check whose walkability predicate silently disagrees with real move-resolution) reproduced on a flood-fill algorithm that IS textbook global-by-construction per test#E17's own classification — showing E17's classification, while correct as far as it goes, is NECESSARY BUT NOT SUFFICIENT.
- Why built: opticon#E6 is verified first-hand (opticon's own balance simulator: timeout rate dropped from ~10-22% to 0% across 900 games after the fix) but was filed as a single-project bug fix, not connected to test#E17's higher-order classification rule. test#E17 itself flagged (in its own Provenance field) that its classification "has not itself been tested against a new procgen algorithm to confirm it correctly predicts which ones need an extra pass" — an explicit open follow-up this session settles for one concrete algorithm class (flood-fill).
- Design: Built a minimal deterministic 3x3 grid sandbox (no RNG, no timing) with a wall row containing exactly one non-wall cell, a SWITCH tile, as the sole route between a START region and a GOAL region — mirroring opticon#E6's real game rule (stepping toward a SWITCH tile toggles it but leaves the mover at their CURRENT tile). Ran three checks: (1) a textbook flood-fill BFS from START using a naive walkability predicate (tile-type only: FLOOR/SWITCH walkable, WALL not) — this is unambiguously GLOBAL BY CONSTRUCTION per test#E17's own definition, no per-pair local blind spot in the algorithm itself; (2) a "real" BFS that respects actual move-resolution (stepping onto SWITCH redirects the mover back to their current position, so the switch cell is never actually landed on); (3) the SAME flood-fill algorithm with only the predicate fixed to exclude SWITCH as a pass-through-walkable tile (mirroring opticon#E6's actual fix).
- Got right: The sandbox isolates the exact causal mechanism opticon#E6 found in production — the connectivity ALGORITHM (flood-fill) was never the problem, and switching to a "more global" algorithm would not have helped, since flood-fill already carries no algorithmic blind spot; the divergence lived entirely in the EDGE PREDICATE (what counts as a valid step) it was fed.
- Where/why it failed: Naive flood-fill certified GOAL reachable (reachable-set size 7 of 9 cells) while the move-resolution-respecting simulation showed GOAL is NOT actually reachable (reachable-set size 3 — the START region only) — a clean false positive, reproducing opticon#E6's production bug shape in an algorithm class test#E17 says should be trusted structurally.
- Fix: Classifying a connectivity algorithm as global-by-construction (test#E17) answers only "does the algorithm itself have a blind spot for the pairs/edges it's given" — it says nothing about whether those edges are CORRECT. Any global-by-construction connectivity check (flood-fill, BFS, spanning tree, union-find) still needs its walkability/edge PREDICATE audited against the actual runtime move-resolution logic (opticon#E6's fix: exclude any interact-in-place / redirect-only tile type from "can be occupied/passed-through," everywhere that question is asked) — fixing the predicate alone (not adding a second connectivity pass, and not changing the algorithm) resolved the false positive in the sandbox.
- Why this fix: test#E17's remedy for a LOCAL algorithm ("add an explicit separate global-connectivity fixup pass") doesn't even apply here — flood-fill already IS the global-by-construction pass. The actual fix axis this composition surfaces is orthogonal to E17's global-vs-local axis: ALGORITHM correctness (does global-by-construction hold) versus PREDICATE correctness (does the edge/walkability definition match real move-resolution) are two independent things that must each be verified — global-by-construction cleared the first, opticon#E6 shows the second still needs its own explicit audit regardless.
- Rule of thumb: Before trusting ANY connectivity/reachability guarantee (local or global-by-construction per test#E17's classification), separately verify its walkability/edge PREDICATE against the real runtime move-resolution semantics — a redirect-only or interact-in-place tile/transition type is a silent predicate bug that a perfectly-correct global-by-construction algorithm will not catch, because the algorithm was never wrong; only the edges it was given were.
- Provenance (verified/assumed): Verified first-hand — deterministic Python sandbox (no RNG, fixed grid, fixed traversal order), run this session: naive flood-fill reachable-set size 7 (GOAL reachable=True), real move-resolution-respecting reachable-set size 3 (GOAL reachable=False), predicate-only fix reachable-set matches real (GOAL reachable=False) — script at `/tmp/claude-0/.../scratchpad/sandbox_combined_opticon_test.py` (session-local, not committed to a repo).
