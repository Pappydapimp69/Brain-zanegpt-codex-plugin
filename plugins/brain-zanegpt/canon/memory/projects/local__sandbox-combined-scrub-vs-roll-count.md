## E1 — scrub safety needs constant roll count not just pure time function
- Date: 2026-08-29
- Project: local/sandbox-combined-scrub-vs-roll-count
- Tags: [gamedesign][state][determinism]
- What: `brain train combined` (draft + the-game-the-waiting-city). draft#E7 established that a scrubbable timeline needs state computed as a pure function of elapsed time. waiting-city#E9 established that autonomous-agent decisions must consume a CONSTANT number of RNG rolls per tick, for a different stated reason (so a later content tweak can't retroactively re-perturb other entities sharing the tick). Neither entry states the third consequence: if per-tick RNG-roll count is instead STATE-dependent (the thing E9 already forbids), then "elapsed time" alone no longer determines how many RNG draws have happened by time T — draws-consumed-by-T becomes path-dependent, not time-dependent — so a scrubber built on E7's assumption (state = f(elapsed time)) breaks specifically when E9's discipline is violated.
- Why built: to test whether E7's scrub-safety and E9's roll-count discipline are actually independent guarantees or whether one is a hidden precondition of the other, since both entries were filed separately with no cross-reference.
- Design: `sandbox.js` (Node, seeded `mulberry32`, zero wall-clock). An authoritative tick reducer where each tick's RNG-roll count is deliberately STATE-dependent (`1 + state.energy % 3`, i.e. exactly the shape E9 forbids) advances `state.pos`/`state.energy` and counts `rngDraws`. Three ways to reach time T=777 (and a 7-point sweep) were compared: (1) ground truth — run the reducer tick-by-tick from 0; (2) a naive "pure function of elapsed time" scrub that reseeds and draws `T * assumedRollsPerTick` times, the only shape a closed-form f(elapsed time) can express; (3) a replay scrub — re-run the same reducer from 0..T, no rendering, consuming RNG in original tick order. Ran twice as independent process invocations; output byte-identical both times.
- Got right: The replay scrub (3) matched ground truth's `energy`, `pos`, AND `rngDraws` exactly on every one of the 7 sampled T values (7/7), including T=777 (`{"energy":6,"pos":60,"rngDraws":1416}` both runs, both methods, verbatim).
- Where/why it failed: The naive fixed-rate scrub (2), the strategy E7's "pure function of elapsed time" framing invites when a per-tick draw count varies with state rather than time, diverged from ground truth on 6 of 7 sampled T values — at T=777 it produced `{"energy":4,"pos":74,"rngDraws":1554}` against ground truth's `{"energy":6,"pos":60,"rngDraws":1416}`. The one coincidental match in the sweep confirms this is a real, generic divergence rather than a guaranteed one — it's a silent, data-dependent failure mode, not a crash.
- Fix: Treat E9's constant-roll-count-per-decision discipline as a PRECONDITION for E7-style scrub-safety, not an unrelated concern. If a system needs both properties (scrubbable timeline + autonomous-agent RNG-driven decisions), either (a) enforce E9's constant-roll-count so draws-by-T truly is a pure function of T and a closed-form scrub stays valid, or (b) if roll count must be state-dependent, drop the closed-form scrub and always scrub via full tick-by-tick replay from 0 (fast-forwarded, unrendered) — which stays correct regardless of roll-count discipline.
- Why this fix: E7 and E9 were filed independently, for different stated reasons (visual-drift correctness vs. cross-entity roll perturbation), so a team that satisfies both individually could still reasonably assume they compose for free. This sandbox shows they don't: E7's scrub-safety silently depends on E9's discipline the moment RNG enters the picture, and the failure (wrong state at a scrubbed timestamp) is exactly the kind of thing a normal playback-order test would never catch, since playback order never desyncs from itself.
- Rule of thumb: A "pure function of elapsed time" scrub target (draft#E7) is NOT safe to combine with RNG-driven, per-decision branching (waiting-city#E9's territory) unless the roll count really is constant per tick. If it isn't, elapsed time no longer determines RNG draws-consumed, and any scrubber must replay the tick sequence from the start rather than compute state directly from a timestamp — check this explicitly whenever a scrubbable/seekable system is layered on top of an RNG-consuming autonomous-decision system.
- Provenance (verified/assumed): Verified first-hand — built and ran `sandbox.js` (deterministic, seeded, zero wall-clock), confirmed byte-identical output across two independent process invocations, and confirmed the divergence/match pattern (naive: 6/7 diverged; replay: 7/7 matched) across a 7-point T sweep, not just a single lucky/unlucky T. This is a general architectural-composition risk demonstrated in an isolated sandbox, not a claim about a live bug in either `draft` or `the-game-the-waiting-city`'s actual shipping code — waiting-city's real AI already follows E9's constant-roll-count discipline (patrol always 2, cars always 1), so this specific failure mode does not currently exist there; no live-unfixed bug is being flagged.
