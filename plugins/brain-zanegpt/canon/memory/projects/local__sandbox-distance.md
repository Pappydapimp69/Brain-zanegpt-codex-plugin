## E1 — euclidean distance misrepresents maze difficulty
- Date: 2026-07-05
- Project: local/sandbox-distance
- Tags: [gamedesign][algorithm][state]
- What: Using straight-line (Euclidean) distance from a spawn point to drive a difficulty/loot/pacing gradient ("harder enemies farther from spawn") badly misrepresents actual difficulty in any map with walls, corridors, or obstacles — a cell can be Euclidean-close to spawn while requiring an enormous walk through the map's actual corridors to reach, or the reverse.
- Why built: A maze-generation sandbox testing whether a common "distance from spawn = difficulty" design pattern holds up once the map isn't an open field.
- Design: Generate a maze (recursive-backtracker spanning tree), run one BFS from spawn to get the true graph/walking distance to every cell, and compare that against each cell's plain Euclidean distance from spawn.
- Got right: In an open, obstacle-free area, Euclidean distance and walking distance are the same thing, which is exactly why this bug is easy to miss — it only appears once the level has any structure (walls, corridors, a maze layout) blocking straight lines.
- Where/why it failed: A straight line from spawn to a nearby-looking cell can be blocked by walls the whole way, forcing the real path to snake through most of the level before arriving — Euclidean distance has no concept of the obstacles in between and simply measures the wrong thing.
- Fix: Compute the true graph distance from spawn with a single BFS (unweighted) or Dijkstra (weighted terrain) over the walkable map, and drive any distance-based difficulty/loot/pacing curve off that distance field instead of Euclidean coordinates.
- Why this fix: BFS/Dijkstra distance is literally "how many steps to actually walk there," which is what a difficulty-by-distance design intends to measure — Euclidean distance is a proxy that only happens to agree with it when there's nothing in the way.
- Rule of thumb: Never drive a "farther from spawn = harder/better" gradient off Euclidean/straight-line distance once the map has any obstacles — compute one BFS/Dijkstra distance field from spawn instead (it's no more expensive than the flood-fills already needed for connectivity/solvability checks) and use that. Verify by sampling the gap between Euclidean and graph distance across the map — a large gap anywhere means the two metrics have diverged and Euclidean-driven placement will misfire there.
- Provenance (verified/assumed): Verified first-hand — 20x20 maze, BFS distance field from spawn compared against Euclidean distance for all 399 non-spawn cells. Worst case: a cell 3 units away in a straight line required a 197-step walk (65.67x farther than Euclidean suggested). Mean relative error between the two metrics across the whole map was 83.1%.
