## E6 — skilltree savesystem undo must pin not live reeval
- Date: 2026-07-13
- Project: local/sandbox-combined-skilltree-formula
- Tags: [architecture][determinism][state]
- What: New seam (`sandbox-combined-save-system` and this project's skilltree-formula stack shared no prior edge). save-system#E1 already established the general reconciliation rule for "live reference by id" (freshness — a save should pick up content patches) versus "replay must be bit-identical" (determinism): content-version PIN each captured snapshot to the content it was computed against, never let a snapshot silently re-resolve against later-patched content. Composed directly with the skilltree's undo/redo (rpg-progression#E1/E2's deep-copy preimage/postimage) and expr-formula evaluation: a naive undo implementation that re-derives a skill's value by re-evaluating its CURRENT (possibly since-patched) formula, rather than restoring the exact captured snapshot, silently returns the NEW patched value after undo — e.g. "learn tier1" (formula `base*2`, value 20) followed by a balance patch changing the formula to `base*5`, followed by "undo learn tier1," incorrectly leaves `tier1 = 50` (the patched formula's live value) instead of correctly leaving `tier1` unset (as if never learned).
- Why built: rpg-progression#E1/E2 verified undo/redo correctness for VALUES that don't change meaning over time (inventory items, positions). Skill formulas are different: their "value" is defined by a formula that CAN legitimately change (a balance patch), which is exactly the freshness-vs-determinism tension save-system#E1 already solved in the save/load domain — this checks whether that same tension, and the same reconciliation rule, applies identically to the undo/redo domain, which had never been tested against a live-patchable formula source before.
- Design: `skillFormulas.tier1` starts as `"base*2"`; a "learn tier1" command captures `pre`/`post` snapshots (rpg-progression's own pattern) around `vars.tier1 = evalExpr(skillFormulas.tier1, vars)` (20). Before undo, `skillFormulas.tier1` is patched to `"base*5"`. Two undo strategies compared: re-deriving `vars.tier1` fresh from the CURRENT formula after restoring `base`, versus restoring the exact captured `pre` snapshot with no re-evaluation.
- Got right: The formula patch itself, and any NEW "learn tier1" command issued after the patch, correctly and desirably gets the fresh (patched) value — nothing about this finding argues against live formula resolution for forward-going gameplay; the issue is specifically retroactive re-derivation during undo of an action that happened BEFORE the patch.
- Where/why it failed: expr/toposort's live-evaluation design (correctly reused across every entry in this project so far, always re-deriving from current formulas and current variable state) has no built-in concept of "this particular value was captured at a specific point in time and must not be re-derived" — that concept only exists in the undo/redo history's snapshot mechanism. A naive undo implementation that tries to be "smart" by re-deriving values (perhaps to save memory, or because it seems more "correct" to always use the latest formula) silently reintroduces exactly the freshness-vs-determinism conflict save-system#E1 already resolved in a different subsystem, because nothing connects the two subsystems' respective fixes — each was verified correct on its own, in isolation from the other's existence.
- Fix: Undo/redo must restore the exact captured snapshot value, never re-evaluate the formula during undo — the fix already implemented and verified in rpg-progression#E1/E2 (deep-copy preimage/postimage, `Object.assign`/spread restore), applied here with no modification. Re-ran the identical patch-then-undo scenario: `tier1` correctly comes back `undefined` (never-learned state) instead of `50`.
- Why this fix: This is save-system#E1's own reconciliation rule (pin snapshots to their captured content, resolve fresh only for NEW computations) applied verbatim to the undo/redo domain rather than the save/load domain it was originally verified in — the underlying tension (a system wants both "always use the latest definition" and "reproduce exactly what happened before") is the same abstract problem regardless of which subsystem (save file, undo history) is doing the capturing, and the same fix (pin at capture time, never re-resolve retroactively) resolves it identically.
- Rule of thumb: Any system that captures a snapshot of a value COMPUTED FROM a live, patchable definition (a formula, a content-versioned asset, a config value) must pin that snapshot to what was actually computed at capture time, never re-derive it later from the definition's CURRENT state — this applies not just to save/load (where save-system#E1 already established it) but to undo/redo, replay, caching, or any other mechanism that captures-then-later-restores a derived value. Recognize the pattern ("is this a captured derived value that might be re-derived instead of restored?") wherever a formula/definition system is composed with ANY capture-and-restore mechanism, not only the specific one (save/load) where it was first found.
- Provenance (verified/assumed): VERIFIED first-hand — ran the exact learn-then-patch-then-undo sequence, confirming the live-re-evaluation undo strategy returns `tier1=50` (the patched formula's value, wrong) and the snapshot-restore strategy returns `tier1=undefined` (correct, matching pre-learn state) with no other variables affected.

## E5 — skilltree csv expr silent nan not loud error
- Date: 2026-07-13
- Project: local/sandbox-combined-skilltree-formula
- Tags: [parsing][algorithm][testing]
- What: Grew group 2 (skilltree-formula environment) with `sandbox-csv` (new pairing). csv#E1: a naive split-on-newline-then-comma parser silently corrupts row count when a quoted field contains a newline (a quoted multi-line formula, realistic for a hand-authored data-driven skill definition, splits into two spurious rows). Composed directly: the corrupted formula string for the affected skill (a leading stray `"` character) was fed into expr's evaluator, which — unlike its already-verified reliable fail-loud behavior for undefined variables (confirmed in `sandbox-combined-skilltree-formula#E1`) — silently returned `NaN` with no thrown error, because the malformed leading character falls through the tokenizer's identifier check straight into `num()`, which calls bare `parseFloat("")` on the empty match and returns `NaN` without validating the result — exactly expr#E2's own already-documented gap ("parseFloat silently truncates/fails on malformed numbers"), triggered here by a NEW upstream corruption source (csv#E1) rather than a directly-malformed number literal.
- Why built: `sandbox-combined-skilltree-formula#E1` established that expr's undefined-variable check is a reliable safety net against ONE specific class of composition gap (toposort's ordering vs. expr's variable usage). This checks whether that same reliability extends to a DIFFERENT upstream corruption source (malformed data ingestion, not graph-ordering) — it does not, because csv's corruption produces a token expr's parser was never designed to recognize as an error case at all (a stray non-identifier, non-digit character), landing squarely in expr#E2's already-known, separate blind spot instead of triggering expr#E1's fix.
- Design: A realistic CSV data file with a hand-wrapped multi-line formula value (`"base\n* 2"`), naive-parsed per csv#E1's own described mechanism (row count corrupted from 4 to 5, the formula split into `"base` and `* 2"` across two spurious rows). The `"base` fragment fed to expr, plus a downstream skill (`tier2 = tier1*1.5`) that references the now-poisoned `tier1` value.
- Got right: expr's undefined-variable fail-loud fix (E1) is not implicated or weakened by this — `tier1` genuinely IS a defined variable by the time `tier2` evaluates (it's just defined as `NaN`), so the undefined-variable check correctly has nothing to catch here; this is purely expr#E2's malformed-number gap, newly triggered by a different upstream cause.
- Where/why it failed: `NaN` is a valid JavaScript number and propagates arithmetically through every downstream formula (`tier1*1.5` = `NaN`, and so on through the entire skill tree) without ever throwing, without ever looking like a parse failure, and without any of the loud signals a developer might expect from "the CSV parser is known to corrupt row counts under this exact condition." The bug is invisible at every layer: csv's row-count corruption produces syntactically-plausible-looking split rows, expr's tokenizer doesn't recognize the leading `"` as an error worth stopping for, and NaN arithmetic never throws — three individually-explainable behaviors chaining into total silence.
- Fix: expr's `num()` must throw when it cannot form a valid number (empty match, or a `parseFloat` result that is itself `NaN`) instead of returning the unchecked `parseFloat` result — this is expr#E2's own documented fix, applied here. Re-ran the identical scenario: the corrupted `tier1` formula now throws `unexpected character '"' at position 0`, and the downstream `tier2` correctly throws `undefined variable 'tier1'` (since the failed assignment never set it) — 2/3 evaluated skills now fail loudly with position-tracked, root-cause-adjacent errors instead of 0/3 throwing and all silently computing `NaN`. (The upstream csv row-corruption itself is a separate, already-documented fix in csv#E1 — proper quoted-field-aware parsing — not re-verified here; this entry is specifically about how the DOWNSTREAM consumer should respond to receiving corrupted input, given that some corruption will always reach it in practice.)
- Why this fix: A parser's "fail loud on malformed input" guarantee is only as strong as its WEAKEST unchecked path — expr#E1's fix covers one path (identifier resolution) thoroughly, but a sibling path (number parsing) was left trusting `parseFloat`'s silent-failure behavior, and any upstream system whose corruption happens to produce output landing on the unchecked path bypasses the otherwise-reliable safety net entirely. Composing with a genuinely new corruption source (csv, not graph-ordering) is what surfaces which path the corruption lands on.
- Rule of thumb: A parser/evaluator's "throws loudly on bad input" reputation, verified against ONE class of bad input (undefined variables, from a graph-ordering composition), does not automatically extend to OTHER classes of bad input (malformed literals, from a data-corruption composition) — audit every parsing path (not just the one a prior composition happened to exercise) for silent-failure primitives (`parseFloat`, `parseInt`, unchecked array access) before trusting the parser as a general safety net against arbitrary upstream corruption.
- Provenance (verified/assumed): VERIFIED first-hand — naive-parsed a CSV with an embedded quoted-newline formula, confirmed the row count corrupts from 4 to 5 (reproducing csv#E1) and that the resulting malformed formula evaluates to silent `NaN` with zero thrown errors across all 3 skill rows; re-ran identically with expr#E2's own fix (throw on empty/NaN number parse) applied, confirming 2/3 skills now throw loud, position-tracked errors.

## E4 — skilltree graphviz force layout scrambles topo order
- Date: 2026-07-13
- Project: local/sandbox-combined-skilltree-formula
- Tags: [algorithm][graph][state]
- What: Grew group 2 (skilltree-formula environment) with `sandbox-graph-viz` (new pairing). graph-viz#E3's force-directed layout (repulsion + spring edges + centering-force + soft-core minimum distance) converges cleanly with no NaN/drift — verified as an UNDIRECTED, symmetric physics simulation with zero concept of edge direction or node rank. Composed with toposort's dependency ordering (visualizing a skill-tree DAG): across 30 random-seeded layouts of the identical graph, the correlation between a node's final Y-position and its topological rank ranged from -0.95 to +0.95 (mean |correlation| only 0.523) — the layout's spatial "reading direction" (does higher rank read as higher or lower Y) flips sign depending purely on the RNG seed used for initial node placement, with no relationship to the graph's actual dependency structure.
- Why built: A natural, common assumption ("run toposort to get the dependency order, then force-layout the graph to visualize it, and it'll roughly read in that order") was never actually tested — force-directed layout was verified only for STABILITY (no NaN, no unbounded drift), never for whether its output has any meaningful correlation with an externally-meaningful node ordering.
- Design: A fixed skill dependency graph (6 nodes) run through graph-viz#E3's exact fixes (soft-core repulsion, spring edges, gravity/centering force, damped Euler integration) from 30 different random initial-position seeds, each settled for 300 iterations. Node Y-position vs. toposort rank correlation (Pearson) measured per run.
- Got right: graph-viz#E3's own fixes did their job — no run produced NaN or unbounded drift; every layout converged to a stable, readable (if directionally arbitrary) configuration. The instability class graph-viz#E3 fixed is orthogonal to the ordering-correlation gap found here.
- Where/why it failed: Force-directed layout's forces (repulsion, spring attraction, centering) are all symmetric under Y-axis reflection — nothing in the physics distinguishes "up" from "down," so the settled configuration's orientation is determined entirely by the (arbitrary) initial positions, which is exactly why the sign of the rank-correlation flips randomly across seeds while its magnitude stays moderate at best. A developer who runs this once, sees a diagram that happens to read top-to-bottom, and ships it will get a DIFFERENT, possibly-inverted reading on the next regeneration (a new node added, a re-layout after a data change) with no code change and no warning.
- Fix: Add an explicit rank-based Y-pull force (`fy += (rank[node] - pos.y) * RANK_PULL`) alongside the existing physics, rather than relying on the symmetric forces alone. Re-ran the identical 30-seed sweep: mean |correlation| rose from 0.523 to 0.977, with EVERY run positively correlated (0.94-0.99) — both reliably strong AND consistently signed.
- Why this fix: This is the general fix for "a physics-based layout needs to respect an external ordering it has no native concept of": add one additional force term that couples the external property (rank) to the dimension that should encode it (Y), sized small enough not to fight the existing repulsion/spring layout quality, but strong enough to break the reflection symmetry that made the sign arbitrary. The existing graph-viz#E3 fixes needed no changes — this is additive, not corrective, to them.
- Rule of thumb: Before assuming a force-directed (or any symmetric, physics-based) layout will spatially reflect an external ordering (topological rank, hierarchy depth, sequence index) just because the underlying graph has that ordering, verify it directly — symmetric layout forces have no way to prefer one orientation over its mirror image, so any apparent correlation with external rank is an accident of initial conditions, not a property of the algorithm, and will not survive re-running the layout. If the ordering must be visually legible, add an explicit force (or a post-hoc layered/hierarchical layout algorithm) that couples rank to position directly.
- Provenance (verified/assumed): VERIFIED first-hand — ran 30 independently-seeded force-directed layouts of the identical 6-node dependency graph, measuring Pearson correlation between toposort rank and settled Y-position per run (range -0.95 to +0.95, mean |r|=0.523), then re-ran identically with one added rank-pull force term, confirming mean |r|=0.977 with consistent sign across all 30 runs.

## E3 — skilltree ratelimit dynamic capacity goes stale until next refill
- Date: 2026-07-13
- Project: local/sandbox-combined-skilltree-formula
- Tags: [algo][state][architecture]
- What: 3-system combination extending group 2 (toposort + expr already composed; `sandbox-ratelimit` never touched before). ratelimit#E1's own verified fix (clamp `elapsed = max(0, now-last)`, clamp `last = max(last, now)`) was tested against a FIXED capacity/rate token bucket. Here, an ability's bucket capacity is DYNAMIC — recomputed each time via an expr formula referencing toposort-ordered stats (e.g. `capacity = 5 + haste` while a haste buff is active, `capacity = 5` once it expires). Composed directly: when the buff expires (capacity legitimately shrinks from 7 to 5) but no new request has arrived yet to trigger the bucket's lazy `refill()`, the raw `bucket.tokens` value stayed stale at 7 — above the new capacity — in 200/200 trials, until the next request finally called `refill()` and silently re-clamped it.
- Why built: ratelimit#E1's fix and its own test suite only ever varied the CLOCK between calls, never the capacity — because in that sandbox's design, capacity was a static configuration value, not a formula output. Once capacity becomes a derived, dynamic value (the natural design once expr/toposort are in the picture — stats change, buffs expire, gear swaps), the lazy-refill pattern ratelimit#E1 itself called "the standard, correct shape" (refill computed only when a request arrives) has an unstated assumption: that nothing OTHER than elapsed time changes the bucket's validity between requests.
- Design: `computeStats()` runs a toposort-ordered stat graph (`haste` derives from `base` via expr); `capacityFor()` evaluates a formula selecting `5 + haste` or `5` depending on buff state. `refill(bucket, now, capacity)` is ratelimit#E1's fix verbatim, unmodified. Sequence: request 1 arrives with the buff active (bucket fills to capacity 7), buff expires (capacity recomputed to 5), THEN — before any second request/refill call — `bucket.tokens` is read directly (matching a realistic consumer: a UI meter, or a "can this burst-cast N times right now" affordability check).
- Got right: `refill()` itself has no bug — when it IS called, its own `Math.min(capacity, ...)` correctly re-clamps to whatever capacity is passed at that moment (confirmed separately: 0/200 trials had `tokens > capacity` immediately after a `refill()` call with the new capacity). ratelimit#E1's clock-backward fix is untouched and doesn't need to be, and isn't implicated in this bug at all — the gap is purely about WHEN re-clamping happens, not whether it's correct when it does.
- Where/why it failed: A lazy-refill token bucket's correctness invariant ("tokens never exceed capacity") is only enforced INSIDE `refill()`, which only runs on request arrival. As long as capacity is static, nothing else can ever cause the invariant to become false between requests, so this was invisible. Once capacity is a formula output that can change on its OWN schedule (buff expiry, a stat recompute triggered by something unrelated to bucket requests), the invariant can be silently violated in the gap between "capacity changed" and "the next request happens to arrive" — and nothing about ratelimit#E1's fix, expr's formula evaluation, or toposort's ordering individually has any way to notice, because none of the three systems knows the other two exist.
- Fix: Add an explicit `onCapacityChanged(bucket, newCapacity)` hook — `bucket.tokens = Math.min(bucket.tokens, newCapacity)` — called at the moment a capacity-affecting event occurs (buff expiry, stat recompute), not deferred to the next lazy `refill()`. Re-ran the identical 200-trial sequence with this hook invoked immediately after the capacity formula changes: 0/200 stale-over-capacity reads.
- Why this fix: This preserves ratelimit#E1's lazy-refill design for the common case (time-based refill, no need to poll) while adding a second, event-driven trigger specifically for the case lazy evaluation can't cover on its own — a value changing for a reason OTHER than the passage of time. This is the general pattern for composing a lazily-evaluated invariant with an external dynamic input: lazy evaluation is correct exactly as long as ALL relevant inputs only change via the calls that trigger evaluation; the moment a second input (capacity, here) can change independently, an explicit invalidation/re-check hook is needed at that second input's own change point, not just at the original trigger.
- Rule of thumb: Before composing a lazily-evaluated structure (a token bucket, a memoized value, any "recompute on next access" pattern) with an EXTERNALLY DYNAMIC parameter of its own formula (capacity, rate, any bound derived from other systems' state), check whether that parameter can change independently of the structure's own trigger events — if so, the structure's invariant can go stale in the gap, and needs an explicit re-check/invalidation hook fired at the parameter's own change event, not just relying on the structure's existing lazy-recompute path to eventually notice.
- Provenance (verified/assumed): VERIFIED first-hand — ran 200 trials of a fixed sequence (fill bucket while buffed, expire the buff, read raw tokens before any further request) confirming 200/200 stale-over-capacity reads with no fix, 0/200 with an eager `onCapacityChanged` re-clamp hook, and separately confirmed `refill()`'s own min-clamp is correct in isolation (0/200 over-capacity immediately after an actual `refill()` call).

## E2 — skilltree toposort myersdiff order noncanonical fakes diff
- Date: 2026-07-13
- Project: local/sandbox-combined-skilltree-formula
- Tags: [algorithm][process][harness]
- What: Grew the toposort/expr group with `sandbox-myers-diff` (new pairing, tag-supported via `[process][harness]`). toposort's output ordering is NON-UNIQUE — many valid topological orderings exist for the same dependency graph, differing only by arbitrary tie-break order. Composed with myers-diff (a minimal-edit-script sequence diff, used here for a realistic "compare skill tree before/after a patch" feature): diffing two toposort orderings of the IDENTICAL dependency graph — where only the node DECLARATION order changed, not any actual dependency — produced 4 non-`keep` ops (2 deletions, 2 insertions) out of 6 total nodes, falsely reporting `tier1`/`tier2` as removed-and-re-added when the graph was byte-for-byte unchanged.
- Why built: myers-diff#E3 already established that a minimal edit script isn't unique (multiple valid op sequences can represent the same transform) and fixed testing around that with reconstruction-based property tests. This checks a related but distinct non-uniqueness problem one level up: if the two INPUT sequences being diffed are themselves arbitrary-but-valid orderings of the same underlying structure, no diff algorithm — however correctly implemented — can avoid reporting spurious changes, because from the diff's point of view the inputs genuinely differ as sequences.
- Design: A fixed skill dependency graph (`base -> tier1 -> tier2`, `base -> sideBranch -> sideBranch2`, `ability` depends on both `tier2` and `sideBranch2`) run through plain Kahn's-algorithm toposort twice, with only the node declaration order changed between runs (an engine-upgrade-style, semantically meaningless detail — exactly the kind of change `sandbox-combined-skilltree-formula#E1` already showed can happen from an unrelated edit elsewhere). The two resulting orderings were fed directly into a standard LCS-based Myers diff.
- Got right: The Myers diff implementation itself is correct — every op it reported is a valid, minimal-cost transform between the two ACTUAL input sequences given. This is not a diff-algorithm bug; per myers-diff#E3's own finding, asserting exact ops would be the wrong test here too, but even a property/reconstruction-style check would pass — the transform correctly turns sequence A into sequence B. The problem is entirely upstream: which sequences were handed to the diff in the first place.
- Where/why it failed: toposort's contract only guarantees "a valid ordering respecting all dependencies" — it says nothing about ordering being STABLE/canonical across runs, calls, or minor unrelated changes (declaration order, Map/Set iteration details, a different environment). A diff algorithm's contract is "report the minimal transform between these two sequences AS GIVEN" — it has no way to know the two sequences represent the same underlying graph and "should" be considered equal. Composing an order-non-unique producer directly with an order-sensitive consumer manufactures false structural changes out of pure representational noise, and nothing in either system's own tests could catch this, since toposort's tests only check ordering validity (never comparing two runs against each other) and myers-diff's tests only check transform correctness (never checking whether the inputs were canonical).
- Fix: Canonicalize toposort's output with a DETERMINISTIC tie-break (e.g. alphabetical/ID-sort among all currently-ready nodes at each step) before diffing two orderings of what might be the same graph. Re-ran the identical before/after scenario through the canonicalized toposort: both runs produced the identical order, and the diff against them produced 0 non-`keep` ops.
- Why this fix: Making the ordering canonical removes the representational noise at its source rather than trying to make the diff "smarter" (e.g. graph-aware diffing, which would require myers-diff to understand toposort's domain — a much larger, more coupled fix for a problem that a one-line deterministic tie-break solves cleanly at the boundary). This is the same "fix at the seam, don't touch either verified system's internals" pattern as every other combined-sandbox fix in this lineage.
- Rule of thumb: Before feeding the output of any algorithm whose result is CORRECT-BUT-NOT-UNIQUE (topological sort, this project's own toposort; a minimal edit script, myers-diff itself; any layout/scheduling/tokenization with multiple valid answers) into a downstream consumer that is ORDER- or REPRESENTATION-SENSITIVE (a diff, a hash, an equality check, a cache key), check whether two independently-valid outputs for the SAME logical input can differ in a way the consumer would treat as a real change — if so, canonicalize (deterministic tie-break, sorted output, stable serialization) before that boundary, don't rely on downstream logic to compensate.
- Provenance (verified/assumed): VERIFIED first-hand — ran toposort twice against the identical dependency graph with only declaration order varied, confirmed both outputs represent the same graph (`sort()`-equal), diffed them with a standard Myers implementation and observed 4/6 nodes reported changed, then re-ran with a canonicalized (alphabetically tie-broken) toposort and confirmed 0 changed nodes on the identical scenario.

## E1 — skilltree toposort expr undeclared dep accidental convergence
- Date: 2026-07-13
- Project: local/sandbox-combined-skilltree-formula
- Tags: [algorithm][architecture][state]
- What: New combination (`sandbox-toposort` and `sandbox-expr` share no prior edge). Composed toposort's dependency-ordered evaluation (schedule nodes by their DECLARED deps) with expr's fail-loud undefined-variable error (E1's position-tracked fix). Built a skill-tree where each skill's formula may reference other skills' computed values, then deliberately introduced a realistic authoring slip: a formula references a skill (`tier2`) that is NOT listed in its own declared deps (`tier3`'s deps list only names `sideBranch2`). Result: the missing edge did NOT cause silent data corruption in any tested case — expr#E1's fail-loud fix caught every genuinely-too-early reference. But when the referenced skill happened to already be scheduled earlier (by incidental topological-round alignment with the declared deps, not by any contract), the formula "just worked" with a correct-looking numeric result and no error at all — and this state was fragile: an edit to a COMPLETELY UNRELATED part of the graph (lengthening a different skill's own dependency chain by 2 hops, with `tier3`'s own formula and declared deps left byte-for-byte unchanged) flipped it from "works, returns 60" to "throws undefined variable 'tier2'".
- Why built: toposort's own sandbox tests correct scheduling FROM a correct, complete dependency graph; expr's own sandbox tests correct evaluation and error-reporting for a GIVEN variable environment. Neither was ever tested against the realistic case where the declared graph (toposort's input) and the formulas' actual variable usage (expr's input) are authored independently and can silently drift apart — a near-universal risk in any spreadsheet-like or skill-tree-like system where "what a node depends on" and "what a node's formula references" are two different, separately-edited pieces of data.
- Design: `toposort()` is Kahn's algorithm scheduling strictly from a `deps` map. `evalExpr()` throws `undefined variable 'X'` (with source position) the moment a referenced identifier isn't yet in the accumulated `values` map. A skill graph was built with a genuine missing edge (`tier3`'s formula uses `tier2`, but `tier3.deps` omits it), then evaluated in topological order across multiple variants: (1) a graph where the missing dependency's node structurally could not be ready before the referencing node (always caught, loud error, every declaration-order permutation tried); (2) a graph engineered so the missing dependency's node lands at the SAME topological round as a properly-declared one (silently "works" in every declaration-order permutation tried); (3) variant 2 with an unrelated 2-hop chain extension added elsewhere, changing nothing about the referencing node.
- Got right: expr#E1's fail-loud fix is genuinely robust here — across every configuration tested, an undeclared reference to a not-yet-computed value ALWAYS throws a clear, position-tracked error; it never silently returns `undefined`/`0`/`NaN`-merged-into-a-plausible-looking-number. The composition never produces silently WRONG data — only "coincidentally correct" or "loudly caught," never "silently corrupted."
- Where/why it failed: toposort's contract is "I will schedule nodes correctly relative to their DECLARED deps" — it has no way to know a formula's actual variable usage exceeds what's declared, because that information lives in a different system (expr's parse target) that toposort never inspects. When an undeclared-but-used dependency happens to already be resolved (an accident of shared topological depth with the declared graph, not a guarantee), the system silently succeeds today and gives zero indication the success is unenforced. The failure mode isn't corruption — it's an invisible landmine: a later, completely unrelated edit to a DIFFERENT skill's dependency depth can flip a long-working formula into a runtime error, and the resulting error message names the symptom node (`tier3`) and the missing variable (`tier2`), but nothing points at the actual root cause (an incomplete `deps` list) — a developer chasing that error has to manually notice the formula references a variable absent from `deps`.
- Fix: Not implemented as running code (decision/architecture-layer finding, matching the scope boundary other combined sandboxes in this project set). The portable diagnosis: derive each node's authoritative dependency set FROM the formula's own variable references (parse first, extract identifiers, treat that as the real deps for toposort) rather than trusting a separately-authored declared-deps list — or, if a separate declared list must exist for other reasons (explicit UI ordering, category grouping), validate at build/load time that every variable expr's parser finds in a formula is a SUBSET of that node's declared deps, and fail loudly (with the parsed formula's own position info, which expr#E1 already carries) at authoring time rather than at accidentally-triggered runtime.
- Why this fix: This turns an implicit, accidentally-enforced invariant (declared deps happen to be a superset of used variables, by construction luck) into an explicit, checked one, using data (expr's own AST/identifier list) the system already computes for evaluation — no new parsing infrastructure needed, just consuming an existing pass's output for validation instead of discarding it after evaluation order is decided.
- Rule of thumb: When a dependency-ordering system (toposort) and a formula/expression system (expr) are composed such that formulas may reference other nodes by name, never treat "the declared-deps graph" and "the formula's actual variable usage" as automatically in sync — verify explicitly (parse-time cross-check) rather than relying on the composed systems' individually-correct behavior (correct scheduling; fail-loud on genuinely-too-early references) to mask the gap. The two systems' individual correctness is exactly why this is dangerous: nothing ever looks broken until an unrelated, seemingly-safe edit elsewhere in the graph silently changes which side of the coincidence you're on.
- Provenance (verified/assumed): VERIFIED first-hand — ran the missing-dependency scenario across 4+ declaration-order permutations of an intentionally-depth-matched graph (100% silent-success), separately confirmed the intentionally-depth-mismatched graph throws loudly in 100% of permutations tried, and directly demonstrated the fragility by editing only an unrelated skill's chain length (leaving the referencing formula and its declared deps byte-identical) and observing the outcome flip from a returned value to a thrown error.
