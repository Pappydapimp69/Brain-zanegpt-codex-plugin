## E19 — the game wrong sky cadence gate overshoot severity scales with period
- Date: 2026-07-13
- Project: pappydapimp69/the-game-wrong-sky
- Tags: [determinism][framerate][gamedesign][architecture]
- What: Composing `the-game-the-recursion#E16` (movement step cadence via `stepCd -= dtMs; stepCd = STEP_MS` discards overshoot, producing a measured ~20% framerate-dependent move-rate swing at `STEP_MS=108`) with `the-game-wrong-sky#E9` (enemy attacks dispatched via a wall-clock-timed `enemyCd[id] = now + ENEMY_CD_MS`, explicitly flagged in that entry as untested for framerate drift) confirmed the two are the SAME bug pattern in different syntactic clothing — a repeating cooldown that resets to `(firing_time_or_counter + period)`, discarding whatever overshoot occurred past the deadline. Composing them further revealed a non-obvious severity law: the bias this pattern produces is not fixed, it scales with `avg_frame_time / period` — severe (~20%) at recursion's 108ms period, negligible (~1.5%) at wrong-sky's 900ms `ENEMY_CD_MS` period, and a swept range in between (~4.6% at 200ms, ~2% at 400ms, ~0% by 1800ms+) confirms a real, live-verified instance of this bug class in wrong-sky's shipping code, but at a magnitude below the threshold of being a priority fix.
- Why built: `brain train group` surfaced `the-game-the-recursion + the-game-wrong-sky` (shared=10) as the top-ranked accessible untested seam, requiring sandbox/live-code verification per current policy (tension T22).
- Design: Cloned both real repos fresh (not mocked) and extracted the exact live constants/control-flow verbatim: recursion's `explore.js` (`STEP_MS=108`, `dtMs` clamp from `main.js`), wrong-sky's `game.js` (`ENEMY_CD_MS=900`, `MAX_FRAME_MS=100`, the `now >= (enemyCd[id]||0)` gate at line 389). Built a deterministic Node.js sandbox reimplementing both gates verbatim under steady frame schedules at 30/60/144fps and a seeded-jittery schedule (mulberry32, no wall-clock, 10 seeds) for robustness. Added a control (wrong-sky's own one-shot, non-repeating `DODGE_MS=400` iframe deadline — fires once per press, does not self-reset in a loop) to isolate whether the mechanism requires a REPEATING self-resetting cycle specifically. Then swept the same gate logic across a range of synthetic periods (108/200/400/900/1800/3600ms) at fixed 30fps-vs-144fps to map bias as a function of period.
- Got right: Reproduced recursion#E16's own already-measured numbers exactly first (450 moves@30fps, 540@144fps over 60s) as a sanity check before touching wrong-sky, confirming the sandbox methodology matches the established prior finding before extending it. Included the one-shot dodge-deadline control specifically to rule out "any wall-clock timing is buggy" as an overbroad conclusion — the control's overshoot shrinks toward 0 with FPS and never compounds, confirming the bug requires repetition, not just wall-clock use.
- Where/why it failed: wrong-sky's `enemyCd[id] = now + ENEMY_CD_MS` gate is a live, verified instance of the same overshoot-discarding bug class as recursion#E16: 66 strikes/60s at 30fps vs 67 at 144fps (~1.5% swing), consistent across a 10-seed jittery-schedule sweep (mean 33.10, tight variance at a related period). The period-vs-bias sweep showed bias tracks `frame_time/period` roughly directly: 20.0% at 108ms (recursion), 4.56% at 200ms, 2.05% at 400ms (wrong-sky's own `DODGE_MS`, if it were ever made repeating), 1.52% at 900ms (wrong-sky's actual `ENEMY_CD_MS`), ~0% by 1800ms+. A secondary worst-case "dodge-spam" figure (~7% swing) was also measured but stands only as a plausibility estimate — it was never checked against wrong-sky's real `input.js` press-edge-detection/debounce logic, is not a confirmed bug, and should not be weighted equally with the enemyCd result.
- Fix: Same fix shape as recursion#E16's own fix (`stepCd += STEP_MS` after clamping to avoid negative accumulation, rather than a flat reset) applies to wrong-sky's `enemyCd[id] = now + ENEMY_CD_MS` line, but given the measured ~1.5% real-world impact at this specific period, this is a real-but-minor entry — worth recording, not worth urgent prioritization, unlike the earlier live-unfixed modal-overwrite-race finding from this same session.
- Why this fix: Both codebases independently arrived at "reset the deadline/counter to now-or-counter plus a flat period" as the natural way to write a repeating cooldown; the fix is the same in both cases (accumulate off the deadline that was missed, not off the observed firing time) but its priority is not automatically the same — determined by measuring the period against realistic frame times rather than assuming.
- Rule of thumb: When triaging a newly-found instance of "cooldown/cadence gate resets via `X = now_or_counter_at_fire + period`, discarding overshoot," don't just flag presence/absence of the pattern — estimate `avg_frame_time / period`. That ratio predicts the bias magnitude directly (roughly matching the ratio itself, per this sweep: ~20% at ratio≈0.15, ~1.5% at ratio≈0.017, ~0% once period is an order of magnitude+ above frame time). The same code shape can be a severe, player-facing fairness bug (a 108ms movement cadence) or a practically negligible one (a 900ms attack cadence) — triage by measured/estimated ratio, not by pattern match alone.
- Provenance (verified/assumed): VERIFIED first-hand — cloned both real repos, extracted exact live constants and control-flow, built a deterministic Node.js sandbox (steady schedules at 30/60/144fps + 10-seed jittery mulberry32 sweep, no wall-clock/Math.random), reproduced recursion#E16's own numbers exactly as a sanity check, then measured wrong-sky's real `enemyCd` gate (66 vs 67 strikes/60s, ~1.5%) and a period-vs-bias generalization sweep (108/200/400/900/1800/3600ms). The dodge-spam secondary figure is a plausibility estimate only, never checked against real input-debounce logic, and sits outside the verified claim.

## E18 — the game wrong sky save snapshot outlives its content
- Date: 2026-07-13
- Project: pappydapimp69/the-game-wrong-sky
- Tags: [architecture][save][gamedesign]
- What: Composing `sandbox-combined-save-system#E1` (snapshotting content into every save trades freshness for determinism; the real fix is an immutable revision-addressed content store with a HEAD pointer, pinning each save's `contentVersion`) with `the-game-wrong-sky#E2` (snapshots the whole constructed world via `JSON.stringify`/`JSON.parse` at run start for deterministic death-respawn, since Continue reaches the same restart code with no options) found that wrong-sky's real save system reuses E2's snapshot-over-reconstruct idiom at a much longer time horizon than E2's own session-local respawn use — and at that horizon, E1's named freshness cost becomes real and measurable in live code, not theoretical.
- Why built: `brain train group` surfaced `sandbox-combined-save-system + the-game-wrong-sky` as an untested seam requiring live-code verification, not just reasoning, per current policy (tension T22).
- Design: Cloned `pappydapimp69/the-game-wrong-sky` (real repo) and imported the actual `src/sim/world.js` (`makeWorld`), `src/sim/reduce.js` (`reduce`), `src/sim/content.js` (`CONTENT`), and `src/app/save.js` (`saveGame`/`loadGame`/`hasSave`) with only a minimal in-memory `localStorage` shim (Node has none) and the game's own seeded RNG (fixed seed 20260713, no `Math.random`/wall-clock). Ran the real `TALK`->`ACCEPT_QUEST` flow to accept a quest, saved via the real `saveGame`, then simulated a content-only patch (bumping a quest's reward and adding an objective in `CONTENT`) WITHOUT bumping `WORLD_VERSION` — since nothing in the repo ties `WORLD_VERSION` (a hand-maintained flat string) to a content edit. Compared the real Continue path (`startGame(canvas, seed, {}, loadGame())`, never re-calling `makeWorld`) against a fresh `makeWorld()` call.
- Got right: Used the actual game code paths end to end (real quest-accept flow, real save/load functions, real Continue entry point from `main.js`), not a reimplementation — the divergence measured is a property of the shipped code, not a model of it. Also checked internal consistency (does the stale save corrupt itself, e.g. index/ordinal drift between `defs` and `progress`) before concluding the staleness was merely inert, and separately checked whether a targeted per-quest fix exists before concluding the only escape hatch is a full wipe.
- Where/why it failed: A save continued via the real load path returns `reward.coins=4, objectives.length=1` (the original, pre-patch values) even after the content patch is live, and remains stale permanently — while a brand new game via `makeWorld()` immediately reflects `reward.coins=999, objectives.length=2`. This is safe in the narrow sense (no crash, no ordinal drift — `defs` and `progress` were snapshotted together at construction, so `ATTUNE` on the stale save completes correctly under the OLD rule and pays the OLD reward) but the only available remedy is blunt: bumping `WORLD_VERSION` doesn't scope-invalidate the one stale quest, it flips `hasSave()`/`loadGame()` to false/null wholesale, discarding an unrelated completed quest, all accumulated coins, and position to fix staleness in a single quest's data.
- Fix: Not applied to shipping code (flagging only, per instructions). The described architectural gap would need something closer to E1's own prescription — either a live reference into `CONTENT` for quest defs (resolved at HEAD on each load, not frozen at accept-time) with `progress` staying the only thing genuinely persisted, or a per-save pinned `contentVersion` with a real migration path, instead of the current all-or-nothing `WORLD_VERSION` gate.
- Why this fix: wrong-sky currently implements neither of E1's two documented poles cleanly — no live-HEAD reference (quest defs are deep-copied at construction) and no per-save pinned revision with migration (just a flat hand-maintained version string with no granularity) — so it inherits the freshness cost E1 describes without any of E1's mitigations.
- Rule of thumb: "Snapshot the constructed state instead of reconstructing it" (wrong-sky#E2's respawn technique) is scope-sensitive — safe and free when the snapshot's lifetime is bounded to one session (respawn, undo, retry), but the identical `JSON.stringify`/`JSON.parse` idiom silently inherits save-system#E1's freshness-vs-determinism tradeoff the moment that snapshot is persisted across deploys/patches (a save file, not a same-session respawn). Before reusing a "snapshot beats reconstruct" fix at a new scope, check what content it freezes and for how long — a snapshot that can outlive the content it was built from needs E1's pinned-revision/HEAD-pointer treatment, not E2's session-local full-copy treatment.
- Provenance (verified/assumed): VERIFIED first-hand against the REAL, currently-shipping `pappydapimp69/the-game-wrong-sky` source (`src/sim/world.js`, `src/sim/reduce.js`, `src/app/save.js`), not a reimplementation — real quest-accept flow, real save/load functions, a simulated content-only patch (no `WORLD_VERSION` bump), measured stale-vs-fresh divergence (reward 4 vs 999, objectives 1 vs 2), confirmed internal self-consistency of the stale save (correct completion under old rule), and confirmed `WORLD_VERSION` bump wipes the save wholesale rather than scoping to the affected quest. This is a structural/architectural gap, not a currently-triggered corruption bug — no evidence a content-only patch has actually shipped without a `WORLD_VERSION` bump in this repo's real history; it describes what would happen if one did.

- Got right: Confirmed the fingerprint/replay mechanism itself works correctly first (reproducible across independent replays, no exceptions, no HP-out-of-bounds, in BOTH variants) before checking whether it caught the injected bug — isolating "the replay check is broken" from the actual claim, "the replay check doesn't check this property." The dodge-gate invariant's violation is completely invisible to every check the repo's real smoke suite and determinism guarantee currently run.
- Fix: Not applied to shipping code — no live bug exists today (the real single gating loop is currently correct). The gap is a missing independent oracle: a dedicated check, run over recorded command/event logs, that verifies no `ENEMY_STRIKE` timestamp falls inside a recorded dodge window, computed from ground truth and never inferred from "fingerprint matched" or "no exception was thrown."
- Why this fix: E9 already says "test those [i-frame] windows explicitly" but doesn't specify a technique; E1 supplies the concrete mechanism — replay/fingerprint checks validate that the COVERED mechanism (the reducer) is deterministic, which says nothing about a precondition (the dodge gate) that lives entirely in the uncovered presentation-layer AI driver. Given this repo has already shipped the "new strike source forgot to thread through an existing gate" bug shape twice (E14, on the hint invariant), the dodge invariant is a specifically plausible target for the same regression class in the future.
- Rule of thumb: When a system's headline correctness guarantee (determinism, replayability, optimality) is checked by re-running the covered mechanism and comparing output/fingerprint, that check says nothing about a second guarantee that depends on an assumption living entirely outside what's covered (heuristic admissibility for a pathfinder; i-frame timing for a command-withholding combat system). Don't let "replay is bit-identical" or "no exception was thrown" stand in for "the untrusted precondition held" — build a dedicated, ground-truth oracle targeting exactly that precondition, independent of the mechanism's own success signal, especially for any invariant a codebase has already broken once via an unthreaded new code path (E14's own pattern).

## E16 — the game wrong sky modal overwrite race live unfixed
- Date: 2026-07-13
- Project: pappydapimp69/the-game-wrong-sky
- Tags: [ui][event-ordering][gamedev]
- What: `the-game-the-answering-deep#E1` documented a "modal overwrite race" bug class in a `reduce -> events[] -> for(e of events) onEvent(e)` architecture: when one dispatched command emits multiple presentation-relevant events in the same batch, and more than one event handler unconditionally writes `view.modal`, a later event silently discards content the earlier event set. `the-game-wrong-sky` shares the identical architecture (verified in its live `src/sim/reduce.js`'s `TALK` case and `src/app/game.js`'s `onEvent` switch) and has the SAME bug, live and unfixed: the player's first-ever conversation with Sable (the game's opening NPC interaction) shows a blank quest-offer modal — title and choice buttons only, empty flavor text — because the `'quests_offered'` handler unconditionally overwrites `view.modal` with no composition against what the just-processed `'talked'` event set.
- Why built: `brain train group` surfaced `the-game-the-answering-deep + the-game-wrong-sky` as an untested seam requiring sandbox/live-state verification, not just reasoning, per current policy (tension T22).
- Design: Verified against the ACTUAL shipping code, not a reimplementation: imported wrong-sky's real `makeWorld`/`reduce`/`CONTENT` (no mocks), moved the player adjacent to Sable, dispatched the real `TALK` command, and replicated `onEvent`'s exact modal-handling logic to observe the real resulting `view.modal`.
- Got right: Traced the full causal chain in live source rather than stopping at "the architecture matches": `reduce.js`'s `TALK` case pushes `{type:'talked'}` then `{type:'quests_offered'}` into one events array (mirroring answering-deep exactly); `game.js`'s `'talked'` handler only sets `view.modal` conditionally (`else if (!view.modal)`) but `'quests_offered'`'s handler is unconditional; `questOfferFlavor()` returns `[]` specifically for `hear-the-world` (Sable's quest); and that quest has no `requires`, so it fires on literally the player's first `TALK` to Sable in every new game — this isn't a rare edge case, it's the opening interaction.
- Where/why it failed: Running the real reducer against a real game start produced `TALK` events `[{"type":"talked","npc":"sable"},{"type":"quests_offered","quests":["hear-the-world"]}]`, and the resulting `view.modal.lines` was confirmed empty (`[]`) despite Sable's real, populated dialog array existing and being generated correctly by the same code path the-game-the-answering-deep#E1 already fixed for its own project — the `'quests_offered'` handler's unconditional `view.modal = mkModal(...)` discarded it, exactly matching answering-deep#E1's root cause.
- Fix: Not applied in this session (flagging pending explicit confirmation, matching this session's established pattern for live-repo fixes) — the already-designed, already-verified fix from `the-game-the-answering-deep#E1`: fold the same dialog-generation call into the offer modal's own `lines` field, so the SECOND event's modal composes with the content the first event would have shown, instead of racing/discarding it.
- Why this fix: The fix is not a design question — it's already been designed, implemented, and verified working in the sibling project with an identical architecture; porting it is a known-safe copy, not new engineering, exactly the same shape as this session's earlier cache-bust port between these same saga siblings.
- Rule of thumb: When two sibling projects share the same reducer/event architecture (a documented, deliberate pattern in this saga per `the-game-wrong-sky#E10`'s independence contract), a bug class fixed in ONE sibling should be checked for LIVE presence in every other sibling sharing that architecture, by running the actual shipping code against the specific trigger condition (here: the game's very first NPC conversation) — not just by checking whether the memory entry documenting the fix mentions the other project. This is the same propagation-gap pattern `the-game-wrong-sky#E15` already named for a different bug (a UI-hint fix), now confirmed to recur for a structurally unrelated bug class (a modal-overwrite race) in the same pair of sibling repos — suggesting the gap is systemic to how this saga propagates fixes across independent repos, not specific to any one bug.

- Date: 2026-07-09
- Project: pappydapimp69/the-game-wrong-sky

## E12 — wrongsky partial occluder integer visibility over binary shadowcasting
- Date: 2026-07-09
- Project: pappydapimp69/the-game-wrong-sky
- Tags: [gamedev][rendering][determinism]
- What: For the light/line-of-sight facet, the team wrote a custom per-tile visibility algorithm — an integer Bresenham line from the player to every candidate tile, multiplying a 0-100 integer "clarity" by `(100 - opacity)/100` for each occluder crossed — instead of using classic recursive/symmetric shadowcasting. Occlusion is driven by a per-tile OPACITY map (0-100), not a binary blocked/clear flag.
- Why built: Classic shadowcasting (recursive octant scanning) is the standard, well-known, more CPU-efficient roguelike FOV algorithm. It is also typically BINARY (a tile either blocks sight or doesn't) and its usual formulations lean on floating-point slope math. This project needed neither of those to be true.
- Design: src/sim/visibility.js lives in `src/sim` (opacity is authoritative content) but is a READ, not a reducer — it never mutates state, so it is not part of saved state. Its header comment states the tradeoff outright: "This supports PARTIAL occluders (a future 40-opacity bush only dims, doesn't blank), unlike classic binary shadowcasting, while staying exact — no floats, no trig, safe for the determinism guard." The same opacity map does double duty: movement collision reads it by key-existence, the visibility system reads it by magnitude (see this project's E5).
- Got right (the choice made): A partial-occlusion FOV model that is exact integer arithmetic. Because clarity is an integer percentage floor-divided per occluder along an integer Bresenham line, there is no float, no trig, and no engine-varying transcendental math — so the visibility computation is safe to sit in `src/sim` under the determinism/forbidden-token guard, and partial occluders (dim-don't-blank) are expressible for free (a future 40-opacity bush, a fog tile), which binary shadowcasting cannot represent.
- Where/why it failed (the tradeoff accepted): The cost is PERFORMANCE and reinventing a solved wheel. Walking a fresh Bresenham line from the player to every candidate tile in the vision radius is O(tiles x line-length) per computation — asymptotically worse than symmetric shadowcasting's octant recursion, and it re-walks shared prefixes of many rays instead of amortizing them. For one small region's vision radius that budget is fine, but the choice explicitly trades the standard algorithm's efficiency (and its large body of known-correct reference implementations) for determinism-safety and partial occlusion. It also means maintaining a bespoke FOV routine rather than a battle-tested one.
- Fix (what was chosen instead of a workaround): Rather than adopt binary shadowcasting and either (a) accept only hard walls or (b) bolt float-based partial transmission onto it and fight the determinism guard, the team wrote the integer per-tile clarity-multiply from scratch, scoped to one region's radius where its higher per-frame cost is affordable. Partial occlusion and determinism were treated as the hard requirements; per-tile efficiency was the negotiable one, given the small world.
- Why this fix: When a rendering/sim algorithm must be BOTH deterministic (integer-only, guard-safe, replayable) AND support a capability the standard algorithm lacks (partial/graded occlusion), a purpose-built exact-integer routine can be the right call even though it is slower and non-standard — provided the working set is small enough that the efficiency you gave up never bites. The determinism and capability requirements are structural; the efficiency is a budget you can check against the actual scale.
- Rule of thumb: Before reaching for a textbook algorithm (shadowcasting, A*, etc.), check whether your hard constraints (integer determinism, graded rather than binary results) are ones it actually satisfies — if not, a slower, exact, purpose-built routine scoped to a known-small working set can beat retrofitting the standard one. Keep such a routine a pure READ in the sim (never mutating state) so it stays under the determinism guard without becoming saved state, and pick integer clarity-multiply over float slopes so the FOV replays bit-exact.
- Provenance (verified/assumed): Verified first-hand — src/sim/visibility.js implements the integer Bresenham + clarity-multiply exactly as described and its header comment states the "partial occluders, unlike classic binary shadowcasting ... no floats, no trig, safe for the determinism guard" rationale verbatim; the opacity map's dual existence/magnitude use is corroborated by this project's E5. The performance comparison (O(tiles x line-length), re-walked ray prefixes, asymptotically worse than octant shadowcasting) is my analysis of the code, not a measured benchmark — no profiling of the visibility routine specifically was run for this entry.

- Date: 2026-07-09
- Project: pappydapimp69/the-game-wrong-sky

Requiring intent (hold + non-combat button, no default) trades a little speed for the guarantee that high-frequency combat input can never resolve a low-frequency, high-stakes narrative choice.

- Date: 2026-07-09

- Where/why it failed (the tradeoff accepted): The cost is that enemy AI timing and i-frame correctness are NOT authoritative and NOT covered by the determinism guarantees. - Fix (what was chosen instead of a workaround): Rather than fold a timed AI loop and an invulnerability flag into the reducer (which would make it stateful and self-acting, breaking the "pure function of the command stream" property the whole determinism harness depends on), the team pushed the AI clock and the i-frame window entirely into the presentation orchestrator and expressed both purely through the command channel — the enemy attacks only when the driver issues `ENEMY_STRIKE`, and "invulnerable" is simply the driver choosing not to issue it during `dodgeUntil`. The sim remains a clean reducer; combat feel/timing is a presentation responsibility.
- Why this fix: Keeping the reducer a pure function of its command stream is what makes the save/replay/fingerprint machinery work at all; any self-initiated behavior (a clock-driven AI tick) or transient-timing state (i-frames) that lives inside it dilutes that property. Expressing "the enemy acted" and "the player was briefly untouchable" as command presence/absence keeps timing where the wall clock already lives (presentation) and leaves the authoritative core deterministic.
- Rule of thumb: In a command-sourced deterministic sim, don't let the reducer tick its own clock or self-initiate actions — model even enemy aggression as an explicit command issued by a presentation-side driver, and model transient timing windows (i-frames, cooldowns) as the driver withholding commands rather than as flags in authoritative state. You gain a pure, replayable, fingerprint-guarded core; you accept that AI cadence and i-frame correctness now live in the untrusted layer and are NOT covered by the sim's determinism tests — so test those windows explicitly at the presentation seam.

## E8 — wrongsky effect gated not existence gated wells
- Date: 2026-07-09
- Project: pappydapimp69/the-game-wrong-sky
- Tags: [gamedev][quest][gamedesign]
- What: For the game's signature interactables — the "wells" the player attunes to restore each visual/audio facet — the team chose EFFECT-gating over EXISTENCE-gating: wells are ALWAYS present and interactable in the world from the start, and ATTUNE only produces a real effect on the well matching the CURRENTLY-active quest's facet; interacting with any other well returns an always-present in-fiction flavor hint, never an error and never a hard "doesn't exist" wall. This deliberately DIVERGES from the same saga's own existence-gating rule for quest ENEMIES and PICKUPS (Prologue #E9: don't spawn quest targets until the quest is accepted).
- Why built: The Prologue established, and this repo inherited, the pitfall `the-game-prologue#E9`: existence-gate quest targets so a player's pre-acceptance actions can never retroactively/accidentally satisfy an objective — objective completion stays agnostic of prior history. Applying that uniformly would have made wells not-yet-exist until their quest was accepted. The team decided wells specifically should NOT follow it.
- Design: The decision and its rationale are written into the code's own header comments in three places (src/sim/world.js, src/sim/reduce.js, src/sim/content.js): "WELLS are different: they are always present ... only their EFFECT is gated on the active quest, so a player can wander to any well early and get a vague hint instead of a hard 'doesn't exist' wall." The ATTUNE reducer case implements it: a well with no active-quest match returns a `well_hint` event ("a soft non-effect ... never a throw, never a hard refusal"), while quest enemies/pickups are still built only on ACCEPT_QUEST.
- Got right (the choice made): Effect-gate the discovery objects. A curious player who explores early finds every well physically there, can interact, and gets a diegetic hint that something is dormant here — turning "you're not ready yet" into a discovery/foreshadowing hook rather than an empty patch of map. The world reads as continuous and alive from the first minute, and the mystery of the wells is seeded before their quests exist.
- Where/why it failed (the tradeoff accepted): The cost is that the codebase now carries TWO gating philosophies for what is conceptually "an interactive object," and effect-gating gives up the clean guarantee existence-gating provides. Because the well physically exists before its quest is active, the reducer must handle "interact with a not-yet-active well" as a real, first-class state (the soft-hint branch) — objective/completion logic can no longer lean on the E9 shortcut that "the target didn't exist before acceptance, so pre-acceptance actions are impossible by construction." Every early-interaction path has to be reasoned about and given a correct no-op, and a future contributor must classify which pattern a new object uses. (This exact tension was later surfaced by Brain's read fan-out into a sibling project, `the-game-the-recursion`, which resolved it per-object.)
- Fix (what was chosen instead of a workaround): Instead of forcing wells under E9's existence rule (which would delete the discovery hook) or letting an early attune silently corrupt/short-circuit progression, the ATTUNE reducer makes the non-matching case an explicit, harmless, in-fiction soft response (`well_hint`) and reserves real effect for the well whose facet matches the active quest. Enemies and pickups — where early satisfaction WOULD corrupt an objective — keep the existence-gated E9 rule. The dividing line is "what does this object protect": discovery/flavor objects are effect-gated; objective-critical targets stay existence-gated.
- Why this fix: Existence-gating and effect-gating are two answers to the same danger (pre-acceptance interaction), each with a different cost: existence-gating is bulletproof but makes the world feel empty/gated; effect-gating keeps the world explorable but requires a correct, deliberate no-op for every early interaction. Choosing per-object by what the object protects gets the discovery feel where it's safe and the hard guarantee where it's needed, instead of paying one pattern's cost everywhere.
- Rule of thumb: Don't reflexively apply "don't spawn quest targets until accepted" to EVERY interactable — for discovery/flavor objects, spawning them always and gating only the EFFECT (with an explicit, harmless in-fiction no-op for the not-yet-active case) turns "not ready" into a foreshadowing hook. But you then owe a correct no-op for every early-interaction path, and you lose the "it couldn't have happened before acceptance" guarantee, so keep objective-CRITICAL targets existence-gated. Pick the gating per object by what breaks if a player interacts early, and document which objects use which rule.

The cross-project tension resolution is corroborated by incoming/2026-07-09__effect-vs-existence-gating-resolved-per-object.md (project the-game-the-recursion), which cites this Wrong Sky pattern by name.

## E7 — wrongsky 100vh off screen and headless cannot repro mobile chrome
- Date: 2026-07-09
- Project: pappydapimp69/the-game-wrong-sky
- Tags: [browser][mobile][harness]
- What: `100vh`/`100vw` on a full-viewport element sizes to the LARGEST possible mobile-browser viewport (with the address/tab bar collapsed), not the currently-visible area — so anything anchored near the bottom of that element renders below the real fold whenever browser chrome is showing. - Design: The canvas backing store is JS-sized to `innerWidth/innerHeight × DPR`; CSS just stretches the element edge-to-edge via `100vw/100vh`. The renderer anchors the touch buttons to the bottom of the canvas's own pixel space (`y = H - offset`).

- Where/why it failed: On a real phone, when the address/tab bar is visible (the default on first load and after any scroll-up), the actual visible viewport is SHORTER than `100vh`. - Why this fix: `dvh/dvw` are exactly the units designed for this problem (the visible-viewport-vs-largest-viewport discrepancy that `vh/vw` created on mobile). Layering them after the fallback keeps the old value for non-supporting engines by construction. HTML/CSS-only, no sim or app-logic change, so it can't affect determinism or gameplay.
- Rule of thumb: For a full-screen mobile web app/canvas, never size the root element with `100vh/100vw` alone — those size to the largest-possible (chrome-collapsed) viewport, overflowing the visible area and pushing bottom-anchored UI off screen when the address bar shows; use `100dvh/100dvw` (with `vh/vw` as a preceding fallback line). And treat "headless-verified but still broken on device" as a category signal, not a fluke: a headless browser has no dynamic chrome, no real touch, no address bar — any bug whose trigger is a mobile-chrome/viewport condition is INVISIBLE to it, so headless green does not verify the actual reported failure. Verify viewport/chrome-dependent fixes by reasoning about the real-device condition (or a device/emulator that models collapsing chrome), not another headless screenshot.

## E3 — wrongsky batch canvas filter not per drawcall
- Date: 2026-07-08
- Project: pappydapimp69/the-game-wrong-sky
- Tags: [gamedev][rendering][canvas][perf]
- What: Setting Canvas 2D `ctx.filter` (e.g. `grayscale`/`hue-rotate`) individually before EVERY `drawImage` call, instead of once per frame on a pre-composited layer, causes catastrophic per-frame cost that scales with entity/tile count — a single `render()` call measured at 19,321.6ms (vs. a normal ~5-8ms) once enough sprites were on screen for the filter to apply to hundreds of draws.
- Why built: The game's presentation reveals sprite layers (`world`/`enemies`/`player`) one quest at a time; until each layer is "restored," its sprites render in grayscale (and briefly hue-cycle through a ~7s "kaleidoscope" on the light reveal). The natural-looking implementation set `ctx.filter = filter` and drew each ground tile, wall, entity, and projectile with that filter active, one `drawImage` per game object per frame.
- Design: World-space rendering already ran through a per-frame loop building a `drawables` list (destructibles/pickups/wells/npcs/enemies/player), each closure doing its own `ctx.fillStyle`/`drawPixelSprite` calls directly against the visible canvas context under a shared camera transform.
- Got right: The VISUAL result (uniform grayscale-until-restored, animated hue-cycle reveal) was correct and matched spec exactly — this was a pure performance defect, not a correctness one. It stayed invisible early on because during quest 1 (light off, world/enemies still flat, few sprites) the draw count per frame was low enough that per-call filtering was cheap; only once `visual.world`/`visual.enemies` sprites were active (quests 2-4, hundreds of tile+entity `drawPixelSprite` calls/frame, all pre-light so still filtered) did the cost become visible, explaining the user's precise report ("tremendous lag during quest 2 through 4, it gets better at 5" — quest 5 is post-light, filter becomes the cheap `'none'`).
- Where/why it failed: Canvas 2D's `ctx.filter` is not a cheap state flag — each draw call with a non-`'none'` filter forces the browser to rasterize an intermediate filtered surface for that call. Applying it hundreds of times a frame (once per ground tile, once per wall, once per entity, once per projectile) multiplies that rasterization cost by the draw count instead of paying it once. Found via direct Playwright profiling: dispatched the sim to the "light off, world+player+enemies revealed" state and timed individual `render()` calls with `performance.now()`, isolating the transition into/out of that state to bracket the spike precisely (an earlier profiling attempt had an off-by-one that measured the SAME state twice and missed the effect entirely — had to explicitly stop the dispatch loop strictly before the state-changing command to isolate it).
- Fix: Introduced an offscreen `worldLayer` canvas the same size as the visible canvas. All ground/wall/entity/projectile drawing for the frame targets that buffer's context (`wctx`), UNFILTERED (`filter: 'none'` / omitted), under the same camera transform as the visible canvas. After all world-space content is drawn, do exactly ONE `ctx.drawImage(worldLayer, 0, 0)` with `ctx.filter` set to the frame's real filter, then reset it to `'none'`. Lighting/shadowcasting darkness overlay and the on-top wall redraw (never the bottleneck — plain `fillRect`, and only a handful of on-screen wall tiles) stay directly on the visible canvas, drawn after the composite.
- Why this fix: The filter only needs to apply to the FINAL composited pixels once — grouping every world-space draw into one unfiltered buffer and filtering the single resulting blit produces the identical visual output (verified: golden sim fingerprint unchanged, browser e2e pixel-behavior unchanged) for O(1) filter applications per frame instead of O(draw calls).
- Rule of thumb: In Canvas 2D, never set `ctx.filter` to a non-`'none'` value before each of many small `drawImage`/fill calls in a loop — composite the whole filtered region into an offscreen buffer first (unfiltered draws), then apply the filter to ONE blit of that buffer. This generalizes past grayscale/hue-rotate to any CSS filter (blur, drop-shadow, etc.) and any renderer that draws a scene procedurally tile-by-tile/entity-by-entity. A frame-time regression that only appears once entity/tile COUNT crosses some threshold (rather than being present from the start) is a strong signal to profile per-draw-call overhead specifically, not just "general slowness."
- Provenance (verified/assumed): Verified first-hand — profiled the exact single-frame spike (19,321.6ms) via direct Playwright `performance.now()` instrumentation before the fix, implemented the offscreen-buffer restructure, then re-ran the identical profiling harness against the same sim state post-fix (max single-frame time dropped to 83.3ms, no stall), plus the full smoke suite (42/42, golden fingerprint unchanged) and a browser e2e regression (fingerprint match, zero page errors) to confirm no behavioral regression.

New-game runs were unaffected (their options were populated), which is exactly why casual testing missed it.
- Fix: At `startGame` entry, capture `const respawn = JSON.stringify(world)` (the run's true starting state, whether freshly built or loaded). On death, `world = JSON.parse(respawn)`. Also: never persist a defeated/ended world (`if (!world.flags.ended && world.player.hp > 0) saveGame(world)`), so a tab closed on the defeat screen doesn't resume a "zombie" at 0 HP.
- Why this fix: Snapshot-and-restore reproduces the exact start (archetype, difficulty, seed, carried skills, RNG) with zero dependence on which construction path was taken. Reconstructing from options only works for the path that happens to carry them; the snapshot works for all paths by construction.

The inputs may be absent on the path that loaded (rather than built) the state, and the constructor will silently substitute defaults. Corollary: never autosave a terminal/defeated state over a good one, or a mid-death resume loads it.

## E1 — wrongsky restore canvas transform in blit
- Date: 2026-07-07
- Project: pappydapimp69/the-game-wrong-sky
- Tags: [gamedev][rendering][canvas]
- What: A render helper that changes the canvas transform to blit a full-screen layer must restore the prior transform, or the caller's next world-space draws land in raw screen space.
- Why built: A 2D game restores a "light" facet by compositing an offscreen darkness-with-light-holes layer over the world. The helper `drawLight()` did `ctx.setTransform(1,0,0,1,0,0)` so it could `drawImage` the layer in screen space, then returned. The caller — still "inside" the world transform conceptually — immediately redrew the wall occluders with `drawWall(x,y)` at world-tile coordinates (`x*TILE, y*TILE`).
- Design: The world is drawn under a camera transform set via `ctx.setTransform(scale,0,0,scale,-camX*scale,-camY*scale)`; the HUD is drawn later under an identity transform. Any helper that touches the transform sits between those two phases.
- Got right: The offscreen light layer + destination-out light holes composited cleanly; the bug was purely that the transform wasn't handed back.
- Where/why it failed: Caught by an adversarial code-review pass before ship (not by a test — canvas transform state isn't asserted by the headless smoke suite). Concretely: once a player attuned the light well (a mandatory quest step), the ridge walls redrew at raw pixel coordinates fixed in the upper-left of the viewport and no longer tracked the camera, while the true wall locations fell dark. Every session that restored light hit it.
- Fix: Wrap the transform change in `ctx.save()` / `ctx.restore()` around the screen-space blit inside the helper, so the caller's world transform is intact on return. (Equivalently: re-apply the world transform before the wall loop.)
- Why this fix: save/restore is local to the helper and self-documenting — the helper owns its transform mutation and cleans it up, rather than the caller having to know the helper left the transform dirty and re-establish it. Re-applying at the call site works but leaks the helper's implementation detail into the caller.
- Rule of thumb: Any drawing helper that calls `setTransform`/`translate`/`scale` on a shared canvas context must bracket it with `save()`/`restore()`. Canvas transform is global mutable state with no compile-time scope; a helper that leaves it changed is the 2D-graphics twin of a function that leaves a global variable dirty. Headless smoke tests won't catch it — the pixels are only wrong on screen — so it needs a render-path review or a screenshot diff.
- Provenance (verified/assumed): Verified first-hand this session — traced the transform state through `drawLight()` and the subsequent wall loop, confirmed the identity transform was live during the world-coordinate wall redraw, applied the save/restore fix, and re-verified in headless Chromium that the light-restored ridge walls render at correct camera-relative positions (screenshot compared before/after).
